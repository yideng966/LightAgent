## 一、结论摘要

这次日志包含两个连续故障，**只修其中一个都不能恢复语音转写**：

1. **Silk 转 WAV 失败，但不是本次线程终止位置。** 当前环境没有安装提供 `pysilk` 导入模块的 `pysilk-mod`。`voice/audio_convert.py` 捕获 `ImportError` 后只记一条 DEBUG 日志，没有给 `pysilk` 绑定哨兵值；随后处理 `.sil/.silk/.slk` 时直接访问未定义名称，产生 `NameError`。`chat_channel.py` 又把原始 Silk 路径继续交给 ASR。
2. **真正终止 Worker 的主故障是 ASR Provider 配置与语音工厂契约不一致。** 当前 `voice_to_text` 为 `custom:a838bee2`，但 `voice/factory.py::create_voice()` 没有任何 `custom` / `custom:<id>` 分支，最终执行无消息的 `raise RuntimeError`。
3. **坏配置不是纯手工误配。** `run.log` 显示 2026-07-03 11:46:46 Web 模型接口成功记录了 `asr updated: provider='custom:a838bee2' model='mimo-v2.5'`。`ModelsHandler._set_asr()` 未校验 Provider，确实会把运行时不支持的值写入配置并返回成功。
4. **存在同链路的潜在 TTS 二次故障。** 当前 `text_to_voice` 也为 `custom:a838bee2`，同时 `voice_reply_voice=true`。即使 ASR 修好，语音消息生成文本回复后还会请求 TTS，并在相同工厂位置再次失败。
5. **`ffmpeg` 缺失不是本次 Silk 报错的直接原因。** Silk 解码由 `pysilk-mod` 完成，不依赖 `ffmpeg`；但当前环境也找不到 `ffmpeg`，其他需要 `pydub` 转换的音频格式仍会受影响，应作为环境完整性项单独处理。

推荐采用“**支持范围内恢复 + 三层防御**”方案：

- 配置层把 ASR/TTS 切回仓库已实现的 Provider 和匹配模型；没有可用 TTS 时先关闭“语音消息回语音”。
- 依赖层安装并声明 `pysilk-mod>=1.6.4`，不要安装 PyPI 上的 `pysilk==0.0.1` 空包。
- 代码层补齐依赖哨兵、格式感知失败策略、Web/API Provider 校验、模型切换清理，以及 Bridge/Factory 的可诊断错误。

## 二、故障调用链

```text
微信群 audio 事件
  -> WechatGroupMessage: audio -> ContextType.VOICE
  -> WechatGroupChannel._generate_reply()
  -> ChatChannel._generate_reply()
       -> any_to_wav(<微信下载的 Silk 文件>, <目标 wav>)
            -> sil_to_wav()
            -> pysilk.decode_file()
            X pysilk 未安装且导入失败后未绑定名称
            X NameError
       -> catch Exception，记录 warning，并把 wav_path 回退为原始 Silk 路径
       -> Channel.build_voice_to_text(raw_silk_path)
       -> Bridge.fetch_voice_to_text()
       -> Bridge.get_bot("voice_to_text")
            provider = custom:a838bee2
       -> voice.factory.create_voice("custom:a838bee2")
            X 无 custom 分支
            X bare RuntimeError
  -> ThreadPool Worker 记录完整异常，当前消息无回复
```

关键判断：

- `NameError` 只会从 `.sil/.silk/.slk` 分支的 `sil_to_wav()` 进入，因此虽然业务日志没有打印真实媒体路径，仍可从分支条件确认本轮进入了 Silk 解码路径。
- `chat_channel.py` 捕获了第一段转换异常，所以堆栈最终停在 `voice/factory.py`；这不代表第一段可以忽略。若只修 Provider，原始 Silk 仍会被错误传给通常只接受 WAV/MP3 等格式的 ASR 端点。
- 若只安装 `pysilk-mod`，音频会成功转换，但 `custom:a838bee2` 仍会让工厂抛出同一个 `RuntimeError`。

## 三、已核实证据

### 3.1 当前运行环境

> 本节记录的是修复方案编写时的故障环境快照。实施后的依赖、自动化与待验收状态见“十三、实施结果”，不覆盖这里的历史根因证据。

| 检查项 | 结果 | 判断 |
| --- | --- | --- |
| Python | `3.13.5` | 与日志中的 `C:\Python313` 一致 |
| `pydub` | `0.25.1` 已安装 | 当前未卡在 `pydub` 导入 |
| `pysilk` 导入 | `find_spec('pysilk') == None` | Silk 解码依赖缺失 |
| `pysilk` PyPI 发行包 | 仅 `0.0.1`，源码中 `packages=[]` | 安装它不能提供 `import pysilk` |
| `pysilk-mod` | 最新 `1.6.4`，导出模块名 `pysilk` | 与当前源码调用契约一致 |
| Windows Python 3.13 wheel | 存在 `pysilk_mod-1.6.4-cp313-cp313-win_amd64.whl` | 当前环境无需自行编译即可安装匹配 wheel |
| `ffmpeg` | 命令不存在 | 不阻断 Silk 解码，但会影响其他 `pydub` 转码 |

`pysilk-mod 1.6.4` 的包源码确认公开了：

- `pysilk.decode_file(path, to_wav=True, sample_rate=...)`
- `pysilk.encode(...)`
- Python 要求 `>=3.8`

这与 `voice/audio_convert.py` 的现有调用签名一致。

### 3.2 当前配置（已脱敏）

```text
voice_to_text       = custom:a838bee2
voice_to_text_model = mimo-v2.5
text_to_voice       = custom:a838bee2
text_to_voice_model = mimo-v2.5-tts
voice_reply_voice   = true
```

同时，当前配置中 OpenAI、DashScope、智谱、LinkAI、MiMo 的独立 API key 均为空。也就是说，不能仅把 Provider 字符串改成某个内置值就宣称修复完成；还必须配置对应凭据，或先确认自定义网关确实支持目标 ASR 端点后再按内置 OpenAI 兼容字段接入。

`mimo-v2.5` 不是仓库现有 ASR Provider 的默认模型。仓库里的 `voice/mimo/mimo_voice.py` 也明确说明 MiMo 当前没有 ASR 端点，`voiceToText()` 只返回“不支持语音识别”的错误。因此 `custom:a838bee2 + mimo-v2.5` 不能被视为可工作的 ASR 组合。

### 3.3 Web/API 写入证据

`channel/web/web_channel.py` 当前存在以下断层：

- `_ASR_PROVIDERS` 只公开 `openai`、`dashscope`、`zhipu`、`linkai`。
- `_handle_set_capability()` 收到 `capability == "asr"` 后直接调用 `_set_asr()`。
- `_set_asr()` 不验证 `provider_id`，直接写入 `conf()` 和 `config.json`，然后刷新 Bridge。
- `_asr_capability()` 对已有 `voice_to_text` 只做字符串归一化，不判断运行时是否支持。
- 前端 `buildCapabilityProviderOptions()` 会把不在能力列表中的 `current_provider` 重新插入下拉选项，使既有坏配置继续表现成可选值。

最小复现结果：

```text
请求：capability=asr, provider_id=custom:a838bee2, model=mimo-v2.5
响应：status=success
准备持久化：voice_to_text=custom:a838bee2
准备持久化：voice_to_text_model=mimo-v2.5
触发：Bridge.refresh_voice()
```

因此根因是服务端能力边界缺少校验，前端行为只会放大问题；不能只在前端隐藏选项。

### 3.4 依赖历史

- 2023 年项目曾在 `requirements-optional.txt` 声明 `pysilk_mod>=1.6.0`，注释为 Wechaty 语音依赖。
- 2024 年提交 `9c17e16` 清理旧 Wechaty 依赖时移除了该项。
- 2026-07-02 提交 `68cdaf8` 新增当前 `channel/wechat_group/` 和 sidecar 下载媒体链路，但没有把 Silk 解码依赖补回。
- `voice/baidu/README.md` 仍写着 `pip install pysilk`，与当前有效发行包不一致。

这说明依赖缺失属于个人微信群语音能力重新接入后的依赖回归，而不仅是某台机器偶然漏装。

## 四、根因分级

### P0：ASR Provider 可保存但运行时不可创建

直接原因：`voice_to_text=custom:a838bee2` 被原样交给 `create_voice()`，工厂无对应分支。

系统根因：Web/API、配置展示、Bridge 和语音工厂没有共享或交叉校验能力契约。配置写入成功不等于运行时可用。

影响：所有语音输入在首次创建 ASR Bot 时直接退出 Worker；异常没有 Provider 名或可操作提示。

### P1：Silk 必需依赖缺失且可选导入处理不完整

直接原因：没有安装 `pysilk-mod`。

代码根因：`except ImportError` 只记录日志，未设置 `_pysilk_available=False` / `pysilk=None`；调用点也没有显式依赖检查。

影响：产生误导性的 `NameError`，用户看不到应安装哪个发行包；当前 INFO 日志级别下，模块导入时的 DEBUG 提示通常不可见。

### P1：转换失败后无条件透传原始 Silk

`chat_channel.py` 把所有音频转换异常统一降级为原路径。这个策略对部分本来就被 ASR 接受的 MP3/ WAV 可能有价值，但对 Silk 不成立。继续调用只能把格式错误推迟到下游，掩盖真正的环境问题。

影响：修复工厂配置后仍可能得到 ASR 400/格式不支持；不同 Provider 的表现不一致。

### P1：ASR Provider 切换会保留不兼容旧模型

`_set_asr()` 在新请求未传模型时保留旧 `voice_to_text_model`。代码注释声称运行时会回退 Provider 默认模型，但只要旧值非空，各 Voice 实现的 `conf().get(...) or DEFAULT_ASR_MODEL` 就不会触发默认值。

影响：例如从 DashScope 切到智谱但保留 `qwen3-asr-flash`，会把供应商 A 的模型发给供应商 B。现有测试 `test_set_asr_empty_model_keeps_existing` 反而固化了这一错误语义，应随修复调整。

### P1：TTS 存在同类坏配置

`text_to_voice=custom:a838bee2` 同样不被 `create_voice()` 支持。由于 `voice_reply_voice=true`，ASR 成功后生成的文本会进入 `build_text_to_voice()`，潜在地再次在工厂失败。

### P2：异常可诊断性不足

- `voice.factory` 使用不带消息的 `RuntimeError`。
- Bridge 不区分“配置值不支持”和 Voice Provider 内部请求失败。
- Worker 最终只有堆栈，没有面向用户的 `ReplyType.ERROR`。

### P2：`ffmpeg` 未安装

当前 Silk 分支不依赖 `ffmpeg`，所以不是本次根因。它会影响 MP3、M4A、OGG 等通过 `AudioSegment.from_file()` 的转换，应在环境验收中补齐，但不要用“安装 ffmpeg”替代本次两个主修复。

## 五、方案比较

### 方案 A：只改配置并安装依赖

优点：最快恢复当前实例，无代码风险。

缺点：API 仍可再次保存坏 Provider；缺依赖时仍抛 `NameError`；其他实例会复现。

结论：作为应急止血可以执行，但不能作为最终修复。

### 方案 B：为 `custom:<id>` 新增通用 ASR/TTS 适配器

优点：可复用自定义 OpenAI-compatible 网关。

缺点：当前没有证据证明该网关提供 `/audio/transcriptions` 或 `/audio/speech`，也没有每个自定义 Provider 的 ASR/TTS 模型、格式、voice、超时和响应契约。`mimo-v2.5` 本身也不是已知 ASR 模型。直接实现会把修 Bug 扩大为新能力开发。

结论：本轮不采用。若业务明确要求，应单独立项并先验证网关文档和真实端点。

### 方案 C：支持范围内恢复并补三层防御（推荐）

1. 用已实现的 ASR/TTS Provider 恢复实例配置。
2. 补回正确 Silk 依赖和可操作的格式错误。
3. Web/API 阻止不支持值进入配置。
4. Bridge/Factory 对历史坏配置仍返回明确错误。

优点：改动范围小，符合当前文档能力矩阵，不引入新网络协议；能同时覆盖新配置和历史坏配置。

结论：推荐。
