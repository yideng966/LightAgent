## 一、结论先行

当前“一个群画像都没生成”不是单纯因为消息数不足，也不是 LLM 调用失败，而是最新设计在真实身份数据上形成了一个确定性的零输出闭环：

```text
画像 reset 后正式画像表为空
  -> 现有画像的自动写入豁免全部消失
  -> 正式身份库没有任何强 wechat_id/manual 成员
  -> _automatic_subject_allowed() 拒绝所有新画像主体
  -> executor 在调用 LLM 前过滤掉全部作者和 mention 成员
  -> projected_messages/member_by_token 为空
  -> run 仍记录 success，并推进 room cursor
  -> 画像、昵称、别名、claim 始终为 0
```

因此继续调整 `profile_evolution_min_messages`、等待更多群消息或重复点击“立即学习”都不能解决根因。只要正式身份仍然没有强 `wechat_id`，当前自动主体门禁就会继续过滤所有人。

最新按群唯一存储和 opaque token 方向是正确的，问题在于把两类安全要求错误地合并成了一个门禁：

1. “是否允许在当前群为当前 runtime membership 生成一份群内画像”。
2. “是否允许跨 runtime 继承身份、合并成员、获得管理员权限或复用敏感数据”。

第一类只需要确认 stable account、stable room 和当前 active member alias，风险被限制在当前群；第二类才必须依赖强 `wechat_id` 或人工确认。

推荐重构为三层画像生命周期：

```text
观察层 observing
  首次有效群消息即可创建
  只保存当前群观察名、计数、最近出现时间

群内画像层 active
  达到证据门槛后补充风格、兴趣、常用词和证据化别名
  允许 auto_isolated/runtime member，但严格限定当前群

敏感身份层 privileged
  管理员权限、跨 runtime 继承、成员合并、跨群身份关系
  仍要求强 wechat_id 或人工确认
```

别名也必须分层：

```text
observed name       当前群名片/联系人昵称，不当作口语别名
explicit alias      唯一目标 + 唯一显式 @称呼，可直接激活
LLM alias candidate 有证据但目标绑定不足，先进入候选
manual alias        管理员确认，最高可信
```

## 三、当前生成链路复盘

### 3.1 人工画像

入口：

```text
Web 选择当前群成员
  -> POST /api/wechat-group/memories/profiles
  -> resolve stable room/member
  -> upsert_manual_profile()
```

人工写入不经过 `_automatic_subject_allowed()`，因此即使成员没有强 `wechat_id`，管理员仍可创建画像。创建后，该成员因为“已有画像”会被允许继续自动更新。

这说明系统当前实际模型是：

```text
每个无强 ID 成员都必须先被管理员手工创建一次
  -> 后续自动学习才会工作
```

对于 1474 个成员，这不是可执行的默认工作流。

### 3.2 启发式 learner

当前入口仍是手动 `POST /learn/run`。`wechat_group_learning_enabled = true` 没有对应的自动 worker 或 trigger。

流程：

1. 首次 profile pipeline 以当前 archive high water 建 baseline，不回放旧消息。
2. 读取 room cursor 后的增量消息。
3. 同一成员在本批至少 6 条文本时学习昵称、风格、兴趣和常用词。
4. 显式别名只处理“唯一非机器人目标 + 唯一非机器人 `@称呼`”。
5. `merge_learned_profile()` 和 `merge_learned_aliases()` 都经过 `_automatic_subject_allowed()`。
6. 无强 ID 且无已有画像时返回空对象。
7. room cursor 仍推进到批次末尾。

除了统一门禁，room 级 cursor 还有一个低频成员问题：某成员本批只有 5 条消息时不会生成画像，但 cursor 已跨过这 5 条；下批不会自动把两批证据累计到 6 条。

### 3.3 LLM 画像进化

当前 opaque token、证据白名单、事务写入已经解决上一版 runtime/stable 主键污染问题。

但 executor 在生成 token 前调用：

```text
resolve_automatic_member_id()
  -> resolve_canonical_member_id()
  -> _automatic_subject_allowed()
```

作者被拒绝后：

- 不加入 `member_order`。
- 不生成 `member_token`。
- 不加入 `projected_messages`。
- 不调用 LLM。

当整批都无 eligible member 时，executor 当前仍：

- 将 run 标为 `success`。
- `batch_message_count` 记录为已消费消息数。
- `analyzed_member_count` 记录为 0。
- 推进 `last_archive_row_id`。

这会造成静默丢失：后续即使管理员确认成员或修改准入策略，已经被 cursor 跨过的 305 条消息也不会自然重试。

### 3.4 trigger 与配置

当前 trigger 用：

```text
latest_observed_row_id - last_archive_row_id
```

近似当前群 pending 数。archive ID 是全库自增，多群消息交错后该差值不是当前群真实消息数。

结果可能同时出现：

- 配置要求 200 条，但某群实际只有少量消息也被触发。
- run 每次只消费 1 至数条消息。
- success 次数增加，但 analyzed/update 始终为 0。

### 3.5 reset 的影响

`reset_wechat_group_profiles.py` 做了两件关键事情：

1. 删除旧正式画像，不迁移旧画像、名称和 evolution 数据。
2. 为选中群的 heuristic/evolution cursor 写入 reset 时 archive high water。

这个 reset 本身符合“从新证据重新学习”的目标。但 reset 后：

- 旧画像不再提供“已有画像”准入豁免。
- 新消息作者又全部缺少强 ID。
- 没有新的观察型画像创建链路。

因此 reset 把原先被旧画像掩盖的门禁矛盾完全暴露出来。

## 四、当前别名生成复盘

### 4.1 当前可写来源

| 来源 | source kind | 当前是否可能生成 |
| --- | --- | --- |
| 人工别名 | `manual` | 可以，但必须管理员逐个维护 |
| 启发式显式 `@称呼` | `learning` | 目标成员被统一门禁拒绝，生产当前基本不能生成 |
| LLM alias | `llm_evolution` | member token 为空，生产当前不能生成 |
| 当前群观察昵称 | `observed` | 依赖启发式画像写入，同样被门禁拒绝 |

### 4.2 当前显式别名规则

规则本身较保守：

- 只处理文本。
- 必须有真实 `at_list`。
- 排除发言人和机器人。
- 必须只剩一个目标成员。
- 必须只剩一个非机器人显式 `@称呼`。
- runtime target 必须解析到当前群 canonical stable member。

但仍有两个已复现问题：

1. learner 没有复用 LLM 的群体泛称过滤，`@所有人` 可被写给唯一目标。
2. `self_display_name` 不是机器人当前群名片时，机器人 visible mention 无法被排除，真实别名会漏学。

### 4.3 LLM alias 的目标证据问题

opaque token 解决了模型伪造主键，但多目标消息中：

```text
@张总 @李老师 请一起看下
mentions = member_002, member_003
```

同一 message ID 会同时进入两个 token 的 evidence allowlist。服务端能证明两个成员都出现在消息里，但不能证明哪个可见称呼属于哪个 token。

在解决结构化 mention 或唯一目标 evidence 前，多目标 LLM alias 不应直接激活。

### 4.4 别名与主昵称仍有语义混用

当前在没有主昵称时，启发式 alias 或 LLM alias 可以被写入 `primary_nickname`。自动学到的识别词不应默认成为机器人回复时使用的称呼。

该部分继续采用 `plans/20260721_群友画像昵称逻辑复盘与优化方案.md` 中的名称语义：

```text
人工首选称呼 > 当前群观察名 > 已存观察名 > 安全兜底
aliases 只做识别集合，不随机决定 reply_name
```

## 五、重构原则

### 5.1 群内画像不等于敏感身份授权

画像只描述当前群中的消息行为，不应参与：

- 管理员权限。
- workspace/知识库/永久记忆写权限。
- 跨群身份合并。
- 跨 runtime 敏感配置继承。

因此允许 `auto_isolated/runtime` member 生成当前群画像，不等于放宽管理员或身份安全边界。

### 5.2 接受重复，不接受误合并和零产出

缺少强 ID 时，runtime 漂移可能产生两个 stable member 和两份群内画像。这个结果可以通过人工 redirect 合并，风险局限在当前群。

相比之下，当前“全部拒绝”虽然没有重复，却让画像功能完全不可用。推荐策略是：

```text
弱身份只允许创建隔离的群内画像
  -> 不跨 runtime 自动继承
  -> 不跨群共享
  -> 不获得权限
  -> 后续人工 redirect 时事务合并
```

### 5.3 画像创建与画像推断分离

“是否存在一条画像”不应依赖 LLM 阈值。

- 第一条有效消息即可创建观察型画像。
- 启发式和 LLM 只负责丰富画像内容。
- LLM 关闭、供应商故障或消息数未达阈值时，画像列表仍应出现当前群成员的基础画像。

### 5.4 按用途拆分成员准入策略

禁止继续用一个 `_automatic_subject_allowed()` 同时控制所有能力。

推荐策略：

| purpose | 准入条件 | 允许内容 |
| --- | --- | --- |
| `observe_profile` | confirmed room + canonical member + 当前 active runtime alias | 创建观察型画像、观察昵称、计数 |
| `deterministic_alias` | 上述条件 + 唯一目标/唯一显式称呼 | 写入证据化显式别名 |
| `infer_room_profile` | 上述条件 + 当前群足够消息证据 | 风格、兴趣、常用词、LLM claims |
| `merge_identity` | 强 `wechat_id` 或人工确认 | 跨 runtime redirect/合并 |
| `grant_privilege` | stable admin 精确配置 | 管理员和敏感写权限 |

## 六、目标画像生命周期

### 6.1 observing

首次有效入站消息完成 stable room/member 解析后创建：

```text
stable_room_id
stable_member_id
primary_nickname = 当前群观察名
msg_count = 1
first_observed_at
last_observed_at
status = observing
```

同时写 `source_kind = observed` 的名称记录。这个操作：

- 不调用 LLM。
- 不要求强 `wechat_id`。
- 不创建跨群关系。
- 不改变权限。
- 必须只在 archive 确认插入新 message ID 时计数，避免重复事件累加。

Web 画像页应该显示 observing 画像，并标识“证据积累中”。Prompt 可以使用其当前群昵称，但不应编造尚未学习的画像字段。

### 6.2 active

成员满足以下任一条件后进入 active：

- 当前群累计可学习文本消息达到 `wechat_group_learning_profile_min_messages`。
- 管理员手动保存画像。
- LLM 画像进化接受至少一个有效 claim。

active 画像可以注入完整群友画像字段，但仍只限当前群。

### 6.3 superseded

管理员确认 member redirect 后：

- identity redirect 指向 canonical stable member。
- profile、name records、claims、revisions 事务合并。
- 旧 profile 标记或删除为 superseded。
- runtime alias 后续解析到 canonical member。

现有 `confirm_member_redirect()` 与 `merge_profile_subjects()` 可以继续复用。

### 6.4 disabled

管理员可禁用错误画像。disabled 画像不进入 prompt 和普通搜索，但保留审计记录，不直接物理删除证据。

## 七、画像生成链路重新设计

### 7.1 轻量观察器

在归档成功后增加轻量 `WechatGroupProfileObserver`，或在 profile service 中增加等价方法：

```text
archive INSERT OR IGNORE
  -> 返回 inserted + archive_row_id
  -> inserted=true 时调用 observe_message()
  -> resolve purpose=observe_profile
  -> upsert observing profile + observed name
  -> note heuristic/evolution signal
```

不要让 observer 承担兴趣、风格或 LLM 调用；它只保证画像存在和基础统计连续。

### 7.2 归档接口幂等

`WechatGroupArchive.record_message()` 当前无返回值。建议返回：

```json
{
  "inserted": true,
  "archive_row_id": 30956
}
```

只有 `inserted = true` 才更新画像 `msg_count`、观察时间和学习信号，避免 sidecar 重投、通道重试或重复事件造成统计膨胀。

### 7.3 启发式自动调度

`wechat_group_learning_enabled` 应产生真实行为，二选一：

1. 推荐：并入现有 profile trigger，按当前群空闲和受影响成员增量执行 heuristic。
2. 或删除“启用学习”开关，只保留明确的手动运行按钮。

不建议再维护第二个常驻线程。可以由同一个 profile maintenance worker 调度 observer 后的 heuristic/evolution 两个阶段。

### 7.4 低频成员证据累计

room cursor 只负责发现“哪些成员有新消息”，不能决定成员证据窗口。

每次 heuristic 对受影响成员查询当前群最近 `profile_sample_limit` 条可学习文本：

```text
new room messages
  -> affected canonical members
  -> archive query by stable_room_id + stable_member_id
  -> 获取该成员滚动样本
  -> 累计达到 min_messages 后更新画像
```

需要增加或确认索引：

```text
(stable_room_id, stable_member_id, id)
```

这样某成员第一批 5 条、第二批 2 条时，第二次能基于 7 条样本生成画像。

### 7.5 LLM 画像进化

保留现有 opaque token 和 evidence allowlist，修改 subject policy：

- `infer_room_profile` 允许当前群 active runtime membership，不要求强微信号。
- LLM 输出仍只能写当前 room/canonical member。
- 不允许跨群复用画像正文。
- runtime 漂移不会自动继承旧画像；只有 redirect 后合并。

### 7.6 空批次状态与 cursor

当 batch 有消息但没有 projected member 时，run 不得标记普通 success。

建议状态和诊断：

```text
status = deferred_no_subject | skipped_no_text | success | failed
input_message_count
eligible_message_count
analyzed_member_count
skipped_member_count
skip_reasons
cursor_advanced
```

真正没有 stable room/member 的消息可以隔离并计数。正常 `runtime/auto_isolated` 当前群成员不再属于 skip 对象。

### 7.7 trigger 使用真实 pending

archive 增加：

```python
count_messages_after_row_id(stable_room_id, cursor)
```

trigger 用真实当前群消息数判断阈值，不再用全库 row ID 差值。

当 backlog 大于 batch limit 时，worker 在单轮受控次数内继续处理，直到：

- pending 小于阈值。
- 达到最大批次数/耗时。
- LLM 临时故障。

## 八、别名生成重新设计

### 8.1 observed name

当前群名片或联系人昵称属于观察名：

- 首条消息就记录。
- 名称变化时更新 `last_seen_at/seen_count`。
- 不自动视为口语别名。
- 人工首选称呼仍可覆盖显示和回复。

sidecar/归档应保留名称来源：

```text
sender_room_alias
sender_contact_name
sender_name_source = room_alias | raw_nickname | contact_name
```

### 8.2 deterministic explicit alias

确定性别名允许 `runtime/auto_isolated` 当前群成员，因为证据已经一一绑定：

```text
唯一非机器人 at_list 目标
  + 唯一非机器人显式 @称呼
  + 当前群 canonical member 解析成功
  + 自动名称 denylist 通过
  -> active explicit alias
```

统一过滤 helper 必须由 heuristic 和 LLM merger 共用，至少拒绝：

- `所有人/全体成员/全员/大家/各位/群友`。
- `all/everyone/here`。
- 机器人所有当前群名称。
- runtime/stable ID、长哈希、纯数字和传输层字段。
- 单字符无意义中文、控制字符和超长文本。

### 8.3 结构化 mention

为解决机器人群名片不一致和多目标别名错配，建议 sidecar 上报：

```json
"mentions": [
  {"runtime_sender_id": "...", "display_name": "张总"},
  {"runtime_sender_id": "...", "display_name": "李老师"}
]
```

Python 层逐个解析到 canonical member，再建立：

```text
member_token -> visible mention name -> evidence_message_id
```

在结构化 mention 落地前，多目标消息中的 LLM alias 只能作为候选，不能自动激活。

### 8.4 LLM alias candidate

LLM 可以发现非显式别名，但自动激活条件应更严格：

- 目标 token 属于当前批 allowlist。
- 每条 evidence 属于该 token 的 alias-specific evidence allowlist。
- 置信度至少 `0.85`。
- 至少 2 条独立消息证据；单条非结构化证据进入 candidate。
- 群体泛称和高歧义称呼拒绝。
- 同一 alias 命中当前群多个成员时不得激活。

建议 name/claim 状态：

```text
candidate | active | suppressed | rejected
```

### 8.5 人工治理

Web 画像详情需要区分：

- 当前群观察名。
- 人工首选称呼。
- 人工 aliases。
- 自动 active aliases。
- 待确认 candidates。
- suppressed/rejected aliases。

管理员 suppress 自动 alias 后，后续学习只能追加证据，不能静默恢复 active。

### 8.6 别名不提升主昵称

自动 alias 不再持久化填充 `primary_nickname`。

推荐优先级：

```text
primary_nickname:
  manual preferred name
  -> active room alias
  -> latest observed room name
  -> stored observed name
  -> safe fallback

reply_name:
  manual preferred name
  -> primary_nickname
```

aliases 只做识别和检索，不因记录排序靠前就变成回复称呼。

## 十、reset 后证据恢复方案

6. 运行 heuristic 滚动样本聚合。
7. 按配置决定是否立即运行 LLM enrichment。

## 十五、风险与回滚

### 15.1 主要风险

- runtime 身份漂移会产生重复群内画像。
- observer 每条消息写画像库会增加 SQLite 写压力。
- 结构化 mention 涉及 sidecar 协议同步。
- 回放 cursor 操作错误可能重复或遗漏证据。

### 15.2 控制方式

- 允许隔离重复但禁止自动合并。
- 只在 archive 新插入、名称变化或计数变化时写入；必要时批量提交。
- sidecar 新字段向后兼容，旧 `at_list` 暂时保留。
- 回放必须 dry-run、备份、限定 stable rooms 和 manifest baseline。
- 管理员/敏感权限继续使用原 stable admin 门禁，不读取画像状态。

### 15.3 回滚

1. 停止 profile maintenance worker。
2. 恢复画像数据库备份和原 cursor。
3. 回退代码，不回退 archive/identity 数据。
4. 不在新旧 profile lifecycle 之间双写。

## 十六、验收标准

只有同时满足以下条件，才能认为生成方案真正修复：

1. 正式无强 `wechat_id` 数据集上能稳定生成画像，而不是仅测试 fixture 能生成。
2. 第一条消息产生 observing profile，画像存在不依赖 LLM。
3. 画像 enrichment、别名和权限使用不同强度的门禁。
4. run 不能再出现无诊断的 `success + analyzed=0 + updates=0`。
5. 被跳过或延迟的证据不会被 cursor 静默永久跨过。
6. 别名证据能够服务端绑定到具体 current-room canonical member。
7. `@所有人`、多人 mention、机器人群名片不一致均有回归保护。
8. 自动 alias 不会自动提升为主昵称或回复称呼。
9. reset 后 305 条已消费零分析消息能够受控重新处理。
10. 群隔离、管理员门禁、跨 runtime 合并规则不被放宽。
