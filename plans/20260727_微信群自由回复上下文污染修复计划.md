**状态：** 代码实施完成，自动化验证通过；待 Docker 真实群 canary 验收

**创建日期：** 2026-07-27

**任务类型：** 线上缺陷修复 / 自由回复判定优化 / Agent 会话隔离

**目标：** 修复微信群普通自由回复把数小时前的成员级 Agent 会话或错误截取的旧群聊内容当成当前话题，进而对无明确指代的短句强行接话的问题；同时保留直接 @、引用机器人和明确连续追问的正常多轮能力。

**关联计划：**

- `plans/20260714_微信群上下文分层与滚动摘要优化.md`：长期分层上下文、统一 timeline、滚动摘要和 `observe_only` 的总设计依据。
- `plans/20260727_PR15自由回复Scorer问题修复方案.md`：已完成 Scorer 模型路由、请求控制和失败回落修复；本计划不重复修改该部分。
- `plans/20260726_自由回复二次判定说明.md`：现有自由回复 Scorer/Judge 行为说明，代码完成后需要同步校正。

## 0. 计划定位与实施边界

本计划是 `20260714_微信群上下文分层与滚动摘要优化.md` 的缺陷执行切片，不重新实施完整滚动摘要工程。当前线上问题已有明确复现证据，应先用最小、可验证的改动解除错误话题锚定，再单独落地自由回复的 Agent 历史隔离。

本计划分为两个代码阶段：

1. **Phase 1：低风险确定性修复**
   - 修正 `<local-extractive-summary>` 取到窗口内最早消息的问题。
   - 阻止微信 transport XML、路径、base64 或密钥样式字段进入本地摘要。
   - 修正 `unanswered_question` 的错误加分条件。
   - 增加“短问句明显承接上一名群友”的硬抑制。
   - 让 legacy Judge 与 Scorer 使用一致的安全近场上下文。
   - 普通 `free_reply` 只注入有界近场 timeline，不再同时注入本地摘要和远期归档证据。
2. **Phase 2：自由回复 Agent 历史隔离**
   - 普通 `free_reply` 使用 `observe_only`，生成时不恢复旧 Agent 对话。
   - 观察轮次仍保留 UI、审计和 scoped 被动学习所需的清洗记录，但不得再次进入回复恢复上下文。
   - 直接 @、引用机器人和明确连续追问继续使用交互会话。

本计划明确不做：

1. 不实现完整 room 级 LLM 滚动摘要 worker；继续由长期计划单独推进。
2. 不修改 Wechaty sidecar 或 JSON Lines 协议。
3. 不修改桌面端 `desktop/`。
4. 不新增第三方依赖或独立模型调用链。
5. 不清空全部会话数据库，不批量改写无法确认来源的历史消息。
6. 不关闭全局 `conversation_persistence`，避免破坏直接 @ 的正常多轮对话。
7. 不通过增加上下文窗口、提高 Token 上限或写更多 Prompt 规则掩盖服务端判定缺陷。

## 1. 已确认的线上复现与因果链

### 1.1 触发场景

同一群成员上午与机器人讨论播放器和投屏；数小时后，当前群已连续讨论牙科、医疗费用和种植牙。某群友说“我弄好了~”，该成员紧接着发送“有用吗”，未 @ 机器人、未引用机器人、未提机器人名称。

机器人却回复“投屏家里大屏看片爽多了”。

### 1.2 请求取证结果

线上请求已完成只读取证，关键事实如下：

1. 主模型请求包含 7 条 messages、4 个可见轮次、共 17074 个正文字符。
2. 前 6 条标准 `user/assistant` 历史是该成员上午最后 3 轮 Agent 会话，主题全部与播放器、电视源和投屏有关。
3. 第 7 条当前 user message 同时包含：
   - `<wechat-group-archive-evidence>`：当前牙科现场的最近证据。
   - `<local-extractive-summary>`：24 小时窗口内最早 100 条消息，其中大段是上午投屏讨论。
   - `<recent-wechat-group-transcript>`：当前 60 分钟牙科现场，共 99 条消息。
4. 模型原始 thinking 明确把“有用吗”解释成“投屏功能是否有用”。
5. 这不是跨群泄露；stable room 隔离正确，问题是同一群内远近话题冲突和成员级旧 Agent 历史权重过高。

### 1.3 根因分解

| 根因 | 当前实现 | 缺陷结果 |
|---|---|---|
| 本地摘要取值方向错误 | `ORDER BY created_at ASC, id ASC LIMIT ?` | 群消息超过 limit 后得到时间窗口内最早 N 条，不是最近 N 条 |
| 本地摘要并非真实摘要 | 逐行拼接 sender + 原始 text | 大量旧原文重复进入 Prompt，且单条文本没有安全长度边界 |
| transport XML 清洗覆盖不完整 | 只依赖 `project_wechat_message_type()` | 某些 `<msg><appmsg>...` 文本仍被视为普通 text，携带 XML 字段进入 Prompt |
| `unanswered_question` 逻辑错误 | 命中 `group_question` 且 `len(recent_messages) >= 2` 就加 25 分 | “近期有消息”被错误等价为“近期无人回答” |
| 泛化问号得分过高 | 任意包含“吗/嘛/呢/？/?”都获得 `group_question` 30 分 | 无对象短句可与错误的 25 分叠加越过 normal 阈值 50 |
| legacy Judge 不看现场 | Prompt 只有当前文本、分数、原因和抑制项 | 无法识别上一条来自特定群友，也无法判断 A 对 B 的连续对话 |
| Scorer 关系字段不足 | 有近场消息，但主要是 sender/text/is_bot | 引用、mention、明确人类收件人等关系没有统一投影 |
| 所有 free reply 都开长历史 | `should_include_contextual_history(..., "free_reply")` 恒为 True | 同时注入 archive evidence、local summary 和 recent transcript，重复且互相冲突 |
| 成员级 Agent 会话无话题过期 | 容器重启后恢复最近 `max(3, 20 // 6) = 3` 轮 | 数小时前的标准 user/assistant 历史被当成当前连续对话 |
| free reply 与 direct reply 共用恢复语义 | `AgentBridge` 未区分观察型插话和明确交互 | 普通群内插话也恢复旧成员会话，形成强话题锚点 |

## 2. 修复目标与验收口径

### 2.1 必须达到

1. `<local-extractive-summary>` 在窗口内消息超过 limit 时返回最新 N 条，并按时间正序展示。
2. 本地摘要不得出现 XML 标签、`aeskey`、`cdnthumburl`、base64、本机路径或其他 transport metadata。
3. `unanswered_question` 不得再由“近期消息数量不少于 2”直接触发。
4. “某群友：我弄好了~”之后另一成员发送“有用吗”，普通自由回复必须在调用主模型前被拒绝。
5. “大家觉得这个有用吗”仍可作为开放群问题进入二次判定。
6. “@小灯 这个有用吗”或引用机器人后的“有用吗”继续正常回复。
7. 普通 `free_reply` 的主模型请求不得恢复该成员旧 Agent 会话。
8. `observe_only` 运行结束后，原交互会话在正常、异常、取消路径中都必须完整恢复。
9. `observe_only` 用户原文和助手正文可以保留用于 UI/审计，但不得被 `AgentInitializer` 恢复进后续回复。
10. Web、其他 IM 渠道、CLI、scheduler 和直接 Agent 会话行为不得改变。

### 2.2 质量指标

1. 当前线上复现场景必须由自动化测试覆盖，不能只做 Prompt 快照测试。
2. 自由回复误插话采用失败闭合：指代不明时宁可不回复。
3. 直接 @ 的必回语义不能因为自由回复变保守而回归。
4. 不增加自由回复主链路的额外模型调用次数。
5. Phase 1 不新增配置项；优先复用现有规则分数、开关和 recent 配置。
6. Phase 2 不要求迁移旧记录；没有 visibility metadata 的历史继续按 legacy 交互记录处理。

## 3. 不可破坏的项目边界

1. 所有房间、成员和会话判断继续优先使用 `stable_room_id + stable_member_id`。
2. runtime room/member ID 只用于微信真实发送和 legacy 快照，不扩大长期会话范围。
3. 当前轮增强块仍只进入当前请求；持久化继续保存清洗后的用户原文。
4. 普通成员管理员门禁、工具过滤和 Prompt 权限提示继续生效。
5. `ChatChannel -> Bridge -> Agent` 仍是唯一最终回复主链路。
6. Scorer 和 legacy Judge 只做是否接话判定，不生成最终回复、不调用工具、不写记忆。
7. persona、style、emotion、reference policy、多模态和回复清洗行为保持不变。
8. 不把群归档、本地摘要或 Agent 交互历史升级为新的长期记忆来源。
9. 任何安全 formatter 都不得把真实 ID、媒体路径、cookie、密钥或本机文件信息写入 Prompt。

## 4. 目标行为矩阵

| 触发场景 | 自由回复本地结果 | 二次判定上下文 | Agent 历史模式 | 预期行为 |
|---|---|---|---|---|
| 群友 A：“我弄好了” -> 群友 B：“有用吗” | `likely_human_followup` 硬抑制 | 不调用 | 不创建回复运行 | 保持沉默 |
| 群友：“大家觉得这个有用吗” | 开放群问题候选 | 最近 3-5 条关系型 timeline | `observe_only` | Scorer/Judge 决定是否低打扰接话 |
| 群友：“谁能总结一下刚才方案” | 群问题 + 机器人能力候选 | 最近 timeline | `observe_only` | 可进入主模型并使用最近现场 |
| 群友提到“小灯”但未 @ | bot target 候选 | 最近 timeline | `interactive_session` 仅在明确承接时，否则 `fresh` | 正常回复 |
| 明确 @ 机器人提出独立完整问题 | 非自由回复必回 | 按现有 direct 逻辑 | `fresh` | 不承接数小时前旧话题 |
| 明确 @ 后“继续/刚才你说的” | 非自由回复必回 | recent + 引用/机器人上一句 | `interactive_session` | 恢复交互会话 |
| 引用机器人回复后短问句 | 非自由回复必回 | 引用锚点 + recent | `interactive_session` | 正确承接机器人上一句 |
| 普通图片自由回复 | 保持现有图片门禁 | 当前多模态 + 有界 recent | `observe_only` | 不恢复旧文本会话 |
| 总结/谁说/回到之前 | 不按普通 ambient 处理 | 由长期分层计划的 contextual/recall 负责 | 明确回指机器人时才 interactive | 本计划不扩大远期召回 |

## 5. Phase 0：发布前立即止血

Phase 0 是运维配置，不修改仓库默认值。修改前备份线上 `config.json`，合并现有字典而不是覆盖其他自由回复规则。

建议临时设置：

```json
{
  "wechat_group_local_summary_enabled": false,
  "wechat_group_free_reply_rule_scores": {
    "unanswered_question": 0
  }
}
```

作用：

1. 暂停错误的旧原文摘要注入。
2. 普通 normal 档位下，“有用吗”只得到通用问句分数，无法以 55 分越过 50 分阈值。
3. 不影响明确机器人能力、机器人名称、强触发词、复读和直接 @ 链路。

验证：

1. Web 设置保存后确认实际配置中的其他 `rule_scores` 未丢失。
2. 重放“我弄好了~ / 有用吗”，日志应显示 `below_threshold` 或新硬抑制，不应进入 worker。
3. 重放“谁能帮我总结一下”，仍应进入候选链路。

回滚：恢复备份值。不得通过清空会话数据库回滚。

## 6. Phase 1：低风险确定性代码修复

### 6.1 修正本地摘要取值方向

目标文件：

- `channel/wechat_group/wechat_group_archive.py`
- `channel/wechat_group/wechat_group_archive_context.py`
- `tests/test_wechat_group_humanization.py`

修改内容：

1. 修改 `WechatGroupArchive.get_messages_for_distill()`：
   - 先在 `since_ts <= created_at <= until_ts` 范围内按 `created_at DESC, id DESC` 取最新 N 条。
   - 再在 SQL 外层或 Python 中恢复为 `created_at ASC, id ASC`。
   - 保持 stable room 严格匹配和 legacy 空 stable ID 回查规则不变。
   - 保持返回类型和调用签名不变，避免影响现有调用方。
2. 推荐采用与 `get_recent_messages()` 一致的“倒序查询 + `reversed(rows)`”模式，减少复杂 SQL。
3. `until_ts` 必须继续参与上界过滤；历史重放测试不得读取目标消息之后的新消息。

目标语义示例：窗口内有 150 条、limit=100 时，返回第 51-150 条，并按第 51 到第 150 条正序排列。

### 6.2 统一本地摘要安全投影

修改 `build_local_extractive_summary_block()`：

1. 不再直接拼接 `row["text"]`。
2. 复用 `wechat_group_context.py` 的安全文本投影能力：
   - transport XML 投影为对应媒体占位；本地摘要只接受确定的普通文本，媒体占位默认跳过。
   - 删除 XML 标签、base64、大段 URL 参数、本机路径和敏感键值样式。
   - sender display name 使用当前群安全昵称，不回退其他群别名。
   - 单条文本保持现有安全截断，避免一个 app payload 占满上下文。
3. 增加 `<msg><appmsg>...`、WPS 小程序分享 XML、图片 XML 和伪装为 text 的媒体 payload 回归样本。
4. 当前 `message_id` 继续排除。
5. 本阶段不新增 `local_summary_max_chars` 配置；普通 free reply 将停止注入该块，长期字符预算由分层计划统一解决。

### 6.3 修正自由回复正向评分

目标文件：

- `channel/wechat_group/wechat_group_free_reply.py`
- `tests/test_wechat_group_free_reply.py`

修改内容：

1. 删除以下错误等价关系：

```python
if "group_question" in reasons and len(recent_messages or []) >= 2:
    score += unanswered_question_score
```

2. 将问句判定拆成两个确定性概念：
   - `generic_question`：只因“吗/嘛/呢/？/?”等形式表现为问句。
   - `explicit_open_group_question`：包含“大家、谁能、谁有、有没有人、哪位”等明确开放收件人。
3. 为兼容现有配置和 Web 规则 ID，`group_question` 继续表示通用问句；`unanswered_question` 仅在满足以下全部条件时追加：
   - 当前是 `explicit_open_group_question`；
   - 没有明确人类收件人；
   - 没有命中成员间连续对话硬抑制；
   - 当前候选之后尚未出现明确回答，worker 提交前仍需再次校验。
4. 现有用户自定义 `unanswered_question` 分数继续可读取；本计划不迁移或删除配置键。
5. active/crazy 档位仍可对普通问句更积极，但不能绕过人类收件人硬抑制。

### 6.4 增加成员间连续对话硬抑制

新增纯函数分析，不调用模型、不读跨群数据：

```text
analyze_free_reply_addressee(current_message, recent_timeline) -> decision
```

至少输出：

```text
target_kind: bot | group | human | unknown
target_member_token
is_short_question
is_explicit_open_group_question
is_immediate_bot_followup
is_likely_human_followup
evidence_codes[]
```

`likely_human_followup` 默认成立条件：

1. 当前正文是短问句或省略句，建议归一化后不超过 12 个字符。
2. 当前没有 @ 机器人、引用机器人、机器人名称、机器人能力请求或明确开放群体词。
3. 上一条有效 timeline event 来自人类成员，且不是当前机器人。
4. 当前消息与上一条间隔在 120 秒内。
5. 上一条是具有可承接语义的陈述、结果或动作状态，而不是纯表情/媒体占位。

命中后添加新的硬抑制 `likely_human_followup`。该抑制：

1. 默认启用并在规则 API 中显示中文说明“疑似群友间连续对话”。
2. Scorer 和 legacy Judge 不得覆盖。
3. 不应用于直接 @、引用机器人、拍一拍和强触发词必回链路。
4. 不把真实 stable/runtime ID写入日志或 Prompt；日志只输出房间、简短文本和 evidence code。

### 6.5 统一 Scorer 与 legacy Judge 的安全近场上下文

建议新增：

- `channel/wechat_group/wechat_group_free_reply_context.py`

职责仅限确定性安全投影和收件人分析，避免 Judge 与 Scorer 分别维护不同规则。

修改：

- `channel/wechat_group/wechat_group_channel.py`
- `channel/wechat_group/wechat_group_free_reply_scorer.py`
- `channel/wechat_group/wechat_group_free_reply_judge.py`
- `tests/test_wechat_group_free_reply_scorer.py`
- `tests/test_wechat_group_free_reply_judge.py`
- `tests/test_wechat_group_channel.py`

具体内容：

1. `_should_enqueue_free_reply_message()` 无论 Scorer 是否启用，都优先读取 `get_recent_conversation_messages()`，使判定窗口同时包含群友入站和机器人真实已发送回复。
2. 上下文窗口最多 5 条用于 legacy Judge、最多沿用现有 `scorer_context_limit` 用于 Scorer。
3. 安全 event 仅包含：
   - 相对时间或安全时间戳；
   - opaque actor token，例如 `member_001` / `assistant`；
   - 是否机器人；
   - 是否回复机器人；
   - 是否提到某个群友；
   - 经过清洗和截断的正文。
4. 不把 runtime/stable ID、media path、原始 quote payload、XML 或完整 URL 参数传给判定模型。
5. legacy Judge Prompt 增加最近小窗口，并明确：
   - 当前短问句自然承接上一名群友时必须拒绝。
   - “有用吗”本身不能证明在问机器人。
   - 只有明确 bot target 或开放群问题才考虑回复。
6. legacy Judge 保持原 JSON schema，避免在本阶段扩大模型适配范围。
7. Scorer 保持现有结构化 schema和阈值，只替换为共享安全 event，并增加确定性 addressee 结果作为 `local_features`。
8. Scorer 未配置、超时、无效 JSON 和 fallback 行为继续遵守已完成的 PR #15 方案。

### 6.6 收紧普通 free reply 的当前轮上下文

目标文件：

- `channel/wechat_group/wechat_group_humanized_context.py`
- `channel/wechat_group/wechat_group_channel.py`
- `tests/test_wechat_group_humanization.py`
- `tests/test_wechat_group_channel.py`

本阶段只针对普通 `trigger_source=free_reply` 建立小范围策略，不提前实现完整 context policy 类：

1. 普通 free reply 默认只注入最近 conversation timeline。
2. 最多取最近 12 条，最大回看 30 分钟；使用命名常量而不是散落魔法数字。
3. timeline 包含机器人已真实发送的回复，并排除当前 `message_id`。
4. 普通 free reply 不注入：
   - `<wechat-group-archive-evidence>`；
   - `<local-extractive-summary>`；
   - 旧焦点消息。
5. 普通 free reply 继续允许：

## 7. Phase 2：普通自由回复 Agent 历史隔离

### 7.1 历史模式映射

本阶段落实以下服务端元数据：

```text
wechat_group_agent_history_mode = fresh | interactive_session | observe_only
```

映射规则：

| 场景 | history mode |
|---|---|
| target=group/unknown 的普通 free reply | `observe_only` |
| 未 @ 但明确点名机器人、问题本身完整 | `fresh` |
| 未 @ 但明确点名机器人且具有“继续/刚才你说的”等承接信号 | `interactive_session` |
| standalone direct @ 且问题完整 | `fresh` |
| quote_self | `interactive_session` |
| 明确“继续/刚才你说的/再查一下”且能确认机器人链路 | `interactive_session` |
| 普通图片自由回复 | `observe_only` |
| 引用机器人继续图片解释 | `interactive_session` |
| scheduler / 其他渠道 | 保持现状，不使用该微信群模式 |

`WechatGroupChannel._submit_free_reply_after_judge()` 在构造 Context 时根据确定性 addressee 结果和 Scorer 决策写入 history mode：`target=group/unknown` 默认 `observe_only`；明确 `target=bot` 但没有承接信号时使用 `fresh`；明确 `target=bot + is_followup_to_bot` 时使用 `interactive_session`。legacy Judge 没有可靠 target 字段时失败闭合为 `observe_only`。直接回复的模式选择保持在微信群通道适配层，不把微信群语义下沉到通用模型 Provider。

### 7.2 AgentBridge 快照、空历史运行与恢复

目标文件：

- `bridge/agent_bridge.py`
- `agent/protocol/agent.py`（仅当需要统一 execution lock）
- `tests/test_agent_bridge_wechat_group_persistence.py`

执行顺序固定为：

1. 取得当前 session 的 Agent。
2. 获取该 Agent/session 的执行互斥；普通运行与 observe-only 运行必须使用同一把锁。
3. 在 `messages_lock` 内复制：
   - `agent.messages`；
   - `agent._last_run_new_messages`；
   - 与当前执行结果读取有关的引用。
4. 将本轮 executor 可见历史置为空，但不调用 `clear_history=True`，避免清空数据库。
5. 继续执行完整系统 Prompt、技能、工具过滤、管理员门禁和当前微信群增强上下文。
6. 运行完成后，在恢复前独立复制本轮新消息、最终文本和待发送文件信息。
7. 在 `finally` 中恢复原 `agent.messages` 和 `_last_run_new_messages`。
8. 正常、模型异常、工具异常、取消和文件回复路径都必须执行恢复。
9. 不在模型调用期间持有 `messages_lock`，避免与 Agent 内部锁重入死锁。
10. 同一 session 并发不得出现两个快照交叉恢复；测试必须主动构造并发屏障验证。

### 7.3 observe-only 持久化可见性

目标文件：

- `bridge/agent_bridge.py`
- `bridge/agent_initializer.py`
- `agent/memory/conversation_store.py`
- `tests/test_agent_bridge_wechat_group_persistence.py`

利用现有 `messages.extras`，每条观察消息写入：

```json
{
  "history_visibility": "observe_only",
  "channel_type": "wechat_group",
  "stable_room_id": "<服务端作用域>",
  "stable_member_id": "<服务端作用域>"
}
```

安全要求：这些 scope 字段只进入本地数据库 extras 和服务端过滤，不进入 LLM Prompt或普通日志。

持久化规则：

1. 预持久化用户消息仍使用 `wechat_group_user_content` 原文，不保存增强块。
2. observe-only 只保存清洗后的 user text 和最终 assistant text。
3. 不保存原始 thinking、tool_use、tool_result、路径或密钥内容到观察轮次。
4. `ConversationStore.load_messages()` 增加明确的恢复可见性参数，模型恢复默认排除 `observe_only`。
5. UI/审计读取可以显式包含 observe-only，不能因为回复隔离而让历史页面丢消息。
6. `AgentInitializer._restore_conversation_history()` 只恢复 interactive/legacy 可见轮次。
7. 没有 extras 的旧消息视为 legacy interactive，不做无法证明来源的批量迁移。
8. 清除上下文、删除消息、编辑消息和 session msg_count 行为必须继续正确。

### 7.4 被动学习与进化信号

observe-only 恢复原 Agent 历史后，现有 `note_user_turn(agent)` 不能再依赖 `agent.messages` 猜测本轮内容。

目标文件：

- `agent/evolution/trigger.py`
- `agent/evolution/executor.py`
- `bridge/agent_bridge.py`
- `tests/test_evolution.py`

修改内容：

2. 只传清洗后的当轮 user/assistant 文本，不传增强块、thinking 或原始工具结果。
3. 观察缓冲不得参与任何回复请求。
4. 普通成员观察仍只能进入当前群 scoped 画像/记忆的既有受限链路，不扩大工具权限。
5. 进化失败时保留未消费观察信号，成功或 no-change 后推进对应游标。
6. 本计划不实现工具 continuation capsule；普通文本承接优先依赖已真实发送的 assistant room timeline。工具连续性留在长期分层计划中实现。

## 8. 端到端数据流

修复后的普通自由回复链路：

```text
Wechaty 入站消息
  -> WechatGroupChannel 归档当前消息
  -> 读取当前 stable room 的有界 conversation timeline
  -> 本地评分 + 确定性 addressee 分析
       -> likely_human_followup：直接拒绝
       -> 其他候选：进入 Scorer 或 legacy Judge
  -> 二次判定只读取安全近场窗口
  -> 通过后构造 free_reply recent-only 当前轮上下文
  -> Context 标记 history_mode=observe_only
  -> AgentBridge 快照旧交互历史
  -> 空历史执行当前 Agent 请求
  -> 捕获最终回复并保存 observe-only 清洗记录
  -> finally 恢复旧交互历史
  -> 微信发送前继续执行清洗、抑制 mention 和现有权限门禁
```

直接 @ / 引用机器人链路不进入自由回复 worker，继续沿现有必回路径，并按 `fresh / interactive_session` 显式选择历史。

## 14. 风险与控制

### 14.1 自由回复过度沉默

风险：成员间硬抑制可能拦截开放闲聊。

控制：明确“大家/谁能/有没有人”、机器人名称、机器人能力、直接 @、引用机器人和强触发词均绕过该抑制；用正反例测试固定边界。

### 14.2 observe-only 破坏正常多轮

风险：自由回复后用户立即追问机器人时看不到上一轮。

控制：机器人真实回复进入 room timeline；引用机器人和明确继续转为 interactive/contextual。工具 continuation 不在本计划内假装支持，后续由长期计划的 capsule 实现。

### 14.3 Agent 快照并发污染

风险：两个请求交叉清空和恢复同一个 Agent messages。

控制：所有同 Agent 执行使用统一 execution lock；`messages_lock` 只保护短临界区；异常和取消必须走 finally；增加并发屏障测试。

### 14.4 UI 历史缺失

风险：恢复过滤 observe-only 时误把 UI/审计记录一起隐藏。

控制：区分“模型恢复读取”和“历史展示读取”，默认参数和测试分别固定。

### 14.5 旧历史无法识别来源

风险：上线前保存的自由回复没有 visibility extras。

控制：不猜测、不批量迁移。普通 free reply 本轮始终空历史，因此不会受旧记录影响；直接会话中的 legacy 记录按原语义保留。

### 14.6 跨渠道影响

风险：ConversationStore 或 AgentBridge 通用改动影响 Web、CLI、Feishu 等渠道。
