# Docker 多架构构建提速计划

## 状态

已完成

## 背景

当前镜像发布在单个 AMD64 Runner 上通过 QEMU 同时构建 AMD64 和 ARM64。实际发布日志显示，ARM64 的依赖安装和 Node 依赖安装占用了大部分时间，并曾在 `libc-bin` 安装脚本中出现 QEMU 段错误。Dockerfile 还会在安装重依赖前复制完整源码，导致常规代码变更使缓存失效。

## 目标

- 保持 `linux/amd64` 与 `linux/arm64` 多架构镜像、现有版本标签和 Chromium 能力不变。
- 使用原生架构 Runner 构建各自平台，并在发布末尾合并多架构 manifest。
- 让 APT、Python、Playwright 等稳定依赖层不因普通业务源码变更而重建。
- 使用可跨发布标签复用的 BuildKit Registry Cache，并为基础版与完整技能版隔离缓存作用域。

## 执行项

- [x] 设计并实现原生双架构构建、digest 汇集与多注册表 manifest 发布流程。
- [x] 重排 Dockerfile 的依赖安装与业务源码复制顺序，保持 Chromium 默认安装行为。
- [x] 更新 Docker 发布回归测试与 `CHANGES.md`。
- [x] 运行 YAML、Docker 发布契约和版本发布相关测试。

## 验收标准

- 发布工作流仍仅由 `v*` 标签触发，并继续发布 Docker Hub 与 GHCR 的基础版、完整技能版标签。
- AMD64 与 ARM64 不再通过同一 Job 内的 QEMU 模拟构建。
- 未改变依赖清单时，普通源码变更可复用依赖层缓存。
- 基础镜像继续包含 Playwright Chromium，微信群图片报告能力不降级。

## 实际改动

- 将基础版和完整技能版各拆分为 AMD64、ARM64 两个原生 Runner 任务；AMD64 使用 `ubuntu-24.04`，ARM64 使用 `ubuntu-24.04-arm`，不再安装 QEMU。
- 每个平台通过 canonical digest 同时推送 Docker Hub 与 GHCR，并将 digest 作为短期 artifact 汇集；两个变体各自创建多架构 manifest，避免一个变体失败阻断另一个变体的发布。
- 为每个 `variant + arch` 使用独立的 GHCR BuildKit Registry Cache 标签，防止并行写入覆盖，并规避 GitHub Actions Cache 无法跨不同标签恢复的限制。
- 将 requirements 文件置于完整源码复制之前，先安装系统、Python、Playwright Chromium 和能力包，再复制应用源码并执行无依赖的可编辑安装。
