# 群友画像功能复盘与架构建议

> 状态：已完成代码实施、正式数据切换与回归验证；真实微信群新消息学习留作运行观察
>
> 复盘与实施日期：2026-07-20
>
> 范围：复盘旧逻辑，完成按群唯一画像重构，并对本机正式画像数据执行备份后全量重建。
>
> 数据处置结果：历史画像与旧画像进化运行数据已清空并备份；归档、身份、群永久记忆及其他微信群运行数据均保留。

## 一、结论先行

1. 用户观察到的“同一个群友在同一个群有多个画像”成立，但它主要是**业务语义重复**，不是同一个数据库主键出现重复行。
2. `wechat_group_global_profiles` 只保证一个 `sender_id` 一行；当前 `sender_id` 同时承载 runtime sender ID、legacy sender ID 和 `stable_member_id` 三种语义，无法保证“同一群同一真人只有一份画像”。
3. 当前重复的直接代码路径已经可以稳定复现：启发式学习按 `stable_member_id` 写画像，LLM 画像进化却在 Prompt 中使用 runtime `sender_id`，merger 不做身份映射就直接写入，于是同一成员可以同时存在 stable 行和 runtime 行。
4. 更普遍的根因在身份层：本机 953 个成员身份都没有可用 `wechat_id`。代码为了避免把同名的不同成员误合并，会在 runtime ID 变化时创建新的隔离 stable member。这个安全取舍本身合理，但画像层仍把每个隔离身份直接当成永久画像主体，导致重复长期累积。
5. 当前系统名义上是“全局画像”，但项目规则、Prompt 注入、Agent 工具和用户期望都要求当前群强隔离。现状是“全局字段 + 群内名称记录 + 当前群读取过滤”的混合模型，写入和读取语义不一致。
6. 推荐架构不是“纯全局画像”，而是：
   - **全局层只解决这个人是谁**，保存经过确定性确认的身份关联；
   - **画像正文按群隔离**，一个 canonical 群成员在一个群最多一份画像；
   - 将来确有跨群复用需求时，再增加显式、可审计、默认不注入的全局稳定特征层。
7. 用户已明确允许删除全部历史画像数据和完全重构旧表，因此后续不再设计旧画像迁移、字段合并、双读 fallback 或历史画像人工清洗；旧画像只作为本次问题证据，不进入新结构。
8. 全量重构只删除画像及画像进化数据，不删除聊天归档、stable identity、群永久记忆、焦点、情绪、风格、表情或 scheduler 数据。新画像学习状态应以清理时的归档高水位为起点，默认不重新消费历史聊天。

## 三、关键概念与当前实际语义

| 标识 | 设计语义 | 当前来源 | 稳定性与边界 |
| --- | --- | --- | --- |
| `runtime_room_id` | 当前登录态的微信群 ID | Wechaty `room.id` | 可能随登录态变化，只用于真实收发和 legacy 快照 |
| `stable_room_id` | CowAgent 的稳定群 ID | identity service | 按 `stable_account_id` 确认，长期群作用域主键 |
| `runtime_sender_id` | 当前登录态的联系人 ID | Wechaty `contact.id` | 本机主要是 `@...` 形式，可能随登录态变化 |
| `stable_member_id` | 某个 stable room 内的成员身份 | identity service | 隶属于单个 `stable_room_id`，不是跨群人物 ID |
| `wechat_id` | 可用于恢复成员身份的强标识 | contact/raw payload | 当前本机成员记录全部为空 |
| 画像表 `sender_id` | 名义上的全局人物主键 | 多条写入路径 | 实际混用了 runtime、legacy 和 stable member ID |

当前没有 `stable_person_id`，因此系统不能可靠表达“同一真人在多个群中的多个 membership”。

## 四、当前内部逻辑

### 4.1 入站身份解析

```text
Wechaty 群消息
  -> sidecar 上报 contact.id、昵称、可选 wechat_id
  -> WechatGroupMessage 保存 runtime room/sender 和 fingerprint
  -> WechatGroupIdentityService.resolve_account()
  -> resolve_room()
  -> resolve_member()
  -> 消息同时携带 stable_room_id、stable_member_id、runtime 快照
  -> WechatGroupArchive 归档两套 ID
```

`resolve_member()` 的当前判定顺序：

1. 如果同一账号、同一 stable room 下有且只有一个相同强 `wechat_id`，复用既有 `stable_member_id`。
2. 否则，如果当前 runtime sender 已有 active alias，复用该 stable member。
3. 否则创建新的 `wgm_*`，并以 `missing_wechat_id` 或 `ambiguous_wechat_id` 隔离。

值得保留的安全边界是：**只凭昵称相同不能自动认为是同一个人**。现有测试明确锁定了这一行为，避免把同名群友误合并并继承权限或私有画像。

当前问题是新建的隔离身份会直接标记为 `confirmed`，且画像写入层不区分“确定身份”和“暂时隔离身份”。结果是每次 runtime 身份漂移都可能获得新的永久画像主体。

### 4.2 画像存储模型

主表：`wechat_group_global_profiles`

- 主键只有 `sender_id`。
- 字段包括 `primary_nickname`、`speak_style`、`interests_json`、`common_words_json`、统计分数和时间。
- 没有 `stable_room_id`、`stable_member_id`、`stable_person_id`、identity 外键、状态或合并重定向。

名称表：`wechat_group_profile_name_records`

- 保存 `sender_id + room_id + display_name + source_kind`。
- 名称为群内来源，但表上没有唯一约束。
- `upsert_name_record()` 实际始终执行 `INSERT`，并不是幂等 upsert。

因此当前模型实质上是：

```text
一行不可靠 sender_id 主体的全局画像
  + 多行带 room_id 的名称来源
  + 服务层读取时临时做当前群投影
```

### 4.3 三条画像写入路径

#### 路径 A：Web 手动修改

```text
POST /api/wechat-group/memories/profiles
  -> Web identity mixin 尝试把 runtime sender 转成 stable member
  -> WechatGroupProfileService.upsert_manual_profile()
  -> store.upsert_profile(sender_id=effective_member_id)
  -> 每个 alias 追加一条 name record
```

当 runtime room 缺失、runtime sender 在多个群有映射或 legacy 映射不唯一时，Web identity mixin 会保留 runtime sender 作为 `effective_member_id`，手动保存仍可能新建 runtime 画像。

#### 路径 B：启发式学习

```text
POST /learn/run
  -> WechatGroupLearner.run_once(room_id)
  -> 从归档增量读取消息
  -> _profile_subject_id() 优先 stable_member_id
  -> 按成员聚合、统计发言风格/兴趣/常用词
  -> merge_learned_profile(stable_member_id)
```

这条新链路优先写 stable member，是当前三条路径中 ID 方向最接近项目规则的一条。

但它仍写入全局画像表，并且 `speak_style`、`interests`、`common_words` 由最新批次直接覆盖。现有测试明确断言 B 群学习结果覆盖 A 群已有字段，说明字段并没有按群隔离。

#### 路径 C：LLM 画像自主进化

```text
群消息归档
  -> note_wechat_group_profile_signal(stable_room_id)
  -> idle trigger
  -> executor 读取当前群增量归档
  -> extractor 构造 LLM Prompt
  -> merger 自动合并
  -> profile store + evolution diff
```

这里存在关键断裂：

- executor 的成员计数优先使用 `stable_member_id`；
- extractor 展示给 LLM 的却是归档行中的 runtime `sender_id`；
- schema 也要求模型返回该 runtime `sender_id`；
- merger 不把它映射回 stable member，也不验证它是否属于本批次允许成员集合；
- merger 直接以模型返回 ID 写全局画像表。

所以 LLM 画像进化是当前正式数据继续产生 runtime 画像的主要路径。

### 4.4 画像读取与 Prompt 注入

```text
WechatGroupChannel._build_memory_context_block()
  -> room_id 使用 stable_room_id
  -> speaker 使用 stable_member_id
  -> mentioned_sender_ids 仍来自 runtime at_list
  -> WechatGroupContextService.preview_context()
  -> WechatGroupProfileService.resolve_profiles_for_prompt()
  -> <wechat-group-memory>
       [speaker_profile]
       [mentioned_profile]
```

Agent 工具链：

```text
AgentBridge
  -> 当前 turn 临时挂载 wechat_group_profile_get
  -> 服务端绑定 stable room 和 stable speaker
  -> 精确读取、搜索、list_all 都尝试限制在当前群
```

当前读取侧有两个相反现象：

1. 当前说话人用 stable member 查询，但正式画像绝大多数仍以 runtime ID 保存，因此说话人画像经常查不到。
2. 按昵称搜索或 `list_all` 又可能通过名称记录和归档映射返回 runtime 画像，所以 Web 看得到、精确 Prompt 注入却拿不到，容易造成“页面有画像但机器人不认识”的错觉。

被 @ 成员也有相同问题：`at_list` 是 runtime ID，没有先统一映射为当前群 canonical stable member。

### 4.5 Web 管理端

- 页面仍称为“全局画像”，可按群筛选。
- GET 接口先读取全局最近 200 条，再在内存做当前群过滤和 query 匹配。
- 前端请求没有传分页 limit，后端默认最多返回 20 条。
- 详情可修改，没有删除、合并或标记重复画像的入口。
- 页面展示 `name_records` 和“出现过的群”，会把名称记录重复与画像主体重复同时暴露给用户，但两者根因不同。

## 五、同群同成员多画像问题

### 5.1 不是主键重复，而是主体键漂移

数据库确实能做到：

```text
同一个 sender_id -> 最多一条 wechat_group_global_profiles
```

但业务真正需要的是：

```text
同一个 stable_room_id + 同一个 canonical 群成员 -> 最多一份当前画像
```

当前没有这条约束，所以以下 ID 即使指向同一个真人，也会被视为不同画像：

```text
旧登录 runtime_sender_id_A
新登录 runtime_sender_id_B
stable_member_id_A
stable_member_id_B（缺强 ID 时再次隔离）
LLM 偶发返回的未校验 ID
```

### 5.2 已确认的形成路径

#### 根因 1：启发式学习和 LLM 进化使用不同 ID

临时数据库最小复现：

1. 服务层以 `wgm_alice` 写入启发式画像。
2. LLM merger 以 `@runtime_alice` 合并同一人的画像结果。
3. 主表最终稳定产生两行：`wgm_alice` 与 `@runtime_alice`。

该复现不需要并发、脏数据或异常状态，说明问题来自确定性的正常代码路径。

#### 根因 2：缺少强身份时，runtime 变化会新建 stable member

当前测试明确要求：同群、同昵称、相同群昵称，但没有 `wechat_id` 时，新 runtime sender 必须创建新的 stable member，不能继承旧身份。

这能防止误合并，但当前没有后续的候选确认、member merge、redirect 或画像合并闭环，所以旧/new stable member 会长期并存。

#### 根因 3：LLM 返回主体没有服务端白名单校验

extractor 只校验 `sender_id` 非空；merger 也只校验非空。模型可以返回：

- 当前批次 runtime ID；
- stable ID；
- 拼错或幻觉 ID；
- 机器人或不属于当前群的 ID。

这些值都可能成为新画像主键。

#### 根因 4：Web legacy 映射失败时继续用 runtime ID 写入

手动修改接口在 stable member 无法唯一解析时不会强制失败，而是使用 runtime sender 兜底。管理员以为在修正已有画像，实际可能又新建一行。

#### 根因 5：名称记录不是幂等写入

相同 `sender_id + room_id + display_name + source_kind` 可以重复插入。它不会直接创建新的主画像，但会产生重复名称历史、放大计数，并让重复画像的页面表象更混乱。

### 5.3 本机数据只读快照

统计时本地配置中 `wechat_group_learning_enabled` 和 `wechat_group_profile_evolution_enabled` 均为开启状态。以下数字只代表 2026-07-20 本次复盘时点，数据库仍可能被运行中的服务继续写入。

- 不把 514 条旧主画像迁入新表。
- 不迁移 378 条旧 name records。
- 不迁移旧画像 evolution run、diff、status 或旧画像学习游标。
- 不按昵称、identity alias 或 evolution room 尝试合并旧画像。
- 不从旧画像推导新画像初值，新表初始为空。

## 六、既有逻辑问题清单

### P0：必须先解决

#### P0-1：画像主体键语义混乱

一个 `sender_id` 字段同时表示 runtime contact、legacy sender 和 stable member。表名叫 global，但 stable member 又是按群隔离的身份。没有任何数据库约束能表达真正的业务唯一性。

#### P0-2：画像写入没有统一 canonicalization

手动、启发式、LLM 三条路径各自选择主体 ID。没有一个统一入口强制校验 `stable_room_id + canonical stable_member_id`，也没有 identity 外键。

#### P0-3：LLM 进化持续写 runtime 画像

这是现有数据继续增长的直接来源。即使后续清理旧数据，只要这条路径不改，重复仍会再次产生。

#### P0-4：身份安全隔离没有画像候选态

缺强 ID 时拆分身份是合理防误合并策略，但隔离身份不应自动获得不可逆的最终画像。当前缺少 provisional/candidate 状态、人工合并和重定向机制。

#### P0-5：实际存量与 stable 读取链路断开

正式画像 514 条中只有 1 条使用 stable member，而说话人 Prompt 和 Agent 工具优先按 stable member 精确读取。画像功能在页面可见，但主回复链路很可能无法读取大多数说话人画像。

#### P0-6：全局字段与按群安全边界冲突

`speak_style`、`interests`、`common_words` 是全局字段，最新群/批次可以覆盖旧值；当前群读取只过滤名字，不能恢复字段来源。它既不是可靠全局总结，也不是群内画像。

### P1：高风险一致性问题

#### P1-1：LLM 输出和证据没有闭环校验

- 未验证输出成员属于当前批次和当前群。
- 未验证 evidence ID 存在于本批次、属于当前群、与目标成员相关。
- 字符串形式的 interests 可绕过 evidence 要求。
- `common_terms`、`catchphrases` 可无证据写入。
- `role_hints` 和 `speak_style` 虽出现在 schema 中，merger 实际没有应用。

#### P1-2：当前群 LLM 仍能看到其他群的画像来源

`list_profiles(room_id=...)` 虽筛选当前群成员，但返回对象仍带完整 `name_records` 和 `room_summaries`；executor 又把整个对象序列化进 `<existing-profiles>`。其他群名称、别名来源和摘要可能进入当前群画像提取 Prompt。

#### P1-3：真实 @ 的 runtime/stable 映射未闭环

当前说话人使用 stable member，但 `at_list` 和 bot sender 仍是 runtime ID。被 @ 成员画像可能查询不到，或者在当前混合存量下误命中 legacy runtime 画像。

#### P1-4：读取操作会修改全局主昵称

`_attach_names_and_content()` 在按群读取时会选择当前群昵称，随后 `_repair_profile_primary_nickname()` 可能把它写回全局主表。一个 GET/Prompt 读取可以改变另一群看到的全局主昵称。

#### P1-5：`reply_name` 优先级仍可能选中无群作用域 alias

当前群会过滤其他明确 room 的 alias，但空 `room_id` 的 legacy/global alias 仍可进入 aliases；`_choose_reply_name()` 又固定先选 aliases，再选当前群 `primary_nickname`。

#### P1-6：列表先截断再过滤

服务先取全局最近 200 条，再做群过滤和 query。正式数据已有 514 条，较旧画像即使精确匹配当前群或昵称，也可能永远进不了候选集合。前端默认只拿 20 条且没有分页。

#### P1-7：回滚不完整

画像进化 rollback 只 upsert 主画像字段：

- 新建画像不能恢复为“不存在”；
- 本轮新增 name records 不会删除；
- diff 主要记录 alias evidence，其他字段证据不完整。

### P2：质量和运维问题

- name record 每次重复追加，长期膨胀。
- learner 对未达到成员最小消息数的数据仍推进群 cursor，低频成员的证据可能永久漏学。
- evolution trigger 用全库自增 row ID 差值近似当前群消息数，跨群交错时不等于真实 pending 数量。
- 单次只处理一个 batch；触发器记录 latest observed 后，如果 backlog 超过 batch limit 且没有新消息，剩余消息可能不再自动排空。
- Web 没有画像合并、删除、重定向和身份候选确认入口。
- 既有文案持续使用“全局画像”，但项目规则和工具都强调当前群隔离，增加维护者误解。

## 七、全局画像与按群画像方案比较

| 方案 | 数据主键 | 优点 | 主要风险 | 结论 |
| --- | --- | --- | --- | --- |
| 纯全局画像 | `stable_person_id` | 跨群信息丰富，同一真人理论上一份 | 当前没有可靠 person ID；跨群隐私泄漏；群内角色和表达差异被抹平；误合并影响所有群 | 当前不适合 |
| 纯按群画像 | `stable_room_id + stable_member_id` | 安全边界清楚，符合当前 Prompt/工具/权限；容易做数据库唯一约束 | 同一真人跨群不共享信息；仍需解决 runtime 身份漂移 | 当前最小可落地方案 |
| 全局身份 + 群内画像 | 全局 identity relation；画像用 `stable_room_id + canonical member` | “身份关联”和“画像内容”解耦；既能防跨群泄漏，也为未来显式共享留接口 | 需要 member merge/redirect；跨群绑定只能使用强证据或人工确认 | 推荐目标架构 |

## 八、推荐架构

### 8.1 核心原则：全局只回答“是谁”，群内回答“在这个群里是什么样”

```text
全局身份层（不直接注入画像正文）
  stable account
    -> 可选 stable person / verified identity relation
    -> 只接受强 wechat_id、确定性历史绑定或人工确认

群 membership 层
  stable_room_id + canonical stable_member_id
    -> 多个历史/runtime sender alias
    -> merged member redirect

群画像层
  stable_room_id + canonical stable_member_id
    -> 当前群昵称/别名
    -> 当前群角色线索、兴趣、表达风格、常用词
    -> 当前群证据、版本和审计
```

直接回答架构选择：**画像正文按群隔离更合理；全局层保留身份关系，不应继续把当前混合字段当作可直接注入的全局人物画像。**

### 8.2 为什么不立即实现完整 `stable_person_id`

当前本机 953 个成员都缺少强 `wechat_id`。如果现在为了“全局人物”按昵称、头像或 LLM 自动建立 `stable_person_id`，会把重复画像问题变成更危险的跨人误合并和跨群泄漏。

建议分两步：

1. 先在现有 stable room/member 基础上实现当前群唯一画像、member merge 和 redirect。
2. 只有获得可靠跨群身份依据或管理员明确确认后，才把多个群 membership 关联到一个 global person；默认仍不把一个群的画像正文注入另一个群。

### 8.3 目标数据模型

#### 群画像当前态

旧画像表可以完全删除，因此直接创建最终正式表，不保留 `_v2` 后缀，也不做新旧双写或 fallback：

```text
wechat_group_member_profiles
  stable_room_id            NOT NULL
  stable_member_id          NOT NULL
  primary_nickname
  speak_style
  interests_json
  common_words_json
  activity_score
  intimacy_score
  msg_count
  first_observed_at
  last_observed_at
  revision
  status                    active / merged / disabled
  PRIMARY KEY (stable_room_id, stable_member_id)
```

`stable_member_id` 必须先经过 `resolve_canonical_member_id()`，不能直接接受 runtime ID。

#### 名称记录

```text
wechat_group_member_profile_names
  stable_room_id
  stable_member_id
  normalized_display_name
  display_name
  source_kind
  confidence
  first_seen_at
  last_seen_at
  seen_count
  evidence_message_ids_json
  UNIQUE(stable_room_id, stable_member_id, normalized_display_name, source_kind)
```

重复观察更新 `last_seen_at/seen_count`，不再无限追加相同记录。

#### 身份合并与重定向

可以给 identity member 增加 `status/merged_into_stable_member_id`，或新增独立 redirect 表：

```text
wechat_group_identity_member_redirects
  stable_room_id
  old_stable_member_id
  canonical_stable_member_id
  reason
  actor
  created_at
  UNIQUE(stable_room_id, old_stable_member_id)
```

历史聊天归档不需要重写；所有新写入和读取先解析 canonical member。redirect 用于处理重构上线后的 runtime 身份漂移或人工身份合并，不用于迁移旧画像。

#### Claims 和 revision

如果继续使用自动 LLM 画像，建议把字段证据与当前态分离：

- claim 保存 `room + member + dimension + value + confidence + evidence IDs + source run`；
- current profile 是 accepted claims 的当前投影；
- revision 保存完整前后快照，支持新建、更新和删除的真实回滚。

这不是为了增加功能，而是为了让“自动写入、证据门禁、冲突处理、回滚”真正可验证。

#### 运行记录与学习基线

```text
wechat_group_member_profile_runs
  run_id
  stable_room_id
  batch_start_row_id
  batch_end_row_id
  status
  counters_json
  failed_reason
  started_at
  finished_at

wechat_group_member_profile_learning_state
  stable_room_id
  pipeline                  heuristic / evolution
  last_archive_row_id
  latest_observed_row_id
  last_signal_at
  last_success_at
  running
  updated_at
  PRIMARY KEY (stable_room_id, pipeline)
```

画像运行记录、diff/revision 和学习游标与画像当前态放在同一个 SQLite 库中。新启用一个已有历史归档的群时，默认用启用时该群 archive 最大 row ID 初始化 baseline；只有显式历史重建任务才允许把 baseline 向前调整。

### 8.4 写入不变量

所有手动、启发式和 LLM 写入必须经过同一个 profile subject resolver：

1. 必须有 `stable_room_id`。
2. 必须有属于该 room 的 `stable_member_id`。
3. 先解析 member redirect，得到 canonical member。
4. runtime sender 只能用于 identity alias 查找，不能成为 profile 主键。
5. identity 未解析或有歧义时，不创建最终画像；可记录为 observation/candidate。
6. LLM 只返回本批次服务端生成的 opaque member token，服务端映射回 stable member。
7. 模型输出 token、evidence 和 room 任一不在 allowlist 时，整项拒绝。

### 8.5 读取不变量

1. 所有读取先绑定当前 `stable_room_id`。
2. speaker、真实 `at_list`、query 命中都转换成 canonical stable member 后查询。
3. Prompt 只包含当前群画像当前态和当前群名称；不携带其他群 name records、room summaries 或证据原文。
4. `reply_name` 优先级由服务端确定：当前群人工首选名 > 当前群高置信 alias > live room alias > 当前群最近显示名 > 无称呼。
5. 默认不以其他群名称或全局 alias 兜底。
6. GET/搜索不得产生持久化写副作用。

## 九、全量重构执行方案

### 9.1 删除与保留边界

| 数据 | 处置 | 原因 |
| --- | --- | --- |
| `wechat_group_global_profiles` | 删除，不迁移 | 主体键混乱，字段已跨群覆盖 |
| `wechat_group_profile_name_records` | 删除，不迁移 | 重复记录多，room/sender 语义混合 |
| 旧 profile evolution runs/diffs/status | 删除，不迁移 | 全部基于旧 runtime sender 语义 |
| `wechat_group_profile_evolution.db` | 备份后退役 | 新画像当前态、claims、revision、run 和 state 统一放入一个画像库，保证事务一致性 |
| `wechat_group_archive.db` | 保留且不改历史消息 | 仍是群消息事实归档，但默认不回放旧消息生成画像 |
| `wechat_group_identity.db` | 保留，只增量支持 canonical redirect/candidate | stable room/member、权限和投递仍依赖它 |
| `wechat_group_knowledge.db` | 保留 | 群永久记忆不属于画像数据；旧 shared learner cursor 不再用于新画像 |
| focus/emotion/style/sticker/scheduler 数据 | 保留 | 与画像重构无关 |

不删除 identity 成员记录，也不按旧昵称清理 identity。旧 identity 中的隔离成员属于身份诊断问题；新画像层通过 canonical resolver 和 candidate 门禁防止它们继续自动生成多份最终画像。

### 9.2 阶段 0：冻结写入和建立回退点

1. 临时关闭 `wechat_group_learning_enabled` 和 `wechat_group_profile_evolution_enabled`。
2. 停止 CowAgent 后端、微信群通道和画像后台 trigger，确认画像 SQLite 文件没有活动写连接。
3. 核对所有目标绝对路径都位于预期的 CowAgent data root。
4. 使用 SQLite backup API 备份：
   - `wechat_group_profiles.db`
   - `wechat_group_profile_evolution.db`
   - `wechat_group_identity.db`，因为实现会新增 redirect/candidate 结构
5. archive 和 knowledge 数据库不做删除操作；可额外备份用于整体验证，但不是重建目标。

备份只用于失败回退，不作为旧画像迁移来源。正式执行记录见第十三节。

### 9.3 阶段 1：先完成新代码和失败测试

在临时数据库中完成新 schema 和所有调用方改造，未通过测试前不碰正式画像库：

1. 建立统一的 `WechatGroupMemberProfileStore/Service`，在一个 SQLite 事务中写 current profile、name、claim、revision 和 run 状态。
2. Web、启发式 learner、LLM extractor/merger 全部调用同一个 canonical profile service。
3. extractor 只给 LLM opaque batch member token，不再暴露可直接落库的 runtime sender 主键。
4. merger 校验 member allowlist、stable room、bot 排除、evidence、置信度和字段 schema。
5. 手动保存无法解析 stable member 时返回明确错误，不再以 runtime ID 兜底写入。
6. speaker 和 mentioned `at_list` 统一执行 runtime -> stable -> canonical 映射。
7. 当前群查询直接由 SQL 按 room/member 过滤；GET 不写库，name 写入幂等。
8. 将启发式画像学习从 `wechat_group_knowledge.db` 的 shared cursor 中拆出，使用画像库自己的 per-room learning state。

### 9.4 阶段 2：创建全新正式画像库

推荐使用“新文件构建 + 校验 + 停服替换”，避免在旧库上执行一半 DDL 后留下不可用状态：

1. 在同一 data root 下创建临时 `wechat_group_profiles.next.db`。
2. 只创建最终正式表，不创建 legacy 表、`_v2` 表或兼容视图：
   - `wechat_group_member_profiles`
   - `wechat_group_member_profile_names`
   - `wechat_group_member_profile_claims`
   - `wechat_group_member_profile_revisions`
   - `wechat_group_member_profile_runs`
   - `wechat_group_member_profile_learning_state`
3. 新库不插入任何旧 profile、name、claim、diff 或 run 数据。
4. 对每个已配置的 `stable_room_id` 查询 archive 当前最大 row ID，并写入 `wechat_group_member_profile_learning_state.last_archive_row_id` 作为 clean baseline。
5. 运行 `PRAGMA integrity_check`、schema 校验和空数据断言。
6. 后端停止状态下，将旧画像库保留为带时间戳备份，再把 `.next.db` 原子替换为正式 `wechat_group_profiles.db`。
7. 旧 `wechat_group_profile_evolution.db` 保留备份后从运行路径退役；新代码不得再打开它。

清理完成后的预期状态：主画像、名称、claims、revisions 和 runs 数量全部为 0；learning state 只包含目标群及其清理时高水位。

### 9.5 阶段 3：切换所有运行链路

1. 移除旧 `WechatGroupProfileStore`、旧 evolution store 和 legacy fallback 的运行时引用。
2. Prompt 注入和 `wechat_group_profile_get` 只读当前群新表。
3. Web 文案从“全局画像”调整为“群友画像”，列表默认要求选定群作用域。
4. Web 初始展示明确空状态；后续只展示清理后新产生的画像。
5. 后续新增目标群时，首次建立 learning state 也使用该群当时的 archive 高水位，不能默认从 row 0 回放。
6. 重新开启画像相关配置前，先用测试群和新消息手动触发一轮启发式/LLM 学习，确认只生成一个 canonical profile。

### 9.6 阶段 4：处理后续身份漂移

全量删除旧画像不能消除未来 runtime ID 变化，因此新逻辑必须长期满足：

- 有唯一强 `wechat_id` 或已确认 alias 时复用 canonical member。
- 缺少强 ID 且无法唯一恢复时，只记录 candidate/observation，不创建最终画像。
- 同昵称、头像相似、活跃时间衔接或 LLM 判断只能生成待确认候选，不能自动合并。
- 管理员确认后写 identity redirect；画像始终以 canonical member 查询和写入。
- 首次切换不要求建设完整历史画像清洗 UI，只保留最小身份候选诊断和确认能力，避免扩大本轮范围。

### 9.7 阶段 5：验证、启用与回滚

1. 确认旧表名和旧 evolution DB 在运行日志、代码搜索和打开文件列表中均不再出现。
2. 新消息学习后检查复合唯一约束、claims evidence、revision 和 run 状态。
3. 验证 A/B 群同一已确认人物可以拥有两份互不泄漏的群画像。
4. 验证清理前 archive 不会自动回放；清理后的新消息可以正常推进 learning state。
5. 聚焦测试通过后，再按项目要求运行微信群通道回归。
6. 若切换失败：立即停服，恢复旧代码、旧 profile/evolution DB 备份和 identity DB 备份；不要在新旧代码之间混用数据库。

## 十、建议补充的回归测试

### 唯一性与身份

- 同一 stable room/member 经 Web、启发式和 LLM 三条路径写入后只有一份画像。
- 同一强 `wechat_id` runtime 变化后复用同一 canonical member/profile。
- 缺强 ID 的新 runtime 只形成候选 observation，不直接创建第二份最终画像。
- 手动 member merge 后旧 stable/runtime ID 都重定向到同一画像。
- 不按昵称自动合并同名不同成员。

### LLM 安全门禁

- Prompt 只包含 opaque batch member token，不包含可作为主键落库的 runtime sender。
- 模型返回不存在、跨群、机器人或未在批次中的 token 时拒绝。
- evidence 必须存在于当前 room/current batch，并与目标成员有关。
- interests、style、common terms 和 aliases 使用一致的 evidence/置信度规则。

### 群隔离

- 同一已确认 person 在 A/B 两群可以有两份不同群画像。
- A 群画像、名称、证据和 revision 不进入 B 群 Prompt、工具结果或 Web API。
- 当前群 `reply_name` 不回退其他群 alias。
- runtime `at_list` 能映射到当前群 canonical member。

### 存储与全量重置

- 新 profile 表的 `stable_room_id + stable_member_id` 复合唯一约束生效。
- name record 重复写入只更新 seen_count/last_seen，不增加重复行。
- 全量重置后 profile、name、claim、revision 和 run 都为空。
- 重置保留 archive、identity 和群永久记忆，不误删其他数据库内容。
- 每个目标群的 learning baseline 等于清理时 archive 高水位，旧消息不会自动回放。
- 后续新启用的已有群也从启用时高水位开始，不回放此前归档。
- 初始化脚本在空库上重复执行保持幂等，不重复插入 learning state。
- 新代码不打开旧 evolution DB，不包含旧表双读或 runtime sender fallback。
- 新建画像、字段更新、名称更新和 member merge 都能完整回滚。

### 查询和 UI

- 当前群查询直接基于新表执行，不再受全局前 200 条截断影响。
- Web 首次切换显示正确空状态，新消息生成画像后只出现在对应群。
- Web 不再展示“全局画像”或旧 name record 历史。
- 页面显示的“画像数”和“名称记录数”语义分开。
