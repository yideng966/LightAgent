# MaiBot 参考迁移调研

## 调研结论

本次调研对象为 `https://github.com/Mai-with-u/MaiBot` 主分支源码，源码已临时解压到 `tmp/MaiBot_main_20260706/MaiBot-main`。结论是：MaiBot 的定位更接近“长期陪伴型群聊生命体”，CowAgent 的定位是“多渠道 Agent Harness”。因此不建议整体移植 MaiBot 架构，也不应替换 CowAgent 的 `ChatChannel`、`Bridge`、`agent/` 主链路。

适合迁移的是机制，不是业务边界：

- 群聊自由回复的多消息调度、回复必要性评分、空窗补偿和退避。
- 长期记忆的治理思路：按近期聊天印象召回、人物画像注入、中期摘要与检索阈值。
- 表达风格、黑话、表情素材的“候选、审核、启用、回退”闭环。
- 插件系统的 manifest 校验、能力声明、插件数据目录和错误隔离。
- 配置 schema、可观测日志、诊断状态与测试组织方式。

需要明确规避：

- 不复制 MaiBot 源码实现。MaiBot 仓库使用 GPL-3.0 许可证，直接复制实现到 CowAgent 会带来许可兼容风险。
- 不把 A_Memorix 整套记忆系统搬进 CowAgent。其依赖和数据模型较重，且会与 CowAgent 现有 `agent/memory`、微信群作用域记忆形成双系统。
- 不把 MaiBot 外部 runner 插件运行时整体替换 CowAgent 插件系统。短期只借鉴隔离机制。
- 不把 MaiBot 人设、提示词、陪伴产品逻辑作为 CowAgent 默认行为。CowAgent 应继续保持通用 Agent 与多渠道能力。

## 模块级取舍

| MaiBot 模块 | 主要价值 | CowAgent 取舍 |
| --- | --- | --- |
| `src/maisaka` | 回复必要性、轮次门控、退避、拟人化聊天节奏 | 只借鉴自由回复调度机制，不迁移 HeartFlow / Planner 主循环 |
| `src/A_memorix`、`src/services/memory_service.py` | 长期记忆、画像、episode、混合检索、管理工具 | 只借鉴记忆治理策略，不引入整套实现 |
| `src/learners`、`src/chat/replyer/maisaka_expression_selector.py` | 表达候选学习、审核、选择和 hook 扩展 | 映射到 CowAgent 现有 style card / sticker / topic 服务 |
| `src/emoji_system` | 表情素材管理和缓存清理 | 可参考素材生命周期，不单独迁移系统 |
| `src/plugin_runtime` | manifest、runner、hook、熔断、能力声明 | 只迁移插件数据目录、校验和错误隔离思想 |
| `src/mcp_module` | MCP 配置、连接、provider 与 host LLM bridge | CowAgent 已有 `agent/tools/mcp`，只在后续 MCP 生命周期治理中对照参考 |
| `src/platform_io` | 平台驱动注册、去重、路由 key、出站跟踪 | CowAgent 已有 channel 工厂和渠道抽象，短期不迁移 |
| `dashboard`、`src/webui` | 运行时可视化和资源管理页面 | CowAgent 继续使用 Web 控制台 / Electron 桌面端，按现有 UI 规则增量补齐 |
| `locales`、`prompts` | 国际化和 prompt 分层管理 | 可参考 prompt 分层，不改变 CowAgent 当前文档与配置策略 |

### P0：升级微信群自由回复调度

MaiBot 做法：

- `reply_necessity.py` 将待处理消息数、直接相关性、问题/请求/观点内容、空窗时间、近期机器人存在感合并为一个可解释评分。
- `turn_gates.py` 使用 `ReplyNecessityTurnGate` 与 `FrequencyThresholdTurnGate` 判断是否进入回复规划。
- `idle_backoff.py` 对连续无动作轮次做退避，待处理消息达到阈值后允许绕过退避。
- `turn_scheduler.py` 把评分、频率、待处理消息和退避串起来，避免单条消息就立刻触发或频繁插话。

CowAgent 当前状态：

- `wechat_group_free_reply.py` 已有本地评分、冷却、小时上限、连续上限、低信息和风险抑制。
- 当前更像“单条消息是否值得接话”的判断，缺少按房间聚合 pending 消息、空窗补偿、近期存在感惩罚和连续 idle 退避。
- `WechatGroupFreeReplyWorkerPool` 已有异步 worker 与 LLM 二次判定，可以继续复用。

建议迁移方式：

- 新增一个微信群自由回复调度层，例如 `wechat_group_free_reply_scheduler.py`。
- 按 `room_id` 保存短期 pending 文本窗口，只处理普通非 @ 文本；@ 机器人和引用机器人仍走必回链路。
- 在现有 `evaluate_wechat_group_free_reply()` 之前或之后加入聚合评分：`pending_count`、最近外部消息间隔、最近机器人回复占比、问题/请求/观点内容、低信息批次。
- 保留现有配置作为兼容默认值，新配置默认关闭或保守启用。
- LLM judge 仍只在本地调度通过后进入，避免新增模型成本。

验证方式：

- 补充 `tests.test_wechat_group_free_reply`：pending 聚合、空窗补偿、存在感惩罚、退避绕过。
- 补充 `tests.test_wechat_group_channel`：非 @ 普通消息不会绕过群范围限制；@ 必回不受自由回复调度影响。
- 手动验证：开启自由回复后，群内连续短句不会每句都插话；多人连续讨论后会在合适时机接话。

优先级判断：

- 这是最值得先做的迁移点。收益高、作用域清晰、可在微信群通道内隔离，不影响 CowAgent 通用 Agent 主链路。

### P1：强化微信群记忆召回治理

MaiBot 做法：

- `heuristic_injector.py` 会先从近期消息构造聊天印象，再用该印象检索长期记忆，并通过会话、群聊、私聊方向规则过滤。
- `person_profile.py` 从当前消息、@ 成员、回复对象中收集人物画像候选，只注入有限数量画像。
- `mid_term.py` 维护中期摘要消息，按 recall cue embedding 做相关性召回，避免全部历史塞进 prompt。
- A_Memorix 支持向量、关系图谱、episode、画像、导入、调优和管理工具。

CowAgent 当前状态：

- `wechat_group_context_service.py` 已能生成 `<wechat-group-memory>`，包含群记忆、发言人画像和被 @ 人画像。
- `wechat_group_profile_service.py` 已有全局群友画像、别名、群内名称记录和 prompt 格式化。
- `wechat_group_learner.py` 已有启发式画像和群知识学习。
- 但当前记忆召回仍偏直接，缺少“先总结近期聊天印象，再用印象检索”的中间层。

建议迁移方式：

- 不迁移 A_Memorix 实现，只借鉴治理策略。
- 在 `WechatGroupContextService.preview_context()` 前后增加一个可选的“近期印象查询词”构造器：从当前消息 + 最近归档消息生成轻量 query，用于群记忆检索。
- 对群记忆、发言人画像、被 @ 人画像分别限制条数与字符数，并保留 room_id / sender_id 强过滤。
- 中期摘要先不做向量回忆，可先扩展现有 `wechat_group_topic_service.py` 或新增轻量 `wechat_group_summary_service.py`，只保存当前群的滚动摘要。

验证方式：

- 测试跨群隔离：不同 `room_id` 的群记忆不会注入。
- 测试人物隔离：只注入当前发言人与明确 @ 成员画像。
- 测试字符预算：长画像、长群记忆被截断且标签完整。

优先级判断：

- 可以排在自由回复调度之后。CowAgent 已有基础能力，后续应做“治理增强”，而不是重写记忆系统。

### P1：表达风格与黑话学习闭环

MaiBot 做法：

- `expression_learner.py` 从上下文抽取表达候选，并有并发门控、AI 审核日志、hook 扩展点和入库前处理。
- `maisaka_expression_selector.py` 先构建候选池，可选向量检索，再由选择器挑选适合当前回复的表达。
- `jargon_context_matcher.py` 按 session scope 匹配黑话，结合高频词和历史使用次数排序。

CowAgent 当前状态：

- `wechat_group_style_service.py` 已有风格卡候选、审核和 prompt 注入，但候选生成偏启发式。
- `wechat_group_sticker_service.py` 已有表情包/贴纸采集、状态和发送限制。
- `wechat_group_topic_service.py` 已有话题块，但与表达选择还没有强关联。

建议迁移方式：

- 先增强现有 style card，不新增独立“表达系统”。
- 将候选风格卡拆成：适用场景、表达方式、来源消息、证据数、状态、最近使用时间。
- 默认保持人工审核；只有明确开启时才自动应用。
- 后续可用 CowAgent 现有记忆或 embedding 能力做候选检索，不引入 MaiBot 的表达向量索引实现。

验证方式：

- 测试候选去重、证据阈值、审核状态切换、active 风格注入数量限制。
- 测试关闭学习时不产生候选。
- 测试跨群风格不混用。

优先级判断：

- 适合在自由回复调度稳定后做。它会提升拟人感，但不是稳定性的前置条件。

### P1：插件安全与运行时隔离的增量借鉴

MaiBot 做法：

- 插件有 `_manifest.json` 强校验，包含版本、依赖、能力、入口、兼容性等。
- `supervisor.py` 管理外部 runner、RPC、hook、event、message gateway 和 reload。
- `circuit_breaker.py` 对插件失败做熔断与冷却。
- `plugin_persistence.md` 明确插件持久化目录与临时目录，不允许插件写源码目录，并校验路径逃逸。

CowAgent 当前状态：

- `plugins/plugin_manager.py` 是进程内事件插件体系。
- `agent/tools/mcp/mcp_client.py` 已有外部 MCP 子进程管理，这部分更接近 runner 隔离。
- CowAgent 插件和 Agent 工具不是一类能力，不应混在一起重构。

建议迁移方式：

- 短期只做三件小事：
  - 为插件新增标准数据目录和运行时目录约定。
  - 为插件配置增加最小 manifest 校验或 metadata 校验。
  - 在插件事件执行处增加失败计数、临时禁用和诊断状态。
- 不引入外部 runner，不改变插件 API。
- MCP 子进程隔离可单独参考 MaiBot runner supervisor，但应归入 MCP 生命周期治理任务，不与聊天插件混做。

验证方式：

- 插件数据目录路径逃逸测试。
- 插件异常不会阻断主消息链路测试。
- 连续失败后插件被跳过，冷却后恢复测试。

优先级判断：

- 对项目稳定性有价值，但影响面涉及插件系统，应单独计划。

### P2：配置 schema、诊断状态与 WebUI 联动

MaiBot 做法：

- 配置项和运行时状态围绕 dashboard、plugin runtime、memory runtime 有更强的结构化输出。
- 插件加载、失败、inactive、blocked 等状态可查询。

CowAgent 当前状态：

- 配置散落在 `config.py`、`config-template.json`、Web 控制台和桌面端。
- 微信群已有较多配置项，继续增加能力后需要更强的分组、默认值和诊断展示。

建议迁移方式：

- 先为微信群自由回复、情绪、记忆、风格增加一个后端只读诊断接口，展示当前配置、最近决策、抑制原因和注入块开关状态。
- 后续再做配置 schema 化，不在功能迁移第一阶段处理。

验证方式：

- Web API 返回结构稳定。
- 敏感配置不返回真实密钥。
- 关闭模块后诊断显示 disabled 原因。

优先级判断：

- 适合作为运维增强，不能阻塞 P0 调度升级。

## 不建议迁移的内容

- MaiBot 整体消息架构、HeartFlow、Planner 和人格循环：会冲突 CowAgent `ChatChannel` / `Bridge` / Agent 主链路。
- A_Memorix 全量引入：依赖重、许可风险高、会造成记忆双轨。
- MaiBot dashboard：CowAgent 已有 Web 控制台和 Electron 桌面端，界面只应按当前项目规范增量补齐。
- MaiBot 外部插件 runner 全套替换：当前 CowAgent 插件生态不需要一次性迁移到 RPC runner。
- MaiBot 人设 prompt 和陪伴话术：不应成为 CowAgent 默认行为，可作为用户自定义 persona 的参考结构。

## 推荐实施路线

### 阶段 1：自由回复调度升级

目标：让微信群自由回复从“单条消息判定”升级为“按房间聚合调度”。

范围：

- 新增 room 级 pending 窗口。
- 新增回复必要性评分。
- 新增近期机器人存在感惩罚。
- 新增连续 no-action 退避。
- 复用现有 LLM judge 与 worker。

不做：

- 不改 @ 必回链路。
- 不改 sidecar 协议。
- 不改 Agent 主链路。
- 不引入新第三方依赖。

### 阶段 2：记忆召回治理增强

目标：提升 `<wechat-group-memory>` 的相关性和可控性。

范围：

- 构造近期聊天印象 query。
- 群记忆和画像注入做字符预算。
- 引入当前群滚动摘要或复用 topic 摘要。

不做：

- 不移植 A_Memorix。
- 不改变 CowAgent 通用 `agent/memory` 存储结构。

### 阶段 3：表达风格候选闭环

目标：让风格学习从简单启发式变成可审核、可回退、可诊断的候选流程。

范围：

- 扩展 style card 元数据。
- 增加候选证据和最近使用时间。
- 保留人工审核默认行为。

不做：

- 不直接复制 MaiBot expression learner。
- 不引入新的向量索引依赖。

### 阶段 4：插件与运维隔离增强

目标：降低插件故障对主链路的影响。

范围：

- 插件数据目录规范。
- 轻量 manifest / metadata 校验。
- 插件失败熔断与诊断状态。

不做：

- 不替换插件 API。
- 不引入外部 runner。

## 验证策略

代码实施时每个阶段都应有独立验证闭环：

- 阶段 1 至少运行 `python -m unittest tests.test_wechat_group_free_reply tests.test_wechat_group_channel tests.test_wechat_group_web`。
- 阶段 2 至少运行微信群记忆、画像、上下文注入相关测试，并新增跨群隔离用例。
- 阶段 3 至少覆盖 style candidate 生成、审核、active 注入、关闭学习和跨群隔离。
- 阶段 4 至少覆盖插件异常隔离、路径逃逸、防止主链路被异常阻断。
- 涉及 Web 控制台时补充 `tests.test_wechat_group_web`。
- 涉及桌面端时再进入 `desktop` 执行 `npm run build`。

## 风险与边界

- 许可风险：MaiBot 为 GPL-3.0，不能直接复制代码实现。后续迁移应独立设计和独立实现，只借鉴机制。
- 范围风险：MaiBot 是陪伴型机器人，CowAgent 是多渠道 Agent Harness。微信群拟人化能力只能作为渠道增强，不能取代通用 Agent 链路。
- 成本风险：LLM judge、记忆摘要、表达学习都会增加模型调用。默认配置必须保守，并提供开关和诊断。
- 安全风险：任何记忆召回必须继续按 `room_id`、`sender_id` 强过滤，不能跨群泄露。
- 运维风险：自由回复调度会影响群体验，必须保留冷却、小时上限、连续上限、低信息抑制和手动关闭能力。
