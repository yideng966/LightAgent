# 微信群全景上下文与 Provider 会话复用方案

> 状态：开发与本地验证完成，目标发布版本 `v2.1.23`
>
> 计划日期：2026-07-30
>
> 前置版本：`v2.1.22`，提交 `d88b80ba`
>
> 前置计划：`plans/20260729_微信群上下文与会话引擎重构计划.md`
>
> 适用范围：个人微信群 Context Engine V2、Agent thread、Provider 调用、群聊拟人化 Web 配置

## 0. 结论

本方案不重复开发已经完成的 V2 thread、room timeline、请求快照、单群串行和发送确认，而是在现有基础上完成两类增强：

1. 让模型在每次自然语言请求中稳定看到“本群所有成员的近期群聊原文 + 本群 24 小时滚动摘要 + 本群相关归档证据 + 当前成员已确认 thread”，提升像持续阅读群聊一样的上下文感知。
2. 在 Provider 官方能力明确、可分支且可回滚时，允许短期复用 Provider 侧续接锚点；Provider 续接只是 thread 连贯性与 token 优化，不能替代每轮最新群现场注入。

同时执行一次 Web 与配置收敛：

1. 微信群只保留 Context Engine V2，删除 Legacy 模式、模式选择 UI 和 `wechat_group_context_engine_mode` 配置。
2. 删除“完整上下文注入预览”的前端、状态、请求逻辑及公开 preview API；保留真实回复链路依赖的内部记忆与画像装配能力。
3. “拟人化上下文”页面不再使用 `<details>/<summary>` 折叠设置，后续也不在该页面新增折叠配置区，统一使用页面主滚动流。
4. 保留会话作用域配置，默认继续按成员隔离。
5. 删除无效、重复或本应固定的用户配置，只保留确实存在业务、成本或隐私取舍的配置。

本方案对 `plans/20260729_微信群上下文与会话引擎重构计划.md` 的以下结论构成更新：

- 不再保留 `legacy` 作为运行时回滚模式。
- 不再通过 Web 暴露 V2 灰度选择。
- rolling summary 的目标默认值改为开启，并扩展到所有普通自然语言请求。
- 回滚改为回退上一稳定镜像或标签，不依赖切换 Legacy 配置。

## 1. “拟人化”的目标定义

本轮讨论中的“拟人化”不主要指语气、情绪、表情、打字延迟或故意模拟真人，而是：

> 机器人像一直在群里阅读消息一样，能理解省略句、指代、话题变化、本群其他成员说过的话和机器人刚刚说过的话，同时不会混入其他群的消息、其他成员的私有 thread 或过期话题。

群级上下文必须按 `stable_room_id` 汇集本群所有成员的公开群消息，而不是只读取当前提问者说过的话。当前提问者的 `stable_member_id` 只用于身份、权限、画像和成员级 Agent thread 隔离，不能被误用为 room timeline 的消息过滤条件。

因此优先级依次为：

1. 群现场完整度与时效。
2. 当前说话人与当前 thread 的连续性。
3. 相关旧事实的准确召回。
4. 去重、预算、权限和跨群隔离。
5. Provider 侧缓存或会话复用。

Provider 会话复用排在本地上下文之后。它可以帮助模型延续同一 thread，但不会自动知道两次请求之间群里新发生了什么；最新群现场仍必须由 LightAgent 每轮重新注入。

## 2. 当前机制与 BaiLongmaPro 复核

### 2.1 BaiLongmaPro 没有复用 Provider 会话 ID

已核对当前本地 `BaiLongmaPro` 源码：

- `src/llm.js:98-125` 每轮构造 `requestParams.messages`，调用 `client.chat.completions.create()`。
- 全项目没有向 LLM Provider 提交 `conversation_id`、`previous_response_id` 或 `parent_message_id`。
- `src/core/turn-state.js:84-86` 的 `newSessionRef()` 每轮生成新追踪 ID，只用于事件、任务和记忆识别，不是 Provider 对话锚点。
- `src/memory/injector.js:280-283` 按目标读取最近 20 条、24 小时本地 conversation。
- `src/social/wechat-groups.js:186-193` 每轮读取最近 100 条、24 小时群聊，同时加入摘要、群记忆、外部知识、图片记忆和 90 天归档证据。

因此 BaiLongmaPro 的上下文优势来自“每轮本地重建并重放较厚的上下文”，不是 Provider 会话复用，也不是 SDK Client 缓存。

### 2.2 LightAgent 当前机制

`v2.1.22` 已完成：

- room timeline、双游标 revision 和安全事件投影。
- 默认 `stable_room_id + stable_member_id` owner session。
- `new_thread / resume_thread / observe_only` 状态机。
- thread 文本历史与 Agent 缓存隔离。
- sidecar `send_result=sent` 后才确认 thread 的两阶段提交。
- 发送失败、未知、超时、清洗为空和 stale 抑制时丢弃 pending turn。
- 后台 rolling summary 与安全工具 continuation capsule。

本轮讨论时的线上非敏感运行基线为：

- 已配置的 7 个群均显式使用 V2。
- `wechat_group_session_scope` 未单独设置，按代码默认 `member` 生效。
- thread TTL 未单独设置，按默认 15 分钟生效。
- rolling summary 已开启。
- 安全工具 continuation 未开启。
- 当前模型为 `mimo-v2.5-free`，`bot_type` 为自定义 OpenAI-compatible。

这组运行值与仓库模板默认值并不完全相同：模板仍是 `mode=legacy`、rolling summary 默认关闭。本方案以已经验证运行的 V2 为新基线，并进一步删除模式选择，而不是把线上配置退回模板旧默认。

当前不足：

1. `recent` 模式只有 12 条、30 分钟原文，且不注入 rolling summary。
2. `contextual` 与 `recall` 才会读取 rolling summary，普通独立提问看不到更早的当天群聊背景。
3. rolling summary 当前按旧摘要增量合并，缺少严格的 24 小时滑动淘汰，旧事实可能长期残留。
4. Web 仍展示 Legacy、最近 100 条/1440 分钟、本地摘要等与 V2 实际策略不一致的设置。
5. 当前自定义 OpenAI-compatible 调用只发送 `model/messages/temperature/tools` 等 Chat Completions 参数，没有 Provider continuation anchor。
6. `wechat_group_continuation_enabled` 表示安全工具结果胶囊，不是 Provider 会话复用，当前命名容易产生误解。

### 2.3 对比结论

| 维度 | LightAgent 当前 V2 | BaiLongmaPro | 本方案目标 |
|---|---|---|---|
| 近期群现场 | 12 条/30 分钟；追问 24 条/2 小时 | 100 条/24 小时 | 保留有界原文，不照搬 100 条 |
| 当天背景 | contextual/recall 可读 rolling summary | 每轮有快速摘要和厚 transcript | 每次自然语言请求都可读 24 小时滚动摘要 |
| 远期事实 | recall 时读取归档证据和群记忆 | 每轮可装配 90 天证据与多类记忆 | 只在语义相关或显式回溯时召回 |
| 机器人对话 | stable member thread，发送成功后确认 | 本地 conversation 重放 | 保留本地已确认 thread 为事实源 |
| Provider 会话 | 无 | 无 | 仅对明确支持的 Provider 可选启用 |
| Provider 切换 | 本地 messages 可故障转移 | 每轮完整 messages | 任何时候都能回退本地重放 |
| 安全隔离 | stable room/member、工具门禁、两阶段提交 | 上下文较厚，状态更集中 | 保持 LightAgent 边界，不复制全局状态 |

明确不照搬 BaiLongmaPro 的“每轮固定塞入 100 条群消息和全部可用历史”。厚上下文能提升命中率，但也会增加无关噪声、token、隐私暴露和错误承接。LightAgent 应借鉴它的持续现场意识，不照搬它的固定容量策略。

## 3. 目标与非目标

### 3.1 目标

1. 所有普通自然语言 direct、follow-up 和允许生成的 ambient 请求都能看到同群最新现场和可用的当天摘要。
2. 当前消息、近期原文、rolling summary、归档证据和 thread 历史之间可追踪、可去重。
3. 独立问题不错误恢复旧 thread，明确追问只恢复同一 stable room/member 的已确认 thread。
4. Provider 续接不改变本地 thread 语义，也不成为上下文正确性的唯一来源。
5. Web 页面只保留真实有效的业务配置，默认值与实际 V2 行为一致。
6. 删除无用预览、Legacy 分支和会造成滚动跳动的折叠配置区。

### 3.2 非目标

1. 不把微信群改造成独立 Agent 或在 sidecar 内实现模型调用。
2. 不让整个群共享一个 Provider conversation。
3. 不把所有群消息写入某个成员的 Agent thread。
4. 不恢复跨轮原始工具消息、thinking、动态增强 Prompt 或媒体本地路径。
5. 不把 Provider Client、HTTP keep-alive 或 SSE 连接复用误认为对话复用。
6. 不为未知 OpenAI-compatible 服务猜测 `previous_response_id` 等非标准字段。
7. 不在本计划中增加新的社交工作台、画像编辑或记忆管理入口。

## 4. 必须保持分离的五层状态

| 状态 | 作用 | 主键 | 是否是模型事实源 |
|---|---|---|---|
| Room timeline | 本群所有成员的入站消息和已发送助手事件 | stable account + stable room + revision | 是 |
| Owner session | 权限、记忆、取消、排队和用户归属 | stable room + stable member，或显式 room scope | 否 |
| Agent thread | 当前成员与机器人的已确认短期对话 | owner session + thread ID | 是 |
| Request | 单次生成、取消、发送确认与审计 | request ID | 否 |
| Provider continuation | 某 Provider/模型的可选远端续接锚点 | account + owner + thread + provider + model | 仅为优化 |

硬规则：

1. room timeline 必须包含同一 stable room 内所有成员的安全消息，不得按当前 stable member 过滤。
2. room timeline 不等于 Agent thread；本群其他成员的群消息进入当前请求上下文，但不写入当前成员的私有 thread。
3. owner session 不等于 thread。
4. request ID 不得复用为 thread ID 或 Provider anchor。
5. Provider anchor 不得跨 account、room、member、thread、Provider、模型或 endpoint fingerprint 使用。
6. 任何远端锚点丢失后，本地快照必须足以继续回答。

## 5. 四层本地上下文架构

### 5.1 数据流

```text
Wechaty sidecar 入站
  -> stable account / room / member 解析
  -> 写入 canonical room timeline
  -> room single-flight 排队
  -> 请求出队后生成不可变 RequestSnapshot
       1. 本群所有成员的有界近期群聊原文
       2. 本群所有成员消息形成的 24 小时滚动摘要
       3. 本群所有成员范围内的语义相关归档证据与群记忆
       4. 当前成员已确认 Agent thread
  -> 去重、预算、安全投影和来源标识
  -> Bridge -> Agent -> Provider candidate
       -> 默认完整本地 messages
       -> 可选 Provider continuation anchor + 当前增量
  -> 清洗最终回复
  -> sidecar 真实发送
  -> send_result=sent
       -> 确认本地 thread
       -> 写 assistant timeline
       -> 确认工具 capsule
       -> 确认 Provider candidate anchor
```

### 5.2 第一层：近期群聊原文

用于理解当前话题、指代、收件人关系、本群其他成员刚才说过的话和机器人上一句，继续由 ContextPolicy 自动选择。查询作用域固定为当前 `stable_room_id`，返回该群内所有成员的安全事件，不增加 `stable_member_id` 过滤：

| 模式 | 原文窗口 | 适用场景 |
|---|---|---|
| `minimal` | 0 至 4 条、10 分钟 | 确定性命令或明确忽略上下文 |
| `recent` | 12 条、30 分钟 | 普通 direct 和 ambient |
| `contextual` | 24 条、2 小时 | 短追问、引用、图片、继续和省略句 |
| `recall` | 最近 20 条、24 小时 | 总结、谁说过、历史约定和显式回溯 |

这些值由 V2 policy 控制，不再暴露通用“最近条数/分钟”配置。原因是不同意图需要不同上下文深度，一个全局 100/1440 设置不能准确表达策略。

当前发言人的消息、其他群友的消息和机器人已确认发送的回复按 room timeline 的真实时序共同渲染，并保留安全显示名、引用关系和消息类型。只有跨群消息、未确认发送的机器人回复和被安全投影拒绝的内容不得进入这一层。

### 5.3 第二层：24 小时滚动摘要

目标行为：

1. `recent`、`contextual` 和 `recall` 都允许注入可用 rolling summary；`minimal` 不注入。
2. summary 覆盖同一 stable room 内所有成员最近 24 小时中未被当前原文尾巴覆盖的较早事件，不按当前提问者过滤。
3. 每次 Prompt 使用 summary revision 过滤 recent block，避免同一事件同时出现在摘要和原文中。
4. direct 请求永不等待摘要生成；摘要缺失或过旧时使用近期原文并异步调度刷新。
5. 摘要必须从 canonical timeline 的当前 24 小时窗口重建，不能无限合并旧摘要。
6. 摘要长度默认不超过 1200 个中文字符，输入事件受安全投影和总量上限约束。
7. 上游 408/429/5xx、空正文或错误 envelope 不更新 summary，也不推进 revision。

当前 rolling summary 的增量合并方式需要调整为有界窗口重建。建议每次读取最近 24 小时最多 500 个安全事件，排除最新 12 条原文尾巴；超过上限时记录 `truncated` 指标，不把更旧原文无条件塞入 Prompt。

### 5.4 第三层：相关归档证据与群记忆

1. archive evidence 只在 `recall` 或明确语义需要时读取，不在每轮无条件注入。
2. 检索范围是当前 stable room 内所有成员的群消息；当前提问者只影响 query 和排序，不限制证据作者。
3. 默认检索 90 天范围，但结果受最多 12 条、约 3200 字符的统一预算限制。
4. 删除 archive evidence 内部“近期消息兜底”，近期事实由第一层负责。
5. 使用 `source_event_id` 排除 recent、summary 和 thread 已覆盖事件。
6. 原始证据优先于摘要；证据不足时明确“不确定”，不允许用摘要推测原文细节。
7. 群永久记忆按 stable room 过滤，成员画像按目标 stable member 过滤，不改变现有管理入口。

### 5.5 第四层：当前成员 Agent thread

1. `new_thread` 不读取旧 thread，只创建新的本地 thread。
2. `resume_thread` 只恢复同 stable room/member 的 active thread。
3. `observe_only` 不读取、不写入交互 thread。
4. 本地只持久化首个用户原文和最终助手文本，继续排除工具原始消息、thinking、增强 Prompt、runtime ID 和媒体路径。
5. thread 继续以 `send_result=sent` 作为确认边界。
6. 当前 thread 中带 `source_event_id` 的消息与 room timeline 去重；无法精确映射时优先保留近期现场，丢弃较旧的重复 thread 文本。
7. 本群其他成员说过的话通过 room timeline、summary 和 archive evidence 提供给当前请求，不追加到当前成员 thread，也不改变 thread owner。

## 6. Prompt 预算、顺序和安全投影

### 6.1 建议预算

| 区块 | 建议上限 | 超限处理 |
|---|---:|---|
| 权限、收件人和 persona | 2000 字符 | 固定规则不可被动态块挤掉 |
| rolling summary | 1200 字符 | 截断低优先级背景 |
| recent/contextual timeline | 2400/4800 字符 | 从最旧事件开始裁剪 |
| archive evidence | 12 条或 3200 字符 | 按相关度与时间排序裁剪 |
| 群记忆和画像 | 1600 字符 | 保留当前说话人和最高相关记忆 |
| 工具 continuation capsule | 800 字符 | 只保留最后一个安全只读结果 |

总动态群上下文还必须受模型上下文窗口和 Agent 历史预算二次约束。裁剪优先级从低到高为：旧归档证据、低相关群记忆、旧摘要片段、旧 recent 事件；当前用户原文、权限策略、当前引用和最新现场不得被裁掉。

### 6.2 来源与去重

每个动态材料必须携带服务端来源元数据，但不得把内部 ID 注入模型正文：

- timeline：`source_event_id`
- summary：`summary_revision + window_start_at + window_end_at`
- archive evidence：`archive_row_id/source_event_id`
- thread：`session_id + thread_id + seq + source_event_id`
- memory/profile：稳定作用域与 revision

RequestSnapshot 生成 `included_source_event_ids` 和 `excluded_source_event_ids` 诊断集合。Web 和日志只输出计数、模式、字符数、revision 和哈希，不输出群聊正文、stable ID 或 Provider anchor。

### 6.3 安全规则

1. 所有群聊动态块继续标记为 untrusted data。
2. XML、base64、本机路径、Secret、URL 查询参数和 transport payload 继续执行安全投影。
3. 权限、persona、工具 schema 和当前用户原文不能被 summary 或 archive evidence 覆盖。
4. Scorer、Judge、Context Engine 和 Agent 应使用同一 request revision，避免各自读取不同现场。
5. Provider candidate 必须从同一规范化请求快照独立构造，不共享被前一个 adapter 修改的 messages 或 tools。

## 7. Provider 会话复用设计

### 7.1 能带来什么，不能带来什么

Provider continuation 可能带来：

- 减少同一 thread 的历史重放 token。
- 延续 Provider 对特定响应链的内部状态。
- 改善“继续刚才”类 thread 内连贯性。

它不能自动带来：

- 对两轮之间新群消息的感知。
- 跨成员或全群统一记忆。
- 可靠的群级事实召回。
- Provider 切换后的连续性。

因此每轮仍必须重新提交最新群现场、当前权限、persona 和当前用户原文。Provider continuation 不能替代四层本地上下文。

### 7.2 当前 Provider 基线

当前运行模型为自定义 OpenAI-compatible Chat Completions 类型。现有 `models/openai_compatible_bot.py` 发送完整 `messages`，只允许少量请求级参数，没有 Provider continuation 字段。

“OpenAI-compatible”只说明基础请求形状近似，不表示服务支持 Responses API、conversation object 或 `previous_response_id`。实施前必须针对实际 Provider 和 endpoint 查阅官方文档并做最小探测，不能直接向 Chat Completions 请求体添加猜测字段。

### 7.3 能力抽象

新增 Provider 中立能力接口，建议状态为：

```text
ProviderContinuationCapability
  mode: none | immutable_parent
  provider_key
  model
  endpoint_fingerprint
  build_request(local_snapshot, committed_anchor)
  extract_candidate_anchor(response)
  classify_anchor_error(error)
```

只接入满足以下条件的 Provider：

1. 官方文档明确支持服务端续接。
2. 新请求能从旧 anchor 创建独立分支，不会不可逆修改一个共享 conversation。
3. anchor 失效时可识别并安全回退完整本地 messages。
4. 当前轮仍能重新提交最新系统约束和群现场。
5. 不要求整个 room 共用一个远端 conversation。
6. 数据保留、删除和隐私语义可被管理员理解并显式选择。

不接入只有“可变 conversation_id”且无法分支、无法回滚的 Provider 会话。

### 7.4 作用域与持久化

```text
provider_continuation_anchors
  stable_account_scope
  owner_session_id
  thread_id
  provider_key
  model
  endpoint_fingerprint
  anchor_type
  anchor_value
  parent_anchor_hash
  request_id
  status: pending | committed | expired | discarded
  created_at
  expires_at
```

规则：

1. anchor 是服务端不透明值，不进 Prompt、不回显 Web、不写普通日志。
2. 日志最多记录 hash 前缀、Provider、状态和失败分类。
3. TTL 不超过本地 thread TTL。
4. 模型、Provider、Base URL、账号、thread 或权限 revision 改变时不复用旧 anchor。
5. `new_thread` 从空 anchor 开始；`resume_thread` 才可读取已确认 anchor；`observe_only` 不创建或续期 anchor。
6. 第一版只允许无工具的文本 turn 复用。发生工具调用时不确认跨轮 Provider anchor，继续使用本地安全工具 capsule，避免远端隐式保留原始工具链绕过本地策略。

### 7.5 两阶段提交

```text
读取已确认 anchor A
  -> 使用 A 或完整本地 messages 请求 Provider
  -> Provider 返回最终正文和候选 anchor B
  -> B 以 request_id 暂存为 pending
  -> 微信发送
     -> sent: 同一提交边界确认本地 thread、timeline、tool capsule 和 B
     -> failed/unknown/timeout/empty/stale: 丢弃 B，A 保持不变
```

即使 Provider 已在远端生成 B，只要微信未确认发送，LightAgent 就不保存或继续使用 B。下一轮仍从 A 分支或使用完整本地历史，避免模型记住用户在群里从未看到的回复。

### 7.6 故障转移

1. 每个 Provider/模型维护独立 anchor，不能把主模型 anchor 交给备用模型。
2. 识别为 anchor expired/not found 的错误时，只允许在同一候选内清除 anchor 并用完整本地快照重试一次。
3. 408/429/5xx 且尚未产生正文时，按现有主备链切换，下一个候选使用自己的 anchor 或完整本地快照。
4. 安全拒绝、权限错误或已产生部分正文时，不得借备用 Provider 绕过。
5. 最终实际发送哪个候选的正文，只确认哪个候选的 anchor。

### 7.7 与现有工具 continuation 区分

当前 `wechat_group_continuation_enabled` 保存的是白名单只读工具的清洗结果，不是 Provider 会话。实施时重命名为：

```json
{
  "wechat_group_tool_continuation_enabled": false
}
```

删除单独的 `wechat_group_continuation_ttl_minutes`，工具 capsule TTL 直接取 `min(thread TTL, 15 分钟)`。Provider 续接使用独立命名：

```json
{
  "wechat_group_provider_continuation_enabled": false
}
```

Provider 配置只有在能力探测明确支持时才进入 Web；不支持时不展示一个无效开关。

## 8. “群聊 -> 拟人化”UI 审计与目标布局

### 8.1 当前问题

当前页面存在以下结构性问题：

1. “上下文与会话引擎”使用 `<details open>`，内部控件变化或页面重绘时容易产生滚动位置异常。
2. 页面提供 Legacy/V2 选择，但线上群已使用 V2，本方案也不再支持 Legacy。
3. 页面展示“最近 100 条/1440 分钟”，V2 主请求实际使用四档 ContextPolicy，这两个值对 V2 recent snapshot 不生效。
4. “本地摘要”只在 Legacy 分支生效，V2 下开关和数值均无效。
5. 多个安全守卫被做成可关闭开关，例如原文持久化、回复对象策略、引用/链接策略和发送前清洗。
6. “完整上下文注入预览”打开页面后会加载成员并触发重绘，本身没有日常运维价值，还增加滚动跳动和公开诊断面。
7. `extra.recent_context`、`extra.context_engine` 和 `extra.humanization` 三份 Web 数据结构重复表达同一组设置。

### 8.2 目标布局

“拟人化上下文”页面改为单一主滚动流，不使用折叠设置：

```text
回复
  [发送最大字符数：800]
```

要求：

1. 页面内不出现 `<details>`、`<summary>` 或折叠卡片。
2. 不显示“引擎模式”和 Legacy/V2 文案。
3. 不显示已经固化的安全开关。
4. 不再异步加载预览成员，不因进入页面自动触发二次重绘。
5. 保存后保持当前主滚动位置，不能跳回页面顶部。
6. 设置保持稳定网格尺寸，移动端单列，桌面端最多两列，文本不得溢出。

## 10. Legacy 移除边界

“摒弃 Legacy”仅指微信群上下文与会话引擎的 Legacy 执行路径，不等于删除所有历史数据兼容：

必须删除：

- `wechat_group_context_engine_v2_enabled()` 模式判断。
- `wechat_group_context_engine_mode` 配置与 Web 处理。
- 微信群 `_handle()`、上下文装配、发送确认和 rolling summary 中以模式为条件的 Legacy/V2 分支。
- `WechatGroupHumanizedContextBuilder` 内的 Legacy local summary 和 Legacy recent 拼装。
- 只验证模式开关或 Legacy 上下文行为的测试。

必须保留：

- stable identity 对历史 runtime room/member 的受控兼容。
- 旧 session 数据、无 `thread_id` 消息和其他渠道的 session 语义。
- `group_shared_session` 到新 session scope 的一次配置迁移。
- 数据库 schema 的向后兼容字段，不执行破坏性删除。

Builder 异常时不再降级到另一套旧上下文算法。安全降级应为：保留当前用户原文、权限、收件人策略和最小同群 recent snapshot；记录结构化错误，不恢复旧 session 或远期材料。

## 11. 分阶段实施

### Phase 0：证据、基线与失败测试

1. 固化当前 UI 字段、默认值、V2 policy、rolling summary 和发送确认测试基线。
2. 增加预期失败测试：无 mode 配置仍走 V2；拟人化页面无 `<details>`；preview API 不再可用；recent 请求注入可用 summary。
3. 针对当前实际 Provider 查阅官方文档，确认是否存在可分支 continuation API。
4. 若 Provider 只支持 Chat Completions 或文档不明确，记录 `capability=none`，不猜测接入。

退出条件：删除与迁移范围明确，Provider 能力有官方证据，未确认能力不进入实现。

### Phase 1：固定 V2 与精简 UI/config

1. 删除引擎模式、Legacy 分支和旧降级拼装。
2. 固定 room single-flight、原文持久化、回复策略、引用/链接策略和发送前清洗。
3. 删除 recent 通用设置与 Legacy local summary 设置。
4. 保留并平铺 session scope、thread TTL、rolling summary、archive recall、archive days、tool continuation 和 max chars。
5. 删除完整上下文注入预览 UI、公开 API 和相关状态。
6. 合并 Web `humanization/recent_context/context_engine` 数据结构。
7. 更新 `AGENTS.md` 中“保留预览”“默认 legacy”“旧轻量降级”的过时规则。

退出条件：页面无折叠区、无模式选择、无预览；无 mode 配置时全部微信群请求仍执行 V2。

### Phase 2：四层上下文与 24 小时摘要

1. `recent` policy 开启 rolling summary 注入。
2. rolling summary 改为 24 小时有界窗口重建，删除无限增量累积。
3. ContextSnapshot 统一执行 summary/recent/archive/thread 去重。
4. archive evidence 取消 recent fallback，纳入统一条数与字符预算。
5. 将 focus 与 style 从已删除的 `wechat_group_recent_context_minutes` 解耦：focus 使用 2 小时内部窗口，style learning 使用 24 小时内部窗口。
6. 加入摘要 freshness、truncated、字符预算和来源计数指标。

退出条件：普通 direct 能看到当天较早背景；摘要不会携带 24 小时外旧事实；同一事件不重复出现。

### Phase 3：Provider continuation 基础设施

1. 增加 Provider capability、anchor store 和 request-scoped candidate 状态。
2. 把 anchor pending/commit/discard 接入现有微信发送两阶段提交。
3. 加入 Provider/model/endpoint 切换、anchor 过期和 fallback 逻辑。
4. 第一版只支持无工具文本 turn，工具 turn 自动退回本地重放。
5. 不支持的 Provider 保持 `none`，行为与当前完全一致。

退出条件：关闭开关或 Provider 不支持时请求体与当前一致；失败发送绝不推进远端续接链。

### Phase 4：首个 Provider adapter

仅在 Phase 0 证明当前或另一个明确 Provider 支持 immutable parent continuation 后实施：

1. 按官方 API 实现专用 adapter，不向通用 Chat Completions 注入猜测字段。
2. 用 mock 合同测试覆盖请求、响应、过期、分支和删除语义。
3. Web 仅在当前 Provider 支持时展示独立开关，默认关闭。
4. 单群 canary 对比本地重放与 Provider 续接的质量、token 和延迟。

退出条件：本地历史与 Provider 续接答案一致性达标，且无跨 thread、失败回复或工具原始数据泄露。

### Phase 5：发布与运行配置迁移

1. 完成本地全量回归、Web 桌面/移动视口检查和本地 `python app.py` 验证。
2. 创建版本化发行说明并按仓库发布规则打新标签。
3. 镜像发布后备份远端配置，删除废弃键，写入保留键目标值。
4. 现有全部已配置群不再保存 `mode=v2`，因为 V2 已是唯一行为。
5. rolling summary 默认开启；Provider continuation 继续默认关闭，先单群 canary。

## 13. 验证矩阵

### 13.1 V2 与会话

- 缺失或残留任意 `wechat_group_context_engine_mode` 值时都执行 V2。
- 独立 direct 创建新 thread，明确追问只恢复同成员 active thread。
- room scope 显式开启时保持兼容，但默认仍为 member。
- `new_thread` 不推进 `context_start_seq`。
- 发送失败、未知、空正文和 stale 抑制不确认 thread、summary assistant event、tool capsule 或 Provider anchor。

### 13.2 四层上下文

- 同一群内 A 提问时，recent 能按真实时序包含 B、C 等其他成员的相关近期消息和机器人已发送回复。
- 当前成员的 `stable_member_id` 不得缩小 room timeline、rolling summary 或 archive evidence 的群级查询范围。
- 其他成员的群消息可以进入当前 RequestSnapshot，但不能写入当前成员 Agent thread 或 Provider anchor scope。
- 普通 recent 请求能注入可用的 24 小时 summary。
- minimal 请求不注入 summary/archive。
- contextual/recall 的 recent 窗口符合 policy，不读取已删除的全局 recent 配置。
- 24 小时外事件从重建摘要中消失。
- recent、summary、archive 和 thread 不重复同一 source event。
- summary 故障不阻塞 direct，不推进 revision。
- 超过 500 个事件时安全截断并记录指标，Prompt 不失控。

### 13.3 Provider continuation

- 不支持 Provider 或开关关闭时完整本地重放。
- anchor 只在完全相同 scope/provider/model/endpoint 下命中。
- `new_thread`、`observe_only`、工具 turn 和权限 revision 变化不复用旧 anchor。
- anchor expired 时同候选只回退一次，不形成重试循环。
- 主模型失败切备用时不携带主模型 anchor。
- 微信发送失败后下一轮继续旧 anchor，不续接未送达回复。

### 13.4 Web 与配置

- 拟人化页面不包含 `<details>`、`<summary>`、Legacy、引擎模式和完整注入预览。
- 控制台不再请求 `/api/wechat-group/memories/preview`。
- preview POST action 返回 unknown/not found，不泄露上下文。
- Web GET 只返回保留配置及新默认值。
- Web 保存不写任何废弃键。
- 页面初次进入不加载预览成员、不发生异步二次重绘。
- 保存、语言切换和移动端布局不造成滚动跳顶或控件溢出。

## 15. 灰度与回滚

### 15.1 灰度

1. V2 固化和 UI 清理先通过本地自动化与单群真实 canary。
2. rolling summary 默认开启，但保留独立成本开关，可在异常时关闭，不影响 recent/thread。
3. archive evidence 保留独立开关，可在召回噪声异常时关闭。
4. tool continuation 默认关闭，完成真实追问 canary 后再决定是否调整默认。
5. Provider continuation 默认关闭，只对一个已验证 Provider、一个测试群开启。

### 15.2 回滚

本方案不保留 Legacy 运行时开关。回滚路径为：

1. 回退到上一稳定镜像或标签。
2. 使用更新远端配置前生成的备份恢复旧键和值。
3. 单独关闭 rolling summary、archive evidence、tool continuation 或 Provider continuation，不影响 V2 thread 基础链路。
4. Provider anchor 表只做兼容保留，不在回滚时删除。
5. 不删除 thread、timeline、归档、记忆、画像或 stable identity 数据。

删除 Legacy 是破坏性行为。发布说明必须明确：旧配置即使仍写 `legacy` 也不会生效，升级后所有微信群统一使用 V2；需要旧行为的用户只能暂缓升级或回退旧版本。

## 16. 完成标准

1. 微信群上下文引擎只有 V2，不存在模式选择、Legacy 默认或旧轻量降级路径。
2. 会话作用域仍可配置，默认按 stable room/member 隔离。
3. 所有普通自然语言请求能看到本群所有成员形成的有界 recent 和可用的 24 小时 rolling summary，而不只是当前提问者的消息。
4. archive evidence、summary、recent 和 thread 有统一预算及来源去重。
5. rolling summary 不保留 24 小时外事实，失败不推进 revision。
6. 完整上下文注入预览的 UI、状态、自动加载和公开 API 全部删除，真实记忆/画像注入不受影响。
7. 拟人化页面无折叠配置区，无滚动跳动，保留配置与实际行为一致。
8. 废弃配置不再出现在默认模板、Web API 或保存体中。
9. BaiLongmaPro 的有益现场重建思路已吸收，但没有复制无界厚 Prompt 或 runtime scope。
10. Provider continuation 仅在官方能力明确时接入，默认关闭，失败后可完整回退本地历史。
11. Provider anchor 和本地 thread 使用同一发送确认边界，不记住未送达回复。
12. 本群其他成员的公开群消息能进入当前请求上下文，但不会写入当前成员私有 thread 或跨群泄露。
13. 自动化、Web 视口、本地真实运行和单群 canary 均通过，相关规则、变更记录和本计划实施回写完整。
