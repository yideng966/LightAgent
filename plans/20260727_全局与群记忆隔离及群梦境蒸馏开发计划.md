# 全局与群记忆隔离及群梦境蒸馏开发计划

> **状态：** 已完成 P0/P1 实施、验证与本地数据重置
> **创建日期：** 2026-07-27
> **完成日期：** 2026-07-27
> **任务类型：** 记忆作用域安全修复 / 群永久记忆自动学习 / 存量数据重置
> **优先级：** P0 数据隔离与清理，P1 群作用域梦境蒸馏
> **实施原则：** 最小修改、先阻断污染再恢复学习、按 `stable_room_id` 强隔离、失败不推进游标

## 1. 目标与已确认决策

本计划解决以下两个已确认问题：

1. 微信群 Agent 会话会被通用 Daily Summary、Deep Dream 和 Self-Evolution 当作全局 shared 学习材料，导致群聊内容进入根目录 `MEMORY.md`、天级记忆、进化记录以及可能的 workspace 文件修改。
2. 当前群永久记忆的“学习运行”没有后台触发器，且启发式规则要求单批至少 20 条消息命中少量固定关键词，真实环境中无法形成有效群记忆。

用户已确认以下决策，实施过程中不得擅自扩大范围：

1. **历史全局记忆不迁移、不人工整理，直接重置。**
   - 清理根 `MEMORY.md` 的历史正文。
   - 清理全局天级记忆、梦境日记、自主进化记录和进化备份。
   - 清理这些文件对应的 shared memory 索引。
   - 不把污染后的全局记忆反向迁移到任何微信群。
2. **群永久记忆复用全局 Deep Dream 的 LLM 蒸馏能力。**
   - 复用“新材料摘要 -> 结合现有长期记忆再次蒸馏”的两阶段逻辑。
   - 复用共享 `TextModelRouter` 的主备模型顺序和熔断状态。
   - 不直接调用现有文件耦合的 `deep_dream()` 写入逻辑，不写全局 `MEMORY.md`。
3. **群记忆始终按 `stable_room_id` 隔离。**
   - 输入只允许来自当前稳定群的归档消息。
   - 输出只允许写入当前稳定群的 `wechat_group_group_memories`。
   - 模型参数中不暴露可由模型覆盖的群 ID。
4. **群画像不在本计划内处理。**
   - 不修改群画像提取、画像 claims、画像 evolution、画像游标或画像 UI。
   - 不借本次群记忆修复顺手调整画像零产出问题。
5. **取消原 P2 的迁移/人工清洗路线。**
   - 一次性全局数据重置并入 P0。
   - 保留群原始归档，后续群记忆只从带稳定群作用域的归档重新生成。

## 2. 当前事实基线

### 2.1 当前全局记忆链路

```text
Agent 会话消息
  -> 上下文裁剪/溢出时 MemoryFlushManager.flush_from_messages()
  -> 每晚 AgentInitializer._flush_all_agents()
  -> memory/YYYY-MM-DD.md
  -> MemoryFlushManager.deep_dream()
  -> 根 MEMORY.md + memory/dreams/YYYY-MM-DD.md
  -> MemoryManager.sync()
  -> index.db 的 shared chunks
```

当前缺陷：上述入口没有拒绝 `channel_type = wechat_group`，`user_id` 也从未被实际设置，因此群会话最终落入 shared。

### 2.2 当前自主进化链路

```text
AgentBridge.agent_reply()
  -> 所有非 scheduler 用户轮次 note_user_turn()
  -> 微信群只把 receiver 置空，仍累计进化轮次
  -> idle trigger
  -> run_evolution_for_session()
  -> write/edit/bash 可修改全局 workspace
```

当前缺陷：清空群通知目标只避免主动往群里推送进化结果，并没有形成数据或写权限边界。

### 2.3 当前群永久记忆链路

```text
WechatGroupArchive
  -> WechatGroupLearner（仅 Web 手动调用）
  -> 固定关键词启发式判断
  -> WechatGroupKnowledgeStore
  -> <wechat-group-memory> / wechat_group_memory_search
```

当前缺陷：

- `wechat_group_learning_enabled` 没有后台消费者。
- `WechatGroupLearner` 在 Web 构造时没有接入真实 `conf()`。
- `wechat_group_learning_group_memory_window_minutes` 未被使用。
- 群记忆需要单批 20 条关键词消息，配置语义和实现不一致。
- 群 Agent 工具只有搜索，没有管理员写入/停用能力。

### 2.4 Deep Dream 是否使用 LLM

**是。** 当前 `MemoryFlushManager.deep_dream()` 会：

1. 读取现有 `MEMORY.md`。
2. 读取最近天级记忆文件。
3. 构造 `LLMRequest`。
4. 通过 Agent 的共享文本模型路由调用 LLM。
5. 解析 `[MEMORY]` / `[DREAM]`。
6. 覆写 `MEMORY.md` 并生成梦境日记。

本计划不复制另一套 Provider、API Key 或 HTTP 调用。群记忆蒸馏必须通过 `Bridge().get_text_model_router().complete()` 使用同一主备路由和熔断状态。

## 3. 目标架构

### 3.1 P0 后的作用域边界

```text
Web/私聊等现有通用 Agent 会话
  -> 保持现有 shared Daily Summary / Deep Dream / Self-Evolution

微信群会话
  -> ConversationStore：保留成员级短期会话历史
  -> WechatGroupArchive：保留当前群原始归档
  -X-> shared Daily Summary
  -X-> shared Deep Dream
  -X-> shared Self-Evolution
```

硬性不变量：只要请求的 `channel_type` 是 `wechat_group`，即使稳定身份缺失、配置缺失或解析异常，也不得降级写入 shared。

### 3.2 P1 群记忆目标链路

```text
当前 stable_room_id 的新增文本归档
  -> 群记忆 idle/manual trigger
  -> 阶段 A：LLM 群天级摘要
  -> 阶段 B：现有群记忆 + 群天级摘要 -> LLM 群梦境蒸馏
  -> 服务端严格 JSON/证据/作用域校验
  -> 当前群 wechat_group_group_memories
  -> <wechat-group-memory> / wechat_group_memory_search
```

这里“复用 Deep Dream”指复用以下核心原则：

- 新材料先压缩为高密度摘要。
- 蒸馏时同时提供现有长期记忆和新摘要。
- 由 LLM 去重、合并、识别冲突和过滤短期噪声。
- 没有值得长期保存的内容时允许零产出。
- 模型失败不破坏现有长期记忆。

群版本与全局版本的差异：

| 维度 | 全局 Deep Dream | 群记忆 Dream |
| --- | --- | --- |
| 输入 | `MEMORY.md` + 天级文件 | 当前群 active 记忆 + 当前群归档窗口 |
| 输出格式 | `[MEMORY]` / `[DREAM]` Markdown | 严格 JSON 操作列表 |
| 目标 | 根 `MEMORY.md` | 当前群 SQLite 记忆表 |
| 作用域 | shared | `stable_room_id` |
| 证据 | 天级摘要文本 | 当前群真实 `message_id` 白名单 |
| 删除行为 | 可重写完整文件 | 自动流程不删除，停用仍需管理员 |

## 4. 明确不做

1. 不处理群画像零产出、画像抽取提示词、画像证据准入或画像回滚。
2. 不删除群归档数据库。
3. 不删除群知识库、群记忆表或群画像表。
4. 不删除普通会话历史；只移除明确的进化注入记录。
5. 不删除 `knowledge/`、`USER.md`、`AGENT.md`、scheduler、skills 或用户文件。
6. 不自动推断污染后的全局记忆属于哪个群。
7. 不在 sidecar 中实现学习、模型调用或记忆写入。
8. 不修改桌面端 `desktop/`。
9. 不新增第三方依赖。

> 注意：历史 Self-Evolution 可能已经修改过 `AGENT.md`、workspace skills 或 knowledge 文件。由于部分历史备份已不存在，无法可靠区分“人工修改”和“进化修改”。本计划只清理可确定的 memory/evolution 数据，不盲目删除或回滚这些业务文件。

## 5. P0：全局记忆隔离与历史重置

### 5.1 建立统一记忆路由判定

新增 `agent/memory/routing.py`，提供单一判定入口，避免三个调用点分别写字符串判断。

建议最小模型：

```python
@dataclass(frozen=True)
class MemoryRoute:
    channel_type: str
    scope_type: str
    scope_id: str = ""
    allow_shared_flush: bool = True
    allow_shared_evolution: bool = True
```

提供：

- `resolve_memory_route(context=None, session_id="", channel_type="")`
- `is_wechat_group_route(...)`
- `allow_shared_memory_write(...)`

判定优先级：

1. 显式 `context.channel_type`。
2. Agent 上保存的当前 route。
3. ConversationStore/session 元数据。
4. `session_id.startswith("wechat_group:")` 只作为旧数据兼容兜底。

微信群规则：

- `scope_type = wechat_group`
- `scope_id = stable_room_id`
- `allow_shared_flush = false`
- `allow_shared_evolution = false`
- 缺少 `stable_room_id` 时仍保持两个 allow 为 false。

其他渠道暂时保持现有 shared 行为，避免扩大本次改动。

### 5.2 阻断群聊进入全局 Daily Summary / Deep Dream

必须同时修改所有 shared flush 入口，不能只修每日任务。

#### 入口一：上下文溢出

修改 `agent/protocol/agent_stream.py`：

- 调用 `memory_manager.flush_memory()` 前读取当前 `MemoryRoute`。
- 微信群 route 直接跳过 shared flush。
- 仍执行上下文裁剪和错误恢复，不影响正常回复。
- 日志只记录 `scope_type/channel_type/reason`，不记录群正文。

#### 入口二：上下文轮次或 token 裁剪

修改 `agent/protocol/agent_stream.py` 的两处 trim flush：

- 微信群不写 `memory/YYYY-MM-DD.md`。
- 微信群仍可使用本轮内存压缩结果维持当前请求连续性，但压缩摘要不得落到 shared 文件。
- 后续如需要群会话压缩持久化，单独设计群作用域摘要，不在本阶段实现。

#### 入口三：每日全量汇总

修改 `bridge/agent_initializer.py::_flush_all_agents()`：

- 遍历 Agent 时先解析 route。
- 跳过全部微信群 Agent。
- `dream_candidate` 只能从允许 shared flush 的 Agent 中选取。
- 当只有微信群 Agent 活跃时，不生成全局 daily，也不运行全局 Deep Dream。

#### MemoryManager 二次防线

修改 `MemoryManager.flush_memory()`：

- 新增可选 `memory_route` 参数。
- `wechat_group -> shared` 时返回 `False` 并记录安全日志。
- 保留上层三处显式判断，使调用方行为清晰；MemoryManager 作为最后一道防误调用保护。

### 5.3 阻断微信群参与全局 Self-Evolution

修改 `bridge/agent_bridge.py`、`agent/evolution/trigger.py`、`agent/evolution/executor.py`：

1. `AgentBridge.agent_reply()` 保存当前 `MemoryRoute` 到 Agent。
2. 微信群轮次不再调用全局 `note_user_turn()`。
3. `trigger._scan_once()` 再次检查 route，防止旧 Agent 状态或直接测试调用绕过入口。
4. `run_evolution_for_session()` 在执行前检查 route，微信群直接返回 `False`。
5. 清除微信群 `_evo_observed_messages/_evo_observed_scope` 的积累路径。
6. 保留群画像 evolution 的独立触发器，本次不修改它。

权限边界：

- 普通群成员对话不能间接触发 `write/edit/bash` 修改 shared workspace。
- 管理员明确要求全局自主进化也不在本计划中放开；后续如确需支持，必须新增独立的显式管理员命令和审计，不得恢复自动群进化。

### 5.4 一次性清理全局 memory/evolution 数据

新增受控脚本 `scripts/reset_global_memory_history.py`，默认 dry-run，必须显式 `--apply` 才修改。

脚本必须使用结构化文件/SQLite API，不使用模糊 shell 删除命令。

#### 清理对象

| 对象 | 处理方式 |
| --- | --- |
| 根 `MEMORY.md` | 重置为干净模板，不直接删除文件 |
| `memory/YYYY-MM-DD.md` | 删除所有全局天级记忆文件 |
| `memory/dreams/` | 删除全部全局梦境日记 |
| `memory/evolution/` | 删除全部全局进化记录 |
| `memory/.evolution_backups/` | 删除全部进化备份 |
| `index.db` 的 memory chunks/files | 定向清理并重新索引剩余 `MEMORY.md` 与 knowledge |
| 会话中的 `[EVOLUTION]` 注入记录 | 按明确 marker 定向删除，并重算 session `msg_count` |

#### 明确保留

- `wechat_group_archive.db`
- `wechat_group_knowledge.db`
- `wechat_group_profiles.db`
- 其他微信群数据库
- `knowledge/`
- `AGENT.md`、`USER.md`、`RULE.md`
- skills、scheduler、images、tmp 之外的用户业务文件
- ConversationStore 中普通 user/assistant 会话历史
- `memory/users/` 下显式 user-scoped 数据；本任务只清全局 shared

#### 安全要求

1. 运行前校验 workspace 真实路径位于配置的 `agent_workspace`。
2. 默认输出待清文件和数据库行数，不输出正文。
3. `--apply` 前要求服务进入维护状态，避免后台线程同时写入。
4. 先在本机临时目录创建短期回退快照。
5. 清理成功并验收后删除临时快照，不保留污染数据的长期副本。
6. 不删除整个 `memory/long-term/index.db`，因为其中同时包含会话 `sessions/messages`。
7. 索引清理复用 `agent.memory.embedding.rebuild.clear_index()` 或等价的 chunks/files 定向逻辑，确保会话表不受影响。
8. 清理后通过 `python app.py` 重新启动本地服务，使所有 Agent 内存态和旧进化游标失效。

- `wechat_group_context_persist_raw_user_only` 保持不变；它只控制会话存储内容，不再被误认为长期记忆隔离开关。

## 6. P1：群作用域 LLM 梦境蒸馏

### 6.1 抽取可复用的 Dream 模型调用层

新增 `agent/memory/dream_engine.py`，只负责无状态 LLM 蒸馏调用，不负责具体存储。

建议接口：

```python
class MemoryDreamEngine:
    def complete(
        self,
        *,
        system_prompt: str,
        user_prompt: str,
        purpose: str,
        temperature: float = 0.2,
    ) -> str:
        ...
```

实现要求：

1. 依赖注入 `TextModelRouter`，默认来自 `Bridge().get_text_model_router()`。
2. 统一调用 `TextModelRouter.complete()`。
3. `purpose` 区分：
   - `memory_daily_summary`
   - `memory_deep_dream`
   - `wechat_group_memory_daily_summary`
   - `wechat_group_memory_deep_dream`
4. 识别 `success=false`、HTTP 408/429/5xx、超时和错误 envelope。
5. 临时供应商故障抛出可分类异常，调用方不得推进游标。
6. 不维护独立 Provider、模型、Key、Base URL、重试或熔断状态。

为了让现有全局 Deep Dream 真正复用该层：

- 将 `MemoryFlushManager._summarize_messages()` 的 LLM 调用逐步委托给 `MemoryDreamEngine`。
- 将 `MemoryFlushManager.deep_dream()` 的 LLM 调用委托给 `MemoryDreamEngine`。
- 保持全局 `[MEMORY]/[DREAM]` Prompt、解析和文件行为不变。
- 给 `TextModelRouter.complete()` 增加向后兼容的可选 `temperature` 参数；现有调用不传时行为不变。

### 6.2 新增群记忆材料构造器

新增 `channel/wechat_group/wechat_group_memory_material.py`。

职责：

1. 只接受服务端绑定的 `stable_room_id`。
2. 从 `WechatGroupArchive` 读取 cursor 后的消息。
3. 只保留安全文本消息。
4. 排除 transport XML、base64、大段 URL 参数、本机路径、密钥样式字段和媒体原始载荷。
5. 使用当前群消息 ID 作为证据标识。
6. 不把真实 stable/runtime member ID 暴露给模型；使用批次内 opaque speaker token。
7. 保留 token -> stable member 的服务端映射，但群记忆输出不得包含画像字段。

窗口语义：

- `wechat_group_learning_batch_message_limit`：单次最多读取的当前群消息数。
- `wechat_group_learning_group_memory_window_minutes`：单次蒸馏材料的最大连续时间跨度。
- cursor 是可靠消费边界，时间窗口不得导致旧消息被静默跳过。
- 读取顺序为当前群 `id ASC`，取 cursor 后第一条作为窗口起点，再按时间跨度和 batch limit 截断。

新增归档接口：

- `count_messages_after_row_id(stable_room_id, row_id)`
- `get_text_messages_after_row_id(stable_room_id, row_id, limit, window_minutes)`
- 查询必须继续使用“stable 优先，只有记录自身无 stable 字段才允许 legacy alias”的规则。

### 6.3 阶段 A：群天级摘要

新增 `WechatGroupMemoryDreamService._summarize_material()`：

- 输入：当前群单个窗口的安全消息。
- 模型：`MemoryDreamEngine`。
- 输出：紧凑的群事件/约定/长期事实摘要。
- 普通闲聊、一次性问答、临时错误、无结论争论输出 `[EMPTY]`。
- 摘要保留证据消息 ID，不得新增输入中不存在的 ID。
- 不提取人物画像、性格、兴趣、亲密度或跨群身份。

该阶段对应全局“对话 -> 天级记忆”，但中间摘要保存在群学习 run 审计中，不写 `memory/YYYY-MM-DD.md`。

### 6.4 阶段 B：群 Dream 蒸馏

新增 `channel/wechat_group/wechat_group_memory_dream.py`：

```python
class WechatGroupMemoryDreamService:
    def run_once(
        self,
        stable_room_id: str,
        trigger_source: str = "manual",
        force: bool = False,
    ) -> dict:
        ...
```

输入：

1. 当前群 active 群永久记忆，转换为批次内 opaque memory token（如 `M001`）。
2. 阶段 A 的群天级摘要。
3. 本批次允许引用的 evidence message ID 白名单。

模型严格输出 JSON：

```json
{
  "memories": [
    {
      "action": "add",
      "target_memory_token": "",
      "content": "长期稳定的群约定或事实",
      "confidence": 0.95,
      "evidence_message_ids": ["message-id"]
    },
    {
      "action": "update",
      "target_memory_token": "M001",
      "content": "更新后的群约定",
      "confidence": 0.96,
      "evidence_message_ids": ["message-id"]
    }
  ],
  "dream_summary": "本轮保留、合并或忽略了什么"
}
```

约束：

- `action` 仅允许 `add`、`update`。
- 自动蒸馏不得输出 `delete/disable`；删除仍由管理员显式操作。
- `update` 只能引用本轮服务端提供的 memory token。
- evidence 必须全部属于当前群、当前批次。
- `content` 必须通过长度、空值、敏感数据和 transport 噪声检查。
- 不允许输出 member profile、sender identity、权限配置或跨群信息。
- 模型不得直接生成或选择 `stable_room_id`。

### 6.5 服务端应用与去重

`WechatGroupKnowledgeService` 继续作为 active 群记忆唯一写入口。

新增：

- `apply_dream_memories(room_id, operations, run_id)`
- `upsert_group_memory()` 的服务层封装
- normalized content 去重
- 当前群 memory token 白名单映射

写入规则：

1. 高于自动写入阈值且校验通过：
   - `add` 调用 `add_group_memory()`。
   - `update` 调用 `upsert_group_memory()`，保持原 memory ID。
   - `source_kind = deep_dream`。
2. 低于自动写入阈值：本期不写 active 群记忆，只记录 run 的跳过数量和原因。
3. 相同规范化正文不重复写入。
4. 数据库写入失败时，本轮不推进 cursor。
5. 不双写全局 `MemoryManager` shared chunk。

本阶段先保留 `WechatGroupKnowledgeStore` 为群记忆事实源，避免同时做通用 MemoryScope 迁移。后续如需要统一搜索能力，另立迁移计划。

### 6.6 运行记录与游标

继续使用 `wechat_group_learning_cursors` 和 `wechat_group_learning_runs` 作为当前 Web 兼容入口，补充最小字段迁移：

- `trigger_source`
- `summary_status`
- `dream_status`
- `skipped_count`
- `dream_summary`
- `llm_status_code`

游标规则：

| 结果 | 是否推进 cursor |
| --- | --- |
| 没有足够消息，未调用 LLM | 否 |
| 阶段 A 返回 `[EMPTY]` | 是，表示已成功分析但无长期价值 |
| 阶段 B 合法但零记忆 | 是 |
| 高置信度记忆写入成功 | 是 |
| LLM 408/429/5xx/超时 | 否 |
| JSON 非法或证据越界 | 否 |
| SQLite 写入失败 | 否 |

首次启用规则：

- 自动 trigger 初始化时以当前 archive high-water 作为自动学习起点，避免启用后突然批量消耗历史消息和模型额度。
- Web 提供显式“从历史归档生成群记忆”动作，只有管理员可触发。
- 历史生成从 row 0 按窗口/批次串行执行，不读取已清理的全局 memory。
- 单次请求设置最大批次数，未完成时返回 remaining count，避免长时间占用 Web 请求。
