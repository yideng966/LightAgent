# 微信群上下文分层与滚动摘要优化实施计划

**状态：** 分阶段实施中（2026-07-27 已完成自由回复缺陷切片；滚动摘要、room revision 与 continuation capsule 待实施）

**总计划约束：** 本文是 `20260715_微信群机器人智能增强完整开发计划.md` 的上下文子计划。默认值、灰度顺序、历史需求变更和发布门禁以总计划为准；本文不得自行覆盖 `AGENTS.md` 或已完成计划。

**目标：** 修复个人微信群自由回复和直接回复偶发承接旧 Agent 会话、旧焦点或远距离群聊的问题，同时保留足够的群聊连续性。最终形成“最近原文保底、滚动摘要承接、焦点辅助召回、归档按需检索”的分层上下文，并在群聊已经推进时取消过时的自由回复。

**架构：** 继续复用 `WechatGroupArchive`、`WechatGroupHumanizedContextBuilder`、`ChatChannel -> Bridge -> Agent` 和现有自由回复 worker。新增确定性的上下文策略选择器和 room 级滚动摘要服务；滚动摘要通过现有 `AgentLLMModel(Bridge())` 异步生成，不新增独立 Agent loop、不调用第三方 SDK、不阻塞当前回复。焦点只提供辅助信息，不再替代最近原始群聊。

**技术栈：** Python、SQLite、`unittest`、现有 Web 控制台 `channel/web/`、现有 Agent/Bridge 主链路。

## 0. 修订说明与既有计划关系

2026-07-27 实施进度：`20260727_微信群自由回复上下文污染修复计划.md` 已完成本计划的 recent-only 自由回复、近场收件人硬抑制、安全 Judge/Scorer timeline、`fresh / interactive_session / observe_only`、ConversationStore 可见性过滤和独立进化观察缓冲。完整 context policy、room 级滚动摘要、统一双游标 timeline、room revision/single-flight 和工具 continuation capsule 仍由本计划继续跟踪。

本计划在 2026-07-14 完成第二轮复核，专门校验是否继续满足“回复像群成员”的拟人化目标。修订后的关系如下：

1. 本计划不替代 `plans/20260708_微信群拟人化上下文优化.md` 的全部内容，只覆盖其中 recent transcript、本地摘要、焦点选择、Agent 历史和自由回复时效性相关实现。
2. 旧计划中的 persona、reply policy、style、emotion、reference policy、多模态、回复清洗、原文持久化和 `ChatChannel -> Bridge -> Agent` 最终回复主链路继续保留。
3. 经总计划复盘批准，允许新增一个受限、异步、默认关闭的滚动摘要调用例外，但必须复用 `AgentLLMModel(Bridge())`，不得形成第二套回复 Agent、执行工具、直接调用供应商 SDK或生成/发送最终回复。
4. 滚动摘要只准备辅助上下文，永远不直接生成或发送群回复；最终回复仍只由 CowAgent 统一 Agent 主链路生成。
5. `wechat_group_humanized_context_enabled = false` 或 builder 异常时，必须进入有界的轻量降级路径，不能因为滚动摘要或新策略异常中断 @ 必回。
6. 首次代码实施前必须先更新 `AGENTS.md` 写入已批准边界；每个 Phase 完成后同步回写本文、总计划和 `CHANGES.md`，不能等全部实施结束再补文档。

本轮修订重点：

- 增加包含群友消息和机器人回复的统一 room timeline。
- 滚动摘要保留一段未摘要近场尾巴，避免与 recent transcript 重复。
- 自由回复不恢复旧会话，但以 `observe_only` 方式保留原文记录和 scoped 被动学习/进化信号。
- 过时任务不再因“单纯超过 15 秒”被取消，改为时间、消息推进和语义状态的组合判断。
- 增加短句、无 mention、persona/style/emotion、回复清洗、typing delay 等拟人化非回归标准。
- observe-only 定稿采用“缓存 Agent 历史快照 -> 空历史运行 -> 捕获本轮结果 -> 恢复原历史”，不为每条自由回复重新初始化完整 Agent。
- timeline 定稿为关系型事件流，除先后顺序外保留安全的发送者、收件人、引用对象和是否回复机器人等关系。
- 旧上下文装配路径保留一版兼容开关和 metadata 别名，支持快速回滚，不在首轮实施中直接删除全部旧行为。

## 1. 背景与已确认问题

当前微信群上下文由最近群聊、归档证据、本地摘要、焦点、群记忆、画像、风格、情绪、多模态和 Agent 会话历史共同组成。问题不在于某一个上下文来源完全错误，而在于它们缺少明确优先级和互斥边界。

已确认的问题如下：

1. `config.json` 未显式配置 `group_shared_session` 时，`ChatChannel` 当前调用点按 `True` 处理，导致一个群内不同成员可能恢复同一个长期 Agent 会话。
2. 即使改成成员级会话，同一成员较早的 Agent 对话仍可能影响后续自由回复；自由回复本应优先依赖当前群现场，而不是旧 Agent 问答。
3. `should_include_contextual_history()` 对所有 `free_reply` 返回 `True`，从而同时打开归档证据、本地摘要和 recent transcript。
4. 当前 `<local-extractive-summary>` 只是将最近消息逐行拼接为“发送者：原文”，没有真正压缩，也不记录覆盖范围。
5. `<wechat-group-archive-evidence>`、`<local-extractive-summary>` 与 `<recent-wechat-group-transcript>` 可能重复注入相同消息。
6. 焦点返回消息时，recent transcript 会优先使用焦点消息，导致未被焦点引用的最新群友发言消失。
7. 焦点沿用时只更新关键词、时间和参与者，不刷新 `title` / `summary`，因此活跃焦点仍可能携带旧摘要。
8. 自由回复 LLM judge 只看当前文本和本地分数，不知道最近聊天、引用对象或消息是否已经有人回答。
9. 自由回复经过防抖、LLM judge 和最终 Agent 生成后，仍按原消息时间构造上下文；群聊在此期间推进时，旧任务不会自动取消。
10. 现有测试覆盖焦点 room 隔离和 pending 防抖，但没有覆盖“旧 Agent 会话 + 短句 + 大量群历史”“焦点命中但遗漏中间消息”“active 任务过时”等组合场景。
11. 当前 `get_recent_messages()` 和 `get_messages_after_row_id()` 只读取群友入站消息；机器人回复单独保存在 `wechat_group_assistant_replies`，因此 recent、judge 和增量摘要无法可靠承接机器人刚说过的话。
12. 如果滚动摘要处理到最新消息，同时 recent transcript 再注入相同尾部消息，会继续产生重复上下文和错误加权。

## 2. 设计原则

1. 当前消息优先级最高，最近原始群聊是上下文事实基线。
2. 滚动摘要用于压缩较早消息，不替代最近原始消息。
3. 焦点只用于解释“当前可能在谈什么”和显式回到旧话题，不得独占 recent transcript。
4. 归档证据只在明确的总结、回溯、查证和引用场景启用。
5. 自由回复宁可不接话，也不要基于无法确认的指代或过时现场强行回复。
6. 所有查询、摘要、焦点和任务状态必须按 `stable_room_id` 隔离；runtime ID 只作兼容回查和真实发送。
7. 当前轮增强块继续只进入当前请求；Agent 持久化仍不得保存 `<wechat-group-*>` 内容。
8. 滚动摘要生成失败不得阻塞回复、不得覆盖旧摘要、不得推进已处理游标。
9. 不新增依赖，不修改 sidecar JSON Lines 协议，不修改桌面端 UI。
10. 不把滚动摘要升级为长期记忆；群永久记忆仍由现有统一记忆服务负责。
11. 群友消息和机器人回复必须进入同一条只读 room timeline；机器人必须能看到自己刚刚在群里说过的话。
12. 自由回复的“生成时不恢复旧历史”与“仍保留审计、UI 和 scoped 被动学习/进化记录”必须分开实现，不能简单丢弃自由回复轮次。
13. 拟人化不只等于上下文正确，还必须保持短句优先、不乱 mention、不暴露内部块名、人设/风格/情绪持续生效和回复节奏自然。

## 3. 目标上下文分层

### 3.1 上下文层级

将当前单一的 `include_history: bool` 替换为确定性的上下文策略：

| 模式 | 适用场景 | 最近 room timeline | 滚动摘要 | 焦点 | 归档证据 | Agent 历史 |
|---|---|---:|---:|---:|---:|---:|
| `current_only` | 内容完整、明确无需群历史的普通 @ | 否 | 否 | 否 | 否 | 按 3.5 的连续性规则决定 |
| `recent` | 普通自由回复、短距离接话 | 是，默认 12 条，包含机器人回复 | 否 | 否 | 否 | 不恢复，`observe_only` 记录 |
| `contextual` | 引用、图片、刚才、上面、继续、什么意思 | 是，默认 20 条，包含机器人回复 | 是 | 仅当前相关焦点 | 否 | 按 3.5 的明确映射 |
| `recall` | 总结、谁说、回到之前、查找历史约定 | 是，默认 20 条，包含机器人回复 | 是 | 是 | 是 | 仅显式回指 Agent 对话时恢复 |

策略必须由服务端根据 `trigger_source`、引用/媒体元数据和用户原文确定，模型不能自行扩大读取范围。

直接 @ 或必回消息出现以下省略/指代表达时，不能进入 `current_only`：

- “你怎么看 / 咋看 / 真的假的 / 那咋办 / 为什么 / 然后呢 / 这个呢 / 所以呢 / 有道理吗”等依赖现场的短句。
- 只有代词、指示词、语气词或省略主语/宾语，无法仅凭当前句独立回答的表达。
- 明确回复某个群友、引用某条消息或紧跟机器人上一条回复的表达。

上述消息优先进入 `recent`；存在引用、机器人上一句或明确焦点锚点时进入 `contextual`。若 bounded timeline 中仍找不到唯一指代，自由回复保持沉默，直接 @ 用一句话澄清，不得猜测。

### 3.2 Prompt 顺序

目标 prompt 顺序如下：

```text
<wechat-group-admin-policy>
<wechat-group-mention-verification>
<wechat-group-reply-policy>
<wechat-group-persona>

<wechat-group-memory>                # 较旧记忆不能压过更新且可追溯的原始消息
<wechat-group-archive-evidence>      # recall only
<wechat-group-rolling-summary>       # contextual / recall
<wechat-group-focus>                 # contextual 命中或 recall
<recent-wechat-group-transcript>     # recent / contextual / recall，事实块中离当前消息最近

<wechat-group-style>
<wechat-group-emotion>
<wechat-group-reference-policy>
<wechat-group-multimodal>

当前用户原文
```

权限、管理员身份和系统配置始终是硬规则。普通事实按时间与来源判断：当前用户消息 > 更新且可追溯的最近原始消息 > 较旧群记忆/成员画像 > 滚动摘要 > 焦点摘要 > 远期归档；管理员后来明确确认且时间更新的记忆可以覆盖更早消息。程序结构和单元测试必须同时断言 recent transcript 位于所有历史事实块之后，不能只依赖文字提示模型遵守优先级。

### 3.3 统一 room timeline、最近原文与焦点合并

在 `WechatGroupArchive` 新增 `get_room_timeline()` 和 `get_timeline_after_cursors()`，将以下两类记录安全投影后按时间合并：

1. `wechat_group_messages` 中的群友入站消息。
2. `wechat_group_assistant_replies` 中机器人已经真实发送成功的回复。

timeline row 使用内部 `source_type = inbound | assistant` 和 `source_row_id` 区分来源。它们只用于数据库游标、去重和诊断，不进入 prompt。机器人回复在 prompt 中使用稳定标签 `assistant` 或机器人当前群内显示名，不得伪装成普通群友。

每个 timeline event 还必须提供经过当前群身份映射和安全清洗的关系字段：

```text
actor_type: member | assistant
actor_display_name
addressee_display_names[]
quote_actor_display_name
quote_excerpt
is_reply_to_assistant
is_directed_to_assistant
created_at
safe_text
```

字段来源：入站消息读取 `at_list`、`quote`、`is_quote_self` 和当前群成员映射；机器人回复读取 `mention_ids`。原始 message/runtime/stable ID、XML、媒体路径和完整引用 payload 不得进入 prompt。服务端可以使用真实 ID 做匹配，但 prompt 只能渲染安全显示名和 `current_image`、`quoted_image`、`recent_image_1` 等当轮临时标签；无法解析成当前群昵称的收件人不输出，不允许回退其他群昵称。

推荐的安全渲染形式：

```text
07-14 14:02 Alice -> Bob (replying to Carol: "……"): 正文
07-14 14:03 assistant -> Alice: 回复正文
```

自由回复没有真实 mention 时不伪造 `-> 某人`；只通过时间邻接和引用关系表达承接。

recent transcript 不再采用“有焦点就完全替换”的逻辑：

1. 先读取当前 room 最近 timeline，包含群友消息和机器人回复。
2. 排除当前 `message_id`。
3. `contextual` / `recall` 模式下再合并焦点引用消息。
4. 按 `source_type + source_row_id` 优先、`message_id` 次之去重。
5. 最后按时间升序排列，并从尾部截取策略上限。
6. 普通 `recent` 模式不添加旧焦点消息。
7. 引用消息和机器人上一条回复即使超出普通计数窗口，也应作为锚点补入，但仍受总字符预算限制。
8. recent 除条数和时间窗口外增加字符预算，避免少量超长消息占满 prompt；默认总字符不超过 4000。
9. judge、stale revalidation 和最终上下文必须消费同一种关系型 timeline 投影，避免三个阶段对“谁在回复谁”作出不同判断。

### 3.4 滚动摘要与近场尾巴不重叠

滚动摘要不得处理到 timeline 的最末端。默认始终保留最近 8 条 timeline event 作为“未摘要近场尾巴”：

1. 摘要 worker 只压缩近场尾巴之前的 eligible events。
2. 摘要成功后，两个来源游标只推进到最后一条 eligible event。
3. `<recent-wechat-group-transcript>` 优先渲染未摘要尾巴，并可按策略扩展到最多 12/20 条。
4. 如果 pending events 不足“刷新阈值 + 近场尾巴”，不刷新摘要。
5. 如果摘要游标因旧版本已经覆盖了近场消息，builder 仍保留至少最近 6 条原文作为事实校验，但在摘要块中增加“recent raw takes precedence”的固定约束。

### 3.5 Agent 会话历史策略

1. 新增微信群专属 `wechat_group_shared_session`；layered 模式缺失时默认按 `False` 处理。旧全局 `group_shared_session` 只在用户配置中显式存在时作为兼容 fallback，不绕过 free reply 的 `observe_only` 策略。
2. Agent 历史模式明确为 `fresh / interactive_session / observe_only`，不得继续使用“按触发来源决定”这种未定义行为。
3. `interactive_session` 是逻辑上的可恢复交互会话：`wechat_group_shared_session = false` 时使用 `stable_room_id + stable_member_id`，显式为 `true` 时使用 `stable_room_id`。scope 只决定会话 ID，不决定某一触发是否允许恢复历史。
4. `quote_self`、明确“继续你刚才的回答”、同一成员在短时间内明确追问机器人时使用 `interactive_session`。
5. standalone direct reply 默认 `fresh`；只有同一成员最近 10 分钟内存在 Agent 轮次且当前文本具有追问/承接信号时才恢复 `interactive_session`，避免独立问题接到很久以前的话题。
6. 普通自由回复使用 `observe_only`：生成时不恢复旧 Agent 对话，但仍将清洗后的用户原文和助手回复持久化为不可参与回复恢复的观察轮次。
7. 图片/视频消息默认 `fresh`；引用机器人或明确继续上一轮视觉解释时使用 `interactive_session`。
8. `recall` 请求主要依赖 room timeline、滚动摘要、焦点和归档；只有明确出现“你刚才说的/继续你的回答”等 Agent 回指时恢复 `interactive_session`。
9. `observe_only` 轮次继续触发带 stable room/member 和角色信息的 `note_user_turn()`，使普通成员消息可以被动参与当前群 scoped 记忆、画像和受限进化；普通成员不能主动命令写入、运行进化或修改技能/全局记忆/workspace，自主进化结果仍不得主动推送群聊。
10. 旧 `wechat_group:<stable_room_id>` 共享会话不删除；缺省切换为成员 scope/观察型模式后自然停止默认读取，便于回滚。

observe-only 的进程内实现固定如下，不再留给实施阶段二选一：

1. 继续复用当前 session 缓存 Agent，避免每条自由回复重新初始化工具、技能和记忆系统。
2. 进入 `run_stream()` 前，在 `agent.messages_lock` 内快照 `agent.messages`、`_last_run_new_messages` 和与本轮历史有关的游标，然后把本轮可见历史置为空。
3. 使用空历史执行当前自由回复，但继续加载系统提示、工具、persona、style、emotion、room timeline 和权限过滤。
4. 运行结束后，在锁内捕获并清洗本轮 user/assistant/tool 结果，生成 observe-only 持久化记录和短期 continuation capsule。
5. 无论成功、异常还是取消，都在 `finally` 中恢复进入本轮前的内存历史和游标；不得清空原 interactive session，也不得让 observe-only 消息残留到下一次缓存 Agent 运行。
6. 恢复前必须完成 `_last_run_new_messages` 的独立拷贝，不能恢复历史后再从 Agent 引用读取本轮结果。
7. 同一 session 的 `concurrency_in_session = 1` 继续作为必要前提；如果显式配置允许更高并发，observe-only 必须使用 session 级锁串行执行，不允许两个快照交叉恢复。

自主进化不从回复用 `agent.messages` 猜测 observe-only 内容，改为显式观察缓冲：

1. `note_user_turn()` 增加可选的 `observed_messages`、stable room/member 和角色参数，只接受清洗后的本轮 user/assistant 文本和允许的工具结果摘要。
2. evolution trigger 将其保存到 `agent._evo_observed_messages` 有界缓冲，默认最多 40 条；该缓冲不参与任何回复请求，并且每项都保留 stable scope 和是否管理员标记。
3. evolution executor 构造 transcript 时合并正常新会话轮次和 `_evo_observed_messages`，并分别维护消费游标。普通成员观察轮次只能使用当前群记忆/画像专用服务，禁止 `write/edit/bash`、全局 `MEMORY.md`、workspace 和技能修改；管理员轮次继续按 stable 管理员授权使用现有能力。
4. evolution pass 完成或明确 no-change 后推进观察游标；失败时保留未消费观察消息，行为与现有进化失败重试一致。
5. 进程重启后允许尚未触发的内存观察缓冲丢失，因为现有 evolution 触发计数本身也是进程内状态；ConversationStore 和微信群归档仍保留审计记录。

### 3.6 自由回复短期 continuation capsule

为避免 observe-only 破坏“继续查一下”之类自然追问，保存一个有时效、不可自动恢复的短期 capsule：

```text
room_id
member_id
user_text
assistant_text
tool_names[]
safe_tool_result_summaries[]
created_at
expires_at
```

约束：

1. capsule 默认有效 10 分钟，按 `stable_room_id + stable_member_id` 强隔离，每个成员只保留最近 1 个。
2. 只有 `quote_self`、明确“继续/再查/刚才你说的”等追问才能注入；普通自由回复和独立 @ 不自动恢复。
3. 工具结果摘要使用白名单：仅允许搜索、网页读取、vision 等只读结果的用户可见短摘要；`bash/read/write/edit`、密钥、cookie、本机路径、记忆写入和管理员工具结果不进入 capsule。
4. 不保存原始 tool_use/tool_result 链，不尝试恢复未完成工具调用；模型需要继续执行时重新调用当前允许的工具。
5. capsule 作为当前轮 `<wechat-group-ambient-continuation>` 块注入，并受 Agent 工具权限过滤；不得绕过管理员门禁。
6. capsule 固定保存在进程内 TTL store，不写 ConversationStore、SQLite、群永久记忆或成员画像；进程重启后自然清空，避免持久化工具摘要扩大敏感数据面。
7. TTL store 使用锁保护，读取时同时校验 room、member、过期时间和当前消息触发类型；命中后可保留到过期，以支持同一短链路的再次追问，但每次写入覆盖该成员旧 capsule。
8. 工具结果摘要使用确定性清洗和字符截断，不为 capsule 再调用 LLM；复用 timeline 的 XML、路径、base64、密钥和 transport metadata 清洗规则。

### 3.7 拟人化行为非回归契约

无论采用哪一种上下文模式，以下现有行为都必须保留：

1. 自由回复通过后优先输出一句自然短回复，不因为有摘要就改成长篇汇报。
2. 自由回复继续设置 `suppress_mention = true` 和 `no_need_at = true`，默认不真实 mention 原发送者。
3. 回复不得出现“根据上下文”“焦点栈显示”“摘要中提到”“归档证据表明”等内部实现措辞。
4. `<wechat-group-persona>`、`<wechat-group-style>` 和 `<wechat-group-emotion>` 继续影响语气；滚动摘要只提供事实背景，不生成第二套人格或风格。
5. 成功发送后继续调用 `mark_replied()`，维持情绪能量和连续插话抑制。
6. 现有 typing delay、回复清洗、引用策略、真实 mention 和多模态安全边界不因本计划回归。
7. 机器人上一条真实回复必须进入 room timeline，使未显式引用的自然追问也有机会正确承接。
8. 无法确认指代时，自由回复可以保持沉默；直接 @ 场景则应简短询问澄清，而不是编造承接对象。

## 4. Room 级滚动摘要

### 4.1 定位

滚动摘要是当前群归档的短中期压缩视图，不是永久记忆、群友画像或 Agent 会话摘要。它只服务 `<wechat-group-rolling-summary>` 注入。

### 4.2 数据模型

在现有 `wechat_group_archive.db` 中新增一张当前态表，不保存多版本历史：

```sql
CREATE TABLE IF NOT EXISTS wechat_group_context_summaries (
    room_id TEXT PRIMARY KEY,
    summary_text TEXT NOT NULL DEFAULT '',
    active_threads_json TEXT NOT NULL DEFAULT '[]',
    attributed_claims_json TEXT NOT NULL DEFAULT '[]',
    open_loops_json TEXT NOT NULL DEFAULT '[]',
    recent_social_context_json TEXT NOT NULL DEFAULT '[]',
    participants_json TEXT NOT NULL DEFAULT '[]',
    source_end_message_row_id INTEGER NOT NULL DEFAULT 0,
    source_end_assistant_row_id INTEGER NOT NULL DEFAULT 0,
    source_end_at INTEGER NOT NULL DEFAULT 0,
    source_event_count INTEGER NOT NULL DEFAULT 0,
    status TEXT NOT NULL DEFAULT 'ready',
    last_error TEXT NOT NULL DEFAULT '',
    last_attempt_at INTEGER NOT NULL DEFAULT 0,
    updated_at INTEGER NOT NULL DEFAULT 0
);
```

约束：

1. `room_id` 必须写 stable room scope；身份未确认时不生成新的持久化摘要。
2. 群友消息与机器人回复来自两张表，必须分别维护 `source_end_message_row_id` 和 `source_end_assistant_row_id`；`source_end_at` 只辅助排序和诊断，不能单独作为去重游标。
3. LLM 失败时只更新 `last_error` / `last_attempt_at`，保留原摘要和原游标。
4. 不保存原始 LLM 输出，不保存媒体路径、XML、base64 或本机路径。
5. 当前表只保留一份当前摘要，避免引入暂时不需要的摘要版本管理。
6. 摘要字段只表达短中期对话状态；不得自动写入群永久记忆、成员画像或全局 shared memory。
7. `record_message()` / `record_assistant_reply()` 可向调用方返回来源表和行 ID；现有忽略返回值的调用保持兼容，摘要信号不得靠时间猜测刚写入的行。

### 4.3 更新触发

摘要更新采用按 room 合并的后台任务，不阻塞消息接收和回复：

1. `_record_inbound_message()` 成功取得归档行后，向滚动摘要 worker 提交 `stable_room_id + inbound source row` 信号。
2. `_record_assistant_reply()` 在确认真实发送成功并写入助手归档后，也提交当前 room 的 assistant source row 信号。
3. 同一 room 多个信号合并，worker 重新读取统一 timeline，不依赖某一个来源的单行 ID 判断全局新旧。
4. 默认累计至少 20 条 pending timeline event，且扣除 8 条未摘要近场尾巴后仍有 eligible events 时刷新。
5. 若距离上次摘要超过 30 分钟，则下一条新 timeline event 到达时允许降低累计阈值，但仍必须保留近场尾巴。
6. 每个 room 同时只允许一个摘要任务执行；全局默认一个 worker，避免抢占回复模型并发。
7. 服务停止时不强制清空或推进 pending 游标；下次新消息到达后继续检查。
8. 摘要任务属于低优先级后台任务。开始模型调用前检查 AgentBridge 是否存在活跃用户回复；存在时重新排队，不能与群聊正式回复争抢同一模型并发。
9. HTTP 429/5xx、供应商 circuit open 或连续超时后进入指数退避，默认从 60 秒起、最长 15 分钟；退避期间继续合并 room 信号，不循环重试。
10. 用户回复优先检查和退避状态必须进入 worker status，便于 Web 诊断摘要为何滞后。

### 4.4 摘要输入

摘要输入只包含：

1. 当前 room 已有滚动摘要。
2. 两个来源游标之后的新 timeline events，合并排序后默认最多 108 条，其中最后 8 条保留为未摘要近场尾巴。
3. 非文本消息统一投影为 `[image message]`、`[video message]` 等安全占位符。
4. 发送者使用当前群昵称；不得回退到其他群别名。
5. 机器人回复可作为上下文事实进入摘要，但必须标记为 assistant，不能冒充群友结论。
6. 当前用户消息、引用消息和最近机器人回复之间的先后关系必须保留，不能先按发送者聚合再摘要。

消息内容属于不可信数据。摘要 prompt 必须明确要求忽略消息中的指令、工具调用要求和角色伪装，只做事实压缩。

### 4.5 摘要输出

通过现有 `AgentLLMModel(Bridge())` 请求严格 JSON：

```json
{
  "summary": "当前群最近讨论的简短摘要",
  "active_threads": ["当前仍在继续的话题"],
  "attributed_claims": ["Alice 认为……，尚未得到其他人确认"],
  "open_loops": ["尚未回答的问题或未完成指代"],
  "recent_social_context": ["当前群正在延续的玩笑或互动背景"],
  "participants": ["群昵称"]
}
```

服务端必须校验：

1. 顶层必须是 JSON object。
2. 每个列表只接受字符串并去重、限长。
3. `summary` 默认不超过 1200 字符。
4. 检测模型错误 envelope；HTTP 408、429、5xx 等临时错误不得当作摘要正文解析。
5. JSON 无效、超长或包含传输层 XML 时，本轮失败且不推进游标。
6. `attributed_claims` 必须保留发言归属或不确定性；不得把单个群友的观点、玩笑或猜测改写为已确认事实。
7. `recent_social_context` 只保留理解当前互动所必需的非敏感短期信息，不推断现实关系、身份、健康、政治立场或其他敏感画像。

### 4.6 注入与降级

1. 只有 `contextual` 和 `recall` 模式注入 `<wechat-group-rolling-summary>`。
2. 普通自由回复 `recent` 模式只看最近原文，不注入滚动摘要。
3. 没有摘要、摘要状态异常或摘要覆盖范围过旧时，不临时同步调用 LLM；直接依赖最近原文。
4. 保留现有 `wechat_group_local_summary_enabled` 一版兼容读取，但新 UI 不再写入；迁移后由 `wechat_group_rolling_summary_enabled` 接管。
5. `<local-extractive-summary>` 在实现完成后停止生成；无需迁移，因为旧逻辑没有持久化摘要数据。
6. 新实现注入摘要时设置 `wechat_group_rolling_summary_injected = true`，并在一版兼容期同时设置 deprecated alias `wechat_group_local_summary_injected = true`；日志和新 UI 只展示新字段。
7. `wechat_group_context_policy_mode = legacy` 时继续执行旧 humanized builder 路径和旧 `<local-extractive-summary>`，且不启动滚动摘要模型任务、observe-only 隔离或 ambient capsule；`layered` 时执行本计划新路径。兼容期结束前不得删除 legacy 分支。
8. layered builder 异常时使用确定性的有界降级：
   - 直接 @ / quote self：保留 admin、mention/reply policy、persona、style、emotion、reference/multimodal 和当前原文；上下文依赖时最多补 6 条安全 timeline。
   - 普通自由回复：最多使用 6 条安全 timeline；timeline 构造也失败时保持沉默，不带盲目上下文发送。
   - 降级路径不注入 rolling summary、focus 或 archive evidence，不同步调用任何模型。
9. `wechat_group_humanized_context_enabled = false` 继续表示显式关闭新旧拟人化增强；只保留通道安全门禁、正确 receiver 和基础回复主链路。

## 5. 焦点栈调整

1. 焦点继续按 stable room 隔离，不恢复已废弃的 topic 表。
2. standalone 和普通自由回复不注入旧焦点消息。
3. `contextual` 模式只有关键词/引用明确命中当前焦点时才注入焦点块。
4. `recall` 模式允许显式回到栈内旧焦点。
5. `_touch_frame()` 使用本轮最新相关消息刷新 `summary`；必要时刷新 `title`，不得只更新时间。
6. 焦点过期同时考虑消息距离和时间：默认超过 8 条不相关消息或 10 分钟未命中即不再作为当前焦点。
7. 旧焦点消息与最近原文合并去重，不得替代最近原文。
8. 关键词仍使用本地确定性逻辑；本计划不引入中文分词依赖或额外焦点 LLM 调用。

## 6. 自由回复时效性与判定

### 6.1 Judge 输入

自由回复 judge 增加一个经过安全格式化的小窗口：

1. 当前候选消息。
2. 当前消息之前最近 3 到 5 条同 room 消息。
3. 引用消息的发送者和安全文本摘要。
4. 当前消息是否明确提到机器人、是否回复其他群友、是否已有群友回答。
5. 不注入滚动摘要、焦点、永久记忆或 90 天归档，保持 judge 轻量。

以下情况默认拒绝自由回复：

1. “为什么”“啥”“然后呢”“什么意思”等短句无法从小窗口确定指代。
2. 当前文本主要是引用群友的问题，引用后正文实际是在回答而不是提问。
3. 候选之后已有群友明确回答。
4. 当前消息明显是 A 对 B 的对话且没有请求机器人能力。

### 6.2 过时任务取消

1. 每个 selected room 维护递增 `room_revision`，每条有效入站消息后增加。
2. 自由回复 task 记录提交时的 revision、message_id、archive row ID 和 queued_at。
3. judge 通过后、调用 `_compose_context()` 前重新检查当前 room。
4. 过时判断分为硬取消和软过期，不能因为单纯超过 15 秒就取消。
5. 硬取消条件：候选之后已有明确回答、引用链明确切换、候选消息被撤回/失效，或 room 身份已经变化。
6. 软过期条件：`elapsed > stale_seconds` 且至少出现 1 条更新消息；或者更新消息超过配置阈值且本地相关性规则判断已切换话题。只有命中软过期组合条件才取消。
7. judge 通过后先读取截至当前时刻的新 timeline 快照，再决定取消或用最新快照构造上下文；不得继续固定使用原 `msg.create_time`。
8. 如果新消息只是补充同一问题且没有人回答，可继续生成，并把补充消息纳入 recent transcript。
9. `is_at = true`、`is_quote_self = true` 和拍一拍必回链路不受过时取消影响。
10. 同一 room 只允许一个自由回复 task 处于 judge/生成阶段；新候选可以替换 pending，但不能并发生成两个自由回复。该 single-flight 不覆盖 @、引用机器人和拍一拍必回链路。
11. 必回消息到达时递增 room revision，使未提交的自由回复 stale；已生成但尚未发送的结果必须在发送前再次校验 revision。无法取消的 Provider 请求可自然结束，但迟到结果不得发送。
12. worker 全局并发仍可服务不同 room，不把并发限制扩大到所有群；底层 Agent session 的历史安全锁继续保留，不新增复杂抢占执行器。

## 7. 配置设计

新增或调整以下配置：

```python
"wechat_group_shared_session": False,
"wechat_group_context_policy_mode": "legacy",  # 首个兼容发布；canary 显式 layered

"wechat_group_recent_context_limit": 20,
"wechat_group_recent_context_minutes": 1440,
"wechat_group_recent_context_max_chars": 4000,

"wechat_group_rolling_summary_enabled": False,
"wechat_group_rolling_summary_min_new_messages": 20,
"wechat_group_rolling_summary_recent_tail_count": 8,
"wechat_group_rolling_summary_max_interval_minutes": 30,
"wechat_group_rolling_summary_max_input_messages": 100,
"wechat_group_rolling_summary_max_chars": 1200,
"wechat_group_rolling_summary_timeout_seconds": 20,

"wechat_group_focus_stale_rounds": 8,
"wechat_group_focus_stale_minutes": 10,

"wechat_group_free_reply_stale_seconds": 15,
"wechat_group_free_reply_stale_message_count": 2,
"wechat_group_free_reply_judge_context_limit": 5,
"wechat_group_agent_history_idle_minutes": 10,
"wechat_group_ambient_continuation_enabled": True,
"wechat_group_ambient_continuation_ttl_minutes": 10,
"wechat_group_ambient_continuation_max_chars": 1200,
```

配置原则：

1. `wechat_group_shared_session` 只影响个人微信群；layered 模式缺失时默认 `False`，旧全局 `group_shared_session` 仅作显式旧配置兼容，其他渠道行为不得变化。
2. 滚动摘要首次发布默认关闭，只允许 stable room canary 显式开启；Web UI 明确提示该能力会增加少量模型请求。
3. 所有数字配置在 Web 保存接口进行 clamp，不能依赖前端输入约束。
4. 旧 `wechat_group_local_summary_*` 保留一版读取兼容，新配置保存后不再写旧键。
5. 不自动修改现有用户 `config.json`；缺失键使用上述服务端缺省值。
6. `wechat_group_free_reply_stale_seconds` 是软过期时间条件，不是单独的硬超时；Web 文案不得把它描述为“超过即丢弃”。
7. `wechat_group_agent_history_idle_minutes` 只控制回复恢复，不影响观察轮次持久化和自主进化计数。
8. `wechat_group_rolling_summary_max_input_messages` 表示单次实际送入摘要模型的 eligible event 上限；worker 可额外读取 `recent_tail_count` 条但不把尾巴送入摘要模型。
9. `wechat_group_context_policy_mode` 只允许 `legacy | layered`；首个兼容发布缺失时默认 `legacy`，canary 显式开启 layered，出现未知值必须回退 `legacy` 并记录 warning。
10. recent 保留 1440 分钟检索窗口，但 `recent` 最多注入 12 条、`contextual/recall` 最多注入 20 条，并统一受 4000 字符预算约束。
11. `wechat_group_ambient_continuation_enabled` 即使为 true，也只在 layered 下生效；legacy 不生成或注入 capsule。
12. 本计划不删除 legacy 分支。legacy 至少保留到 layered 成为默认后的一个完整稳定发布周期；是否移除必须另建计划并依据真实使用量和回滚记录决策。

## 11. 风险与控制

### 11.1 模型调用成本

- 风险：滚动摘要增加后台模型请求。
- 控制：默认 20 条消息或 30 分钟后才刷新；同 room 合并；全局单 worker；Web 明示状态和开关。

### 11.2 摘要事实失真

- 风险：LLM 摘要遗漏或误写群聊事实。
- 控制：最近原文始终优先；摘要块声明为辅助信息；事实冲突时以 recent transcript 为准；摘要不写入永久记忆。

### 11.3 跨群泄露

- 风险：stable/runtime ID 混用导致摘要串群。
- 控制：新摘要表只接受已确认 stable room；所有读取先按 stable room 精确过滤；新增双群隔离测试。

### 11.4 模型故障推进游标

- 风险：503/429 错误正文被当摘要保存，后续消息被跳过。
- 控制：复用已确认的错误 envelope 识别规则；失败不推进游标；测试覆盖重试成功。

### 11.5 自由回复过度沉默

- 风险：stale guard 和短句拒绝使机器人少接话。
- 控制：只约束普通自由回复；@、引用机器人、拍一拍必回完全不受影响；阈值可在 Web 调整。

### 11.6 跨渠道回归

- 风险：修改 `ChatChannel` / `AgentBridge` 影响其他渠道。
- 控制：所有新历史模式必须同时检查 `channel_type == wechat_group`；运行全量测试；其他渠道不读取新字段。

### 11.7 机器人忘记自己刚才的回复

- 风险：自由回复不恢复旧 Agent 历史后，后续自然追问失去机器人上一句内容。
- 控制：recent/judge/rolling summary 全部改用统一 room timeline；timeline 测试必须包含 assistant reply；引用机器人仍走 quote-self 必回链路。

### 11.8 观察轮次与回复恢复混淆

- 风险：`observe_only` 被错误恢复会重新引入旧话题；完全丢弃又会破坏 UI、审计和自主进化。
- 控制：ConversationStore 保存 visibility metadata，AgentInitializer 回复恢复时过滤，进化和历史 UI 使用明确的包含策略并分别测试。

### 11.9 缓存 Agent 内存污染或快照恢复失败

- 风险：只过滤数据库不能清理已缓存 `agent.messages`；异常路径漏恢复会破坏原 interactive session。
- 控制：所有 observe-only 运行在 `messages_lock` 和 session 级互斥下完成快照、捕获与 `finally` 恢复；正常、异常、取消和并发均有测试；不得通过 `clear_history=True` 实现隔离。

### 11.10 群聊关系丢失

- 风险：只有时间顺序而没有 addressee/quote，会把群友互聊误判为对机器人说。
- 控制：timeline 统一投影当前群 addressee、引用对象、reply-to-assistant；judge、stale 和最终 builder 复用同一投影；无法解析的原始 ID 不输出。

### 11.11 后台摘要影响正式回复时延

- 风险：滚动摘要与用户回复使用同一供应商，可能抢占并发或触发限流，导致接话变慢。
- 控制：摘要 worker 为低优先级；活跃用户运行期间让路；429/5xx/circuit open 指数退避；状态可观测且不阻塞当前消息。

### 11.12 continuation capsule 泄露工具结果

- 风险：工具结果可能包含路径、密钥、内部文件或写操作信息。
- 控制：只允许明确白名单的只读工具生成短摘要；高风险工具只记录工具名或完全跳过；capsule 有 TTL、stable room/member 隔离且不进入永久记忆。

## 12. 回滚方案

按以下顺序可低风险回滚：

1. 关闭 `wechat_group_rolling_summary_enabled`，保留 recent transcript。
2. 关闭 `wechat_group_focus_enabled`，避免焦点召回参与上下文。
3. 将自由回复 stale 阈值设置为宽松值，不影响 @ 必回。
4. 显式设置 `wechat_group_shared_session = true` 恢复微信群共享会话行为；旧全局键只作显式配置兼容。
5. 新摘要表可以保留，不影响旧版本读取；不要在紧急回滚中删除数据库文件。
6. 如果 observe-only 过滤异常，关闭自由回复并保留直接 @；不要通过清空全部会话数据库回滚。
7. 设置 `wechat_group_context_policy_mode = legacy` 可回退旧上下文装配；回滚不删除 observe-only metadata、摘要表或旧会话。
8. 关闭 `wechat_group_ambient_continuation_enabled` 可单独停用 capsule，不影响 recent timeline 和直接 @。

## 13. 手工验收场景

### 场景 A：短句不接旧话题

```text
群友 A：讨论硬件升级
机器人：参与一次
10 分钟后群里切换到钓鱼
同一群友：为什么
```

预期：机器人无法确认指代时不自由回复；不得继续硬件话题。

### 场景 B：最近原文优先于焦点

```text
旧焦点：发布排期
群友连续讨论三条新的团建消息
群友：刚才这个怎么定
```

预期：recent transcript 至少包含三条团建消息；旧发布焦点不得替代最近原文。

### 场景 C：滚动摘要承接较早内容

```text
群内累计讨论 30 条项目安排
最近 10 条转为执行细节
管理员：总结一下目前结论和待办
```

预期：最近原文提供执行细节，滚动摘要提供较早结论，归档证据按需补充；内容不重复堆叠。

### 场景 D：过时自由回复取消

```text
群友 A：有人知道怎么处理吗
机器人进入 judge
群友 B：我来处理，方法是……
群友 C：收到
```

预期：旧自由回复任务标记 `stale_candidate`，不再插入一条重复答案。

### 场景 E：群隔离

```text
群 A：讨论项目甲
群 B：询问刚才总结
```

预期：群 B 的 recent、summary、focus、archive 均不能出现群 A 内容。

### 场景 F：模型摘要故障

```text
摘要模型返回 HTTP 503 error envelope
下一批消息到达后模型恢复
```

预期：失败时保留旧摘要和旧游标；恢复后从未处理行继续摘要，不丢消息、不保存错误正文。

### 场景 G：自然承接机器人上一句

```text
机器人自由回复：这配置看着像缓存没刷新。
群友：那重启就行？
```

预期：第二轮 recent timeline 能看到机器人上一句；回复围绕缓存和重启，不回到更早话题，也不说“根据历史记录”。

### 场景 H：慢回复但现场未变化

```text
群友：这个报错有人了解吗
judge 和 Agent 总耗时 20 秒
期间群内没有新消息
```

预期：不能仅因超过 15 秒取消；仍发送自然短回复。

### 场景 I：拟人化能力非回归

```text
群内以轻松语气讨论一个普通问题
自由回复通过
```

预期：回复优先一句短句，不真实 mention，不暴露摘要/焦点/归档措辞；persona、style、emotion、回复清洗和 typing delay 继续生效，发送后更新情绪回复状态。

### 场景 J：观察历史与自主进化

```text
连续发生若干自由回复轮次
随后同一成员发起一个独立直接问题
```

预期：直接问题不恢复 observe-only 旧话题；历史 UI/审计仍能看到清洗后的轮次；scoped 进化用户轮次计数正常增加，但不主动向群推送结果。普通成员观察不能修改技能、全局记忆或 workspace。

### 场景 K：识别谁在对谁说

```text
Alice：@Bob 这个配置你改过吗
Bob 引用 Alice：我没动过
机器人处于自由回复开启状态
```

预期：timeline 明确 Alice -> Bob 和 Bob replying to Alice；judge 默认不让机器人插话，prompt 不暴露成员原始 ID。

### 场景 L：直接 @ 的省略句承接现场

```text
群友连续讨论一段部署失败日志
Alice：@机器人 你怎么看
```

预期：该消息进入 recent/contextual 而非 current-only；机器人结合最近现场回答。找不到唯一锚点时只做一句澄清，不编造原因。

### 场景 M：缓存 Agent observe-only 隔离

```text
同一 session 已有一个正常 direct reply 历史
中间发生一次自由回复
随后再次 direct reply
```

预期：自由回复运行时看不到旧 direct 历史；运行后原 direct 历史完整恢复；下一次 direct reply 看不到 observe-only 轮次；进化观察缓冲能看到该轮清洗文本。

### 场景 N：自由回复后的工具连续性

```text
机器人自由回复时使用网页搜索并给出一句结论
群友引用机器人：继续查一下后续
```

预期：当前轮注入未过期 ambient capsule，包含原问题、机器人结论和安全的只读工具摘要；不恢复原始 tool chain，不包含路径、密钥或写工具结果。

### 场景 O：兼容回滚

```text
layered 模式运行异常
管理员切换为 legacy
```

预期：旧 humanized 路径继续可用；已有摘要、observe-only 记录和旧会话不被删除；切回 layered 后可以继续增量处理。

## 14. 完成标准

只有同时满足以下条件才可将本计划标记为完成：

1. 四种上下文策略有确定性测试，普通自由回复不再无条件打开全部历史。
2. 统一 room timeline 同时包含群友消息和机器人真实回复，并通过 stable room 隔离测试。
3. recent transcript 不再被焦点消息替代，引用锚点和机器人上一句能够被安全补入。
4. room 级滚动摘要使用双来源游标，保留未摘要近场尾巴，可以失败重试并安全注入。
5. 自由回复默认不恢复旧 Agent 会话，但 observe-only 记录、历史 UI 和 scoped 被动学习/进化信号正常；普通成员不能修改技能、全局记忆或 workspace，直接 @ 多轮仍正常。
6. stale candidate 不进入最终回复生成；单纯耗时超过阈值且现场未变化时不能误取消。
7. 自由回复短句、无 mention、persona/style/emotion、`mark_replied()`、typing delay 和回复清洗非回归。
8. humanized builder 关闭或异常时，轻量降级和 @ 必回仍正常。
9. observe-only 在缓存 Agent 上完成锁内快照/恢复，正常、异常、取消和并发测试均通过；进化观察缓冲独立生效。
10. timeline 能表达当前群 addressee、引用对象和 reply-to-assistant，judge/builder 使用同一关系投影。
11. 省略式直接 @ 能读取 bounded recent；无法解析时按直接澄清/自由沉默处理。
12. ambient continuation 仅对白名单只读工具生成安全摘要，TTL 和跨群/跨成员隔离测试通过。
13. legacy/layered 切换、旧 metadata alias 和 builder 有界降级测试通过。
14. Web 可以配置并观察新能力，服务端完成 clamp。
15. stable room 隔离、媒体安全、错误 envelope 和路径安全测试通过。
16. 微信群要求测试和全量 Python 测试通过。
17. `AGENTS.md`、`CHANGES.md` 和本计划进度已同步回写。
18. 外部真实微信群完成至少一次场景 A、C、D、G、H、I、K、L、M、N 的手工验证。
