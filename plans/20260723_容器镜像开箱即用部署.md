# 容器镜像开箱即用部署实施计划

> **状态：远端镜像已发布，待容器与真实微信群人工验收**
>
> **面向 Agent 执行者：** 实施时必须使用 `superpowers:subagent-driven-development`（推荐）或 `superpowers:executing-plans` 按任务逐项执行，并持续回写本文档中的完成状态、实际改动、验证结果和剩余事项。

**目标：** 让 `yideng966/lightagent` Docker 镜像在 `linux/amd64` 与 `linux/arm64` 上同时具备完整的 Python、Node.js、个人微信群 sidecar 及其 npm 依赖，并通过明确的双目录挂载持久化配置、登录态、群数据库和 Agent workspace。

**架构：** 保持现有“Python 主进程通过 JSON Lines 管理同容器 Node.js sidecar”的边界，不拆分第二个服务。Dockerfile 使用 Node 官方镜像作为依赖构建阶段，将 `/usr/local/bin/node` 和锁定后的 `node_modules` 复制到 Python 运行镜像；Compose 将只读镜像内容、私有运行数据和 Agent workspace 分开管理；GitHub Actions 使用一个 Buildx 工作流发布统一的多架构标签。

**技术栈：** Docker / Docker Compose、Docker Buildx、GitHub Actions、Python 3.10、Node.js 22、npm `ci`、Wechaty、Python `unittest`、PyYAML。

## 一、背景与已确认事实

### 1. 当前发布链

- `docker/docker-compose.yml` 只有 `image: yideng966/lightagent`，没有 `build`，因此 Compose 本身不构建镜像。
- `.github/workflows/deploy-image.yml` 使用仓库根目录作为构建上下文，并使用 `docker/Dockerfile.latest` 发布 Docker Hub 与 GHCR 镜像。
- `.github/workflows/deploy-image-arm.yml` 单独发布带 `-arm64` 后缀的 GHCR 镜像，Docker Hub 的 `latest` 当前不是统一的多架构标签。
- `docker/Dockerfile.latest` 会把仓库内容放到 `/app`，但没有 Node.js，也没有执行 `npm ci`。
- `channel/wechat_group/sidecar/node_modules` 被 Git 忽略，GitHub Actions 的干净 checkout 不会把本地依赖带入镜像。

### 2. 当前容器路径

| 容器路径 | 当前内容 | 当前持久化状态 |
| --- | --- | --- |
| `/app` | 项目源码、sidecar 源码、内置技能、配置模板 | 镜像层，不通过 volume 挂载 |
| `/app/config.json` | 构建时复制的初始配置；Web 控制台默认写回此处 | 容器可写层，重建后丢失 |
| `/app/run.log`、`/app/user_datas.pkl` | 日志与应用数据 | 容器可写层，重建后丢失 |
| `/app/plugins` | 内置插件代码；当前非 frozen 模式仍有插件配置与安装写入 | 镜像层与容器可写层混用，需在本计划中拆分 |
| `/app/ms-playwright` | Playwright Chromium | 镜像层 |
| `/usr/local/lib/python3.10/site-packages` | Python 依赖 | 镜像层 |
| `/entrypoint.sh` | 容器入口脚本 | 镜像层 |
| `/home/agent/lightagent` | Agent workspace、记忆、会话库、知识库、技能、scheduler | 已映射 `./lightagent` |

| `/home/agent/.weixin_lightagent_credentials.json` | legacy 个人微信凭据 | 未映射，重建后丢失 |

### 3. Node.js 约束

- `wechaty`、`wechaty-puppet-wechat4u`、`file-box` 与 `memory-card` 当前锁定版本均要求 Node.js `>=16`。
- 本机 Node.js `v22.17.0` 下，sidecar 49 项 Node 测试通过，`wechaty`、`wechaty-puppet-wechat4u` 和 `file-box` 动态导入成功。
- `node:22-bullseye-slim` 与当前 `python:3.10-slim-bullseye` 均已确认提供 `linux/amd64` 和 `linux/arm64/v8` manifest，可在不升级 Debian 基线的前提下组合使用。

## 二、目标与非目标

### 目标

1. 用户只需拉取镜像并启动 Compose，不需要在宿主机安装 Node.js 或手工执行 `npm install`。
2. 最终镜像中的 Node.js 固定为 `/usr/local/bin/node`，继续兼容默认配置 `wechat_group_sidecar_node: "node"`。
3. sidecar 依赖固定安装到 `/app/channel/wechat_group/sidecar/node_modules`，由 Node.js 按现有工作目录自动解析。
4. Docker Hub 与 GHCR 的 `latest`、`master` 和 `v*` 标签同时包含 `linux/amd64`、`linux/arm64`。
5. `/app` 保持不可变，不使用源码 volume 覆盖镜像内容。
6. `./config` 持久化配置与私有运行状态，`./data` 持久化 Agent workspace。
7. Web 控制台保存的 `channel_type`、模型与通道配置在容器重建后仍然生效。
8. 个人微信群登录态、媒体、归档、稳定身份、群记忆、画像、焦点、风格、情绪和表情包数据库在升级后保留。
9. 插件运行配置、云端同步配置和用户安装的 legacy 插件不得继续写入 `/app`；持久化状态统一进入 `LIGHTAGENT_DATA_DIR`。

### 非目标

1. 不把 sidecar 拆成独立容器，不改 JSON Lines 协议。
2. 不修改 `WechatGroupChannel`、`Bridge`、Agent loop 或微信群业务逻辑。
3. 不修改桌面端 `desktop/`。
4. 不修改第三方 Wechaty 依赖源码，不维护 fork。
5. 不自动完成真实微信扫码；真实扫码、消息收发与 mention 仍需人工验收。
6. 不修改根目录旧 `Dockerfile`；发布链继续以 `docker/Dockerfile.latest` 为唯一目标。
7. 不持久化 `__pycache__`、临时转码文件、下载缓存等可再生成数据；“重建不丢失”仅指用户配置、凭据、登录态、数据库、用户安装扩展和 Agent workspace。

## 三、选定设计

### 1. 单镜像多阶段构建

采用以下文件布局：

```text
node:22-bullseye-slim 构建阶段
  /build/wechat-group-sidecar/package.json
  /build/wechat-group-sidecar/package-lock.json
  /build/wechat-group-sidecar/node_modules

python:3.10-slim-bullseye 最终阶段
  /usr/local/bin/node
  /app/channel/wechat_group/sidecar/*.mjs
  /app/channel/wechat_group/sidecar/node_modules
```

构建阶段执行 `npm ci --omit=dev` 和 `npm test`。最终阶段只复制 Node.js 可执行文件与生产依赖，不复制 npm CLI；最终阶段再执行一次核心模块动态导入，确保目标架构下 Node 运行库与依赖均可加载。

### 2. 双目录持久化

Compose 目标结构：

```yaml
services:
  lightagent:
    image: yideng966/lightagent:latest
    container_name: lightagent
    restart: unless-stopped
    security_opt:
      - seccomp:unconfined
    ports:
      - "9899:9899"
    environment:
      LIGHTAGENT_DATA_DIR: /home/agent/.lightagent
      WEB_HOST: "0.0.0.0"
      WEB_PASSWORD: "${WEB_PASSWORD:-__LIGHTAGENT_AUTO_GENERATE__}"
    volumes:
      - ./config:/home/agent/.lightagent
      - ./data:/home/agent/lightagent
```

路径职责：

- 宿主机 `./config`：配置与私有运行状态目录；名称虽为 `config`，实际还包括密钥、登录态、群数据库和媒体，必须整体备份。
- 宿主机 `./data`：Agent 数据工作区目录，包括记忆、知识库、技能、MCP 配置和 scheduler。
- `/home/agent/.lightagent`：`config.json`、`run.log`、`user_datas.pkl`、`.env`、浏览器 profile、个人微信凭据、微信群 MemoryCard、媒体和群数据库。
- `/home/agent/lightagent`：`AGENT.md`、`USER.md`、`RULE.md`、`MEMORY.md`、每日记忆、会话索引、知识库、技能、MCP 配置、scheduler 和临时文件。
- `/app`：只读应用代码、内置技能、sidecar 代码及依赖、Playwright 浏览器。

不得给 `/app` 增加 bind mount 或 named volume：bind mount 会立即遮蔽镜像内项目代码、Playwright 和 sidecar `node_modules`；named volume 首次复制后会长期遮蔽新镜像中的升级内容。发现仍写入 `/app` 的持久状态时，应把具体写路径迁到 `LIGHTAGENT_DATA_DIR`，不能用持久化整个应用目录规避路径问题。

`CHANNEL_TYPE` 不再由 Compose 环境变量固定覆盖。首次启动使用 `config-template.json` 中的 `channel_type: web`；用户在 Web 控制台连接个人微信群后，服务端将 `web,wechat_group` 写入持久化的 `config.json`。

### 3. Web 监听地址的作用域

`config.py` 与 `config-template.json` 继续保留 `web_host: ""`。空值是现有安全自动策略：配置了 Web 密码时自动监听 `0.0.0.0`，未配置密码时只监听 `127.0.0.1`。把全局模板直接改成 `0.0.0.0` 会同时影响源码部署，并可能默认暴露未鉴权控制台，因此不采用。

Docker Compose 必须显式设置 `WEB_HOST=0.0.0.0`，因为容器端口映射要求进程监听容器所有接口。`WEB_PASSWORD` 未设置或为空时，Compose 传入自动生成哨兵值，由 entrypoint 生成强随机密码、持久化到 `./config/config.json` 并打印到 Docker 日志；用户仍可在 Compose 同目录 `.env` 中提供固定密码。Docker 的公网监听策略由 Compose 负责，全局模板继续服务本地源码部署和桌面端的安全默认值。

### 4. 首次启动初始化

`docker/entrypoint.sh` 负责：

1. 默认并导出 `LIGHTAGENT_DATA_DIR=/home/agent/.lightagent`。
2. 创建数据目录和 Agent workspace。
3. 仅当数据目录没有 `config.json` 时，从 `/app/config-template.json` 初始化。
4. 未提供 `WEB_PASSWORD` 时，复用持久化配置中的密码；首次为空时生成强随机密码，并在每次启动日志中打印当前自动管理密码。
5. 不覆盖已有配置、MemoryCard 或 SQLite 文件。
6. 修正两个挂载根目录及新建配置文件的 `agent:agent` 所有权。
7. 降权为 `agent` 用户后，从 `/app` 启动 `python app.py`。

### 5. 统一多架构发布

保留 `.github/workflows/deploy-image.yml` 作为唯一镜像发布工作流：

```yaml
- name: Set up QEMU
  uses: docker/setup-qemu-action@v1

- name: Set up Docker Buildx
  uses: docker/setup-buildx-action@v1

- name: Build and push Docker image
  uses: docker/build-push-action@v3
  with:
    context: .
    file: ./docker/Dockerfile.latest
    platforms: linux/amd64,linux/arm64
    push: true
    tags: ${{ steps.meta.outputs.tags }}
    labels: ${{ steps.meta.outputs.labels }}
```

删除 `.github/workflows/deploy-image-arm.yml`，避免重复构建、架构后缀和标签状态分叉。现有 `latest-arm64`、`master-arm64`、`v*-arm64` 不再更新，新统一标签由 manifest list 自动选择宿主机架构。

## 七、风险与控制

- **Node 动态库缺失：** 最终镜像按 Node 官方 Bullseye Slim 运行要求安装 `libatomic1` 与 `libstdc++6`，并在每个目标架构构建阶段执行 `node --version` 和模块动态导入。
- **QEMU 构建时间增加：** 只保留一个发布工作流，避免当前 amd64 与 arm64 重复维护；不在本次顺带引入缓存策略。
- **配置被环境变量覆盖：** Compose 仅保留数据根、Web 监听和部署级 Web 密码，不再注入空模型/通道配置。
- **映射 `/app` 阻断升级：** 部署合同明确拒绝 `/app` volume；持久状态逐项迁移到数据根。
- **公网暴露未鉴权控制台：** 全局模板保留安全自动值；Compose 绑定 `0.0.0.0` 时由 entrypoint 保证密码非空，并把自动管理密码持久化后输出到容器日志。日志属于敏感信息，部署方应限制 Docker 管理权限和日志读取权限。
- **持久化目录权限：** entrypoint 只初始化缺失文件并修正挂载根目录权限；测试必须覆盖 `agent` 用户可写性。
- **敏感文件进入镜像：** `.dockerignore` 排除 `.env`、`config.json`、运行数据和本地依赖。
- **历史 ARM 标签停止更新：** 文档明确迁移到无后缀统一标签，历史标签暂不删除。
- **微信群真实链路无法自动化：** 自动化只验证进程、模块、路径和持久化；扫码、登录恢复和群消息仍保留人工验收记录。
