>
> 计划日期：2026-07-29
>
> 适用范围：个人微信群渠道、Agent 会话恢复、群聊上下文装配和自由回复调度
>
> 历史依据：`20260714_CowAgent与BaiLongmaPro群聊机器人对比分析.md`
>
> 取代计划：`20260714_微信群上下文分层与滚动摘要优化.md`、`20260715_微信群机器人智能增强完整开发计划.md`

## 0. 结论与可行性

本次重构**可行，且比继续在 `WechatGroupHumanizedContextBuilder` 上叠加布尔开关更稳妥**。LightAgent 已经具备 stable room/member、入站归档、助手回复归档、成员级 session、统一文本模型路由、Agent 持久化和较完整的回归测试，重构不需要更换模型、数据库或消息渠道。

建议采用“保留主链路、重构上下文与会话状态”的方案：

1. 保留 `Wechaty sidecar -> WechatGroupChannel -> ChatChannel -> Bridge -> Agent` 主链路。
2. 借鉴 BaiLongmaPro“每轮从持久化现场重建请求”的思路，不依赖缓存 Agent 自己记住群里发生了什么。
3. 将 room timeline、上下文策略、会话线程和单次 LLM 请求拆成四个独立概念。
4. 将当前破坏性的 `fresh` 改为“创建新线程”，不再推进原 session 的永久恢复边界。
5. 默认仍按 `stable_room_id + stable_member_id` 隔离；显式共享配置只作为兼容能力。
6. 所有上下文都形成不可变、可审计、有预算和 revision 的请求快照；自由回复发送前按最新 room revision 复核。

风险等级为中高，主要风险位于共享的 `AgentBridge` 和 `ConversationStore`。控制方式是让新增 thread 参数默认留空，其他渠道保持原行为；微信群 V2 通过单一功能开关灰度，不做一次性替换，也不删除旧会话数据。

## 1. 当前基线与旧计划修正

旧计划形成于 2026-07-14 至 2026-07-15，以下事项已经完成，不应再次开发：

| 能力 | 当前状态 | 本计划处理方式 |
|---|---|---|
| 微信群默认 session 隔离 | 已按 `stable_room_id + stable_member_id` 生效，缺失配置默认不共享 | 保留，改名为 owner session 语义 |
| `fresh / interactive_session / observe_only` | 已部分落地 | 迁移为非破坏式 thread action，废止 `fresh` 的清边界语义 |
| 自由回复近场关系判断 | Scorer/Judge 已能读取安全 timeline | 统一改为消费同一请求快照 |
| 入站与助手最近 timeline | `get_recent_conversation_messages()` 已合并两类记录 | 升级为正式 TimelineService，并补关系字段、cursor 和 revision |
| stable 画像数据迁移 | 2026-07-20 已选择备份后清空重建 | 不再迁移旧 runtime 画像 |
| 请求温度、结构化 Scorer、主备模型故障转移 | 相关链路已完成主要修复 | 只补请求快照一致性，不重复重写 |
| 直接 @ 注入群上下文 | 2026-07-28 已完成 | 从当前 24 小时/100 条倾向改为 V2 有界 recent 场景尾巴 |

仍未闭环的问题：

1. `fresh` 会清空缓存 Agent 历史，并调用 `ConversationStore.clear_context()` 永久推进 `context_start_seq`。这不是“本轮不读旧历史”，而是改变了未来可恢复范围。
2. `session_id` 同时承担排队、Agent 缓存、历史持久化、记忆路由、取消和 UI 会话等职责，无法准确表达“同一群友的新话题”和“继续上一条回答”。
3. direct reply、recent、archive evidence、本地抽取摘要、focus 和 Agent 历史分别取数，可能重复、冲突或使用不同时间截面。
4. direct reply 当前可能注入 24 小时最多 100 条原文，同时再注入归档证据和本地抽取摘要，成本和噪声偏高。
5. unified timeline 目前主要服务自由回复；直接 @、焦点、摘要、回溯和最终 Agent 尚未统一消费。
6. 同一群内不同成员拥有不同 owner session，可以并发进入 Agent；当前缺少 room 级顺序、revision 和发送前复核。
7. 工具链只在单次 Agent loop 内完整存在；下一轮“继续查”没有按群、成员和线程隔离的安全 continuation capsule。

## 2. BaiLongmaPro 会话与上下文机制复核

### 2.1 实际机制

BaiLongmaPro 并没有复用一个 Provider 侧 LLM 会话。其 `newSessionRef()` 每轮生成新的 `session_<time>_<counter>`，只用于追踪、事件和记忆识别，不参与模型上下文恢复。

每次请求的真实流程是：

```text
群消息到达
  -> 写入群归档 / conversations
  -> 构造本轮群 Prompt（24 小时最多 100 条群消息及多类记忆）
  -> 显式 @ 使用 runtime room + runtime member 作为 fromId
     自由接话使用 runtime room 作为 fromId
  -> pushMessage(noPersist=true)
  -> runInjector 按 fromId 读取近 24 小时最多 20 条 conversations
  -> buildLLMMessages 每轮重新组装完整 messages
  -> callLLM 在本轮 messages 内执行多轮工具循环
  -> send_message 把助手文本写回 conversations
  -> 另将助手回复写回群归档 / 群记忆系统
```

关键证据：

- `BaiLongmaPro/src/core/turn-state.js`：`newSessionRef()` 只是每轮 trace reference。
- `BaiLongmaPro/src/memory/injector.js`：按 `senderId` 调用 `getRecentConversation(senderId, 20, 24)`。
- `BaiLongmaPro/src/social/wechat-groups.js`：群 Prompt 读取 24 小时最多 100 条记录。
- `BaiLongmaPro/src/social/wechaty-duty-group.js`：显式 @ 与 ambient 使用不同 runtime target，并以 `noPersist: true` 入队。
- `BaiLongmaPro/src/core/context-builder.js`：每轮从 `conversationWindow` 重建 `messages`。
- `BaiLongmaPro/src/llm.js`：工具调用历史只在当前 `callLLM()` 循环内追加。
- `BaiLongmaPro/src/social/wechaty-duty-worker-pool.js`：显式 @ 优先于 ambient，但没有同群 single-flight。

### 2.2 两边会话对比

| 维度 | LightAgent 当前 | BaiLongmaPro 当前 | 本计划目标 |
|---|---|---|---|
| Provider 会话 | Agent 每轮发送完整 messages；`session_id` 主要是本地状态键 | 每轮发送重建后的 messages；`newSessionRef` 只是追踪 ID | 正确性只依赖本地快照，不依赖 Provider 隐式会话 |
| 会话 owner | 默认 stable room + stable member，可显式按群共享 | 显式 @ 为 runtime room + member，ambient 为 runtime room | owner 继续使用 stable scope |
| 新话题 | `fresh` 清内存并永久推进恢复边界 | 没有正式的新线程状态；主要靠厚群上下文覆盖 | 创建新 thread，不修改旧 thread 和恢复边界 |
| 继续对话 | `interactive_session` 复用同 owner 的当前 Agent | 依赖同 target 的少量助手历史和每轮群上下文 | 通过 quote anchor 或短时 active thread 精确恢复 |
| 普通自由接话 | `observe_only` 快照执行后恢复 | ambient room target，可积累 room 级助手历史 | observe-only，不创建或污染交互 thread |
| 群现场 | 多个消费者分别读取，直接 @ 可达 100 条 | 每轮固定准备 100 条群现场 | 每轮准备不可变、有界、去重的 ContextSnapshot |
| 工具续接 | 不恢复原始工具链，也没有正式 capsule | 本轮工具 loop 完整；全局 `lastToolResult` 可进入后续 tick | 只保存 scoped、TTL、只读安全 capsule |
| 并发 | owner session 内串行，同群不同成员可并发 | 全局 worker 并发，mention 优先，无同群锁 | room single-flight，显式 @ 优先，ambient 可取消 |

### 2.3 借鉴与拒绝照搬

借鉴：

1. 每轮调用前从数据库重建群现场，而不是把群连续性押在 Agent session 上。
2. 当前消息到达即归档，助手真实发送后写回同一 room timeline。
3. 显式 @ 优先于 ambient，自由接话有 TTL 和过期丢弃。
4. 高频意图先分类，减少通用 Agent 在无关工具之间选择。
5. 工具循环在单次请求内保持完整，下一轮只带安全结果摘要。

不照搬：

1. 不使用 runtime room/member 作为长期会话主键。
2. 不固定注入 24 小时 100 条消息。
3. 不使用 `noPersist` 造成用户问题和助手历史不对称。
4. 不使用全局 `state.lastToolResult`、全局 focus 或其他跨群共享状态。
5. 不允许同一 room 的多个最终回复并发生成和乱序发送。
6. 不让意图路由器绕过 LightAgent 的 Bridge、权限门禁和 Agent 主链路直接生成通用回复。

## 3. 必须拆开的五个概念

| 概念 | 唯一职责 | 建议标识 |
|---|---|---|
| Request | 一次 LLM 调用和取消单位 | `request_id` |
| Room timeline | 群里真实发生的入站与已发送助手事件 | `stable_room_id + revision` |
| Owner session | 排队、权限、记忆、UI 和取消的归属 | 默认 `stable_room_id + stable_member_id` |
| Agent thread | 可选择新建、继续或恢复的短期交互链 | `thread_id` |
| Provider transport | HTTP/SSE 连接与模型调用 | 不作为对话正确性的状态源 |

硬规则：

1. room timeline 不能等同于 Agent thread。群友之间的消息属于现场，但不能自动写入某个成员与机器人的交互历史。
2. owner session 不能等同于 thread。同一群友可以连续开启多个话题，旧线程必须保留但不能污染新线程。
3. `request_id` 不能复用为 thread ID。一次线程可包含多次请求。
4. Provider 即使将来支持 server-side thread，也只能作为缓存优化；本地消息快照必须足以恢复。
5. 模型不能传入或选择 room、owner session、thread ID；这些值只能由服务端策略生成。

## 4. 目标架构

```text
Wechaty sidecar
  -> WechatGroupChannel 解析与 stable identity
  -> inbound archive
  -> WechatGroupTimelineService
       -> inbound + sent assistant + quote + mention + addressee
       -> RoomRevision(inbound_cursor, assistant_cursor)
  -> WechatGroupRequestSnapshotFactory
       -> 当前原文、权限、关系型 scene tail、revision
  -> WechatGroupIntentRouter
       -> 只分类与建议工具集合，不直接发送通用回复
  -> WechatGroupContextPolicy
       -> minimal / recent / contextual / recall
  -> WechatGroupSessionPolicy
       -> new_thread / resume_thread / observe_only
  -> WechatGroupContextEngine
       -> 去重、预算、顺序、安全投影，生成不可变 ContextSnapshot
  -> WechatGroupReplyCoordinator
       -> room single-flight；mention > ambient；stale revalidation
  -> ChatChannel -> Bridge -> Agent
       -> owner_session_id 管权限、记忆和归属
       -> thread_id 管 LLM 文本历史
       -> request_id 管取消和追踪
  -> 清洗并真实发送
  -> sent assistant 写回 timeline，并绑定 thread_id
  -> 保存安全 continuation capsule、指标和审计
```

职责边界：

- `WechatGroupTimelineService` 只负责事实事件和安全关系投影。
- `WechatGroupContextPolicy` 只决定读取哪些层，不决定会话复用。
- `WechatGroupSessionPolicy` 只决定新建、恢复或 observe，不决定上下文厚度。
- `WechatGroupIntentRouter` 只返回 route 和工具建议，不执行通用回复。
- `WechatGroupContextEngine` 只装配当前请求，不持久化增强 Prompt。
- `humanized_context.py` 降为兼容门面，V2 下只调用 Context Engine。

## 5. 会话线程状态机

### 5.1 标识模型

```text
owner_session_id = wechat_group:<stable_room_id>:<stable_member_id>
thread_id        = wgt_<random-or-monotonic-id>
request_id       = 当前已有请求追踪 ID
room_revision    = inbound_cursor + assistant_cursor
```

显式共享配置开启时，`owner_session_id` 可为 `wechat_group:<stable_room_id>`，但 thread 仍必须记录真实发起成员和收件关系，不能把某成员的敏感上下文默认暴露给全群。

### 5.2 Thread action

| action | 是否读取旧 Agent 历史 | 是否写入交互 thread | 是否改变旧 thread | 典型场景 |
|---|---:|---:|---:|---|
| `new_thread` | 否 | 是，创建并激活新 thread | 否 | 独立问题、明确“新话题” |
| `resume_thread` | 是，只读目标 thread | 是，追加到目标 thread | 否 | 引用机器人、明确“继续”、短时追问 |
| `observe_only` | 否 | 否，只写审计可见记录 | 否 | 普通 ambient 接话、开放群问题 |

`fresh` 仅作为 legacy 输入别名，在 V2 中映射为 `new_thread`；不得再调用 `clear_context()`。`interactive_session` 映射为 `resume_thread`，`observe_only` 保持原语义。

### 5.3 选择优先级

按以下顺序确定 thread action，禁止由模型自由判断：

1. 当前消息精确引用机器人历史回复，且 anchor 能映射到同一 stable room 下允许恢复的 thread：`resume_thread(anchor_thread_id)`。
2. 文本明确表达“继续你刚才的回答 / 接着查 / 上一个结果”，同一 stable member 存在未过期 active thread：`resume_thread(active_thread_id)`。
3. 当前消息紧跟机器人回复、关系字段确认是 reply-to-assistant，且 active thread 未过期：`resume_thread`。
4. 文本明确表达“新话题 / 忽略前面的对话 / 重新开始”：`new_thread`。
5. 独立 direct @ 或明确点名机器人但不是承接：`new_thread`。
6. 普通自由回复、面向全群的 ambient 参与：`observe_only`。
7. 无法确认承接对象时：direct @ 创建新 thread 并在必要时澄清；ambient 保持沉默，不猜测旧 thread。

默认 follow-up TTL 建议为 15 分钟。精确 quote anchor 优先于 TTL；若引用回复已超出保留期或无法映射，则把安全引用内容作为 contextual 证据并创建新 thread，不伪造恢复。

### 5.4 持久化与缓存

在 `ConversationStore` 中增加可选 thread 维度，默认值为空以保持其他渠道兼容：

```text
conversation_threads
  session_id
  thread_id
  channel_type
  stable_room_id
  stable_member_id
  status: active | closed | expired
  root_message_id
  last_message_id
  last_assistant_reply_id
  created_at
  last_active_at
  expires_at
  revision

messages
  + thread_id TEXT NOT NULL DEFAULT ''
  + INDEX(session_id, thread_id, seq)
```

规则：

1. `session_id` 继续作为 owner，不改 memory route、权限或 UI 所属关系。
2. `thread_id` 只控制模型历史读取和追加。
3. `AgentBridge` 缓存键改为 `(owner_session_id, thread_id)`，但 `AgentInitializer` 的工具和记忆仍使用 owner session。
4. 其他渠道不传 `thread_id`，行为与当前完全一致。
5. Agent 缓存采用有界 LRU；被淘汰 thread 可从 text-only 持久化历史恢复。
6. 持久化只保留原始用户文本和最终助手文本；增强块、thinking、原始 tool chain、runtime ID 和媒体路径不得写入 thread 历史。
7. `context_start_seq` 只保留给显式清除历史等旧功能；新开 thread 不修改它。
8. thread 消息 extras 保存同 room 的 `source_event_id`；助手归档行保存 `thread_id`，用于恢复时跨 Agent history 与 room timeline 精确去重。
9. Web 历史和审计仍按 owner session 聚合展示，不把内部 thread 注册成多个用户可见 session；模型加载才按 `thread_id` 过滤。
10. 记忆路由、自主进化和权限判断继续使用 owner 与 stable scope，不因创建新 thread 被误判为新用户或新群。

### 5.5 Provider 会话规则

当前主流 Agent Provider 调用以完整 `messages` 为事实来源，`session_id` 最多作为本地或供应商附加字段。V2 必须保证：

1. 每次主备候选都从同一规范化 RequestSnapshot 独立构造 messages。
2. 不依赖 HTTP 连接、SSE 连接或 Provider 隐式 thread 保存上下文。
3. Provider 切换后可仅凭本地 thread 文本历史继续。
4. 若未来接入 Provider 原生 thread ID，必须绑定本地 `thread_id`，并在失效时回退完整 messages；不得改变本地状态机语义。

### 5.6 旧会话兼容

1. 不删除旧 `wechat_group:<room>:<member>` 或显式 room shared session。
2. V2 上线后，下一条独立 direct @ 创建新 thread；旧无 thread 行只在 legacy 模式恢复。
3. 已推进的 `context_start_seq` 不自动回拨，避免复活用户曾主动清除的历史。
4. 旧 `observe_only` extras 继续用于 UI 和审计，但不进入任何新 thread。
5. 回滚到 legacy 时仍可读取旧 session；V2 thread 数据保留但不参与 legacy 请求。

## 6. Context Engine V2

### 6.1 上下文模式

借鉴 BaiLongmaPro“每轮都看现场”的体验目标，但将范围控制在有界 scene tail：

| 模式 | 适用场景 | room scene tail | 其他材料 | 默认 thread action |
|---|---|---|---|---|
| `minimal` | 确定性管理命令、明确要求忽略上下文 | 0 至 4 条 | 权限、persona、当前消息 | `new_thread` 或既有命令语义 |
| `recent` | 普通自然语言 direct @、ambient 候选 | 12 条 / 30 分钟 | 相关群记忆、画像 | direct 为 `new_thread`，ambient 为 `observe_only` |
| `contextual` | 短追问、引用、图片、继续、指代 | 24 条 / 2 小时 | quote anchor、相关 focus、可选 capsule | `resume_thread` 或 `new_thread` |
| `recall` | 总结、谁说过、历史约定、时间范围查询 | 最近 20 条 | 检索证据、滚动摘要、群记忆 | 非明确回指机器人时 `new_thread` |

自然语言 direct @ 默认至少使用 `recent`，不再依赖关键词决定“完全没有群现场”；这正是从 BaiLongmaPro 借鉴的核心。`minimal` 只用于可确定的命令或用户明确要求，不作为普通问答默认值。

### 6.2 不可变请求快照

每个请求在进入 Agent 前生成一次：

```text
WechatGroupRequestSnapshot
  request_id
  stable_room_id
  stable_member_id
  runtime delivery snapshot       # 只供发送，不进 Prompt
  current_message_id
  current_created_at
  room_revision_before
  relation: actor / addressee / quote / reply_to_assistant
  context_mode
  thread_action
  owner_session_id
  thread_id
  safe_timeline_events[]
  selected_memories[]
  selected_profiles[]
  archive_evidence[]
  rolling_summary
  continuation_capsule
  section_budgets
  diagnostics
```

Scorer、Judge、Context Engine、Agent 和发送前复核必须引用同一个 `request_id`。队列等待后应重建快照，而不是继续使用入队时的旧 Prompt。

### 6.3 Timeline 事件契约

正式 TimelineService 基于现有 `get_recent_conversation_messages()` 扩展：

```text
event_id                 # 服务端去重，不进入 Prompt
source_type: inbound | assistant
source_row_id            # 服务端 cursor，不进入 Prompt
actor_type: member | assistant
actor_display_name
addressee_display_names[]
quote_actor_display_name
quote_excerpt
quote_message_id         # 服务端 anchor，不进入 Prompt
is_reply_to_assistant
is_directed_to_assistant
created_at
safe_text
safe_media_refs[]
thread_id                # assistant 事件可绑定，不进入 Prompt
```

`RoomRevision` 使用双游标 `(last_inbound_id, last_assistant_id)`；不要求为此引入新的全局计数器。查询必须优先严格匹配 `stable_room_id`，仅对记录自身 stable 字段为空的 legacy 行允许 runtime fallback。

助手事件只有在真实发送成功后才能进入 timeline。若需要将微信 quote 的 `message_id` 精确绑定 thread，实施前必须先验证当前 Wechaty/puppet 的发送返回值；无法得到稳定 outbound ID 时，只使用同 room/member active thread 和安全 quote 文本降级，禁止按相似文本跨群猜测。

### 6.4 装配顺序与事实优先级

```text
硬权限 / mention 验证 / reply policy
persona
较旧群记忆与成员画像
recall evidence（recall only）
rolling summary（contextual / recall）
focus（只作辅助）
recent room timeline（最接近当前消息的事实块）
continuation capsule（resume only）
quote / multimodal / reference policy
当前用户原文
```

事实优先级：当前消息 > 更新且可追溯的原始 timeline > quote 原文 > 群记忆/画像 > rolling summary > focus > 远期归档。persona、style 和 emotion 只能影响表达，不能覆盖事实。

### 6.5 预算与去重

首版建议使用内部常量并记录指标，不立即把所有数字暴露到 Web：

| 部分 | 初始上限 |
|---|---:|
| `recent` scene tail | 12 事件、30 分钟、2400 字符 |
| `contextual` scene tail | 24 事件、2 小时、4800 字符 |
| recall evidence | 12 个命中、6000 字符 |
| 群记忆 + 画像 | 3000 字符 |
| rolling summary | 2500 字符 |
| continuation capsule | 1200 字符 |
| 全部微信群动态块 | 12000 字符，并继续受 Agent token 上限约束 |

去重规则：

1. timeline 事件以 `source_type + source_row_id` 去重。
2. rolling summary 只覆盖其双 cursor 之前的事件，recent tail 只读取 cursor 之后或最后有界尾巴。
3. archive evidence 命中 recent 已有事件时不重复渲染。
4. 当前 `message_id` 始终从历史块排除。
5. 同一事实在群记忆和原始 timeline 冲突时保留两者来源，但 Prompt 明确采用较新原始事件。
6. `resume_thread` 时，从 room timeline 排除已存在于目标 thread 的 `source_event_id`，但保留两个 thread turn 之间其他群友新增的事件。
7. 所有历史消息块都标记为不可信现场资料；其中出现的命令、Prompt 或工具要求不得提升权限或替代当前请求。

## 7. Room 级调度与时效性

新增 `WechatGroupReplyCoordinator`，解决成员级 session 无法保证群内顺序的问题：

1. 每个 stable room 同时最多一个最终 LLM 回复在生成或发送。
2. 队列优先级：显式 @ / 引用机器人 > 管理员明确命令 > ambient。
3. 显式请求按到达顺序保留，不因后续消息静默覆盖。
4. ambient 每个 room 只保留最新候选，可防抖、TTL 过期和主动取消。
5. worker 真正开始前重建 RequestSnapshot，并记录 `room_revision_before`。
6. 发送前再次读取 `room_revision_after`：
   - ambient revision 变化时重新判断；无法确认仍适合则取消。
   - direct @ 不直接丢弃；若引用对象或关键事实已变化，最多重建一次上下文再生成。
7. 已取消或过期请求不得持久化助手回复、推进 thread、生成 capsule或触发主动学习结果。

不通过提高 `concurrency_in_session` 解决吞吐；那会引入同一 Agent 历史竞争。room coordinator 与 owner session 队列的锁顺序必须固定，并有死锁回归测试。

## 8. 高频意图与工具收窄

借鉴 BaiLongmaPro 的前置路由，但保持 LightAgent 主链路：

```text
WechatGroupIntentRoute
  route: chat | summarize | recall | image_understand | image_generate |
         sticker | link_read | scheduler | memory_query | unknown
  confidence
  evidence
  required_context_mode
  suggested_tool_names[]
```

规则：

1. 图片理解、生图、群总结、历史检索、链接读取等已有明确入口优先用确定性规则。
2. 规则不确定时才调用低温结构化分类器；分类失败回退 `chat`，不能阻断 direct @。
3. route 只收窄工具候选，最终工具集合必须再经过管理员硬门禁和现有权限过滤。
4. 除已有且确定性的渠道适配外，router 不直接调用模型生成并发送通用回复。
5. 工具 schema 的裁剪结果写入 diagnostics，不把权限原因或内部工具名暴露给群成员。

## 9. Continuation capsule 与滚动摘要

### 9.1 安全 continuation capsule

借鉴 BaiLongmaPro 的“下一轮可见最近工具结果”，但改为严格 scoped：

```text
thread_id
stable_room_id
stable_member_id
request_id
created_at / expires_at
tool_name
safe_argument_summary
status
safe_result_summary
source_urls[]             # 仅公开、已清洗 URL
```

仅对白名单只读工具生成，默认 TTL 10 分钟。不得保存原始 tool messages、shell 输出、文件正文、密钥、cookie、本机路径、跨群结果或管理员写操作参数。只有 `resume_thread` 且权限复核通过时注入。

### 9.2 Room rolling summary

滚动摘要基于统一 inbound + sent assistant timeline 和双 cursor：

1. 只压缩 recent tail 之前的较早事件。
2. 输入和输出均按 stable room 隔离。
3. 失败不推进 cursor、不覆盖旧摘要。
4. 摘要不是群永久记忆，也不直接进入画像。
5. recall 时优先返回原始证据；摘要只补背景。
6. 后台低优先级生成，不增加 direct @ 首包时延。

## 13. 验证矩阵

### 13.1 Session/thread

- 独立 direct @ 创建新 thread，同时仍能看到有界 room recent。
- 创建新 thread 不改变旧 thread 的消息、状态或 `context_start_seq`。
- “继续刚才”只恢复同 room/member 的 active thread。
- quote-self 优先恢复 anchor thread；无法映射时安全降级为新 thread。
- 普通 ambient 不读取、不追加 active thread。
- 同名成员、不同 stable member、不同 room、不同 account 均不能串 thread。
- 显式 room shared 模式仍受 addressee 和权限限制。
- Agent cache 淘汰和进程重启后恢复结果一致。
- 主模型切备用模型后使用相同 thread 文本快照。

### 13.2 Context/timeline

- inbound 与成功助手回复按统一时序出现。
- 当前消息不在 recent 中重复。
- recent、summary、archive evidence 不重复同一来源事件。
- Agent thread 与 room timeline 不重复注入同一 user/assistant 事件，二者之间的新群消息仍保留。
- direct @ 的短指代能承接最近群现场，独立问题不承接旧 Agent thread。
- quote、mention、addressee 和 assistant 角色渲染正确。
- Prompt 中不存在 stable/runtime ID、XML、base64、本机路径和 Secret。
- 长消息、媒体和 100 条活跃群聊仍受预算约束。

### 13.3 并发与时效

- 同 room 两个 direct 请求按到达顺序处理。
- direct 到达时优先于尚未开始的 ambient。
- ambient 排队后有人回答或 room revision 改变时被取消。
- 不同 room 可并行，单 room lock 不扩散为全局锁。
- 取消、超时、发送失败不会写 assistant timeline、thread 或 capsule。

### 13.4 工具与安全

- 普通成员 route 后仍无写记忆、写文件、scheduler 修改和配置工具。
- 工具 chain 只在本请求内恢复；下一请求只看到白名单 capsule。
- capsule 过期、跨 thread、跨 member、跨 room 均不可注入。
- recall 和 summary 的模型错误 envelope 不当正文、不推进 cursor。
- 每个 fallback candidate 从规范化请求快照独立构造。

## 14. 完成标准

1. 新话题不再通过清空或推进旧 session 恢复边界实现。
2. 独立 direct @、明确继续、quote-self 和 ambient 的 thread action 可解释且可测试。
3. 所有自然语言 direct @ 至少看到有界、最新、同 room 的安全 scene tail。
4. room timeline 成为 direct、free reply、focus、summary、recall 和 Agent 的统一事实来源。
5. 同 room 不再出现并发生成导致的乱序回复；过时 ambient 不发送。
6. Prompt 动态块不超过预算，不重复注入同一事件。
7. 用户原文、最终助手文本、审计记录、Agent thread 和 room timeline 的持久化边界明确。
8. Provider 切换、Agent cache 淘汰和进程重启不改变 thread 恢复语义。
9. 工具续接不恢复原始 tool chain，不泄露跨群、文件或权限信息。
10. stable room/member 隔离、管理员硬门禁和安全投影回归为零失败。
11. Web/IM/CLI 其他渠道的既有 session 行为不变。
12. 对应测试、文档、`CHANGES.md` 和本计划实施回写全部完成。

## 15. 回滚方案

1. 将 `wechat_group_context_engine_mode` 切回 `legacy`，停止读取 V2 snapshot/thread。
2. 单独关闭 room single-flight、rolling summary 或 continuation，保留已写数据。
3. 新 thread 表和 `messages.thread_id` 只做向后兼容扩展，回滚不删除字段或数据。
4. Agent cache 可安全清空并从持久化文本恢复，不清空 ConversationStore。
5. 不回拨 stable identity，不启用 runtime 跨群 fallback，不删除群归档、画像或记忆。
6. 数据迁移脚本必须支持 dry-run、备份和幂等；本计划首轮不需要迁移历史画像。

- `ConversationStore` 增加兼容的 `thread_id` 与 `conversation_threads`，Agent 缓存键改为 `(owner_session_id, thread_id)` 并使用 128 项默认 LRU；其他渠道不传 thread，仍按旧 session 恢复。
- V2 thread 使用发送确认后的两阶段提交：Agent 只暂存 pending 的“首个用户原文 + 最终助手文本”，模型恢复、Web 历史和 timeline 去重均过滤 pending；只有 sidecar 返回 `sent` 才在同一事务确认消息并创建或续期 thread，再保存 capsule。失败、未知、超时、清洗为空、静默抑制和 stale ambient 都删除 pending 并从已提交文本历史重载缓存。
- 助手 timeline 只记录确认发送后的事件，确认时把实际发送的清洗正文和 `source_event_id` 写回 thread；工具原始消息、thinking、runtime ID 和媒体路径不进入可恢复 thread。
- Web“群聊 -> 拟人化上下文”增加 V2 模式、session 作用域、thread TTL、room single-flight、rolling summary 和 continuation 配置；首版仍默认 `legacy`，summary/capsule 默认关闭。

与原计划的差异：

- 未单独创建 `wechat_group_context_engine.py`；V2 装配由 `WechatGroupHumanizedContextBuilder` 作为兼容门面调用 Snapshot、Policy、Timeline 和各独立服务，避免再增加一层无状态转发类。
- 当前 Wechaty/puppet 只能通过 `send_result` 确认成功或失败，不能返回可稳定持久化的 outbound message ID；因此不伪造 quote anchor，quote-self 使用同 room/member 的 active thread 和安全引用文本降级。
- IntentRouter 首版只落地确定性高频规则。低温分类器继续留空，避免为不确定分类增加一次 LLM 延迟和新的失败面；普通请求回退通用 Agent。
- Scorer/Judge 尚未改为直接持有同一个 Snapshot 对象；它们继续使用现有同群安全归档尾巴。direct 关键事实变化后的“最多重建一次”也未实现，本版只对 ambient 做发送前 revision 抑制。
- recall 已按分层块组合原始证据、rolling summary、群记忆和 recent timeline，但未实现跨来源统一时间排序；原始证据仍优先于摘要。
