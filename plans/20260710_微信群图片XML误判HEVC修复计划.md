# 微信群图片 XML 误判 HEVC 修复实施计划

> **面向执行 Agent 的要求：** 实施本计划时先使用 `superpowers:test-driven-development`，再使用 `superpowers:subagent-driven-development` 或 `superpowers:executing-plans` 按任务逐项推进。步骤使用 checkbox (`- [ ]`) 跟踪；完成后必须回写本文的实际改动、验证结果与剩余事项。

**目标：** 阻止 Wechaty 图片消息的传输层 XML 进入 LLM 当前消息和 Agent 持久会话，消除模型把 `hevc_mid_size` 误判为“用户发送 HEVC 视频”并连续回复“又是HEVC”的问题，同时保持图片归档、Vision 摘要和回复路由不变。

**架构：** sidecar 继续上报图片原始 `message.text()` 和本地 `file_path`，归档层继续保存原始协议数据；`WechatGroupChannel` 在图片进入 `_compose_context()` 前把当前用户内容转换为固定的语义化图片问题，共享传输层检测器结合 `message_type` 与正文形态识别媒体载荷，使引用、recent transcript、archive evidence、local summary、焦点栈和画像提取把图片/贴纸 XML 投影为语义占位符，贴纸 Agent 工具对既有污染描述做输出防御，只让 Vision 视觉摘要表达图片事实。已污染会话不删除历史，而是在用户再次明确确认后停服调用现有 `ConversationStore.clear_context()` 设置新的上下文起点，再重启创建干净的 Agent 实例。

**技术栈：** Python、`unittest`、现有 Wechaty JSON Lines 协议、`WechatGroupChannel`、`WechatGroupMultimodalContextService`、`AgentBridge`、SQLite `ConversationStore`。

## 2. 问题记录与证据

### 2.1 用户可见现象

2026-07-10 的近期群聊中，群成员只发送了普通图片，Bot 却多次回复：

```text
HEVC视频都整上了，大海你是懂压体积的
又是HEVC压缩视频
又一个HEVC
HEVC 又双叒叕来了
又是HEVC
```

最新一次回复同时正确描述了图片中的限流仪表盘，说明 Vision 摘要已经生效，但回复前缀仍被错误的 HEVC 上下文污染。

### 2.2 日志和数据库证据

- `run.log` 中共有 6 条 Bot 回复包含 `HEVC`。
- 微信群归档中共有 667 条入站记录包含字符串 `HEVC`；这些命中全部来自图片 XML 的 `hevc_mid_size` 属性。
- 排除 `hevc_mid_size` 后，真实群成员文本中包含 `HEVC` 的记录数为 0。
- 首次误判对应的归档图片实际是 Codex 模型界面截图，最新误判对应的归档图片实际是限流仪表盘；两张图片均没有可见的 HEVC 视频内容。
- 首次误判时 Vision 请求因上游 `HTTP 503 system_cpu_overloaded` 失败，随后 Agent 仍收到原始图片 XML。
- 持久会话中保存的模型 reasoning 明确写出：`hevc_mid_size attribute presence suggests it's an HEVC video`，直接证明误判来源。
- 受影响会话的用户消息被持久化为 `<?xml version="1.0"?>...`，会话标题也被污染为 XML 开头；后续图片消息继续携带同名字段，模型因历史上下文而使用“又是”。

脱敏后的关键协议片段：

```xml
<msg>
  <img md5="masked" hevc_mid_size="31347" />
</msg>
```

`hevc_mid_size` 是微信图片协议元数据，不能作为“用户发送了 HEVC 视频”的业务语义证据。

## 3. 根因链路

```text
Wechaty image message
  -> sidecar: text = message.text()              # 图片协议 XML
  -> WechatGroupMessage.text = payload["text"]
  -> 图片直接回复 / 自由回复批准分支
  -> content = msg.text or 默认图片问题          # XML 非空，默认问题未生效
  -> _compose_context()
  -> wechat_group_user_content = context.content # XML 被标记为“用户原文”
  -> <wechat-group-multimodal> + 原始 XML
  -> AgentBridge 持久化 wechat_group_user_content
  -> LLM 把 hevc_mid_size 解释成 HEVC 视频
  -> 错误 assistant 回复继续进入后续会话历史
```

对应代码落点：

- `channel/wechat_group/sidecar/wechaty-sidecar.mjs:168-193`：上报 `text: message.text()`、`message_type` 和 `file_path`。
- `channel/wechat_group/wechat_group_message.py:22-33`：把 sidecar `text` 保存为 `msg.text`，媒体路径保存为 `msg.media_path`。
- `channel/wechat_group/wechat_group_channel.py:630-668`：直接图片回复把非空 `msg.text` 当作用户内容。
- `channel/wechat_group/wechat_group_channel.py:843-889`：`_compose_context()` 把传入内容写入 `wechat_group_user_content`，再追加微信群增强块。
- `channel/wechat_group/wechat_group_channel.py:1608-1645`：自由回复图片获批后同样把非空 `msg.text` 当作用户内容。
- `bridge/agent_bridge.py:959-991`：按设计持久化 `wechat_group_user_content`；Bridge 行为正确，错误输入来自通道层。
- 实施期代码审查进一步确认：引用消息、媒体下载失败时的 recent/focus、画像进化 LLM 和贴纸 Agent 工具也存在从归档或既有数据库回灌原始 XML 的旁路；历史归档中还有 473 条媒体 XML 被旧版本误标为 `message_type = text`，因此不能只依赖类型字段。

现有测试未发现问题，是因为图片测试统一构造 `text=""`，只覆盖了默认问题的理想分支；引用、无媒体路径、超长 XML 标签和既有污染工具结果也都没有真实 sidecar 形态的 fixture。

## 4. 方案比较

### 方案 A：在图片回复上下文入口语义化内容，并重置受污染上下文（推荐）

- 图片原始 XML 仍由 sidecar 上报并由归档保存。
- 图片进入 LLM 前不再读取 `msg.text`，统一使用 `WECHAT_GROUP_DEFAULT_IMAGE_REPLY_QUESTION`。
- Vision 仍通过 `msg.media_path` 获取真实图片，并通过 `<wechat-group-multimodal>` 注入摘要。
- `wechat_group_user_content` 自动变成语义化图片问题，AgentBridge 无需修改。
- 部署后经用户单独确认，为受影响群会话设置新的上下文起点，保留数据库历史但不再向 LLM 注入旧污染。

优点：修改小、边界清楚、不会破坏协议归档和媒体下载，也不会把字段黑名单散落到 prompt 清洗逻辑中。

### 方案 B：只删除 `hevc_mid_size` 字段

不采用。它只压住本次症状，`aeskey`、`cdnthumburl`、`md5`、本机协议数据等仍会进入 LLM，模型还可能从其他字段继续产生错误推断。

### 方案 C：在 `WechatGroupMessage` 中清空所有非文本消息的 `text`

不采用。`msg.text` 当前还承担归档、贴纸备用下载和协议诊断用途，在适配器层全局清空会扩大影响面。正确边界是“原始协议可以保存，但不能成为 LLM 用户内容”。

## 6. 验收标准

- 图片 XML 中的 `<?xml`、`<img`、`hevc_mid_size`、`aeskey` 和 `cdnthumburl` 不出现在当前 LLM 用户消息中。
- `context["wechat_group_user_content"]` 对图片消息等于 `WECHAT_GROUP_DEFAULT_IMAGE_REPLY_QUESTION`，不再是 XML。
- AgentBridge 持久化的是语义化图片问题，不再新增 XML 会话记录。
- 当前图片仍由 `WechatGroupMultimodalContextService` 调用一次 Vision，并在 `<wechat-group-multimodal>` 中注入摘要。
- 直接图片与自由回复图片两条路径行为一致。
- `wechat_group_image_understanding_comment_enabled = false` 时，图片 XML 不再被误认为“附带了用户文字”。
- 引用图片/贴纸、无媒体路径的 recent/focus、archive evidence、local summary、画像进化 LLM 和贴纸 Agent 工具均不输出传输层 XML；历史误标为文本的媒体记录及既有污染的焦点摘要、贴纸描述也在模型边界被投影。
- 原始 XML 和 `media_path` 仍可在微信群归档中查询，图片下载、识图和发送行为不受影响。
- 受污染会话设置新上下文起点后，新图片回复不再引用旧的 HEVC 误判。
- 微信群必跑测试和新增定向测试全部通过。

## 8. 风险与回退

- **风险：图片直接回复内容统一为默认问题。** 当前 sidecar 合同没有独立图片 caption 字段，`message.text()` 是协议 XML，因此该变化符合真实语义；用户另发的文字仍作为独立文本消息处理。
- **风险：非文本引用和历史上下文不再展示原始 `text`。** 原始字段是协议载荷而非用户语义；消息类型、发送者、消息 ID 和 Vision 摘要继续保留，文本消息不受影响。
