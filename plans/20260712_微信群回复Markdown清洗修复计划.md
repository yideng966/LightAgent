# 微信群回复 Markdown 清洗修复开发计划

> **供执行 Agent 使用：** 实施时必须使用 `superpowers:test-driven-development`；如按任务拆分执行，可使用 `superpowers:subagent-driven-development` 或 `superpowers:executing-plans`。所有步骤使用复选框跟踪，开发完成后必须回写本计划的实施状态、实际改动、验证结果与剩余事项。

**目标：** 微信群文本回复在发送前去除 Markdown 展示符号，避免 `**加粗**`、`* 列表`、标题、引用、代码围栏等不被微信渲染的格式原样发到群里，让回复更像真实群友说话。

**架构：** 保留现有 `WechatGroupChannel.send()` 出口清洗链路，复用 `wechat_group_response_cleanup_enabled` 和 `cleanup_wechat_group_reply_text()`；在 prompt 层降低 Markdown 生成概率，在发送出口做确定性兜底。不新增回复引擎，不修改 sidecar JSON Lines 协议，不影响 Web、桌面端和其他渠道。

**技术栈：** Python、`unittest`、`channel/wechat_group/wechat_group_reply_cleanup.py`、`channel/wechat_group/wechat_group_reply_policy.py`、`WechatGroupChannel.send()`。

---

## 一、当前状态与问题判断

- 当前状态：已定位到微信群文本回复发送前会调用 `cleanup_wechat_group_reply_text()`，但该清洗器目前只处理内部 prompt 块、固定开场白、尾部追问和长度限制，没有处理 Markdown 展示符号。
- 用户问题：模型在微信群中输出 Markdown 风格文本，例如 `**重点**`、`* 条目`、`### 标题`。微信不会渲染这些符号，直接展示会显得像机器人或文档生成器，不符合拟人化要求。
- 影响范围：仅微信群通道的 `ReplyType.TEXT`、`ReplyType.INFO`、`ReplyType.ERROR` 中最终作为文本发送的内容。媒体、表情包、文件、语音发送链路保持不变。
- 本计划只产出方案与开发步骤，没有修改业务代码。

## 二、根因

### 2.1 发送链路

```text
Agent / 普通模型生成回复
        ↓
WechatGroupChannel.send(reply, context)
        ↓
reply.type == ReplyType.TEXT 时进入 cleanup_wechat_group_reply_text()
        ↓
client.send_text(receiver, reply.content, mention_ids=mention_ids)
```

关键文件：

- `channel/wechat_group/wechat_group_channel.py`：`send()` 里已有微信群文本清洗入口。
- `channel/wechat_group/wechat_group_reply_cleanup.py`：当前清洗逻辑的最小修改点。
- `channel/wechat_group/wechat_group_reply_policy.py`：微信群当轮回复策略 prompt，可补充“不要输出 Markdown”的生成约束。
- `channel/wechat_group/wechat_group_persona.py`：默认 persona 中已有口语化要求，可补一条不使用 Markdown 展示格式的风格约束。
- `tests/test_wechat_group_humanization.py`：已有 `WechatGroupReplyCleanupTest`，适合新增清洗回归测试。

### 2.2 为什么不能只改 prompt

只提示模型“不要用 Markdown”不能提供确定性保障。不同模型、不同上下文、工具调用后的总结文本仍可能产出 `**`、`*`、`#`、代码围栏等格式符号。微信群是最终发送出口，必须在出口层兜底清洗。

### 2.3 为什么不新增配置项

现有 `wechat_group_response_cleanup_enabled` 已经表达“微信群回复发送前清洗”的总开关。新增 `wechat_group_markdown_cleanup_enabled` 会增加 UI、配置模板和测试面，当前问题不需要额外运行时开关。若用户确实要保留 Markdown 原文，可关闭既有总清洗开关。

## 三、方案比较

### 方案 A：只加强人设和回复策略 prompt

- 做法：在 persona 和 reply policy 中要求“微信群不要使用 Markdown 格式”。
- 优点：改动小。
- 缺点：不可验证、不可保证；模型仍可能输出 Markdown。
- 结论：只作为辅助约束，不作为主修复。

### 方案 B：在 `WechatGroupChannel.send()` 中直接正则替换

- 做法：发送前在 `send()` 里直接处理 `reply.content`。
- 优点：离发送出口最近。
- 缺点：会让 `send()` 继续膨胀，也绕开已有 `wechat_group_reply_cleanup.py` 单元测试入口。
- 结论：不采用。

### 方案 C：扩展 `cleanup_wechat_group_reply_text()` 做微信群 Markdown 去格式化（推荐）

- 做法：新增 `_strip_markdown_for_wechat()`，由 `cleanup_wechat_group_reply_text()` 调用；同时补 prompt 约束和回归测试。
- 优点：复用现有清洗开关与测试位置；只影响微信群文本；可通过单元测试精确验证。
- 缺点：需要谨慎避免误删正常内容，例如数学乘号、普通星号、代码标识符里的下划线。
- 结论：采用。

## 四、清洗规则

### 4.1 必须清洗的 Markdown 展示符号

1. 加粗 / 斜体包装符号：
   - `**重点**` -> `重点`
   - `__重点__` -> `重点`
   - `*重点*` -> `重点`
   - `_重点_` -> `重点`
2. 标题：
   - `### 结论` -> `结论`
3. 引用：
   - `> 这句很关键` -> `这句很关键`
4. 无序列表：
   - `* 先看日志` -> `先看日志`
   - `- 先看日志` -> `先看日志`
5. 代码围栏：
   - 去掉成对或单独的三反引号 / `~~~` 围栏行，保留中间内容。
6. 行内代码：
   - `` `config.py` `` -> `config.py`
7. Markdown 链接：
   - `[官方文档](https://example.com)` -> `官方文档 https://example.com`
   - `[https://example.com](https://example.com)` -> `https://example.com`

### 4.2 不主动清洗的内容

1. 普通句子中的星号表达，如 `2*3=6`，不能误删。
2. 文件名、变量名和命令中的下划线，如 `wechat_group_response_cleanup_enabled`，不能误删。
3. URL 中的特殊字符，不能破坏链接。
4. 中文文字表情，例如 `[捂脸][吃瓜]`，不能当 Markdown 链接处理。
5. 代码块内部内容只去围栏，不做激进改写；微信群里如果必须发命令或代码，允许保留可读文本。

```python
def _strip_markdown_for_wechat(text: str) -> str:
    result = text
    result = re.sub(r"(?m)^\s{0,3}#{1,6}\s+", "", result)
    result = re.sub(r"(?m)^\s{0,3}>\s?", "", result)
    result = re.sub(r"(?m)^\s{0,3}[*+-]\s+", "", result)
    result = re.sub(r"(?m)^\s*(```+|~~~+).*$", "", result)
    result = re.sub(r"`([^`\n]+)`", r"\1", result)

    def replace_link(match):
        label = match.group(1).strip()
        url = match.group(2).strip()
        if label == url:
            return url
        return "{} {}".format(label, url).strip()

    result = re.sub(r"\[([^\]\n]+)\]\((https?://[^)\s]+)\)", replace_link, result)
    result = re.sub(r"(?<!\w)(\*\*|__)(\S(?:.*?\S)?)\1(?!\w)", r"\2", result)
    result = re.sub(r"(?<![\w*])\*(\S(?:.*?\S)?)\*(?![\w*])", r"\1", result)
    result = re.sub(r"(?<![\w_])_(\S(?:.*?\S)?)_(?![\w_])", r"\1", result)
    return result
```

注意：上面是计划中的目标实现形态，执行时可以根据测试结果微调正则，但不得改成“删除所有星号/下划线”的粗暴逻辑。

## 七、风险与回滚

- 风险 1：正则误删正常星号或下划线。控制方式：只处理成对包装符号和行首列表符号，补不误伤测试。
- 风险 2：代码示例的格式变弱。控制方式：只去围栏和行内反引号，保留代码内容；微信群场景优先自然可读。
- 风险 3：模型仍生成很长的文档式结构。控制方式：继续复用 `wechat_group_response_cleanup_max_chars`，并在 reply policy 和 persona 中降低生成概率。
- 回滚方式：撤销 `wechat_group_reply_cleanup.py`、`wechat_group_reply_policy.py`、`wechat_group_persona.py` 与测试改动；或临时将 `wechat_group_response_cleanup_enabled` 设为 `false`。
