# 微信群登录态保留与强制重扫开发计划

> **状态：执行中**
>
> **目标：** CowAgent 的普通启动、停止、重启、Web 断开和 `Ctrl+C` 退出均不得主动登出个人微信或清空 `wechat_group.memory-card.json`；只有用户在 Web 控制台二次确认“强制重新扫码登录”后，才允许删除该登录缓存并重新生成二维码。

## 一、问题与边界

当前普通停止链路为 `WechatGroupChannel.stop() -> WechatGroupClient.stop() -> sidecar stop -> state.bot.stop()`。`wechaty-puppet-wechat4u` 会把 `bot.stop()` 下传为 `wechat4u.stop()`，执行远端 logout，并在 logout 回调中删除 `PUPPET-WECHAT4U` MemoryCard 槽，最终可能把登录文件写成 `{}`。

本次只调整个人微信群登录态生命周期，不修改消息处理、稳定身份、群选择、权限、记忆、画像或桌面端 UI。

明确行为：

1. 普通 channel stop/restart/disconnect 仅关闭本地 sidecar，不调用 Wechaty logout。
2. `python app.py` 收到 `Ctrl+C` 或退出时，安全回收微信群 sidecar，但保留登录缓存。
3. sidecar 对底层非显式 `delete/clear/destroy` 登录槽操作做保护，避免被动事件自动清空缓存文件。
4. 强制重新扫码由 Python 监督进程按“停止旧 sidecar -> 确认退出 -> 删除唯一 MemoryCard 文件 -> 启动新 sidecar”执行。
5. 前端不得传入文件路径；后端只根据当前有效 `wechat_group_sidecar_memory_path` 计算目标 `.memory-card.json`。
6. 强制重扫不删除 stable identity、群配置、归档、记忆、画像、媒体或其他数据库。
7. 默认仅修改 Web 控制台，不修改 `desktop/`。

## 二、方案比较与选择

### 方案 A：只修改普通 stop，不保护被动 logout

改动最少，但微信端或依赖触发 logout 时仍可能把文件写成 `{}`，不满足“只有按钮才清空”的要求。

### 方案 B：维护 `wechaty-puppet-wechat4u` fork

可以直接改依赖的 logout 行为，但会引入长期 fork 和升级维护成本，不符合最小修改原则。

### 方案 C：安全停止 + 受保护 MemoryCard + Python 显式删除（采用）

普通 stop 通过 JSON Lines `stop` 命令让 sidecar 直接退出进程，不调用 `bot.stop()`；超时由 Python terminate/kill 兜底。sidecar 使用受保护的 MemoryCard，阻止依赖自动删除登录槽。只有 Web `force_rescan` action 调用 Python 的显式删除方法，旧进程退出后删除精确缓存文件并启动新进程。

该方案不修改第三方依赖源码，能覆盖普通停止、运行中重启、Web 断开、`Ctrl+C` 和依赖被动清理，同时把唯一破坏性入口绑定到已认证 Web API。

## 五、验收标准

1. 登录成功后的 MemoryCard 非空；普通 stop、restart、disconnect、`Ctrl+C` 后文件内容哈希不变。
2. 再次 `python app.py` 时，有效会话优先自动恢复，不主动生成二维码。
3. Web 只有“强制重新扫码登录”确认操作会删除 MemoryCard。
4. 强制重扫后旧 sidecar 已退出，缓存文件被删除，新 sidecar 返回新的 `qr_ready`。
5. 强制重扫失败时显示原因并允许重试，不误删其他数据。
6. stable room/member、群配置、记忆、画像、归档和媒体不受影响。
7. 普通 sidecar 停止路径不调用 `Wechaty.stop()`、`wechat4u.stop()` 或远端 logout。
