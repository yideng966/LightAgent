# 微信群图片与表情包入站分类修复开发计划

## 状态

- 当前状态：已完成。
- 计划日期：2026-07-31。
- 计划创建阶段不修改运行代码；实施阶段已按项目规则同步更新 `CHANGES.md`。

## 目标

修正个人微信群入站消息中表情包被映射为图片的问题，使普通图片继续使用现有图片理解链路，而表情包只进入其已有的归档与素材收集链路，不再异常触发当前图片识别、图片自由回复或 `Vision` 调用。

## 现状审计结论

### 1. Sidecar 已正确区分图片与表情包

`channel/wechat_group/sidecar/wechaty-sidecar-core.mjs` 当前已区分 Wechaty 消息类型：

| Wechaty 类型 | Sidecar `message_type` |
| --- | --- |
| 数值 `5`、字符串 `Emoticon` / `Sticker` | `sticker` |
| 数值 `6`、字符串 `Image` | `image` |

`wechaty-sidecar.mjs` 还分别处理媒体文件：表情包使用 `.gif` 目标扩展名及专用下载回退，普通图片走 `FileBox` 下载。最终 JSON Lines 事件会原样发送 `message_type`，因此问题不在 Wechaty 类型识别或 Sidecar 协议层。

### 2. Python 消息适配层发生类型合并

`channel/wechat_group/wechat_group_message.py` 当前映射为：

```python
"image": ContextType.IMAGE,
"sticker": ContextType.IMAGE,
```

因此 Sidecar 虽然发送了 `message_type="sticker"`，进入 Python 后 `msg.ctype` 仍变成 `ContextType.IMAGE`。公共 `ContextType` 目前没有独立的 `STICKER` 成员。

### 3. 通道分流按 `ctype` 把表情包送进图片链路

`WechatGroupChannel.handle_text()` 当前首先判断 `msg.ctype == ContextType.IMAGE`：

- 明确触发（`@`、引用机器人）时，将消息改写为“请根据这张图片作出简短回应”，再构造 `trigger_source="image_message"` 的文本上下文。
- 非明确触发时，只要开启 `wechat_group_free_reply_image_understanding_enabled`，就用 `[image]` 作为自由回复候选；候选获批后仍进入图片理解。

由于表情包的 `ctype` 也是 `IMAGE`，上述两个分支都无法区分真实图片与表情包。

### 4. 多模态服务对“当前消息”仍有 `ctype` 回退

`WechatGroupMultimodalContextService._current_image_item()` 当前条件是：

```python
message_type == "image" or ctype == ContextType.IMAGE
```

表情包虽然保留了 `message_type="sticker"`，仍会因第二个条件被包装成当前图片候选，随后调用 `Vision().execute()`。`_infer_multimodal_trigger_source()` 也存在相同的 `ctype == IMAGE` 回退。

### 5. 归档、历史图片和表情包素材层已经能区分

- 入站归档写入的是原始 `msg.message_type`，表情包会保存为 `sticker`，不会在数据库中被改写为 `image`。
- `_collect_sticker_from_message()` 只接受 `message_type="sticker"`，普通图片不会进入表情包素材库。
- 历史图片候选使用 `project_wechat_message_type(...) == "image"`，已经会排除归档中的 `sticker`。
- 引用上下文已能把表情包投影为 `message_type: sticker` 和 `[sticker]`，不会作为历史图片交给 Vision。

因此本次不需要修改 Sidecar 协议、媒体下载、归档表结构、表情包数据库或历史图片查询。

## 已复现行为

使用只读临时验证构造 `message_type="sticker"` 且被 `@` 的入站消息，当前输出为：

```text
{
  'sidecar_message_type': 'sticker',
  'python_context_type': 'IMAGE',
  'composed_type': 'TEXT',
  'trigger_source': 'image_message',
  'produced': 1
}
```

这证明异常路径为：

```text
Sidecar sticker
  -> WechatGroupMessage ContextType.IMAGE
  -> handle_text 图片分支
  -> image_message 多模态上下文
  -> 当前图片候选
  -> Vision
```

## 目标行为矩阵

| 入站消息 | 明确触发 | 图片自由回复开关 | 目标行为 |
| --- | --- | --- | --- |
| 普通图片 | 是 | 任意 | 保持现状，进入当前图片理解并回复 |
| 普通图片 | 否 | 关闭 | 只归档，不回复 |
| 普通图片 | 否 | 开启 | 保持现状，通过自由回复门控后才识图 |
| 表情包 | 是 | 任意 | 归档并按配置自动收集，不进入图片理解，不调用 Agent/Vision |
| 表情包 | 否 | 任意 | 归档并按配置自动收集，不进入图片自由回复，不调用 Agent/Vision |
| 后续文本引用已归档图片 | 是 | 任意 | 保持现有历史图片选择与识图逻辑 |
| 后续文本引用已归档表情包 | 是 | 任意 | 保持 `[sticker]` 语义投影，不作为图片候选 |

本次遵守最小修改原则，不新增“收到表情包后实时生成语义描述并自动回复”的能力。现有表情包描述、批量图片理解、素材搜索和发送工具保持独立；如后续需要机器人理解入站表情包，应另行设计显式开关、成本门控与缓存策略。

## 方案设计

### 1. 增加独立上下文类型

在 `bridge/context.py` 末尾追加 `ContextType.STICKER`，不调整任何已有枚举值，避免影响现有渠道和序列化语义。

在 `wechat_group_message.py` 中将：

```python
"sticker": ContextType.IMAGE
```

改为：

```python
"sticker": ContextType.STICKER
```

只有个人微信群 Sidecar 当前会产生该类型，其他渠道行为保持不变。

### 2. 在微信群通道显式终止表情包回复分支

`WechatGroupChannel.handle_text()` 在图片分流之前识别 `ContextType.STICKER` 并返回。生产链路在进入 `handle_text()` 前已经完成归档和 `_collect_sticker_from_message()`，因此提前返回不会丢失素材收集，只会阻止其进入回复链路。

图片相关判断改为以投影后的 `message_type == "image"` 为准，而不是仅依赖宽泛的 `ctype == IMAGE`。同样收紧：

- 当前图片明确触发分支；
- 图片自由回复候选和获批后的处理；
- `_infer_multimodal_trigger_source()` 的 `image_message` 判断。

### 3. 收紧多模态当前图片候选

`WechatGroupMultimodalContextService._current_image_item()` 只接受明确投影为 `image` 的当前消息。即使调用方传入旧式 `ctype=IMAGE, message_type=sticker` 对象，也必须拒绝生成当前图片候选。

历史图片候选、引用图片匹配和 Vision 摘要缓存已有严格类型判断，本次不重构这些逻辑。

### 4. 保持既有表情包能力不变

以下链路不得因修复而变化：

- Sidecar 识别、下载并发送 `message_type="sticker"`；
- 入站归档保留 `message_type="sticker"`；
- 按稳定群隔离的表情包自动收集；
- Web 表情包描述编辑与管理员确认后的批量 Vision 标注；
- Agent 主动搜索、选择和发送表情包；
- 表情包冷却、日上限、域名白名单和文件大小限制。

## 验收标准

- Sidecar 发出的 `message_type="sticker"` 在 Python 中不再映射为 `ContextType.IMAGE`。
- 明确触发和非明确触发的入站表情包都不会设置 `trigger_source="image_message"`。
- 表情包不会成为 `WechatGroupMultimodalContextService` 的 `current_image`，不会调用 `Vision().execute()`。
- 普通图片的明确识图、自由回复图片理解、历史图片引用、摘要缓存和路径脱敏全部保持原行为。
- 表情包仍按原始 `message_type` 归档，并在开关允许时继续自动收集。
- 不新增配置项、数据库迁移、第三方依赖或 Web UI 改动。

## 风险与控制

- 风险：新增共享枚举后，表情包意外流入通用 `ChatChannel` 会被视为未知类型。
  - 控制：微信群通道在调用 `_compose_context()` 前显式终止表情包路径，并用通道测试锁定“不 produce”。
- 风险：只修改适配映射但遗漏多模态的兼容回退，旧式测试对象或未来调用仍可能误触发 Vision。
  - 控制：多模态层再按 `message_type` 做一次防御性拒绝。
- 风险：提前返回导致表情包不再收集。
  - 控制：保留 `_consume_message()` 先归档、后 `handle_text()` 的既有顺序，并增加归档/收集回归断言。
- 风险：误伤正常图片。
  - 控制：保留现有图片正向测试，并同时覆盖明确图片和图片自由回复两条路径。
