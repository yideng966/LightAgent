# 微信群联系人同步告警降噪开发计划

## 状态

- 当前状态：已完成。
- 计划日期：2026-07-31。
- 已按计划完成运行代码、回归测试、`AGENTS.md` 和 `CHANGES.md` 更新。

## 问题现象

微信群 sidecar 运行期间，Python 日志约每 2 秒重复出现：

```text
WARN PuppetWechat4u contactRawPayload(AssertionError [ERR_ASSERTION]: 1205 == 0) wechat4u.batchGetContact() exception: undefined
```

`WechatGroupClient._read_stderr_loop()` 当前会把 sidecar stderr 的每一行都按 `WARNING` 原样转发，因此上游同类重试会持续占用控制台和 `run.log`。

## 根因结论

当前 sidecar 安装版本为：

- `wechaty 1.20.2`
- `wechaty-puppet-wechat4u 1.14.14`
- `wechat4u 0.7.14`

`wechaty-puppet-wechat4u 1.14.14` 已是 npm 当前最新版本。其联系人更新逻辑会把未知群成员加入批量查询队列，每次最多处理 40 条，并用 2 秒定时器继续处理后续批次。微信接口返回非零状态 `1205` 时，上游在 stderr 记录上述告警。

这条告警表示联系人批量补全失败，但不能单独证明 sidecar 已退出、登录态已断开或群消息收发链路整体失败。直接修改依赖、停止联系人重试或全局降低 Wechaty 日志级别，可能造成群成员昵称、微信号和稳定身份映射无法继续补全，或掩盖其他真实异常。

## 目标

1. 保留首次出现的 `1205` 联系人同步告警，确保故障可见。
2. 对短时间内完全同类的重复告警进行合并，避免每 2 秒写入一条 `WARNING`。
3. 持续发生时按固定周期输出包含重复次数的摘要，保留可观测性。
4. 其他 sidecar stderr，包括其他断言状态码、进程错误和发送错误，继续逐条按 `WARNING` 输出。
5. 不改变 sidecar 重试、登录、联系人缓存、成员查询和消息收发行为。

## 实施方案

在 `channel/wechat_group/wechat_group_client.py` 中增加窄范围分类与限频：

- 仅同时匹配以下特征的日志进入合并逻辑：
  - `WARN PuppetWechat4u contactRawPayload(`
  - `wechat4u.batchGetContact() exception`
  - `AssertionError [ERR_ASSERTION]: 1205 == 0`
- 第一次匹配仍输出原始告警。
- 后续重复项在 60 秒窗口内只累计计数。
- 窗口到期且仍有重复项时，输出一次摘要并开始新窗口。
- 非匹配 stderr 不参与限频，也不重置或吞掉已知告警的统计。
- 限频状态限定在单个 stderr 读取线程内，避免 sidecar 重启前后的旧、新进程相互污染。

本次不修改 `channel/wechat_group/sidecar/` 和 `node_modules/`，也不新增配置项。

## 实际改动

- 在 `wechat_group_client.py` 中使用三个固定特征精确识别 Wechat4u 联系人同步 `1205` 告警。

## 验收标准

- 同一 sidecar 进程持续每 2 秒产生目标告警时，60 秒内不再逐条写入日志。
- 第一条目标告警仍可见；持续发生时可看到带重复次数的周期摘要。
- `1205` 之外的任何 stderr 仍逐条可见。
- 不改变联系人同步请求和微信群消息收发行为。
- 定向测试及差异检查全部通过。

## 风险与回退

- 风险：过宽匹配可能掩盖不同故障。通过三个固定特征同时匹配，并用近似错误测试约束边界。
- 风险：完全静默会降低排障能力。方案保留首条和周期摘要，不做永久丢弃。
- 回退：撤销 `wechat_group_client.py` 中的分类与限频逻辑即可恢复逐条转发；不涉及配置、数据迁移或 sidecar 会话文件。
