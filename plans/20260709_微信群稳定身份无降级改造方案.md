# 个人微信群稳定身份无降级改造方案

> **面向执行 Agent 的要求：** REQUIRED SUB-SKILL: Use `superpowers:subagent-driven-development`（推荐）或 `superpowers:executing-plans` 按任务逐项实施。步骤使用复选框语法跟踪进度；每完成一个任务后回写本文档的执行状态、实际改动、验证结果与剩余事项。

**Goal:** 在个人微信群通道中引入 CowAgent 稳定身份层，确保重新扫码登录导致 Wechaty `room_id`、`sender_id`、人员 ID 全部变化后，群选择、权限、会话、归档、记忆、画像、学习、焦点、情绪、自由回复、风格、表情、多模态、定时任务和管理端能力完整延续。

**Architecture:** 将 Wechaty 当前登录态 ID 与 CowAgent 长期业务 ID 分离。`runtime_room_id` / `runtime_sender_id` 只用于 sidecar 查找房间、联系人、发送消息、真实 mention 和自消息判断；`stable_room_id` / `stable_member_id` 用于配置、权限、会话、归档、记忆、画像、学习、上下文、Web API 和调度。上线采用全链路双写、兼容读、绑定确认、一次性迁移和全量回归，禁止发布任何只迁移部分功能的生产状态。

**Tech Stack:** Python `unittest`、SQLite、现有 `channel/wechat_group` 通道层、Node.js Wechaty sidecar JSON Lines 协议、`bridge/agent_bridge.py`、`agent/memory`、`agent/tools/scheduler`、Web 控制台原生 JavaScript。

---

## 1. 背景与硬约束

已确认事实：个人微信群重新扫码登录后，Wechaty 暴露的 `room_id`、`sender_id`、机器人 `self_id` 以及人员 ID 都可能变化。当前代码大量把这些运行时 ID 当成长期主键使用，因此重登会造成同一群、同一人被系统识别为全新对象。

本方案的硬约束：

- 所有既有能力不允许因为稳定身份改造而减少、关闭或改变用户可感知行为。
- 不允许把发送链路改成 stable ID；sidecar 发送必须继续使用当前登录态 runtime ID。
- 不允许用群名、昵称、备注名做管理员自动授权依据。
- 不允许把跨群、跨成员数据合并交给模型判断。
- 不允许在生产默认状态发布“部分功能已迁移、部分功能仍断层”的版本。
- 迁移期旧字段不得悄悄换语义；`wechat_group_room_id`、`wechat_group_sender_id` 在所有旧调用点完成迁移前必须继续表示 runtime ID。
- 重登后的恢复流程必须在通道管理 UI 内完成；不能要求用户通过日志、数据库或手工改配置恢复。
- 所有长期数据访问必须以 stable ID 为第一查询键，并保留 legacy runtime 数据兼容读取路径，直到迁移完成。
- 新增 Web/API 入参必须显式命名为 `stable_room_id`、`runtime_room_id`、`stable_member_id`、`runtime_sender_id`；旧 `room_id` / `sender_id` 参数只作为 legacy 兼容入口。

## 2. 术语与身份边界

| 名称 | 含义 | 生命周期 | 允许用途 | 禁止用途 |
| --- | --- | --- | --- | --- |
| `runtime_room_id` | Wechaty 当前登录态的群 ID | 本次扫码登录有效 | `findRoom()`、发送文本/文件、真实 mention、诊断展示 | 权限、记忆、画像、长期配置主键 |
| `runtime_sender_id` | Wechaty 当前登录态的成员 ID | 本次扫码登录有效 | 当前消息发送人识别、真实 mention、发送命令 `mention_ids` | 管理员长期授权、画像主键 |
| `runtime_bot_sender_id` | 当前登录态机器人自身 ID | 本次扫码登录有效 | 自消息判断、引用自己判断、过滤机器人自身 @ | 稳定会话或权限主键 |
| `stable_account_id` | CowAgent 对“当前扫码微信账号/机器人主体”的稳定标识 | CowAgent 数据生命周期内稳定 | 区分同一 CowAgent 被不同微信账号扫码登录时的数据边界、恢复向导、审计 | 直接判断联系人或群成员身份 |
| `stable_room_id` | CowAgent 内部稳定群 ID | CowAgent 数据生命周期内稳定 | 群选择、会话、归档、记忆、学习、焦点、情绪、风格、表情、多模态、Web API、调度目标 | sidecar 直接发送 |
| `stable_member_id` | CowAgent 内部稳定群成员 ID，按 `stable_room_id` 隔离 | CowAgent 数据生命周期内稳定 | 管理员、群友画像、成员画像、同发送者图片定位、成员维度统计 | sidecar 真实 mention |

命名约定：

- 新上下文字段使用明确前缀：`wechat_group_stable_account_id`、`wechat_group_runtime_room_id`、`wechat_group_stable_room_id`、`wechat_group_runtime_sender_id`、`wechat_group_stable_member_id`、`wechat_group_runtime_bot_sender_id`、`wechat_group_stable_bot_member_id`。
- 旧字段 `wechat_group_room_id` / `wechat_group_sender_id` 在迁移期保留为 runtime 语义，避免现有发送、mention、图片额度、权限守卫等调用点被静默破坏；新代码必须使用明确 stable 字段，不得继续把旧字段当长期主键。
- `Context.receiver` 在微信群发送路径继续保存 `runtime_room_id`；新增 `wechat_group_stable_receiver` 保存 `stable_room_id`，供调度、会话和管理端使用。
- Web/API 与桌面端类型也必须使用明确字段名，不能继续让 `selected_room_ids` 同时承担 runtime 和 stable 两种语义。

## 3. 当前影响面全量盘点

### 3.1 入口、群选择与触发

当前 `channel/chat_channel.py` 使用 `cmsg.other_user_id` 匹配 `wechat_group_room_ids`，并用它设置 `session_id` 与 `receiver`。`channel/wechat_group/wechat_group_channel.py` 的 `_is_selected_room()` 也用 `msg.other_user_id` 匹配配置。重登后同一群会被视为未选中群，导致 @ 触发、自由回复、图片触发、白名单规则全部断开。

改造要求：

- 群选择配置迁移为 stable 群 ID。
- 首次发现 runtime 群时，必须通过 identity service 解析到 stable 群后再进入 ChatChannel 群白名单判断。
- 具体实现必须二选一：在 `WechatGroupChannel._compose_context()` 调用 `super()._compose_context()` 前完成身份预解析并把 stable 字段放入 kwargs；或在 `ChatChannel` 增加微信群专用 identity hook。不得等 `super()` 返回后才解析，否则未选中群会在白名单阶段提前返回 `None`。
- `receiver` 仍是 runtime 群 ID，保证发送不变。
- `session_id` 改为基于 stable ID：群共享会话为 `wechat_group:<stable_room_id>`，非共享会话为 `wechat_group:<stable_room_id>:<stable_member_id>`。

### 3.2 管理员、黑名单与安全门禁

当前 `wechat_group_admin_members` 按 `room_id + sender_id` 精确生效，`wechat_group_blocked_sender_ids` 也依赖 runtime sender。重登后管理员身份和黑名单都会失效。

改造要求：

- 管理员配置改为 `stable_room_id + stable_member_id`。
- 旧 `room_id + sender_id` 配置迁移到 stable 配置；迁移结果必须记录 legacy 字段用于审计。
- 未确认成员绑定不得继承管理员身份。
- 黑名单改为支持 `stable_member_id`，同时保留 legacy runtime sender 兼容读。
- 通道层拒绝、Agent 工具过滤和 Prompt 权限提示都必须使用 stable 身份判断。

### 3.3 会话与 Agent 历史

当前群会话使用 runtime room 或 sender。重登会创建新 session，导致历史上下文、scheduler 注入记录、Agent 消息清理策略断裂。

改造要求：

- `Context.session_id` 必须稳定。
- `AgentBridge._sanitize_wechat_group_runtime_messages()` 继续只清理当前增强消息，不影响 stable session。
- scheduler 注入到目标会话时使用 stable session ID。
- 旧 session 需要在迁移工具中合并或保留兼容读取，避免历史对话丢失。

### 3.4 消息归档、recent transcript、引用与图片定位

当前 `WechatGroupArchive` 的 `wechat_group_messages`、`wechat_group_assistant_replies`、`wechat_group_image_create_usage` 均以 `room_id` / `sender_id` 查询。图片理解和引用定位依赖同一群 recent archive 和同发送者 recent image。

改造要求：

- 归档表新增 `stable_room_id`、`runtime_room_id`、`stable_member_id`、`runtime_sender_id`。
- 查询 API 统一以 stable ID 入参，内部兼容读取 legacy runtime 记录。
- `message_id` 仍保存原始消息 ID；如果重登后消息 ID 也变化，不把它作为跨登录长期主键。
- 引用消息精确查找优先 `stable_room_id + message_id`；同发送者图片定位使用 `stable_member_id`。
- 图片生成额度、助手回复归档、recent transcript、archive evidence、本地摘要全部改为 stable room 作用域。

### 3.5 群永久记忆、群友画像与 Agent 工具

当前 `MemoryScope.wechat_group(room_id)`、`MemoryScope.wechat_group_member_profile(room_id, sender_id)`、`wechat_group_group_memories`、`wechat_group_global_profiles`、`wechat_group_profile_name_records` 都绑定 runtime ID。重登会导致群记忆不可见、同一成员画像分裂。

改造要求：

- `MemoryScope.wechat_group()` 参数语义迁移为 stable room。
- `MemoryScope.wechat_group_member_profile()` 参数语义迁移为 stable room + stable member。
- 画像 store 主键从 runtime `sender_id` 迁移为 `stable_member_id`；name records 保留 `runtime_sender_id`、`runtime_room_id`、群昵称、备注、来源。
- Agent 动态创建的 `wechat_group_memory_*` 与 `wechat_group_profile_*` 工具只接受服务端绑定的 stable room/member，不允许模型传 runtime room 或跨群 room。
- Prompt 中不暴露 runtime ID；必要诊断只显示脱敏 stable ID。

### 3.6 学习、画像进化与游标

当前学习游标、learning runs、画像进化触发和合并基于 runtime room/sender。重登会导致重复学习、漏学、画像演进断层。

改造要求：

- `wechat_group_learning_cursors.room_id` 迁移为 stable room。
- `wechat_group_learning_runs.room_id` 迁移为 stable room，并保存 runtime alias 作为审计字段。
- 画像进化 store、trigger、executor、merger 全部以 stable member 读写。
- 批量学习时 archive 游标基于 stable room 下的 archive row id 推进。

### 3.7 焦点、情绪、自由回复、风格、表情

当前 focus、emotion、free reply、style、sticker 多数按 runtime room 隔离；自由回复还使用 `wechat_group_free_reply_room_ids` 和 runtime sender 黑名单。

改造要求：

- focus stack、focus refs、emotion state、free reply state、style cards、sticker records、sticker usage 全部迁移到 stable room。
- 自由回复群范围配置迁移为 stable room；blocked sender 迁移为 stable member。
- 运行时防抖、冷却、小时上限、连续上限使用 stable room，确保重登后不丢节奏控制。
- 表情素材按 stable room 保存，`file_hash` 与媒体路径继续作为素材识别辅助。

### 3.8 多模态、引用策略与媒体缓存

多模态服务当前从当前群 archive 中查找图片、视频、转发、链接上下文。重登后同群历史图片不可见。

改造要求：

- `WechatGroupMultimodalContextService` 入参和查询统一使用 stable room/member。
- 当前图片 Vision 调用仍使用真实 `media_path`；prompt 不暴露本机路径。
- 引用图片、同发送者图片、唯一近图、多图歧义判断全部基于 stable room。
- 诊断字段同时记录 stable 命中和 runtime 发送信息，便于排障。

### 3.9 Web 控制台、API 与桌面端

当前 Web 管理 API 用 runtime room 查询群成员、记忆、画像、学习、焦点、情绪、风格、表情。配置保存也写 runtime room。

改造要求：

- Web 群列表展示 stable 群、当前 runtime 绑定、绑定状态、最近登录时间。
- 通道管理扫码流程加入“身份恢复确认”步骤；确认前不进入正常运行态。
- 所有配置保存改为 stable ID；UI 同时展示当前 runtime ID 作为诊断信息。
- 所有 Web API 入参改为 stable ID，保留 legacy runtime 入参兼容并在响应中返回迁移提示。
- 桌面端已直接调用微信群二维码和群选择 API，必须同步 API 类型、`GroupsPage`、二维码弹窗和 i18n。

### 3.10 定时任务与主动通知

当前 scheduler action 保存 `receiver` 和 `notify_session_id`，微信群场景下都是 runtime room。重登后任务无法投递到新 runtime room。

改造要求：

- 新建任务保存 `stable_receiver`、`receiver_kind = "wechat_group"`、`notify_session_id` stable 化。
- 任务执行前通过 identity service 将 stable room 解析为当前 active runtime room。
- 如果没有 active runtime room，任务状态记录为 `waiting_identity_binding`，并在 Web UI 显示需要重新绑定；不得静默丢弃。
- 旧任务迁移时将 legacy `receiver` 绑定到 stable room，并保留 legacy receiver 用于审计。

### 3.11 登录账号、sidecar profile 与账号切换

当前 `wechat_group_sidecar_memory_path` 影响 Wechaty 登录态目录，sidecar 状态事件只暴露当前 `self_id` / `self_name`。重新扫码同一微信账号时这些 runtime ID 可能变化；如果用户改用另一个微信账号扫码，也可能看到同名群和同名成员。

改造要求：

- identity store 必须增加 `stable_account_id`，把“同一个 CowAgent 被哪个微信账号登录”纳入审计边界。
- `stable_account_id` 不能依赖可变 `self_id`，应由用户在首次登录或恢复向导中确认。
- 同名群跨账号出现时只能标记为 suspected/conflict，不得自动继承旧账号下的管理员、黑名单、群记忆、画像或定时任务。
- `wechat_group_sidecar_memory_path` 变化时必须触发身份恢复检查，并在 UI 展示当前 sidecar profile 与历史绑定的关系。
- sidecar 登录态文件仍在仓库外数据目录，identity store 只记录路径指纹和审计信息，不把登录态搬入仓库。

### 3.12 媒体文件、图片缓存与素材路径

当前 sidecar 下载媒体时使用 runtime room ID 构造目录，表情服务也会把 room ID 放入在线候选、下载路径和 sticker ID hash。重登后，如果只迁移数据库主键，旧图片、视频、表情文件仍可能挂在旧 runtime 路径下。

改造要求：

- 新媒体文件目录应优先按 `stable_room_id` 组织；sidecar 可以继续先按 runtime 下载，但 Python 通道必须在归档前完成 stable 路径归一或记录 stable 与 runtime 双路径。
- 旧 `media_path`、表情 `media_path`、在线表情候选缓存、Vision 缓存必须保留 legacy lookup，确保旧图片理解和旧表情发送不丢失。
- `sticker_id`、`online_id`、每日发送额度和在线发送冷却必须基于 stable room 计算，不能继续使用 runtime room hash。
- 迁移脚本需要校验文件是否存在，输出缺失媒体清单；缺失文件不能导致数据库迁移失败。

### 3.13 名称类兜底配置

当前仍存在 `wechat_group_names`、`wechat_group_ambient_names`、`wechat_group_free_reply_names` 等名称类兜底配置。群名不会随着 runtime ID 必然变化，但同名群和群改名会导致误匹配。

改造要求：

- 名称类配置保留为“发现候选群”的辅助条件，不再作为长期授权或最终接入范围。
- UI 需要把名称兜底迁移为 stable room 候选确认流程：命中名称后生成 suspected stable room，用户确认后才写入 `wechat_group_stable_room_ids`。
- `wechat_group_free_reply_names` 同步迁移为自由回复候选群确认机制，不得绕过 stable room 范围。
- `wechat_group_ambient_names` 如果继续保留，也必须明确只参与候选发现，不参与权限和记忆隔离。

## 4. 目标数据模型

### 4.1 Identity Store

新增 `channel/wechat_group/wechat_group_identity_store.py`，默认 SQLite 路径与现有微信群数据目录一致。

核心表：

```sql
CREATE TABLE IF NOT EXISTS wechat_group_identity_accounts (
    stable_account_id TEXT PRIMARY KEY,
    display_name TEXT NOT NULL DEFAULT '',
    status TEXT NOT NULL,
    confidence TEXT NOT NULL,
    sidecar_memory_path TEXT NOT NULL DEFAULT '',
    created_at INTEGER NOT NULL,
    updated_at INTEGER NOT NULL,
    confirmed_at INTEGER NOT NULL DEFAULT 0,
    metadata TEXT NOT NULL DEFAULT '{}'
);

CREATE TABLE IF NOT EXISTS wechat_group_identity_account_aliases (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    stable_account_id TEXT NOT NULL,
    runtime_self_id TEXT NOT NULL DEFAULT '',
    self_name TEXT NOT NULL DEFAULT '',
    sidecar_memory_path TEXT NOT NULL DEFAULT '',
    first_seen_at INTEGER NOT NULL,
    last_seen_at INTEGER NOT NULL,
    is_active INTEGER NOT NULL DEFAULT 1,
    metadata TEXT NOT NULL DEFAULT '{}'
);

CREATE TABLE IF NOT EXISTS wechat_group_identity_rooms (
    stable_room_id TEXT PRIMARY KEY,
    stable_account_id TEXT NOT NULL DEFAULT '',
    canonical_name TEXT NOT NULL,
    status TEXT NOT NULL,
    confidence TEXT NOT NULL,
    created_at INTEGER NOT NULL,
    updated_at INTEGER NOT NULL,
    confirmed_at INTEGER NOT NULL DEFAULT 0,
    metadata TEXT NOT NULL DEFAULT '{}'
);

CREATE TABLE IF NOT EXISTS wechat_group_identity_room_aliases (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    stable_account_id TEXT NOT NULL DEFAULT '',
    stable_room_id TEXT NOT NULL,
    runtime_room_id TEXT NOT NULL,
    room_name TEXT NOT NULL DEFAULT '',
    self_runtime_id TEXT NOT NULL DEFAULT '',
    source_kind TEXT NOT NULL,
    first_seen_at INTEGER NOT NULL,
    last_seen_at INTEGER NOT NULL,
    is_active INTEGER NOT NULL DEFAULT 1,
    metadata TEXT NOT NULL DEFAULT '{}',
    UNIQUE(stable_account_id, runtime_room_id)
);

CREATE TABLE IF NOT EXISTS wechat_group_identity_members (
    stable_member_id TEXT PRIMARY KEY,
    stable_room_id TEXT NOT NULL,
    stable_account_id TEXT NOT NULL DEFAULT '',
    display_name TEXT NOT NULL DEFAULT '',
    status TEXT NOT NULL,
    confidence TEXT NOT NULL,
    created_at INTEGER NOT NULL,
    updated_at INTEGER NOT NULL,
    confirmed_at INTEGER NOT NULL DEFAULT 0,
    metadata TEXT NOT NULL DEFAULT '{}',
    UNIQUE(stable_room_id, stable_member_id)
);

CREATE TABLE IF NOT EXISTS wechat_group_identity_member_aliases (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    stable_account_id TEXT NOT NULL DEFAULT '',
    stable_room_id TEXT NOT NULL,
    stable_member_id TEXT NOT NULL,
    runtime_sender_id TEXT NOT NULL,
    runtime_room_id TEXT NOT NULL DEFAULT '',
    display_name TEXT NOT NULL DEFAULT '',
    room_alias TEXT NOT NULL DEFAULT '',
    source_kind TEXT NOT NULL,
    first_seen_at INTEGER NOT NULL,
    last_seen_at INTEGER NOT NULL,
    is_active INTEGER NOT NULL DEFAULT 1,
    metadata TEXT NOT NULL DEFAULT '{}',
    UNIQUE(stable_account_id, stable_room_id, runtime_sender_id)
);

CREATE TABLE IF NOT EXISTS wechat_group_identity_binding_events (
    event_id TEXT PRIMARY KEY,
    entity_type TEXT NOT NULL,
    stable_account_id TEXT NOT NULL DEFAULT '',
    stable_id TEXT NOT NULL,
    old_runtime_id TEXT NOT NULL DEFAULT '',
    new_runtime_id TEXT NOT NULL DEFAULT '',
    action TEXT NOT NULL,
    actor TEXT NOT NULL DEFAULT '',
    reason TEXT NOT NULL DEFAULT '',
    created_at INTEGER NOT NULL,
    metadata TEXT NOT NULL DEFAULT '{}'
);
```

状态约定：

- `confirmed`：人工确认或历史迁移明确绑定，可承载全部功能。
- `active`：当前 runtime alias 正在使用。
- `suspected`：系统候选匹配，只能进入恢复向导，不得继承管理员或敏感数据。
- `legacy_imported`：从旧 runtime 配置或旧数据导入，等待首次重登确认。
- `conflict`：同一 runtime 或候选指纹对应多个 stable 对象，需要人工处理。

active alias 约束：

- 同一个 `stable_account_id` 同一时间只能有一个 active account alias。
- 同一个 `stable_account_id + stable_room_id` 同一时间只能有一个 active runtime room alias。
- 同一个 `stable_account_id + stable_room_id + stable_member_id` 同一时间只能有一个 active runtime sender alias。
- 激活新 alias 必须在同一 SQLite 事务内完成：先把同作用域旧 alias 置为 `is_active = 0`，再插入或更新新 alias 为 `is_active = 1`，最后写入 binding event。
- `get_active_runtime_room_id()` 与 `get_active_runtime_sender_id()` 遇到 0 个 active alias 时返回空并让调用方进入绑定待处理；遇到多个 active alias 时必须记录错误并拒绝自动发送，不能随机取第一条。

建议索引：

```sql
CREATE UNIQUE INDEX IF NOT EXISTS idx_wechat_group_identity_account_aliases_one_active
ON wechat_group_identity_account_aliases(stable_account_id)
WHERE is_active = 1;

CREATE UNIQUE INDEX IF NOT EXISTS idx_wechat_group_identity_room_aliases_one_active
ON wechat_group_identity_room_aliases(stable_account_id, stable_room_id)
WHERE is_active = 1;

CREATE UNIQUE INDEX IF NOT EXISTS idx_wechat_group_identity_member_aliases_one_active
ON wechat_group_identity_member_aliases(stable_account_id, stable_room_id, stable_member_id)
WHERE is_active = 1;
```

### 4.2 稳定 ID 生成

- 新群首次纳入 CowAgent 管理时生成 `wgr_` 前缀 UUID，不使用群名 hash。
- 新成员首次在某个 stable room 出现时生成 `wgm_` 前缀 UUID，不使用昵称 hash。
- 从 legacy runtime 数据迁移时，保留原 runtime ID 到 alias 表，stable ID 仍使用新 UUID。
- 所有 stable ID 一经确认不得修改；合并时保留 survivor stable ID，并把被合并对象写入 binding events。

## 8. 身份恢复流程

### 8.1 扫码登录后

1. sidecar 上报登录状态和当前可见群列表。
2. Python 通道调用 identity service 对每个 runtime room 建立或匹配 stable room。
3. Web 控制台显示三类状态：
   - 已确认绑定：直接进入正常运行。
   - 发现疑似旧群：展示旧群名、旧 runtime、新 runtime、最近归档时间、管理员数量、记忆/画像数量，要求管理员确认。
   - 冲突：展示多个候选，必须人工选择。
4. 只有 confirmed stable room 才能承载旧管理员权限、旧记忆、旧画像和旧调度任务。

### 8.2 成员首次出现后

1. 根据当前 stable room 和 runtime sender 建立 member alias。
2. 若存在同名、同群昵称或历史 alias 候选，标记为 suspected。
3. 普通聊天可以生成当前新 alias 的 stable member；画像合并、管理员继承、黑名单继承必须确认。
4. Web 成员页提供“合并到已有成员”操作，写入 binding event。
5. Web 恢复向导必须提供批量成员绑定确认：按旧画像、旧管理员、旧黑名单、最近发言人、群昵称和 wechat_id 候选分组展示，允许逐项确认或跳过；跳过项不得继承敏感权限，但必须保留候选，后续可再次确认。
6. 批量确认必须是显式用户操作，不允许根据昵称自动批量继承管理员、黑名单或画像写权限。

### 8.3 不进入部分功能状态

生产切换规则：

- 不新增稳定身份总开关；本改造按完整功能分支一次性交付。
- 代码合入生产前，所有功能域必须完成双写、兼容读、迁移脚本和测试，不能把中间态发布给生产用户。
- 合入生产后，微信群通道只在 confirmed stable room 上进入正常运行态。
- 对疑似绑定群，UI 显示恢复向导；完成绑定后一次性恢复所有能力。
- 不发布“只保问答、不保记忆画像”或“只保记忆、不保定时任务”的运行模式。

## 11. 回滚与风险控制

回滚原则：

- 不依赖运行时总开关回滚；生产合入前的回滚方式是撤销功能分支或恢复备份。
- 生产合入后，必须保留 legacy runtime 查询路径、旧配置字段读取和新增数据的 runtime 快照写入，至少覆盖一个完整重登恢复周期。
- 新增配置、归档、scheduler task、记忆候选、画像、表情和媒体索引在 stable 写入的同时保留 legacy runtime 快照字段，确保紧急回滚到旧 runtime 读取时新增数据不完全丢失。
- 数据迁移脚本默认 dry-run；实际写入前输出完整差异。
- 所有绑定、合并、迁移都写入 binding events，支持审计和反向修复。
- 回滚时恢复 legacy runtime 读取；已经写入的 stable 字段保留，不删除数据。

主要风险与控制：

- 同名群误合并：不自动确认，Web 恢复向导必须展示证据并要求人工选择。
- 昵称冒名提权：管理员只按 confirmed stable member 生效，昵称不作为授权依据。
- 发送失败：发送前总是 stable -> active runtime 解析，并在无 active runtime 时显示绑定待处理。
- 跨群记忆泄露：所有 memory/profile/archive 查询必须先按 stable room 过滤。
- 迁移遗漏：端到端测试必须覆盖验收矩阵中的每个功能域。

- 连续性：scheduler 隔离会话、生图额度、assistant reply 和 image usage 归档均改为 stable 主语义并保留 runtime 快照。
- 候选门禁：inactive candidate alias 重复解析仍保持 suspected；本轮 alias 未确认时，通道硬门禁、Prompt、Agent 工具过滤和人设判断都按普通成员处理。

五次实施后复查新增修正：

- 历史画像关联：stable 群画像过滤展开 active room alias 和显式确认的历史 runtime room alias，禁止同名 `suspected` 候选直接进入画像 scope。
- 画像链路一致性：画像列表、群内昵称、群内别名、Web、通道上下文和 Agent 画像工具统一使用 identity-aware profile service。
- 显式字段语义：Web 画像筛选改传 `stable_room_id`；画像编辑仅在成员 ID 确为 `wgm_*` 时写 `stable_member_id`，legacy sender 写入 `runtime_sender_id`。
- 迁移完整性：迁移脚本修复 stable 配置中的 runtime 污染，扫描历史画像 room 来源，并允许显式确认已有 `suspected` 历史 alias；确认历史 alias 不改变当前 active 发送目标。
- 数据验证：本机 7 个污染配置和 7 个历史画像 room alias 已在备份后修复；画像总量保持 102，修复后 dry-run 无新增 room、候选、冲突或人工确认项，active alias 与备份一致。
- 迁移运行边界：最终复核捕获到遗留旧版 `app.py` 进程把迁移前内存配置重新写回磁盘；停止 Python/sidecar 进程树并重新 apply 后恢复，计划已补充“迁移必须离线执行”的硬约束。
- 验证结果：身份/画像/Web/Agent/通道组合回归 202 个测试通过；全量 `unittest` 611 个测试通过。

外部上线前仍需重点确认：

- stable account 的人工确认 UI 文案和冲突处理流程必须足够清晰，避免用户误把不同微信账号绑定到同一稳定账号。
- 数据库迁移要先 dry-run，并输出每一类 legacy 数据的数量、目标 stable id、冲突项和缺失媒体文件。
- 端到端测试必须构造“旧 runtime 全功能数据 + 新 runtime 绑定”的完整样本，不能只测权限和会话。
