## 目标

修复个人微信群中 bot 把“（没@我，不插嘴）”这类静默说明当作普通回复发到群里的问题。符合预期的行为是：这类内容只代表“不回复”，不得真实发送到微信群，也不得 @ 原发送者。

## Issue 核验

issue #23 当前状态为 `OPEN`，标题为 `[Bug] （没@我，不插嘴）`，描述明确要求：

- 微信群中 bot 发出的“（没@我，不插嘴）”这类话不要回复到群里。
- bot 不回复即可，保持静默。

## 方案比较

### 方案 A：发送层精确拦截静默说明，并补充自由回复负向规则（推荐）

在微信群通道发送前识别“短文本静默说明”，命中后直接记录日志并返回，不调用 sidecar 发送；同时在自由回复本地评分阶段把同类文本作为负向规则抑制，避免它进入 worker。

优点：
- 风险最小，改动集中在微信群通道和自由回复评分。
- 即使上游模型、人设或自由回复链路生成了静默说明，发送层仍有兜底。
- 不影响 @ 必回和正常长文本解释，只拦截短文本静默标记。

缺点：
- 需要维护一个很小的静默说明识别规则。

### 方案 B：只调整 prompt，让模型不要输出这句话

在人设或自由回复 prompt 中强调“需要静默时不要输出任何内容”。

优点：
- 改动少。

缺点：
- 依赖模型遵守，不能保证第三方模型、不同人设或未来 prompt 变化下稳定生效。
- 无法覆盖已经生成静默说明后的发送行为。

### 方案 C：关闭或显著收紧自由回复

通过默认配置或阈值减少非 @ 场景接话。

优点：
- 能降低普通非 @ 误接话概率。

缺点：
- 影响既有自由回复功能，范围过大，不符合本 issue 的最小修复目标。

推荐采用方案 A。

## 设计

新增一个微信群专用的窄口径静默说明识别 helper，例如：

```python
def _is_wechat_group_silent_reply_text(text: str) -> bool:
    value = re.sub(r"\s+", "", str(text or "")).strip()
    value = value.strip("()（）[]【】{}")
    if not value:
        return False
    if len(value) > 24:
        return False
    return (
        ("没@我" in value or "没有@我" in value or "未@我" in value)
        and ("不插嘴" in value or "不接话" in value or "不回复" in value)
    )
```

发送层只在文本内容整体就是短静默说明时拦截，不拦截较长解释文本，避免影响用户 @ 机器人询问“解释这句话是什么意思”的正常回答。

自由回复评分层复用同类判断，新增负向抑制原因 `bot_silent_notice`。当普通群消息或模型遗留文本是这类静默说明时，不进入 worker，不触发 LLM judge。

## 风险与回退

- 风险：规则过宽会误伤正常回答。控制方式是只拦截短文本、整体像静默标记的内容；长文本解释不拦截。
- 风险：发送层拦截会绕过 `_record_assistant_reply()`。这是预期行为，因为没有真实发送。
- 回退：若误伤，回滚 `channel/wechat_group/wechat_group_channel.py` 的 helper 和 `send()` 拦截即可；自由回复负向规则可独立保留或同步回滚。
