**目标：** 修复重新扫码后 runtime 账号、群和成员 ID 变化造成的连续性问题，同时杜绝不同微信账号、同名群和同名成员误继承 stable 权限、记忆、画像、归档、会话与 scheduler 数据。

## 二、已确认问题

### P0-1：不同微信账号可被唯一 profile 自动合并

证据链：

- `channel/wechat_group/sidecar/wechaty-sidecar.mjs` 的 `logged_in` 状态只上报 `self_id/self_name`，群列表阶段没有上报账号强微信号。
- `channel/wechat_group/wechat_group_channel.py` 的群列表解析使用空 metadata 调用 `resolve_account()`。
- `channel/wechat_group/wechat_group_identity_service.py` 在没有强微信号时，把 `sidecar_memory_path + self_name` 的唯一候选直接确认为原 stable account。
- 后续消息即使带来了另一个强微信号，也会先命中新 runtime alias，再把新微信号覆盖写进旧账号 metadata。

最小复现结果：账号 A 与账号 B 使用同一 MemoryCard 路径、相同显示名但不同强微信号时，房间列表和首条消息都返回账号 A 的同一个 `wga_*`，旧账号 metadata 最终被改成账号 B 的微信号。

影响：不同微信账号可能共享 stable room，继而跨账号继承目标群、管理员、黑名单、Agent session、归档、记忆、画像、焦点、情绪、风格、表情和 scheduler 数据，属于权限与数据隔离阻断问题。

### P0-2：首个到达的同名群可抢占旧 stable room

证据链：

- `resolve_room()` 对同账号内唯一完全同名候选直接激活并确认。
- 通道的登录会话重名集合只能在看到第二个 runtime room 后才知道名称有歧义。
- 消息可以早于完整 rooms 快照到达，所以第一个同名群已经完成绑定，后续检测无法撤销。

最小复现结果：旧 `wgr_*` 对应“同名群”；新会话中错误群先发消息、真实旧群后发消息时，错误群得到旧 `wgr_*`，真实旧群得到新 `wgr_*`。

影响：错误群可读取旧群归档、群记忆和画像，并继承管理员、自由回复、会话与 scheduler 作用域；真实旧群反而丢失连续性。

### P1-1：无强微信号成员会永久分裂，且没有恢复入口

`resolve_member()` 在缺少 `wechat_id/weixin/wxid` 时创建新的 confirmed `wgm_*`。这是安全的默认隔离，但当前改动同时删除了 Web 身份恢复页，并让三个 confirm API 统一返回 `wechat group identity recovery is automatic`。

最小复现结果：同群、同昵称成员从 `sender-old` 变成 `sender-new` 且没有微信号时，新旧 stable member 不同；旧 stable member 仍是管理员，新 stable member 不是管理员。

影响：大量无法由 Web WeChat 暴露 Alias/handle 的成员在重扫后丢失管理员、黑名单、画像、别名和成员级上下文连续性，而且无法人工绑定回原 stable member。群改名、账号缺少强 ID、强 ID 冲突时也存在同类死路。

### P1-2：`wechat_group_names` 仍被当作直接路由条件

`WechatGroupChannel._is_selected_room()` 在 stable/runtime 列表为空时仍按群名直接放行，新增测试也明确断言该行为。它与 `CHANGES.md` 和既有方案中“群名只用于候选发现与显示，不直接放行”的约束相冲突。

影响：启用通用 `ALL_GROUP` 或名称白名单时，同名但未选中的群仍可进入归档和回复链路；在 stable 配置暂时为空或保存异常时尤其危险。

### P1-3：Web 与桌面端会破坏已保存群配置

Web 问题：

- `selected_room_ids`、`runtime_selected_room_ids`、`selected_room_names` 被当作按索引对齐的三个数组。
- 保存时 runtime ID 和群名使用 `.filter(Boolean)`，部分群离线时会造成索引左移。
- `selected_room_names` 实际来自独立的 legacy `wechat_group_names` 候选列表，本来就没有与 stable ID 一一对应的契约。
- 删除一个群时按 stable ID 的索引同时 splice 三个数组，可能删除错误的 runtime 快照或候选群名。

桌面端问题：

- 保存时只保留当前 rooms 中 `selectable` 的 stable ID。
- 重扫后群列表尚未恢复、群暂时离线或 identity unresolved 时，用户只要保存其他设置，就会静默删除原 stable 目标群。
- `selectedNames` 没有与过滤后的 stable ID 同步，继续存在错位。

影响：重扫窗口内保存设置可能清空目标群、错配显示名或错写 legacy runtime 快照，造成后续消息拒收或投递错误。

### P1-4：现有候选模型无法安全表达多个目标，确认接口不能原样恢复

证据链：

- `wechat_group_identity_room_aliases` 对 `(stable_account_id, runtime_room_id)` 唯一，`wechat_group_identity_member_aliases` 对 `(stable_account_id, stable_room_id, runtime_sender_id)` 唯一；同一个新 runtime 实体只能指向一个 stable 实体。
- `record_room_alias_candidate()` / `record_member_alias_candidate()` 在候选已存在时会覆盖 `stable_*_id`，因此两个同名历史群或成员不能同时作为候选保留。
- 当前 `list_room_binding_candidates()` / `list_member_binding_candidates()` 只筛选实体 `status <> 'confirmed'`，无法列出“已确认旧实体 + 新 runtime 候选”；最小复现中写入 confirmed room 的 inactive candidate 后，候选列表仍为空。
- 当前没有 account 候选查询；`confirm_account_binding()`、`confirm_room_binding()` 和 `confirm_member_binding()` 也没有校验“当前待确认实体、目标实体、runtime alias 和页面读取版本”仍是同一组关系。

影响：仅删除 confirm API 的 early return 并恢复旧页面并不安全。候选可能丢失、被后到记录覆盖，或者用户基于过期页面把 runtime alias 绑定到错误作用域；必须同时修正候选表示与原子确认契约。

### P2-1：强标识来源与状态机仍缺少防冲突约束

- 当前安装版本的 `node_modules/wechaty/src/user-modules/contact.ts` 明确说明 `handle()` 可能因 puppet 实现拿不到，`weixin()` 已弃用；`node_modules/wechaty-puppet/src/schemas/contact.ts` 对 `address` 直接保留“what's this for?”注释。wechat4u mapper 虽把 raw `Alias` 同时映射到 `address/weixin`，但当前通用解析没有验证 puppet 来源，因此不能把任意 `address` 当强微信号。
- 强账号微信号出现多个候选时，代码仍继续尝试 runtime/profile fallback，没有进入 conflict。
- account alias 只保证“一个 stable account 一个 active alias”，没有拒绝同一个 `runtime_self_id + memory_path` 同时活跃在多个 stable account。
- Web confirm 分支保留在统一 early return 后面，形成不可达死代码；状态 API固定声明无需确认，掩盖真实冲突。

## 三、方案比较

### 方案 A：保留当前全自动恢复

优点是无需用户操作；缺点是群名、显示名和 profile 路径不具备授权强度，已出现可复现的跨账号/跨群数据泄露。否决。

### 方案 B：所有重扫绑定都人工确认

安全边界最清晰，也可直接复用提交前已有的确认服务与 Web 页面；缺点是每次正常重扫都需要用户处理账号、群和部分成员。可作为兜底，但不必让有强证据的场景也退化为手工。

### 方案 C：证据分级自动恢复，弱证据人工兜底（推荐）

唯一强账号/成员微信号和已确认的当前 runtime alias 可以自动恢复；profile 路径、群名、昵称只生成候选。无历史候选的新实体可创建隔离 stable ID，不继承任何旧数据。该方案同时满足最小操作成本和安全隔离要求。

## 四、目标状态机

### 4.1 Stable account

| 输入证据 | 结果 |
| --- | --- |
| 唯一强账号微信号命中，且 active runtime alias 不冲突 | 自动复用 confirmed stable account；弱 profile 候选不覆盖强证据，只写诊断 |
| 当前 active runtime alias 命中，且没有冲突强微信号 | 自动复用 |
| incoming 强微信号与 active alias 已保存的不同强微信号冲突，或同一强微信号命中多个账号 | 当前账号进入 `pending/conflict`，禁止 room/member 解析，等待人工选择 |
| 没有强微信号，只有 `memory_path + self_name` 一个或多个历史候选 | 为当前 runtime 创建自己的 `pending` account；alias 只指向该 pending account，历史账号仅作为只读目标候选 |
| 新强微信号没有强匹配，但 profile 候选均已有其他强微信号 | 创建新的 confirmed stable account；profile 弱匹配仅写诊断，不阻断、不继承 |
| 新强微信号没有强匹配，且 profile 候选缺少强微信号 | 创建自己的 `pending` account，并把无强标识历史账号作为人工候选 |
| 没有强微信号且没有历史账号 | 创建新的 confirmed 隔离 account；因为没有继承任何旧数据，不需要无意义的人工确认 |

账号 metadata 不得用新微信号覆盖已有不同微信号。强标识冲突必须保留旧值并写审计事件。pending account 的人工选择必须同时提供“绑定到某个历史账号”和“明确认作新账号”两种操作；选择历史账号时把 pending account 标记为 `superseded`，选择新账号时只把当前 pending account 改为 `confirmed`。

### 4.2 Stable room

| 输入证据 | 结果 |
| --- | --- |
| confirmed account 下已确认 runtime alias 命中 | 自动复用 confirmed stable room |
| 新 runtime room 只按群名命中一个或多个历史群 | 为当前 runtime room 创建自己的 `pending` room 并激活到它；历史群只作为只读目标候选，不激活、不继承 |
| 新 runtime room 没有任何历史候选 | 创建新的隔离 stable room；由用户在群选择页显式选中后生效 |
| 账号未确认、群名冲突或候选跨账号 | 未解析/冲突，禁止进入消息与长期数据链路 |

消息早于 rooms 快照时也必须执行同一规则；不能因为“目前只看到一个同名群”就确认。人工操作必须允许“绑定历史群”或“明确认作新群”：前者在事务内切换 alias 并把 pending room 标记为 `superseded`，后者只确认当前 pending room。未来若找到经过真实链路验证的稳定 room fingerprint，可单独计划增加自动证据，不在本轮猜测 `EncryChatRoomId`、成员集合或 owner 字段的稳定性。

### 4.3 Stable member

| 输入证据 | 结果 |
| --- | --- |
| confirmed room 内唯一强成员微信号命中 | 自动复用 confirmed stable member |
| 当前 active runtime alias 命中，且强微信号不冲突 | 自动复用 |
| 无强微信号、仅昵称命中一个或多个历史成员 | 为当前 runtime 创建 confirmed 隔离 member，同时动态返回全部只读历史候选；不继承旧画像或权限 |
| 强微信号重复/冲突 | 隔离当前 member，并要求人工选择或保持隔离 |
| 无强微信号且无历史候选 | 创建新的 confirmed 隔离 member |

人工确认把当前 runtime alias 从隔离 member 绑定到目标旧 member；原隔离实体标记为 `superseded` 并保留审计，不删除历史数据。确认前所有消息继续按隔离 member 处理，不能注入候选旧成员画像。

### 4.4 候选与确认契约

- alias 表只表示“当前 runtime 实体实际归属于哪个自身隔离/已确认 stable 实体”，不得再把历史目标实体写成 inactive alias candidate；这样同一个 runtime 不会在候选阶段提前指向旧权限作用域。
- account/room 的当前 `pending` 实体与 member 的当前 `auto_isolated` 实体负责保存 runtime 现场；候选 API 按 profile、群名或同群昵称动态列出**全部**历史目标，排除当前实体和 `superseded` 实体，不能使用 `LIMIT 1` 或“最近一条”。
- `IdentityResolution.status` 只使用 `confirmed`、`pending`、`superseded`；硬冲突通过 `metadata.conflict_reason` 和 `requires_confirmation=true` 表达。只有 `confirmed` account/room 可以成为权限、归档、记忆、画像、会话和 scheduler 作用域；confirmed `auto_isolated` member 只能使用自己的新作用域。
- 旧库中的 `legacy_imported` 只作兼容读取，行为等同 `pending`，不得在一次普通启动或消息到达时批量改成 confirmed；新代码不再写入该状态。旧自动恢复产生的 confirmed 数据由 Task 8 报告，不在启动迁移中猜测降级或拆分。
- identity 实体和 alias 行增加从 1 开始的 `binding_revision`；只在 status、父级、强标识、stable 归属或 active 状态变化时原子递增，普通 `last_seen_at`、显示名刷新不得让确认页面持续失效。不能用当前秒级 `updated_at/last_seen_at` 充当并发版本，因为同一秒内多次更新无法区分。
- GET `candidates` 返回 `entity_type`、current stable/runtime ID、target stable ID、证据类型、显示名、`current_binding_revision`、`target_binding_revision`、`alias_id` 和 `alias_binding_revision`。不得返回消息正文、媒体路径、数据库路径、MemoryCard 路径或原始 contact payload。
- confirm 请求必须携带 current stable ID、target stable ID、runtime ID 和上述 binding revision/alias 字段。服务端在同一 SQLite 事务内重新校验父级 confirmed、当前 active alias、目标作用域、各 binding revision 和强 ID 冲突；任一不一致返回 `409 stale/conflict`，不修改 alias。
- account/room 选择“认作新实体”时 target 等于 current；选择历史实体时先停用 current alias，再激活 target alias，最后把 current 标记为 `superseded` 并写 binding event。member 的 current 隔离实体已可安全使用，无需“确认保持隔离”；只有用户主动绑定历史 member 时才切换。不得自动合并 current 实体在隔离期产生的长期数据。

### 4.5 配置与 API

- `wechat_group_stable_room_ids` 是目标群唯一主配置。
- `wechat_group_room_ids` 只由后端根据 active alias 生成 legacy runtime 快照，前端不再自行按数组映射。
- 保存请求显式包含 `wechat_group_stable_room_ids` 时（包括空数组）以它为准；旧客户端仅提交 `wechat_group_room_ids` 时，只允许通过当前 confirmed active alias 一对一迁移为 stable IDs。任一 runtime ID 未解析或歧义时整次保存返回冲突并保持原配置，不按群名补猜。
- `wechat_group_names` / `wechat_group_free_reply_names` 保持独立候选字段，不参与 stable ID 显示名映射和直接路由。
- `/api/channels` 增加派生只读结构 `selected_rooms`：每项包含 `stable_room_id`、`runtime_room_id`、`room_name`、`binding_status`。不新增持久化配置键。
- Web 与桌面端都按 stable ID 增删；未在线、未出现在本次 rooms 快照中的已选群默认保留，只有用户明确点击删除才移除。
- 恢复并加固 `accounts/confirm`、`rooms/confirm`、`members/confirm`，按 4.4 的 current/target/version 契约执行 account -> room -> member 顺序和跨作用域校验；不能原样启用当前 dead code。

## 六、验收标准

1. 不同强微信号账号永远不会因相同 MemoryCard 路径或显示名共享 `wga_*`。
2. 任一同名群都不能仅凭到达顺序占用旧 `wgr_*`。
3. 群名和昵称候选在确认前不能读取旧群/旧成员的权限、记忆、画像、归档或会话。
4. runtime sender ID 变化但唯一强成员微信号保持不变时可自动恢复；无强微信号时有可操作的人工绑定路径，且确认前不继承旧权限或画像。
5. Web 与桌面保存任意其他设置时，不会删除离线或未出现在本次 rooms 快照中的 stable 目标群。
6. `wechat_group_names` 与 stable room 列表不再按索引耦合，也不直接放行消息或自由回复。
7. stable -> active runtime 仍只用于真实发送；无 active runtime 时 scheduler 保持 waiting，不退回旧 runtime 猜测投递。
8. 审计脚本只报告疑似错误绑定，运行前后 identity 表逻辑数据完全一致；真实数据拆分/合并必须另行形成实例级映射计划。
9. 同一 runtime 命中多个弱证据目标时，候选 API 返回全部目标且 alias 始终指向当前隔离实体；过期或跨作用域确认不会产生任何数据库修改。
10. 全量 Python、Node、Web 语法、桌面测试和桌面构建通过，且完成真实微信重扫矩阵。

## 七、回退边界

- 开发前必须备份配置、identity DB、归档/画像 DB；MemoryCard 登录态由独立计划管理，本计划不删除。
- 回退代码时保留新增 stable/runtime 数据与 binding events，不执行数据库删除。
- 若新状态机无法确认身份，安全行为是停止继承并提示确认，不得回退到群名、昵称或“最近一条记录”猜测。
- 当前工作区存在多批未提交内容，禁止使用 `git reset --hard`、`git checkout --` 或批量覆盖；只按文件和 hunk 审核本计划改动。
