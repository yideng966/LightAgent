# GitHub Webhook 全事件通知配置开发计划

## 1. 计划状态

- 计划日期：2026-07-28
- 当前状态：方案已形成，代码尚未实施
- 关联计划：`plans/20260723_GitHub提交通知微信群.md`
- 目标入口：Web 控制台「群聊 -> 基础设置 -> GitHub Webhook 通知」
- 兼容基线：现有 `push` 提交通知、`/api/github/webhook` 路由、Webhook Secret、稳定群投递和 scheduler 重试链路

## 2. 背景与现状

当前功能已经具备一条安全、可重试的固定投递链路：

1. `channel/web/web_channel.py` 暴露 `/api/github/webhook`。
2. `channel/web/github_commit_webhook.py` 对原始请求体做 HMAC-SHA256 验签，校验 25 MB 请求上限、JSON 类型和 `X-GitHub-Delivery`。
3. 服务只接受 `ping` 和 `push`；其他 `X-GitHub-Event` 在验签后直接返回 `unsupported_event`。
4. `push` 继续经过单仓库、分支和稳定群过滤，再聚合 commit 文本。
5. 消息通过 `enqueue_wechat_group_message()` 写入 scheduler，由微信群稳定身份解析后异步发送。
6. SQLite delivery 表和 scheduler 任务 ID 共同保证同一投递不会重复发送。
7. Web 控制台只能配置仓库、分支、单个目标群、commit 展开数、重试、去重和 Secret，不能选择其他 GitHub 事件。

本次扩展的核心不是“把任意 JSON 原样转发到群”，而是把接收层从仅 `push` 扩展到仓库 Webhook 可发送的全部事件，再由 UI 控制哪些事件和动作允许进入群投递链路。

## 3. 目标定义

### 3.1 “全部消息”的定义

本计划将“全部消息”定义为：同一个 GitHub **仓库级 Webhook** 在选择 `Send me everything` 后可投递的全部仓库级事件。

- 所有签名有效、格式合法的仓库级事件都由现有端点接收并返回明确结果。
- `ping` 只用于连通性检查，不进入群投递配置，也不创建 scheduler 任务。
- UI 提供“选定事件”和“全部事件”两种模式。
- 选定事件模式只推送勾选的事件；事件还可按 `action` 进一步过滤。
- 全部事件模式推送当前已知以及未来新增的仓库事件；未知事件只能使用安全通用摘要。
- 未被配置选中的事件仍返回 `202 Accepted` 和 `ignored` 结果，避免 GitHub 将正常过滤误判为投递失败。

### 3.2 业务目标

- 支持代码、PR、Issue、讨论、工作流、部署、发行、安全告警、仓库管理等仓库级事件。
- 用户可以在 Web 控制台决定事件类型和动作是否推送到群。
- 保留单仓库、单目标稳定群模型，不扩大消息路由职责。
- 所有消息使用确定性模板，不调用 LLM，不进入 Bridge、Agent、插件、归档、记忆或画像链路。
- 默认配置保持当前行为：只推送 `push`，只允许既有分支配置，继续忽略标签 push、删除 ref 和无 commit 的 push。
- 不回显 Secret，不持久化原始 payload，不在日志中输出评论正文、安全告警内容或其他敏感字段。

## 4. 本期边界

### 4.1 纳入范围

- 单个仓库的 repository webhook。
- 一个 Webhook Secret、一个精确仓库、一个已选择的稳定微信群。
- 事件级筛选和可选的 action 级筛选。
- 现有 `push` 专用格式，以及其他仓库事件的确定性安全摘要。
- 当前 GitHub 官方仓库事件目录和未来未知事件的安全降级。
- Web 配置读写、配置校验、中文/英文 UI 文案、部署文档和回归测试。

### 4.2 不纳入范围

- 组织、企业、Marketplace 或 GitHub App 专属 Webhook。
- 多仓库规则、多 Secret、多目标群、同一事件按不同规则分发到不同群。
- 通过 GitHub API 自动创建、修改或探测远端 Webhook。
- 用户自定义模板、表达式、JSONPath、脚本或原始 payload 转发。
- 事件历史管理页面、原始 payload 重放、跨 delivery 语义去重、消息合并或批量摘要。
- GitHub Enterprise Server 的独立兼容承诺。
- `desktop/` 历史归档端的任何修改。

上述能力若后续确有需求，应另立计划，不能在本次实现中顺手扩展。

## 5. 官方约束与依据

截至 2026-07-28，GitHub 官方文档确认：

- `X-GitHub-Event` 表示事件名，`X-GitHub-Delivery` 是全局唯一 delivery GUID。
- `X-Hub-Signature-256` 是基于原始请求体和 Secret 的 HMAC-SHA256 签名。
- Webhook payload 上限为 25 MB；超过上限时 GitHub 本身可能不投递。
- 不同事件只对特定 webhook 类型可用，仓库 webhook 不能订阅组织或 GitHub App 专属事件。
- 大多数 payload 包含 `sender`，但系统触发场景可能使用 `ghost`，不能把 sender 当作安全身份依据。
- GitHub 建议只订阅真正处理的事件并尽快返回成功响应；本需求选择远端 `Send me everything` 时，本地筛选必须保持轻量且无外部 API 调用。

实施时以以下官方资料为准，并在事件目录变化时显式更新代码快照和测试：

- [Webhook 事件和 payload](https://docs.github.com/en/webhooks/webhook-events-and-payloads)
- [创建 Webhook](https://docs.github.com/en/webhooks/using-webhooks/creating-webhooks)
- [验证 Webhook 投递](https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries)
- [Webhook 最佳实践](https://docs.github.com/en/webhooks/using-webhooks/best-practices-for-using-webhooks)

## 6. 总体架构

```text
GitHub repository webhook
        |
        v
/api/github/webhook
  请求长度 -> 原始体验签 -> Content-Type/JSON -> 必要 Header
        |
        +-- ping ------------------------------> 202 accepted，不入队
        |
        v
仓库精确匹配 -> 事件注册表 -> event/action 配置过滤
        |                       |
        |                       +-------------> 202 ignored，不入队
        v
事件专用格式器或安全通用格式器
        |
        v
X-GitHub-Delivery 去重 -> scheduler 固定消息任务
        |
        v
stable_room_id -> 当前 runtime room -> Wechaty 群发送
```

### 6.1 保持不变的契约

- 路由继续使用 `/api/github/webhook`，避免公网反向代理和 GitHub 配置迁移。
- 环境变量继续使用 `LIGHTAGENT_GITHUB_WEBHOOK_SECRET`，且优先于本地配置。
- 继续使用 `github_commit_notify_*` 配置前缀承载现有字段，避免已有用户的 Secret 和配置迁移风险。
- 继续使用 `source = "github_webhook"`、`external_delivery_id` 和现有 scheduler 投递标记。
- 继续使用 `wechat_group_stable_room_ids` 作为目标群信任边界。
- 继续复用现有 SQLite delivery 表；本期不新增表、不保存 payload，也不要求数据库迁移。

### 6.2 新增模块边界

新增 `channel/web/github_webhook_events.py`，只承载纯数据和纯格式化逻辑：

- 仓库级事件注册表。
- 事件分类、中英文名称、已知 action、兼容/弃用标记。
- 是否使用专用格式器、允许读取的 payload 字段路径和安全链接路径。
- 事件/action 配置归一化与匹配函数。
- 通用安全摘要和各类专用摘要格式器。

`channel/web/github_commit_webhook.py` 继续负责接收编排、验签、仓库/群过滤、delivery 去重和 scheduler 入队。这样可以保留现有安全入口，又避免把几十种事件格式器堆进同一个服务类。

## 7. 事件目录设计

### 7.1 注册表结构

每个事件定义至少包含以下只读字段：

| 字段 | 说明 |
| --- | --- |
| `name` | `X-GitHub-Event` 的精确值，例如 `pull_request` |
| `category` | UI 分组标识 |
| `labels` | 中文和英文显示名 |
| `actions` | 当前官方已知 action；无 action 的事件为空 |
| `formatter` | 专用格式器标识；缺省时使用通用格式器 |
| `legacy` | 是否为 GitHub 已宣布关闭或兼容保留的事件 |
| `high_volume` | 是否需要在 UI 中显示高频提示 |
| `safe_fields` | 通用格式器允许读取的代码内白名单字段 |
| `url_fields` | 允许作为详情链接的 GitHub 对象 URL 字段 |

注册表是运行时代码快照，不在启动或打开 UI 时联网抓取 GitHub 文档。更新事件目录必须通过代码评审和回归测试完成。

### 7.2 首期仓库事件快照

根据 2026-07-28 GitHub 官方事件页面，首期目录包含 53 个可选仓库事件；`ping` 单独作为健康检查处理。

| 分类 | 事件 |
| --- | --- |
| 代码与引用 | `push`、`create`、`delete`、`commit_comment`、`fork`、`gollum`、`public` |
| 协作与评审 | `discussion`、`discussion_comment`、`issue_comment`、`issue_dependencies`、`issues`、`label`、`milestone`、`pull_request`、`pull_request_review`、`pull_request_review_comment`、`pull_request_review_thread`、`sub_issues` |
| CI/CD 与部署 | `check_run`、`check_suite`、`deployment`、`deployment_status`、`page_build`、`status`、`workflow_job`、`workflow_run` |
| 发行与包 | `release`、`package`、`registry_package` |
| 仓库治理 | `branch_protection_configuration`、`branch_protection_rule`、`custom_property_values`、`deploy_key`、`member`、`meta`、`repository`、`repository_import`、`repository_ruleset`、`security_and_analysis`、`team_add` |
| 安全 | `code_scanning_alert`、`dependabot_alert`、`repository_advisory`、`repository_vulnerability_alert`、`secret_scanning_alert`、`secret_scanning_alert_location`、`secret_scanning_scan` |
| 项目与关注 | `project`、`project_card`、`project_column`、`star`、`watch` |

`repository_vulnerability_alert` 以及 GitHub 已标记为 legacy/closing down 的事件在 UI 中保留兼容标识，不作为推荐默认项。

### 7.3 未知未来事件

- 选定事件模式：未知事件返回 `202 ignored`，原因是 `event_not_selected`。
- 全部事件模式：未知且符合事件名格式的仓库事件进入安全通用格式器。
- 通用格式器只输出事件名、action、仓库、sender 和代码白名单中的标题/状态/链接。
- 通用格式器禁止递归遍历对象、禁止 JSON 序列化、禁止输出任意 key/value 列表。
- 未知事件 payload 缺少仓库时按非仓库事件忽略，不能绕过本期作用域。

## 8. 配置模型与兼容策略

### 8.1 新增配置

在保留全部现有字段的基础上，只新增以下三个配置：

```json
{
  "github_commit_notify_event_mode": "selected",
  "github_commit_notify_events": ["push"],
  "github_commit_notify_event_actions": {}
}
```

| 配置 | 类型 | 默认值 | 语义 |
| --- | --- | --- | --- |
| `github_commit_notify_event_mode` | string | `"selected"` | `selected` 仅允许所选事件；`all` 允许全部当前和未来仓库事件 |
| `github_commit_notify_events` | string[] | `["push"]` | 选定事件模式下允许推送的事件 |
| `github_commit_notify_event_actions` | object | `{}` | 按事件限制 action；缺少 key 或空数组表示该事件允许全部 action |

action 配置示例：

```json
{
  "github_commit_notify_event_actions": {
    "pull_request": ["opened", "closed", "reopened"],
    "workflow_run": ["completed"],
    "issues": []
  }
}
```

### 8.2 现有字段语义

- `github_commit_notify_repository`：继续要求精确的 `owner/repository`，大小写不敏感比较。
- `github_commit_notify_branches`：只作用于 `push` 提交聚合，不隐式过滤 PR、workflow 或其他事件。
- `github_commit_notify_max_commits`：只作用于 `push`。
- `github_commit_notify_stable_room_id`：所有允许事件共享一个目标稳定群。
- `github_commit_notify_retry_hours`、`github_commit_notify_delivery_retention_days`：对所有入队 GitHub 事件生效。
- `github_commit_notify_webhook_secret`：继续只做本地 Secret fallback，API 不返回真实值。

### 8.3 兼容行为

- 老配置缺少三个新字段时，运行时按 `selected + [push] + {}` 解释。
- `config.py` 和 `config-template.json` 的新默认值同样保持仅 `push`。
- 现有 `push` 文本格式、分支过滤、无 commit 过滤、标签/删除 ref 过滤和最大 commit 数不变。
- 不重命名旧配置、不自动删除旧字段、不修改数据库 schema。
- UI 第一次保存后写入新字段，但不要求一次性迁移已有本地配置。

### 8.4 服务端校验

- `event_mode` 只允许 `selected` 或 `all`。
- `events` 去重并只保留注册表中的仓库事件；`ping` 不允许进入列表。
- 选定事件模式在启用通知时至少需要一个事件。
- `event_actions` 必须是对象，key 必须是已知事件，value 必须是去重后的字符串数组。
- action 非空时只允许注册表已知值；空数组表示全部 action，便于兼容 GitHub 后续新增 action。
- 启用状态保存时必须具备合法仓库、已选择稳定群和已配置 Secret；关闭状态允许保存未完成草稿。
- 服务端是最终校验边界，不能只依赖前端控件。

## 9. 请求处理顺序

`GitHubCommitWebhookService.handle()` 按以下顺序调整：

1. 检查功能开关和请求体类型/长度。
2. 使用原始请求体校验 `X-Hub-Signature-256`，验签失败时不解析 JSON。
3. 校验 `application/json` 并解析顶层对象。
4. 校验 `X-GitHub-Event` 格式；除 `ping` 外统一校验 `X-GitHub-Delivery`。
5. `ping` 返回 `accepted`，不检查目标群、不入队。
6. 从 payload 读取 `repository.full_name`，缺失时按非仓库事件忽略，错误仓库按 `repository_not_allowed` 忽略。
7. 根据 `event_mode`、事件列表和 action 列表判定是否允许；被过滤事件返回 `202 ignored`。
8. 只有允许推送的事件才校验目标稳定群是否仍在 `wechat_group_stable_room_ids` 中。
9. `push` 继续执行既有分支、ref、删除和 commit 校验；其他事件进入对应格式器。
10. 格式器字段缺失时使用安全通用摘要，不因单个可选字段缺失返回 500。
11. 以 `X-GitHub-Delivery` 生成任务 ID、检查 delivery 状态、写入 scheduler 并记录 queued。
12. 返回 `202 accepted`；scheduler 成功发送后继续通过现有回调标记 delivered。

入队 metadata 增加 `github_event` 和 `github_action`，保留 `source`、`external_delivery_id`、`repository` 和 `ref`。非 push 事件的 `ref` 使用空字符串或格式器提取到的安全 ref，满足现有表结构而不扩表。

## 10. 消息格式设计

### 10.1 通用结构

除 `push` 保留旧格式外，其他事件统一使用短文本结构：

```text
[GitHub PR] owner/repository
动作：opened
操作者：alice
内容：#123 修复登录超时
状态：open
查看详情：https://github.com/owner/repository/pull/123
```

- 缺少 action 时不显示动作行。
- sender 为 `ghost` 或缺失时显示“系统”，不得用于鉴权或权限判断。
- 文本继续经过控制字符清理、单行压缩和总字符数限制。
- 链接只从注册表允许的 GitHub 对象字段读取，不读取用户自定义 URL 字段。

### 10.2 专用格式器

首期至少为以下高价值事件族提供专用格式器：

- `push`：保留现有 commit 聚合格式。
- PR：`pull_request`、review、review comment、review thread。
- Issue/讨论：`issues`、`issue_comment`、`discussion`、`discussion_comment`。
- CI：`workflow_run`、`workflow_job`、`check_run`、`check_suite`、`status`。
- 部署与发行：`deployment`、`deployment_status`、`release`、`package`。
- ref 与仓库：`create`、`delete`、`repository`、`repository_ruleset`。
- 安全：Dependabot、code scanning、secret scanning、repository advisory。

其他已知事件由注册表驱动的安全通用格式器处理。格式器不得调用 GitHub REST API，也不得为了补字段阻塞 Webhook 响应。

### 10.3 内容安全

- 不输出完整 issue、PR、discussion 或 comment body，只输出标题、编号、状态和详情链接。
- 不输出 Secret scanning 的 secret、location 详情、匹配片段或 token。
- 不输出 `hook.config`、`client_payload`、认证字段、邮箱、安装 token 或任意原始对象。
- 不把 payload 写入 SQLite、scheduler metadata、Agent workspace 或日志。
- 日志只记录 delivery ID、事件、action、仓库、过滤原因、任务 ID 和最终状态。
- 所有输出均为纯文本，不执行 Markdown、HTML、表达式或用户模板。

## 11. Web 控制台方案

### 11.1 信息架构

保留「群聊 -> 基础设置」位置，将区域标题从“GitHub 提交通知”调整为“GitHub Webhook 通知”。页面主体保持紧凑：

1. 启用开关、仓库和目标群。
2. “选定事件 / 全部事件”分段控件。
3. 事件选择摘要和“配置事件”按钮。
4. 仅在 `push` 被允许时显示分支与最大 commit 数。
5. 重试、去重、Webhook URL 和 Secret 放入“高级设置”折叠区。

事件目录不直接全部展开在基础设置页，避免 53 个事件撑长页面。

### 11.2 事件配置弹窗

使用现有控制台模态层模式实现二级弹窗，不引入新 UI 框架：

- 顶部提供事件搜索，可按中文名、英文名和原始事件名匹配。
- 左侧或顶部使用类别筛选；窄屏改为单列筛选器。
- 每个事件使用原生 checkbox，显示中文名、原始事件名、高频/兼容状态。
- 提供“选择常用事件”“全选仓库事件”“清空”三个明确操作。
- 已启用且存在 action 的事件可展开“动作过滤”；默认“全部动作”。
- action 使用 checkbox 列表，不用逗号文本输入，避免拼写错误。
- 弹窗内“取消”丢弃草稿，“应用”只更新当前页面表单；页面总保存按钮才写入后端。
- 全部事件模式仍允许为已知事件设置 action 例外；未知未来事件默认全部 action。

“常用事件”只作为快捷选择，不改变默认配置，建议集合为 `push`、`pull_request`、`issues`、`issue_comment`、`workflow_run`、`release`。

### 11.3 交互与可访问性

- 使用 `dialog`/`aria-modal`、`fieldset`/`legend`、可见 label 和明确焦点顺序。
- 打开弹窗后聚焦搜索框，关闭后把焦点还给“配置事件”按钮，`Escape` 可关闭。
- 保存失败时在相关字段下显示原因，并聚焦第一个错误字段；不能只用 toast 或颜色提示。
- 所有按钮和输入触控区域至少 44px，键盘可完成搜索、选择、展开、应用和取消。
- 使用现有图标体系，不新增 emoji 或另一套图标库。
- 延续现有亮色/暗色 token，正文对比度至少 4.5:1，焦点环清晰可见。
- 375px 宽度不得横向滚动；事件名允许换行，原始事件名可在必要时断行。
- 弹窗内容独立滚动，底部操作栏保持可见，但不得遮挡最后一个事件。
- 中英文文案同步补齐，不把内部配置 key 或未经解释的原始状态暴露给普通用户。

## 14. 测试与验证矩阵

### 14.1 接收与安全

- 正确/错误/缺失 `X-Hub-Signature-256`。
- 超过 25 MB、非法 Content-Length、错误 Content-Type、非法 UTF-8/JSON、非对象 payload。
- 缺失或非法 `X-GitHub-Event`、`X-GitHub-Delivery`。
- 验签失败时确认 JSON 不被解析、scheduler 不被调用。
- 配置 API 和日志中确认 Secret、payload canary、扫描位置和评论正文均不泄漏。

### 14.2 筛选

- 默认配置只允许既有 `push/main`。
- selected 模式：已选/未选事件、有/无 action、action 命中/不命中。
- all 模式：已知事件、未知未来事件、未知 action。
- `ping` 永不入队；组织/App 专属或缺少仓库的事件不入队。
- 错仓库、目标群未选择、stable room 已移除等错误路径。

### 14.3 格式化

- 每个专用事件族至少覆盖一个真实结构样例和一个缺字段样例。
- 通用格式器只输出白名单字段，任意嵌套对象不会被展开。
- `push` 文本与当前快照一致，commit 数和总字符数限制继续生效。
- URL、控制字符、多行标题、Unicode、ghost sender 和超长字段正确降级。
- 安全事件只显示编号/状态/仓库/安全详情链接，不显示 secret 或位置内容。

### 14.4 去重与投递

- 同一 selected delivery 最多创建一个任务。
- queued/delivered 重投递均不重复发群消息。
- 被过滤 delivery 不创建记录；配置改变后手动 redelivery 按新配置重新判定。
- 非 push 任务仍携带 stable receiver、禁止 mention，并在发送成功后标记 delivered。
- 群离线或身份未恢复时在 retry window 内继续等待，过期逻辑不变。

### 14.5 UI

- 事件目录搜索、分类、全选、清空、常用选择和 action 展开。
- 模式切换保留选定事件草稿，取消弹窗不污染页面状态。
- 开启时前端校验仓库、目标群和选定事件；运行时校验 Secret。
- 环境变量接管 Secret 时输入和显隐按钮禁用。
- 1440px/1024px/768px/375px、亮色/暗色、键盘焦点、Escape、滚动位置和错误聚焦。
- 事件名最长场景无文本溢出，弹窗底部操作栏不遮挡内容。

## 15. 人工验收场景

在 GitHub 测试仓库把 Webhook 事件设置为 `Send me everything`，依次验证：

2. 默认配置下 push 到 `main` 仍收到原提交聚合消息。

5. 未选择 `pull_request.synchronize` 时继续 push PR 分支，群内无 PR 更新消息。
6. 选择 `workflow_run.completed` 后完成一次 workflow，群内收到结果和链接。
7. 选择 `release.published` 后发布测试 Release，群内收到发行摘要。
8. 在 GitHub Webhook 页面 redeliver 已发送事件，群内不重复发送。
9. 切换为全部事件模式后触发一个未配置专用格式器的仓库事件，群内只收到安全通用摘要。
10. 临时移除目标群或断开微信群登录，确认任务等待并在恢复后发送。

## 16. 风险与控制

| 风险 | 控制措施 |
| --- | --- |
| `Send me everything` 导致消息量激增 | 默认仍为 selected/push；全部模式明确标记高频事件，不默认开启，不在本期隐式批量发送 |
| GitHub 新增事件或 action | 全部模式使用安全通用摘要；注册表快照和测试要求显式更新，空 action 列表允许未来 action |
| payload 包含 Secret、正文或敏感安全信息 | 代码白名单字段、无递归序列化、无 payload 持久化、敏感 canary 测试 |
| 多种事件描述同一动作造成群内语义重复 | 不做危险的跨 delivery 合并；UI 对 `push` 与 `create/delete` 等重叠事件给出清晰名称，由用户选择 |
| 事件格式差异导致 KeyError 或 500 | 所有读取使用类型检查和安全 getter，专用格式器失败时降级为通用摘要 |
| 旧配置升级后通知范围变化 | 默认新字段严格等价于旧 push 行为，旧字段和路由不重命名 |
| 与数据库双后端计划冲突 | 本期不改 delivery schema；若数据库计划先落地，只适配其 Store 接口，不重复设计迁移 |
| UI 事件列表过长 | 基础页只显示摘要，完整目录放入可搜索、分类的二级弹窗 |

## 17. 回滚方案

- 最小业务回滚：在 UI 把模式改回“选定事件”，只保留 `push`。
- 紧急停止：关闭 `github_commit_notify_enabled`，端点恢复 `404 webhook_disabled`。
- 代码回滚：删除三个新配置不会破坏旧版本，旧版本继续读取原字段和 Secret。
- 路由、环境变量和 delivery 表均不迁移，因此无需修改反向代理、GitHub Payload URL 或恢复数据库。
- 已创建的 scheduler 任务按创建时的不可变文本继续执行；如需取消任务，沿用现有 scheduler 管理能力，不直接操作 SQLite。

## 18. 验收标准

- GitHub 仓库 Webhook 选择 `Send me everything` 后，所有签名有效、格式合法的仓库事件均得到明确 `202 accepted/ignored` 或可诊断的 4xx/5xx。
- `ping` 永不创建群消息。
- selected 模式严格按事件和 action 推送；all 模式可处理当前 53 个仓库事件及未来未知仓库事件。
- 默认配置与升级前 `push/main` 行为和文本兼容。
- 错仓库、未选择事件、action 不匹配、组织/App 专属事件和未绑定稳定群均不会误发。
- 所有允许事件复用同一 scheduler、stable room、重试和 delivery 去重链路。
- 消息不调用 LLM、不进入 Agent，不包含原始 payload、Secret、安全扫描敏感内容或本机路径。
- 配置 API 不回显 Secret，环境变量优先级不变，前后端都拒绝非法事件配置。
- Web 控制台能完成模式、事件、action、仓库、目标群和高级参数配置，并通过桌面/移动、亮色/暗色和键盘验收。
- 专项测试、微信群投递回归、全量 Python 测试、Python/JavaScript/JSON 语法和 `git diff --check` 均通过。
- 实施完成后已回写本计划、`AGENTS.md` 和 `CHANGES.md`。
