# 修复微信群扫码入群识别

## 背景

2026-07-29 09:30 左右，线上 `LightAgent` 群出现成员通过他人分享的二维码入群，但机器人未发送配置好的欢迎消息。只读日志与线上依赖源码确认：`wechaty-puppet-wechat4u 1.14.14` 对该系统消息要求开引号后存在固定空格，实际微信文案没有空格，导致消息退化为普通文本并进入自由回复链路。

## 目标

- 兼容实际文案：`"成员"通过扫描"分享人"分享的二维码加入群聊`。
- 只信任 wechat4u 原始 `MsgType=10000` 系统消息，普通成员发送同文案不能伪造入群事件。
- 复用现有 `room_join`、稳定群门禁、欢迎配置和发送链路，不新增独立欢迎逻辑。
- 成员 ID 暂时无法解析时，继续使用现有 `member_info_missing` 降级行为。

## 实施步骤

- [已完成] 在 sidecar core 增加纯函数，校验系统消息类型、群 ID 和扫码文案并返回结构化名称与时间。
- [已完成] 在 sidecar 消息入口补充兼容接线，优先尝试解析成员 ID，再进入现有 `handlePuppetRoomJoin()`。
- [已完成] 增加正向、安全边界、成员查询降级和源码接线回归测试。
- [已完成] 更新 `CHANGES.md`，运行 Node 全量测试、Python 相关回归与语法检查。

## 边界

- 不直接修改 `node_modules`，避免镜像重建后丢失。
- 不顺带扩展其他尚未观察到的微信系统文案。
- 本任务只修改本地仓库，不更新或重启远端 Docker。

## 实际结果

已在 `wechaty-sidecar-core.mjs` 增加受限兼容解析，只接收 wechat4u 原始 `MsgType=10000`、原始群 ID 与当前房间一致且精确命中无空格扫码文案的消息。`wechaty-sidecar.mjs` 在普通消息下发前构造 fallback puppet 入群事件并复用 `handlePuppetRoomJoin()`；成员查询失败时保留 runtime 群与事件时间，由现有构造器显式产生 `member_info_missing=true`。
