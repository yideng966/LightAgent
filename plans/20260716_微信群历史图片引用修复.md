# 微信群历史图片引用修复方案

## 背景

2026-07-16 的真实微信群链路中，用户引用群内历史图片并询问“看我当前配置”时，`wechaty-puppet-wechat4u` 已将引用消息展示为：

```text
「发送者：[图片]」
- - - - - - - - - - - - - - -
@机器人 看我当前配置
```

但 CowAgent 归档中的 `quote` 为空，导致多模态服务无法按被引用消息 ID 取得真实图片。当前图片意图规则也没有识别“看我当前配置”，最终 Agent 根据工作空间信息自行构造了不存在的临时路径并调用 Vision。

原图实际仍保存在 `~/.cow/wechat_group/media/<room_id>/<message_id>.jpg`，问题发生在引用结构化解析和候选图片绑定阶段，不在 Vision 文件读取阶段。

## 目标

1. 从 Wechaty 原始消息载荷中稳定解析 `appmsg.type = 57` 的 `refermsg`。
2. 将 `svrid`、引用消息类型、发送者和内容转换为现有 `quote` 结构，通过 JSON Lines 协议传给 Python 通道。
3. 让引用图片优先按 `quote.message_id` 从当前稳定群归档中取得真实 `media_path`。
4. 当结构化引用暂时不可用时，对包含引用图片展示文本的请求启用受限回退，只能选择当前群、当前发送者或唯一时间窗口内的真实归档图片。
5. 保持真实媒体路径只在服务端传给 Vision，不写入 LLM prompt、诊断字段或会话历史。

## 非目标

- 不修改 Vision Provider 或模型 API。
- 不引入新的图片存储系统。
- 不扩大跨群图片检索范围。
- 不允许模型提供或猜测本地图片路径。
- 不改动桌面端或其他消息渠道。

## 设计

### 1. 规范化引用 XML

在 `wechaty-sidecar-core.mjs` 中复用现有 XML 解析器，并对原始载荷做以下处理：

1. 按 `Content`、`OriginalContent`、`OriContent`、`MMActualContent` 顺序收集候选字段并去重。
2. 解码 XML 实体，截取第一个 `<msg` 到最后一个 `</msg>`，去除群发送者前缀和尾部噪声。
3. 逐个解析候选，优先返回含 `appmsg` 的有效结果。
4. 对 `refermsg` 的单对象或单元素数组形态做兼容归一化。
5. 不把原始 XML 写入日志或侧车事件。

### 2. 保守图片回退

在 `wechat_group_multimodal_context_service.py` 中扩充图片引用意图识别：

- 明确识别 Wechaty 展开的 `「发送者：[图片]」` 引用文本。
- 识别与该引用块同时出现的“看我当前配置”等查看图片内容请求。
- 回退仍复用现有当前群、同发送者、唯一近期图片和歧义拒绝规则，不直接从文本生成路径。

### 3. 安全边界

- 结构化引用查询继续使用当前 `stable_room_id`。
- 归档结果必须是图片类型且存在非空 `media_path`。
- 多张候选无法唯一确定时返回 `ambiguous_recent_images`，不猜测。
- LLM 只接收 Vision 摘要及安全元数据，不接收真实路径。

## 真实链路复测反馈

2026-07-16 20:29 至 20:31 的真实微信群复测未通过，计划重新打开：

### 二次修复设计

1. Sidecar 直接使用 `xml2js`，与 `wechaty-puppet-wechat4u` 的 `parseAppmsgMessagePayload()` 保持同源解析行为；`extractQuotedMessageFromRawPayload()` 改为异步并由消息处理函数显式 `await`。
2. `xml2js` 作为 Sidecar 直接依赖声明，移除 Sidecar 已不再直接使用的 `fast-xml-parser`；同步更新 lock 文件。
3. 同发送者近期图片只有一张时才允许 `same_sender_recent_image` 回退；超过一张时返回 `ambiguous_same_sender_images`，禁止按最新时间猜测。
4. 增加与真实失败一致的测试：结构化引用通过 `svrid` 精确命中较早图片；结构化引用缺失且同发送者存在两张图片时不调用 Vision。

## 精准引用根因与第三轮修复

- 当前 Sidecar 只调用 `puppet.messageRawPayload()`；方法不可用或调用抛错时使用空 `catch` 静默放弃，没有读取同一 Puppet 实例已经存在的缓存，也无法判断失败阶段。

### 第三轮修复设计

1. 新增可测试的原始载荷解析入口，依次尝试：
   - `puppet.messageRawPayload(message_id)`；
   - `puppet.cacheMessageRawPayload.get(message_id)`；

2. 原始载荷诊断只包含状态，不包含 `Content`、XML、路径或其他原始数据：
   - `status`：`resolved / missing`；
   - `source`：`puppet_method / puppet_cache`；
   - `method_error`：归一化错误分类；
   - `has_content / has_original_content / msg_type / app_msg_type`。
3. 引用解析诊断只记录候选数量、成功解析数量和状态：
   - `quote_parsed / not_quote / refermsg_missing / appmsg_missing / xml_candidate_missing`。
4. Sidecar 通过现有 message 事件追加 `quote_diagnostics`；Python 消息适配器读取后写入当前群归档 metadata，并在多模态选择日志中输出关键状态。
