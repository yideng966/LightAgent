# 修复表情包直接解读回复开发计划

## 关联问题

- GitHub Issue：#25
- 标题：表情包发送解读异常

## 目标

群成员发送未明确触发机器人的表情包时，只生成安全的视觉语义并进入群聊公开上下文，由既有自由回复规则决定是否接话；不得因为表情包本身直接触发模型回复。

## 边界

- 保留表情包素材采集、视觉摘要、多模态上下文和表情包发送工具。
- 保留真实 @、引用机器人等明确触发场景的直接回复能力。
- 普通表情包必须复用既有自由回复本地判定、Scorer、worker 和最终主链路，不新增独立回复引擎。
- 表情包传输 XML、媒体路径和技术描述不得进入模型或群消息正文。

## 实施步骤

1. 核对 sidecar 消息类型、Python 消息投影、归档与多模态摘要的现有顺序。
2. 调整普通表情包的触发路由，使语义摘要先归档，再按自由回复规则形成候选。
3. 保持明确触发和媒体失败场景的既有安全边界。
4. 增加普通表情包不直接回复、命中自由回复才回复、明确触发仍可回复的回归测试。
5. 更新当前文档、`AGENTS.md`、`CHANGES.md` 并回写本计划。
6. 以单独 Git 提交交付 Issue #25；全部发布引用推送成功后关联关闭问题。

## 实际改动与验证结果

### 根因

- sidecar 正确上报 `message_type = sticker`，Python 适配层将其映射为 `ContextType.IMAGE`。
- 普通表情包与普通图片共用 `allow_media_payload=True` 分支，直接得到等于当前阈值的 `media_payload_allowed` 分数，未先依据表情含义执行正常文本判定。
- 归档只保存媒体类型、传输 XML 与路径，安全投影固定降级为 `[sticker message]`，未来群聊上下文无法看到表情语义。

### 实际改动

- 普通表情包在自由回复图片理解开启时复用现有 GIF 多帧兼容 `vision_label()` 生成短语义；已有有效素材描述则直接复用，避免重复调用 Vision。
- 语义以 `[sticker] <语义>` 形式按 `message_type = text` 进入既有自由回复评估，移除媒体自动得分；语义失败、normal 档位分数不足或其他抑制命中时静默。
- worker 真正放行后直接以该语义构造 `free_reply` 文本上下文，不再转换成确定性图片评论请求，也不会重复调用 Vision。
- 新增 `metadata.media_semantic_text` 归档更新和安全投影，使 V2 timeline、recent transcript 与 Scorer 上下文可复用语义，同时拒绝 XML、URL、本机路径和协议字段。
- 普通图片、真实 @ / 引用等明确触发路径、表情包素材采集和发送工具保持原行为。
