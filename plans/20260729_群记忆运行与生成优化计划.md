# 群记忆运行与生成优化开发计划

> **状态：** 代码开发与本地验证已完成；远端部署和生产验收待后续发布
> **创建日期：** 2026-07-29
> **完成日期：** 2026-07-29
> **任务类型：** 微信群永久记忆运行治理 / 增量调度 / 历史回放 / 可观测性 / 召回质量
> **优先级：** P0 积压消费与游标治理，P1 失败恢复与运行诊断，P2 召回质量
> **实施原则：** 最小修改、稳定群强隔离、失败不推进游标、复用共享文本模型路由、先恢复可控运行再优化质量

当前群永久记忆已经形成完整闭环，并且 `2.1.16` 中的空正文故障转移修复已在远端真实环境生效；当前问题不再是“完全无法生成”，而是“能生成，但积压消费、历史回放和运行状态治理仍不稳定”。

推荐先实施以下最小闭环：

1. 让“稳定群列表 + 归档高水位 + 持久化游标”成为自动调度事实源，不再依赖进程内信号决定是否存在待处理数据。
2. 自动任务成功后继续根据游标判断是否仍有积压，不把最新观测行整体视为已处理。
3. 总积压已达到门槛时，允许按顺序消费不足 20 条的旧稀疏窗口，避免每个小窗口等待 24 小时。
4. 历史回放使用独立、可恢复的 backfill 游标，失败后从断点续跑，不再无条件把增量游标重置为 0。
5. 补齐运行状态、积压、过滤数、有效材料数、重试时间和中断恢复信息，再处理召回相关性与候选审核。

## 2. 范围定义

### 2.1 本计划处理的“群记忆”

本文只讨论存储在 `wechat_group_group_memories` 中、按 `stable_room_id` 隔离的微信群永久记忆，包括：

- 群约定、群规则、长期事实和稳定决策；
- 管理员手工写入或停用的当前群记忆；
- 从当前群消息归档经两阶段 LLM Dream 自动生成的记忆；
- 群消息回复时的自动上下文注入和 Agent 工具查询。

当前 Web 的“管理 -> 知识 -> 群知识”与“群聊 -> 永久记忆”读取和维护的是同一套群记忆数据。这是前端信息架构上的重复入口，不代表群记忆属于知识库。本计划统一按以下边界实施：“管理 -> 记忆”增加“群记忆”作用域并作为唯一管理入口；“管理 -> 知识”只承载全局 Markdown 知识库；“群聊”不再保留独立的群永久记忆管理页。

### 2.2 相邻能力但不纳入本计划

- 群友画像、别名、常用词和画像自主进化的生成算法、数据结构与安全规则；
- 最近聊天上下文、焦点、滚动摘要、情绪、风格和群聊报告；
- 全局 `MEMORY.md`、Daily Summary、全局 Deep Dream 和 Self-Evolution；
- sidecar 登录、消息收发和媒体下载；
- 新增独立模型 Provider、专属 API Key 或群记忆专属模型链。

群友画像与群永久记忆虽然共用“学习”页面，但数据、游标、提示词和安全边界不同，实施时不得再次合并成一条学习管线。为完成 UI 职责拆分，本计划只移动现有画像学习管理界面和完整注入预览，不改变画像或拟人化的业务算法。

## 3. 当前运行架构

### 3.1 数据流总览

```text
已选择且身份确认的微信群消息
  -> WechatGroupChannel._record_inbound_message()
  -> WechatGroupArchive.record_message()
  -> wechat_group_archive.db / wechat_group_messages
  -> note_wechat_group_memory_signal(stable_room_id, archive_row_id)
  -> WechatGroupMemoryDreamTrigger（60 秒扫描、空闲/门槛/退避判断）
  -> WechatGroupMemoryDreamService.run_once()
  -> 阶段 A：当前群消息窗口 -> 群长期事实摘要
  -> 阶段 B：现有群记忆 + 新摘要 -> add/update 操作
  -> JSON、证据、群作用域、内容和置信度校验
  -> WechatGroupKnowledgeService.apply_dream_memories()
  -> wechat_group_knowledge.db / wechat_group_group_memories
  -> 当前群回复的 <wechat-group-memory> 注入或 wechat_group_memory_search
```

### 3.2 与全局记忆的边界

`agent/memory/routing.py` 会把微信群请求解析为 `wechat_group` 作用域，并禁止写入 shared Daily Summary、全局 Deep Dream 和 shared Self-Evolution。群永久记忆只读取当前群归档，只写当前群 SQLite 表，不写 `MEMORY.md`。

该隔离已由 `tests/test_wechat_group_global_memory_isolation.py` 等测试覆盖，本计划继续把它作为不可破坏的不变量。

## 4. 当前生成逻辑

### 4.1 消息归档和信号

关键文件：

- `channel/wechat_group/wechat_group_channel.py`
- `channel/wechat_group/wechat_group_archive.py`
- `channel/wechat_group/wechat_group_memory_dream_trigger.py`

当前行为：

1. 通道先完成稳定身份解析和已选群门禁，未选择或未确认的群不会进入归档和学习链路。
2. 消息使用 `INSERT OR IGNORE` 按 `message_id` 去重后写入归档。
3. 只有存在明确 `stable_room_id` 且 `wechat_group_learning_enabled=true` 时才通知群记忆触发器。
4. 触发器在微信群通道启动成功后创建守护线程，每 60 秒扫描一次。
5. `_signals`、`_last_triggered_observed_row_ids`、`_backoff_until` 和 `_running_rooms` 均只存在于当前 Python 进程内。
6. 当前群第一次发出信号且数据库没有游标行时，`note_message()` 会把当前消息行直接设为高水位，默认不自动回放更早历史。

### 4.2 自动触发条件

每个群同时满足以下条件才会自动调用 Dream：

1. 自动学习开关已开启；
2. 当前进程收到过该群的新消息信号；
3. 距离最后一条信号已达到空闲时间，远端当前为 10 分钟；
4. 当前群不在运行中或退避期；
5. 当前游标后的首个连续时间窗达到最少有效文本数，或距游标更新时间达到最长等待时间；
6. 全局 Dream 锁可用。

当前材料窗口不是“游标后的全部消息”，而是：

- 从游标后的第一条文本开始；
- 只取其后 120 分钟内的文本；
- 最多读取 200 条；
- 后续时间窗留到下一批；
- 对全部不安全/不可用文本组成的窗口强制运行，以便无 LLM 地推进游标。

### 4.3 材料清洗

`WechatGroupMemoryMaterialBuilder` 只保留当前稳定群的安全文本，并执行：

- 排除非文本、空消息和无消息 ID 的记录；
- 排除 XML、超长文本、本地路径、密钥样式和大段 Base64；
- 去除 URL 查询参数；
- 把真实成员 ID 映射为批次内 `speaker_001` 等不透明 token；
- 保留真实消息 ID 作为服务端证据白名单；
- 不向模型暴露稳定群 ID、runtime 群 ID 或成员稳定身份。

`scanned_count` 表示数据库窗口内文本行数，`batch.messages` 才是实际进入 LLM 的有效文本数。当前运行表只持久化前者，无法直接看出过滤比例。

### 4.4 两阶段 Dream

关键文件：

- `channel/wechat_group/wechat_group_memory_dream.py`
- `agent/memory/dream_engine.py`
- `bridge/agent_bridge.py`

阶段 A：群消息摘要

- 使用共享 `TextModelRouter.complete()`；
- `purpose=wechat_group_memory_daily_summary`；
- 当前固定 `temperature=0.1`、`max_tokens=800`；
- 只提取群约定、长期事实和稳定决策；
- 普通闲聊无长期价值时返回 `[EMPTY]`；
- 非空时必须返回摘要及当前批次证据消息 ID。

阶段 B：群 Dream 蒸馏

- 输入当前群最多 200 条 active 记忆与阶段 A 摘要；
- 现有记忆只以批次内 `M001` 等 token 暴露给模型；
- `purpose=wechat_group_memory_deep_dream`；
- 当前固定 `temperature=0.2`、`max_tokens=1600`；
- 最多返回 20 个 `add` 或 `update` 操作；
- 自动流程不得删除或停用记忆。

共享文本路由按现有主备模型、熔断和半开探测工作。`2.1.16` 已补充“HTTP 成功但最终正文为空”的候选故障转移；不会把 `reasoning_content` 当成最终正文，也不会通过备用模型绕过安全拒绝。

### 4.5 校验、写入和游标

模型输出在写入前必须通过：

- 严格 JSON 对象校验；
- 操作数上限校验；
- 只允许 `add/update`；
- `update` 只能引用当前群 active 记忆 token；
- 证据 ID 必须属于当前批次白名单；
- 禁止画像、群 ID、成员 ID 和 speaker token 字段；
- 内容再次执行安全清洗；
- 置信度必须位于 0～1；
- 远端当前低于 0.9 的操作只计入 `skipped_count`，不会写入候选表；
- 精确规范化后的重复内容会跳过。

游标规则：

- 摘要为 `[EMPTY]`：成功推进到本批结束，不写记忆；
- 全部材料被过滤：成功推进到本批结束，不调用 LLM；
- Dream 成功：完成写入/跳过后推进游标；
- 模型、JSON、证据或写入失败：记录失败，不推进游标；
- 低于门槛且非强制：记录 `skipped`，不推进游标。

### 4.6 手动运行和历史回放

Web 控制台通过已鉴权接口提供：

- “运行一次”：调用 `WechatGroupLearner.run_once(mode="memory")`，仍受最少消息门槛限制；
- “从历史生成”：调用 `run_history()`，强制处理历史批次；
- 学习运行列表：读取当前群 `wechat_group_learning_runs`；
- 手工新增、停用和预览当前群记忆。

当前 `run_history()` 每次调用都会先把主学习游标更新为 0，再循环最多 10 批。失败后再次点击会重新从 0 开始，而不是从上一次成功批次继续。

群内 Agent 还提供：

- 所有成员可用的当前群记忆搜索；
- 仅当前群已确认管理员可用的手工写入和停用工具；
- 工具 schema 不接收 `room_id`，作用域由服务端绑定。

## 5. 当前召回逻辑

关键文件：

- `channel/wechat_group/wechat_group_knowledge_service.py`
- `channel/wechat_group/wechat_group_context_service.py`
- `channel/wechat_group/wechat_group_memory_tools.py`

当前自动注入：

1. 每次群文本回复前，以用户当前问题查询当前群 active 记忆；
2. 默认最多注入 5 条；
3. 查询只做去空白、转小写后的整串包含匹配；
4. 如果没有任何包含匹配，会退化为返回当前群最近更新的 5 条；
5. 结果渲染到 `<wechat-group-memory>` 中。

当前工具搜索复用相同逻辑。工具 schema 声明了 `min_score`，但执行代码没有读取或应用该参数，也没有返回实际相关性分数。

因此当前召回保证了“不会跨群”，但不能保证“与当前问题相关”；当群记忆增长后，无匹配回退到最新记忆可能造成无关提示注入。

### 6.6 当前积压

| 群代号 | 归档文本总数 | 当前游标后待处理 | 下一窗口有效文本 | 是否达到 20 条门槛 | active 记忆 |

| selected-3 | 1785 | 1486 | 6 | 否 | 2 |
| selected-4 | 82 | 2 | 2 | 否 | 1 |
| selected-5 | 6 | 0 | 0 | 否 | 0 |
| selected-6 | 686 | 411 | 2 | 否 | 1 |
| selected-7 | 113 | 91 | 8 | 否 | 0 |

关键事实：

- 待处理总量约 2246 条；
- `selected-3`、`selected-6` 和 `selected-7` 总积压分别为 1486、411、91 条，但首个连续窗口只有 6、2、8 条；
- 当前算法只用首个窗口的有效消息数判断门槛，无法利用后续窗口证明“整体积压足够大”；
- 最长等待以当前游标 `updated_at` 为基准，每成功消费一个稀疏窗口都会重新开始 24 小时等待；
- 若一个群在进程重启后没有新消息，内存 `_signals` 中就没有该群，即使数据库仍有少量积压也不会被扫描。

这说明当前积压不是单纯“模型太慢”，而是调度条件与时间窗语义组合后形成的消费饥饿。

### 6.7 最近失败

`2.1.16` 当前容器内有 5 次失败：

1. 1 次历史摘要返回了批次外证据 ID，被严格证据校验拒绝；
2. 2 次历史 Dream 返回非法 JSON；
3. 1 次自动摘要调用中，一个候选超时、另一个候选 429，最终记录为临时失败；

## 7. 根因分析

### 7.1 调度事实源不持久

持久化数据库知道游标和归档高水位，但自动扫描只遍历当前进程 `_signals` 中的群。信号、退避和最后触发行均会在进程重启后丢失。

这使系统形成两套状态：

- 数据库：有哪些群、游标在哪里、还有多少归档；
- 内存：哪些群值得扫描、何时重试、最新观测到了哪里。

两者不一致时，数据库有积压并不保证自动任务会发现它。

### 7.2 门槛应用在单个连续窗口，而非积压队列

120 分钟窗口用于保持话题连续性是合理的，但“至少 20 条”同时被当作调度门槛，导致低活跃时间段挡住后续高活跃窗口。

当前最长等待只能每 24 小时强制通过一个稀疏窗口；成功后游标更新时间重置，下一个稀疏窗口再次等待 24 小时。

### 7.3 成功后按观测高水位去重，而非按实际游标判断

自动运行成功后，触发器把 `_last_triggered_observed_row_ids[room]` 设置为运行前看到的最新消息行。Dream 实际可能只消费其中第一个时间窗；如果没有后续新消息改变观测高水位，剩余窗口不会继续触发。

### 7.4 历史游标和增量游标混用

历史回放直接重置主游标，既破坏增量位置，又无法表达：

- 第一次历史回放；
- 失败后断点续跑；
- 管理员明确要求从头重建；
- 历史回放期间仍有新消息进入。

### 7.5 结构化输出只有拒绝，没有一次受控修复

严格 JSON 和证据校验应保留，但当前历史回放中已经出现 2 次非法 JSON 和 1 次证据越界。任一格式错误都会终止整次历史循环，用户再次点击又从 0 开始，放大了偶发模型格式错误的成本。

### 7.6 可观测性只能看到结果，不能看到阻塞原因

Web 当前展示运行状态、批次消息数、写入数、跳过数和失败原因，但缺少：

- 归档高水位和当前游标；
- 总待处理数；
- 下一窗口扫描数和有效材料数；
- 过滤原因分布；
- 最旧待处理消息年龄；
- 当前是否等待 idle、门槛、最长间隔、全局锁或退避；
- 下次允许重试时间；
- 运行是否由上次进程中断；
- 模型候选是否发生 fallback；
- 阶段耗时与完整任务耗时。

因此“没生成”仍需要直接查询数据库才能区分合法空摘要、低门槛跳过、等待、模型失败或触发器根本没有扫描。

### 7.7 召回接口混合了“查询”和“兜底注入”

显式工具搜索与被动上下文注入都调用 `search_group_knowledge()`。无匹配时统一返回最新 active 记忆，使 `min_score` 无法生效，也无法区分“没有相关记忆”和“为了保持背景而注入最近记忆”。

## 8. 优化目标与不变量

### 8.1 目标

1. 进程启动后，不依赖新消息也能识别已选稳定群的持久化积压。
2. 每次成功都按实际游标推进，剩余积压能继续排队消费。
3. 低密度旧窗口不会按“一个窗口一天”的速度阻塞后续消息。
4. 历史回放失败后可从断点继续，普通重试不重复从 0 调用 LLM。
5. 临时模型故障、非法 JSON 和证据越界继续不推进游标。
6. Web 能直接回答“为什么当前没有生成、下一次何时运行、还有多少积压”。
7. 显式记忆查询不再返回明显无关的最新记忆，`min_score` 具有真实语义。
8. 群永久记忆只有“管理 -> 记忆 -> 群记忆”一个 Web 管理入口，知识页和群聊页不再提供重复增删界面。

### 8.2 不变量

- 只处理 `wechat_group_stable_room_ids` 中身份已确认的稳定群；
- 不接受模型提供 `room_id`；
- 不跨群读取归档、证据、记忆或游标；
- 不把画像字段写入群永久记忆；
- 不把 `reasoning_content` 当正文或持久化；
- 不为群记忆增加独立 Provider 或绕过共享 `TextModelRouter`；
- 失败不推进游标；
- 自动流程只允许 add/update，不允许删除或停用；
- `[EMPTY]` 是合法成功，不以“每批必须写入”作为健康标准；
- 不删除现有 6 条 active 记忆，不自动清理历史归档。
- UI 迁移不复制、不迁移或重写群记忆数据；
- 管理知识页不再请求 `/api/wechat-group/memories/*`；
- 全局记忆文件、自主进化、群友画像和完整注入预览能力不得因页面归并而丢失。

## 9. P0：修复增量调度和积压消费

### 9.1 以持久化状态为事实源

调整 `WechatGroupMemoryDreamTrigger`：

1. 每次扫描从当前配置中的已选稳定群集合开始，而不是只遍历 `_signals`。
2. 对每个群读取：
   - 学习游标是否存在；
   - 归档高水位；
   - 游标后文本数；
   - 最后一条待处理消息时间；
   - 最近运行和持久化退避状态。
3. `_signals` 只作为低成本活动提示和 idle 时间缓存，不能再决定一个群是否有待处理数据。
4. 启动时校验群仍在已选列表且身份已确认；已取消选择的群不自动继续学习。
5. 进程退出不要求专门保存 `_signals`，因为下一次启动能从数据库重建可运行集合。

### 9.2 明确首次启用语义

推荐保留当前“自动学习默认从启用后的新消息开始”，避免无提示地对大量旧历史发起 LLM 调用，但必须把它变成显式持久化状态：

- 游标行不存在：表示从未初始化；
- 初始化时把当前归档高水位保存为增量基线，并记录 `initialized_at` 和 `initialization_mode=from_now`；
- 游标行存在且值为 0：表示管理员明确要求从历史起点处理，不得被 `note_message()` 覆盖；
- Web 显示“历史未回放/从当前开始”的状态；
- 历史回放使用独立 backfill 状态，不再借用“游标不存在”的语义。

不得继续在第一次消息信号中静默写高水位，否则无法区分设计选择和数据丢失。

### 9.3 按实际游标持续排空

自动运行成功后：

1. 读取服务实际提交的新游标；
2. 若游标仍小于本轮观察到的归档高水位，保留该群为 pending；
3. 下一次扫描继续处理下一窗口，不要求出现新消息；
4. 每轮每群最多处理一个 LLM 批次，继续使用全局单任务锁，避免瞬时模型流量放大；
5. 多个群使用稳定轮询顺序，避免单个高流量群长期占用全局锁；
6. 全部材料被过滤的批次可无 LLM 连续推进，但仍设置单轮上限，避免长事务。

不要用 `_last_triggered_observed_row_ids == latest` 判断积压已完成；完成条件应是“持久化游标已达到观察高水位，且没有可消费的过滤行”。

### 9.4 解决稀疏窗口阻塞

保留 120 分钟窗口作为内容边界，但调整运行判定：

1. 下一窗口有效文本达到 20 条：正常运行；
2. 下一窗口不足 20 条，但游标后的总有效/文本积压达到 20 条：强制消费当前最旧窗口，使后续窗口可达；
3. 总积压也不足 20 条，但最旧待处理消息年龄达到最长等待：强制运行；
4. 全部材料被过滤：无 LLM 推进；
5. 没有待处理数据：不创建空运行记录。

这里的“强制”只跳过数量门槛，不跳过清洗、JSON、证据、作用域和置信度校验。

首版不新增更多可调参数，继续复用现有批次上限、窗口、最少消息和最长等待配置，避免控制台继续膨胀。

### 9.5 持久化退避与中断恢复

在当前游标表增加最小状态字段，或新增单一 `wechat_group_memory_scheduler_state` 表，保存：

- `last_signal_at`；
- `last_attempt_at`；
- `last_success_at`；
- `next_retry_at`；
- `consecutive_failures`；
- `last_failed_reason_code`；
- `initialized_at` / `initialization_mode`。

启动时：

1. 将 `status=running` 且属于旧进程/超过合理时长的运行标记为 `interrupted`；
2. 不推进这些运行的游标；
3. 根据持久化 `next_retry_at` 恢复退避；
4. 临时模型故障使用有上限的递增退避；
5. JSON/证据类非临时失败至少等待下一轮或人工重试，不做高频循环。

迁移必须兼容现有游标行；新增字段使用安全默认值，不重写当前游标。

## 10. P0：重构历史回放语义

### 10.1 独立 backfill 游标

历史回放不得再执行 `update_cursor(room_id, 0)`。推荐状态模型：

```text
incremental_cursor：自动新消息消费位置
backfill_cursor：历史回放位置
backfill_target_row_id：开始回放时冻结的历史终点
backfill_status：idle/running/failed/completed/cancelled/interrupted
```

规则：

- 第一次回放从 0 开始，冻结当时高水位；
- 失败后默认从 `backfill_cursor` 续跑；
- 只有显式“重新从头生成”并二次确认时才清零 backfill 游标；
- 新消息继续由 incremental cursor 管理，不与历史回放互相覆盖；
- 回放完成后不回退 incremental cursor；
- 同一群同一时刻只能有一个 backfill 任务；
- 仍使用现有全局 Dream 串行边界。

### 10.2 可预览、可恢复、可停止

历史回放前提供不含正文的预览：

- 起点和冻结终点；
- 预计批次数；
- 文本总数；
- 已完成批次；
- 上次失败阶段和原因分类。

Web 默认按钮语义改为“继续历史生成”；只有 completed/未初始化时显示“开始历史生成”。“从头重跑”放入二次确认操作，不作为普通失败重试路径。

首版可以继续同步执行单批或小批循环，不必引入新的分布式任务系统；关键是持久化断点和幂等语义。

## 11. P1：提高结构化生成稳定性

### 11.1 保留严格校验，增加一次受控修复

对以下可修复错误最多追加一次同候选链重试：

- JSON 非法；
- 缺少必需字段；
- evidence ID 不在白名单；
- update token 无效。

修复请求只包含：

- 原任务的安全材料；
- 允许的 token / evidence 白名单；
- 简短的错误类型；
- 再次要求只返回 JSON。

不得：

- 放宽证据子集校验；
- 从原始文本中正则猜测不存在的 evidence；
- 保存或记录模型推理正文；
- 无限重试；
- 在失败后推进游标。

实施前先补充安全诊断，确认远端非法 JSON 是否主要由 Markdown fence、截断或 schema 漏字段造成；没有证据时不提前引入复杂 JSON 修复器。

### 11.2 限制全局锁占用

07:40 和 08:12 的失败运行分别占用约 134、165 秒，而正常成功约 18 秒。需要：

- 核对现有 Provider 请求超时与共享路由总耗时；
- 为单阶段和完整两阶段任务定义有限总时限；
- 超时仍通过共享路由的既有候选与熔断处理；
- 不新增群记忆专属 Provider；
- 超时退出后释放全局锁并持久化退避。

具体时限在实施前基于当前 Provider 配置和现有 API 签名验证，不在本计划中凭空指定。

> **实施结果：** 本次保留共享 `TextModelRouter` 的候选顺序、熔断状态和各 Provider 既有请求超时，并补充阶段耗时、失败分类、持久化退避与 stale run 恢复；没有新增跨候选、跨两阶段的可取消总 deadline。当前 Provider 调用没有统一的可取消句柄，用后台线程提前返回会留下仍在占用资源的请求，因此该项不以伪超时方式实现，保留为共享文本路由后续治理事项。

### 11.3 运行记录补充字段

建议新增：

- `batch_scanned_count`；
- `batch_eligible_count`；
- `batch_filtered_count`；
- `pending_before_count` / `pending_after_count`；
- `cursor_before` / `cursor_after`；
- `summary_duration_ms` / `dream_duration_ms` / `total_duration_ms`；
- `failure_code`；
- `fallback_used`；
- `attempt_count`；
- `interrupted_reason`。

不记录 prompt、消息正文、模型正文、推理正文、Header、Key 或完整原始响应。

#### 12.4.6 “记忆内容”页签

该页签只维护当前稳定群的 active 永久记忆：

1. 顶部工具栏包含搜索框、搜索按钮、active 记忆总数和“新增记忆”主按钮；输入框支持 Enter 搜索；
2. 记忆条目展示正文、`source_kind`、`confidence`、更新时间和短 ID；没有值的元数据不展示空占位；
3. `manual` 和 `deep_dream` 使用文本标签区分，不能只靠颜色；数值使用等宽/表格数字，避免刷新时布局跳动；
4. 停用使用现有 Font Awesome `ban` 图标按钮并提供 tooltip、`aria-label` 和 44px 点击区域；确认框明确显示当前群名和正文摘要；
5. “新增记忆”打开单层对话框，字段仅包含必填“记忆正文”和可选“来源摘要”，不暴露 runtime ID；提交期间按钮禁用并显示进度，成功后关闭、刷新列表并通过 `aria-live="polite"` 提示；
6. 对话框存在未保存内容时，关闭、切群或切作用域需要确认，避免草稿丢失；
7. 首版不增加批量编辑、硬删除、恢复 inactive 记忆或富文本编辑器，避免扩大接口和数据治理范围。
8. 列表按 20 条分页，搜索和切群重置到第一页；后端返回准确 `total`、`limit` 和 `offset`，不能继续以 `limit=200` 的结果长度冒充总数。

| 状态 | 展示与操作 |
| --- | --- |
| 群列表加载中 | 固定高度骨架，不先显示空状态 |
| 未选择任何稳定群 | 显示“尚未选择可管理的稳定群”，提供跳转到“群聊 -> 群与管理员”的按钮 |
| 当前群无记忆 | 显示空状态和“新增记忆”操作 |
| 搜索无匹配 | 保留搜索词，显示“清除搜索”操作 |
| 请求失败 | 在当前区块显示原因和“重试”，不清空上一次成功数据 |
| 停用中 | 只锁定当前条目操作，不冻结整页 |

#### 12.4.7 “生成运行”页签

该页签将“当前群运行状态”和“适用于全部已选群的生成策略”明确分区，避免用户误以为选择某个群后修改的是单群配置。

顶部状态区展示：

- 待处理文本数；
- incremental cursor / 归档高水位；
- backfill 进度；
- 当前阻塞原因和下次计划时间；
- 最近成功、最近失败及失败阶段。

状态不只使用颜色：`running`、`backoff`、`failed`、`idle` 必须同时显示图标和文字。对 `backoff`、stale `running`、低于门槛和全局锁占用给出可恢复说明，但不展示群消息正文或模型响应。

“当前群操作”只影响已选群：

- `立即运行一次`：主操作，调用增量 Dream；运行时禁用重复提交并轮询/刷新状态；
- `继续历史回放`：先展示待处理范围、冻结高水位和预计批次数，再确认执行；
- `从头重新回放`：放入更多操作菜单，使用危险样式和二次确认，明确不会覆盖 incremental cursor；
- 有任务运行时禁止同群重复发起，但允许切换查看其他群状态。

“全局生成策略”使用折叠区渐进展示，并明确标注“适用于全部已选群”。仅保留群永久记忆相关字段：

- 启用群永久记忆（内部继续兼容 `wechat_group_knowledge_enabled`，只修正文案）；
- 启用自动记忆 Dream；
- 群记忆上下文上限；
- 批次消息数、最少消息数、窗口分钟、空闲分钟；
- 自动应用阈值、最长等待、历史批次上限。

以下字段从该页签移出，归入“群聊 -> 群友画像 -> 自主学习”：

- `wechat_group_profile_enabled`；
- `wechat_group_profile_context_limit`；
- 全部 `wechat_group_profile_evolution_*` 配置；
- 画像学习状态、运行详情和回滚操作。

运行记录按当前稳定群加载，使用紧凑列表或语义表格展示时间、触发来源、状态、扫描数、有效材料数、写入数、跳过数、耗时和脱敏失败原因。手机端改为逐条纵向布局，不强行压缩成宽表。

#### 12.4.8 “召回测试”与完整注入预览分离

现有 `/api/wechat-group/memories/preview` 同时返回群永久记忆、发言人画像和被提及成员画像，不能整体视为记忆功能。拆分为：

1. “管理 -> 记忆 -> 群记忆 -> 召回测试”只输入查询文本，调用严格群记忆查询，展示命中正文、分数、来源和过滤原因；无相关结果必须显示空，不回退最新记忆；
2. “群聊 -> 拟人化”增加折叠的“完整上下文注入预览”，保留当前群、发言人、被提及成员和查询输入，并继续调用 `/api/wechat-group/memories/preview`；
3. 完整预览结果分别展示“群记忆命中 / 发言人画像 / 被提及画像 / 过滤原因”，原始 `<wechat-group-memory>` 块放在可展开代码区；
4. 记忆召回测试不要求输入成员 ID，不加载画像接口；完整注入预览仍要求稳定成员身份并保持 fail closed；
5. 召回页显示 `score` 和过滤原因依赖第 13 节严格查询改造，在后端完成前不得用前端伪造分数。

完整注入预览中的发言人和被提及成员使用昵称可搜索的稳定成员选择控件，提交值为 `stable_member_id`；不要求管理员手工输入 runtime ID。成员列表复用 `/api/wechat-group/members`，切群后清空不再有效的成员选择。

#### 12.4.9 前端状态与请求模型

将页面归属型的 `groupsMemoryState` 调整为独立的 `groupMemoryState`，由记忆视图管理；不要让新记忆页依赖先访问 `/api/channels` 或 `renderGroupsView()`。

建议状态至少包含：

```text
memoryScope: global | group
globalMemoryState:
  category, page, viewer
groupMemoryState:
  rooms, selectedRoomId, activeTab, query
  memories, summary, runtimeStatus, runs, recallResult
  loading: rooms | memories | status | runs | action
  errors: rooms | memories | status | runs | action
  requestSequence, dirtyDraft
```

请求策略：

- 首次进入群记忆时加载群列表，选择第一个稳定群；之后保留用户本次会话的已选群；
- “记忆内容”只加载 summary + memories，“生成运行”首次打开时再加载 status + runs，召回测试只在用户提交后请求；
- 切群时递增 `requestSequence` 或使用 `AbortController`，旧群迟到响应不得覆盖当前群；
- 独立区块分别处理失败，运行记录失败不能清空已经成功加载的记忆列表；
- 成功写入或停用后只刷新当前群记忆和 summary，不重新加载全局记忆或整个群聊配置；
- 切换作用域不重置另一作用域状态，离开页面后停止轮询和未完成的非写请求。

#### 12.4.10 接口复用与最小新增

| UI 能力 | 接口 | 处理方式 |
| --- | --- | --- |
| 稳定群列表 | `GET /api/wechat-group/memories/groups` | 复用；只返回稳定群并提供准确记忆数 |
| 群记忆列表/搜索 | `GET /api/wechat-group/memories/group` | 扩展准确 total/offset 分页，并接入第 13 节严格查询和分数 |
| 手工新增 | `POST /api/wechat-group/memories/group` | 复用；证据校验下沉服务层 |
| 停用 | `POST /api/wechat-group/memories/disable` | 复用；继续按 stable room 校验 |
| 运行记录 | `GET /api/wechat-group/memories/learn/runs` | 复用并补充第 11.3 节字段 |
| 当前运行状态 | `GET /api/wechat-group/memories/learn/status` | 新增只读聚合接口，对应第 12.1 节 |
| 手动增量 | `POST /api/wechat-group/memories/learn/run` | 复用 |
| 历史预览 | `POST /api/wechat-group/memories/learn/history/preview` | 新增，只计算范围和批次数，不改游标 |
| 历史继续/重跑 | `POST /api/wechat-group/memories/learn/history` | 扩展显式 operation，不再隐式重置主游标 |
| 群记忆全局配置 | `GET/POST /api/wechat-group/memories/config` | 新增白名单配置接口，禁止前端误传并覆盖目标群、人设等无关群聊字段 |
| 群画像全局配置 | `GET/POST /api/wechat-group/memories/profiles/config` | 新增画像字段白名单；旧 profile-evolution/config 暂作兼容 |
| 完整注入预览 | `POST /api/wechat-group/memories/preview` | 复用，但 UI 迁入群聊拟人化 |

关键响应约束：

- 群列表返回 `room_id`、`room_name`、`active_memory_count`，不得返回 runtime room 或群消息内容；
- 群记忆列表返回 `memories`、`total`、`limit`、`offset` 和已确认的 `identity`，搜索结果中的每条记忆可选携带真实 `score`；
- 运行状态返回第 12.1 节的游标、积压、阻塞与时间字段，不包含 prompt、归档正文、记忆正文或模型正文；
- 配置 GET 只返回当前白名单字段；配置 POST 忽略或拒绝白名单外字段，并复用 `_apply_wechat_group_config()` 的类型归一化与 `_write_channel_config()` 的合并写入；
- 历史预览是严格只读操作，返回 `cursor_start`、`frozen_high_watermark`、`pending_count`、`estimated_batches` 和 `can_continue`；
- 历史执行显式接收 `operation=continue|restart`。`restart` 必须另带确认标记且只重置 backfill 状态，不能重置 incremental cursor。

建议群记忆列表响应形态：

```json
{
  "status": "success",
  "memories": [],
  "total": 0,
  "limit": 20,
  "offset": 0,
  "identity": {
    "stable_room_id": "wgr_..."
  }
}
```

前端不根据 HTTP 200 直接判定业务成功，继续检查 JSON `status`；HTTP 超时、非 JSON、业务错误和身份未解析分别给出可恢复提示。

不新增数据库来支撑页面迁移；不复制 `wechat_group_group_memories`；本阶段也不批量重命名 `WechatGroupKnowledgeStore` / `WechatGroupKnowledgeService`。内部历史命名可以在后续独立重构中处理。

## 13. P2：优化召回相关性

### 13.1 拆分查询与背景读取

将当前单一接口拆成明确语义：

- `search_group_memories(room_id, query, limit, min_score)`：群记忆主查询入口；严格查询，无相关结果返回空；
- `list_recent_group_memories(room_id, limit)`：明确请求最近 active 记忆；
- 现有 `search_group_knowledge()` 仅保留为兼容包装并逐步迁移调用方，不再作为 UI、工具 schema 或文档中的主名称；
- 自动上下文注入根据策略决定是否使用最近背景；
- Agent 工具的显式查询绝不在无匹配时偷偷回退到最新记忆。

### 13.2 首版相关性评分

不引入新依赖，先使用可解释的轻量评分：

- 规范化整句包含；
- 中文片段/关键词重合；
- 证据摘要命中；
- 轻量时间衰减只用于同分排序，不覆盖文本相关性；
- 返回实际 `score` 并应用 `min_score`。

若后续数据量和查询复杂度证明需要语义搜索，再评估复用现有 Embedding 能力；首版不为只有 5 条自动记忆的存量引入独立向量索引。

### 13.3 被动注入策略

推荐：

- 当前问题有明确匹配时注入匹配记忆；
- 当前问题为空或属于开放背景请求时，才允许注入最近记忆；
- 普通不相关问题没有命中时不注入群永久记忆；
- 保持当前群最多 5 条上限；
- Web 预览显示命中分数和过滤原因。

## 14. P2：生成质量与候选治理

当前低于 0.9 的操作只计入 `skipped_count`，远端本次容器已经跳过 10 个操作。现阶段不建议立即恢复旧候选审核体系，因为：

- 远端旧 `wechat_group_memory_distill_runs/candidates` 已无当前数据；
- 旧表混合群记忆与群画像语义；
- 旧键使用 runtime room 和旧阈值，不应直接接回稳定群 Dream。

推荐顺序：

1. 先补齐操作置信度分布和跳过原因统计；
2. 观察一段真实运行，确认低置信度操作中是否存在稳定价值；
3. 只有确有审核需求时，在当前群记忆存储体系中设计纯群记忆 candidate 表；
4. candidate 必须绑定 stable room、run、evidence 和内容哈希；
5. 审批仍经过当前群 Web 鉴权和服务端作用域校验；
6. 不复用或执行旧表中的待审数据。

近似重复与冲突也先通过统计确认，再决定是否增加规范化键或语义去重；不在 P0 调度修复中顺手引入复杂合并算法。

## 21. 实际改动与数据迁移

### 21.1 后端与存储

- `WechatGroupMemoryDreamTrigger` 从 `wechat_group_stable_room_ids`、归档和持久化状态扫描候选群，内存 signal 仅保留为活动提示。
- `WechatGroupKnowledgeStore` 幂等创建 `wechat_group_memory_scheduler_state`、`wechat_group_memory_backfill_state`，并用 `_ensure_column()` 为既有运行表补充诊断字段；现有群记忆、增量游标和归档正文不重写、不复制。
- `WechatGroupMemoryDreamService` 返回实际前后游标和积压数，历史回放冻结终点并使用独立断点；完成态继续只处理新增归档，重跑必须显式确认。
- 共享路由只透传 `primary/fallback` 和尝试次数等受控元数据；运行表不保存 prompt、模型正文、reasoning 或 Dream 审计摘要。
- 群记忆服务集中校验 evidence，召回拆分为严格查询与 recent 读取，并在严格查询中应用真实分数和 `min_score`。

### 21.2 Web 与文档

- “管理 -> 记忆”新增“全局记忆 / 群记忆”作用域；群记忆内含“记忆内容 / 生成运行 / 召回测试”。
- “管理 -> 知识”删除群作用域，只保留全局 Markdown 文档与图谱；“群聊”删除永久记忆导航。
- 群友画像自主学习迁入“群聊 -> 群友画像”，完整注入预览迁入“群聊 -> 拟人化”。
- Web API 增加群记忆精确分页、配置、运行状态、历史预览/续跑和召回接口，所有写操作继续要求登录鉴权与稳定群解析。
- `AGENTS.md`、中文 README 和 Deep Dream 文档统一“群永久记忆属于记忆，不属于知识”的产品边界；内部 legacy knowledge 类名、配置键和表名暂时兼容保留。

### 21.3 剩余事项

1. 远端尚未部署本次代码，因此约 2246 条历史积压、stale run 迁移和生产模型退避需要发布后按第 18、19 节验收。

3. 新候选审核体系继续等待真实跳过分布；不接回旧 runtime room、旧阈值和混合画像语义的候选表。
4. 同群并发历史回放当前由进程内全局/群锁串行化，后续如改为异步任务，需要增加显式 busy/复用任务状态。
5. 多群生产流量公平性继续在远端验收中观察；如出现连续模型突发，再单独增加持久化轮询位置或每轮任务预算。
