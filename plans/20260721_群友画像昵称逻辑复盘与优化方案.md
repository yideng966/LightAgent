# 群友画像昵称逻辑复盘与优化方案

> 状态：现状复盘与优化方案已完成，待确认后实施业务代码。
> 复盘日期：2026-07-21。
> 代码基线：当前工作区最新代码，包含尚未提交的群友画像按群重构；当前 `HEAD` 为 `225dc9fa6f4141af023650d0c1a0c6157bd06311`。
> 范围：个人微信群的群成员昵称、画像主昵称、别名、回复称呼及其自动学习链路。
> 非目标：本轮不修改业务代码、不迁移或清理正式画像数据、不修改桌面端。

## 一、结论先行

当前代码已经完成上一轮画像重构中的关键安全修复：

1. 群友画像主键已经改为 `stable_room_id + stable_member_id`，同一群成员在当前群最多一份画像。
2. runtime sender 会先在当前 stable room 内解析为 canonical stable member，再进入画像读写。
3. LLM 画像进化不再让模型返回 runtime/stable ID，而是使用批次内 `member_001` 这类 opaque token。
4. LLM 输出必须通过成员白名单、证据消息白名单、置信度和群体泛称过滤，画像、名称、claim、revision 和 run 使用同一画像数据库事务落地。
5. 人工主昵称能够稳定压过归档中的实时群昵称；人工保存只替换人工来源名称记录，不直接删除其他自动来源记录。

但“昵称”当前仍混合了四种不同语义：

- 微信当前群名片或联系人昵称：sidecar/归档观察到的实时名称。
- 画像主昵称 `primary_nickname`：画像表中的持久化字段。
- 别名 `aliases`：多个 `name_records` 扁平化后的其他名称。
- 回复称呼 `reply_name`：最终注入 LLM、要求模型优先使用的称呼。

这些语义没有完全拆开，导致当前仍存在以下主要问题：

- 自动学到的别名在无主昵称时可以反向成为 `primary_nickname`，把“识别词”提升成“主显示名”。
- 存量 `primary_nickname` 优先于当前群实时昵称，群名片改名后可能长期显示旧名称。
- Web 表单把人工、启发式和 LLM 别名扁平化后整体回写为人工别名，用户看不到来源，也无法明确否决一个自动别名。
- 启发式正文学习没有复用 LLM 的群体泛称过滤，已验证 `@所有人` 可以被错误绑定到唯一 runtime 目标成员。
- 机器人在当前群的展示名与 `self_display_name` 不一致时，真实目标别名会因候选数不唯一而漏学。
- LLM 多目标消息虽然校验了 token 和 evidence，但 evidence 与“具体可见称呼属于哪个被 @ 成员”的绑定仍不够强。
- 当前 prompt 只召回说话人和真实 `at_list` 中的成员，`query` 参数未参与普通文本别名解析；“张总是谁”不会因为已有“张总”别名自动注入目标画像。

推荐目标不是放宽自然语言猜测，而是先建立清晰、可审计的名称模型：

```text
当前群观察名      = 微信群名片优先，联系人昵称兜底，属于可变事实
人工首选称呼      = 管理员显式设置，最高优先级
画像别名          = 只用于识别和检索，保留来源、证据、状态
effective_name    = 人工首选称呼 > 当前群观察名 > 已存观察名 > 安全兜底
reply_name        = 人工首选称呼 > effective_name
```

自动别名不应仅因首次出现就自动成为主昵称或回复称呼。自动学习先保证“目标绑定正确”，再讨论提高召回率。

## 二、概念边界

### 2.1 runtime 身份 alias 不是画像别名

身份库中的 account/room/member alias 用于把本次 Wechaty runtime ID 恢复到 stable identity：

```text
runtime_room_id + runtime_sender_id
  -> stable_account_id
  -> stable_room_id
  -> stable_member_id
  -> canonical stable_member_id
```

这里的 alias 是 ID 映射，不应该直接展示为群友画像别名，也不能因为昵称相同就自动合并成员。

### 2.2 当前群观察名

当前群观察名表示微信此刻或最近一次可见的成员名称，可能来自：

1. 当前群的 `room.alias(contact)`，即群名片。
2. 微信原始消息中的 `ActualNickName` 等字段。
3. 联系人 `contact.name()`。

它可能随用户改群名片而变化，不应等同于永久画像事实。

### 2.3 人工首选称呼

管理员在画像页面手动设置的主昵称，本质上是“机器人在当前群优先怎么称呼此人”。当前代码用 `source_kind = manual_primary` 的名称记录表达这一意图。

### 2.4 画像别名

画像别名是“哪些名称可以识别为这个成员”，来源可以是：

- `manual`：管理员手工维护。
- `learning`：启发式归档学习。
- `llm_evolution`：LLM 画像进化。
- `observed`：启发式画像学习记录的成员昵称。

别名应该服务识别、检索和证据审计，不应默认决定机器人如何称呼用户。

## 三、当前实现链路

### 3.1 sidecar 采集昵称

核心实现：

- `channel/wechat_group/sidecar/wechaty-sidecar-core.mjs`
- `channel/wechat_group/sidecar/wechaty-sidecar.mjs`

`resolveContactDisplayName()` 当前按以下顺序返回第一个有效名称：

```text
room.alias(contact)
  -> raw payload ActualNickName / RecommendInfo.NickName / User.NickName
  -> contact.name()
```

消息事件同时上报：

- `sender_id`：runtime sender ID。
- `sender_name`：上述合成后的显示名。
- `sender_room_alias`：单独读取的群名片。
- `member_fingerprint.display_name`。
- `member_fingerprint.room_alias`。
- `member_fingerprint.wechat_id`。

当前不足是 `sender_name` 已经把群名片、原始消息昵称和联系人昵称合并为一个字符串，归档后无法判断名称具体来自哪一层。

### 3.2 stable 身份解析

核心实现：

- `channel/wechat_group/wechat_group_channel.py`
- `channel/wechat_group/wechat_group_identity_service.py`
- `channel/wechat_group/wechat_group_identity_store.py`

入站消息先解析 account 和 room，再调用 `resolve_member()`：

1. 有唯一强 `wechat_id` 时复用对应 stable member。
2. 没有强 ID，但当前 runtime alias 已绑定时复用现有 stable member。
3. 强 ID 歧义或缺失时创建隔离 stable member，记录 `ambiguous_wechat_id` 或 `missing_wechat_id`。
4. 已确认 member redirect 时继续解析到 canonical stable member。

画像自动写入还有一层更严格的 `_automatic_subject_allowed()`：

- 已经存在画像的成员允许继续自动更新。
- `confidence = manual` 或 `wechat_id` 的成员允许自动创建画像。
- metadata 中存在强 `wechat_id` 的成员允许自动创建画像。
- 只有 `auto_isolated/runtime` 身份且无已有画像时，不允许自动创建正式画像。

这是必要的防误合并门禁，不应为了提高自动学习数量而直接放宽。

### 3.3 消息归档

`WechatGroupChannel._record_inbound_message()` 同时保存：

- runtime room/member ID。
- stable room/member ID。
- `sender_nickname`。
- `metadata.at_list`。
- `metadata.self_id`。
- `metadata.self_display_name`。

归档成功后以 stable room 优先通知画像进化 trigger。

### 3.4 画像与名称存储

当前正式画像库包含：

```text
wechat_group_member_profiles
  PRIMARY KEY (stable_room_id, stable_member_id)

wechat_group_member_profile_names
  UNIQUE (
    stable_room_id,
    stable_member_id,
    normalized_display_name,
    source_kind
  )

wechat_group_member_profile_claims
wechat_group_member_profile_revisions
wechat_group_member_profile_runs
wechat_group_member_profile_learning_state
```

名称记录保存 `source_kind`、`confidence`、`evidence_message_ids`、`run_id`、首次/最近出现时间和 `seen_count`。同一文本可以因来源不同保留多条记录，服务层再按文本去重形成 `aliases`。

### 3.5 人工写入

入口：

```text
POST /api/wechat-group/memories/profiles
  -> stable room/member 校验
  -> WechatGroupProfileService.upsert_manual_profile()
  -> WechatGroupProfileStore.apply_manual_update()
```

当前行为：

- 主昵称写入画像表，并写一条 `manual_primary`、置信度 `1.0` 的名称记录。
- 人工别名写为 `manual`、置信度 `1.0`。
- 再次保存会删除不在新表单中的 `manual_primary/manual` 记录。
- `observed/learning/llm_evolution` 记录不会因人工保存而删除。

### 3.6 启发式学习

入口：

```text
POST /learn/run
  -> WechatGroupLearner.run_once(stable_room_id)
```

画像与群记忆现在使用独立 cursor。画像首次运行会把当前群归档高水位设为 baseline，因此默认只处理此后新增消息，不回放已有历史。

成员画像学习：

- 每批最多 200 条消息。
- 单成员至少 6 条文本消息。
- 最多取该成员本批前 30 条样本。
- 从样本中选择最近一个非原始 ID 形态的 `sender_nickname`。
- 主昵称作为 `observed` 名称记录写入，置信度 `0.8`。

正文显式 `@称呼` 别名学习：

1. 只处理文本消息。
2. 从 `at_list` 排除发言人和机器人 runtime ID。
3. 必须只剩 1 个目标 runtime member。
4. 从正文提取 `@` 或 `＠` 开头的显式称呼。
5. 排除与 `self_display_name` 相同的机器人称呼。
6. 必须只剩 1 个非机器人显式称呼。
7. runtime 目标在当前 stable room 内解析到 canonical stable member。
8. 写入 `source_kind = learning`、置信度 `0.8` 的名称记录。

这条路径不从普通自然语言猜昵称，不处理多目标映射，方向正确。

### 3.7 LLM 画像进化

默认配置：

```text
wechat_group_profile_evolution_enabled = false
idle_minutes = 10
min_messages = 10
max_interval_minutes = 120
batch_message_limit = 200
```

开启后的链路：

```text
群消息归档
  -> note_message(stable_room_id, archive_row_id)
  -> 空闲扫描
  -> executor 读取当前群增量消息
  -> server 将 canonical member 映射为 member_001 等 opaque token
  -> LLM 只返回 token + claim + confidence + evidence IDs
  -> merger 校验 token、当前群、证据白名单和置信度
  -> profile/name/claim/revision 在同一数据库事务中写入
```

当前阈值：

- alias 最低置信度 `0.85`。
- 其他 claim 最低置信度 `0.72`。
- 所有 claim 必须带当前 token 允许的 evidence message ID。
- `all/everyone/here/所有人/全体成员/全员/大家/各位/群友` 会被 LLM merger 拒绝。
- LLM 返回 runtime ID、stable ID、未知 token、重复 token 或跨成员证据会被拒绝。

这部分相较上一版已经有明显改进。

### 3.8 昵称读取与回复称呼

`WechatGroupProfileService._attach_names_and_content()` 当前计算主昵称的优先级：

```text
manual_primary 名称记录
  -> 画像表 primary_nickname
  -> 当前群归档中最近可见 sender_nickname
  -> 最近一条名称记录
```

`aliases` 是当前成员全部名称记录中排除主昵称后的去重列表，原始顺序来自：

```text
last_seen_at DESC, updated_at DESC, id DESC
```

`reply_name` 当前优先级：

```text
manual_primary
  -> manual alias
  -> primary_nickname
  -> 其他 aliases
```

Prompt 中的 naming policy 要求模型优先使用 `reply_name`，否则使用 `primary_nickname`，禁止把 sender ID 当名字。

### 3.9 画像召回

当前 `<wechat-group-memory>` 只注入：

- 当前说话人的画像。
- `at_list` 中排除机器人和说话人后、能解析到当前群 canonical member 的画像。

`resolve_profiles_for_prompt()` 接收 `query` 参数，但当前不使用它做普通文本昵称或别名匹配。因此：

```text
真实 @张总：可以通过 at_list 解析目标画像
普通文本“张总是谁”：不会仅凭“张总”别名注入目标画像
```

这符合当前项目“首轮只处理明确 @ 成员，不把普通文本昵称匹配作为强需求”的安全边界。

### 3.10 Web 管理端

当前画像页面按 stable room 过滤，支持分页查询、从当前群成员创建画像、编辑主昵称和别名。

页面显示的是扁平化结果：

- 一个 `primary_nickname` 输入框。
- 一个把所有 `aliases` 用逗号连接的输入框。
- 只展示 name record 数量，不展示每条记录的来源、置信度、证据和状态。

保存时整个扁平 alias 列表都会作为人工 alias 提交。

## 四、当前已经满足的关键不变量

以下能力建议保持，不在昵称优化中回退：

1. 所有画像和名称读写必须绑定 `stable_room_id + canonical stable_member_id`。
2. runtime ID 只用于微信侧收发和身份 alias，不作为画像主键。
3. 不按昵称自动合并 stable member。
4. 不把 A 群昵称或别名注入 B 群。
5. 未锚定身份不得直接自动创建正式画像。
6. LLM 不接触可直接落库的真实成员主键。
7. LLM claim 必须有当前群、当前批次、当前成员的证据白名单。
8. 人工主昵称优先于自动来源。
9. LLM 临时错误不得推进 cursor。
10. evolution 回滚必须同时恢复画像、名称和 claims。

## 五、问题与风险评估

### P0：自动别名的目标绑定仍不够强

#### P0-1：LLM 多目标消息可能发生别名错配

executor 会把一条消息同时加入作者及所有被 @ 成员的 `evidence_by_token`。当消息包含多个被 @ 成员时，LLM 可以看到：

```text
mentions=member_002,member_003: @张总 @李老师 请一起看下
```

当前服务端能证明这条消息与两个 token 都相关，但不能证明“张总”一定属于 `member_002`、“李老师”一定属于 `member_003`。只要模型把称呼分配反了，现有 evidence allowlist 仍可能通过。

影响：高置信错误别名会写入正式画像，并影响后续识别和回复称呼。

#### P0-2：启发式与 LLM 的自动名称过滤不一致

LLM merger 有群体泛称 denylist，启发式 `_normalize_mention_alias()` 没有。

已用当前代码复现：

```text
text = "@CowBot 请@所有人看下"
at_list = [bot-runtime, bob-runtime]

结果：("bob-runtime", "所有人")
```

影响：异常 at_list、微信协议差异或构造消息可能把“所有人”写给单个成员。

### P1：名称语义和优先级不清晰

#### P1-1：自动别名可以成为画像主昵称

`merge_learned_aliases()` 在没有已有主昵称时会取第一个 alias 作为 `primary_nickname`；LLM merger 也会在“当前读取结果无主昵称”时用第一个 alias 填主昵称。

别名是“可用于识别该成员的其他称呼”，主昵称是“当前群展示名或人工首选称呼”。两者语义不同，不应自动互相提升。

#### P1-2：存量主昵称优先于当前群实时昵称

当前主昵称优先级中，画像表 `primary_nickname` 位于 live archive name 之前。因此：

- 用户修改微信群名片后，只要画像表已有旧主昵称，读取仍优先返回旧值。
- 启发式学习只在手动运行时更新主昵称，不是每次名称变化都同步。
- `archive.list_members()` 最多返回 100 个 runtime 成员，虽然调用方传入 500；大群中较少发言成员可能无法获得 live name 兜底。

#### P1-3：昵称来源在归档中丢失

sidecar 知道 `room_alias`，但归档的主名称字段只保存合成后的 `sender_nickname`。后续服务无法判断它是：

- 当前群名片。
- 原始消息昵称。
- 联系人全局昵称。

这会妨碍稳定优先级、变更检测和 UI 来源展示。

#### P1-4：机器人群内别名不一致导致显式学习漏召回

sidecar 构造 `selfInfo` 时没有传入当前 room，`self_display_name` 可能是机器人联系人昵称，而正文显示的是机器人在本群的群名片。

已用当前代码复现：

```text
self_display_name = "CowBot"
text = "@小灯 请@张总看下"
```

解析会得到两个可见 mention 名称，因候选数不等于 1 而放弃学习“张总”。

#### P1-5：人工编辑无法明确否决自动别名

画像详情把所有来源的 aliases 扁平化到一个输入框。用户删除一个 LLM alias 后保存：

- 只会删除同名 `manual` 记录。
- 原来的 `llm_evolution` 或 `learning` 记录仍然存在。
- 刷新后该 alias 会再次出现。

当前没有 `suppressed/rejected` 状态，也没有“仅编辑人工别名”的 UI 语义。

#### P1-6：manual alias 的首选顺序是隐式的

`reply_name` 会在没有人工主昵称时选第一个 manual alias，但 name record 按最近时间和 ID 倒序返回，不等于用户输入顺序。用户不能明确指定哪个 alias 是首选称呼。

### P2：召回、运维和可观测性问题

#### P2-1：普通文本别名不参与目标画像召回

当前 `query` 参数对画像目标解析无效。这是保守策略，不是立即必须修复的缺陷；但 UI 和用户可能误以为“已经学会别名”就意味着“普通文本提到该别名一定能找到画像”。

#### P2-2：自动学习开关语义不一致

`wechat_group_learning_enabled` 当前存在于配置和 UI，但旧启发式画像学习仍以手动 `learn/run` 为入口，没有基于该开关的自动调度或明确拒绝。

#### P2-3：画像进化 pending 数量使用全库 row ID 差值

trigger 用 `latest_observed_row_id - last_archive_row_id` 近似当前群待处理消息数。归档 ID 是全库自增值，多群消息交错时该差值不等于当前群实际新消息数。

#### P2-4：别名统计不是“实际新增数”

`alias_update_count` 当前统计本轮通过校验的 alias claim 数，不区分：

- 新增名称。
- 已有名称的证据刷新。
- 同文本不同来源新增。

UI 若将其解释为“新增别名”会造成误导。

#### P2-5：首次学习默认不回放历史

heuristic 和 evolution 第一次运行都会以当前归档高水位作为 baseline。这个行为避免历史脏数据被重新写入，但 UI 没有明确说明“只从启用后的新消息开始学习”。

## 六、推荐目标语义

### 6.1 不新增全局人物昵称

本次继续坚持按群隔离：

```text
stable_room_id + canonical stable_member_id
  -> 当前群观察名
  -> 当前群人工首选称呼
  -> 当前群 aliases
  -> 当前群画像字段
```

不把其他群的群名片或别名带入当前群。

### 6.2 名称角色拆分

推荐对外返回以下明确字段：

| 字段 | 语义 | 是否持久化 | 是否可自动更新 |
| --- | --- | --- | --- |
| `observed_room_name` | 当前群最近确认的群名片/展示名 | 可来自 identity alias 或 observed name record | 是 |
| `manual_preferred_name` | 管理员指定的首选称呼 | `manual_primary` name record | 否，只能人工修改 |
| `primary_nickname` | 兼容字段，返回最终有效显示名 | 由服务端计算 | 否，不再被 alias 直接填充 |
| `aliases` | 当前群可识别的其他称呼 | name records | 是，但必须有来源和门禁 |
| `reply_name` | LLM 应使用的称呼 | 由服务端计算 | 否 |

兼容阶段不必立即新增 profile 主表字段。现有 `manual_primary` 和 identity member alias 已经能表达前两类信息，优先通过服务层统一计算，避免不必要迁表。

### 6.3 推荐优先级

主显示名：

```text
manual_preferred_name
  -> 当前 active identity member alias.room_alias
  -> 当前群最近 archive sender_nickname
  -> 有 observed 证据的存量 primary/name record
  -> 最高可信 active alias 兜底
  -> 空字符串
```

回复称呼：

```text
manual_preferred_name
  -> effective primary_nickname
```

aliases 只做识别集合，不再因为排序靠前就自动成为 `reply_name`。

### 6.4 自动别名门禁

所有自动名称候选统一经过同一 helper：

- 清理空白、前导 `@/＠` 和常见标点。
- Unicode NFKC/大小写归一化仅用于比较，展示保留原文。
- 拒绝 runtime/stable ID、长哈希、传输层字段和纯数字消息 ID。
- 拒绝机器人自身名称。
- 拒绝 `all/everyone/here/所有人/全体成员/全员/大家/各位/群友`。
- 单字符中文默认拒绝；人工输入不受此自动门禁限制。
- 长度、控制字符和 HTML/XML 做保守限制。

### 6.5 证据必须绑定到具体成员

别名自动落库必须满足至少一种服务端可验证条件：

1. 单目标显式 mention：消息只有一个非机器人目标，且只有一个非机器人可见称呼。
2. 结构化 mention：sidecar 上报 `{runtime_sender_id, display_name}`，服务端将 display name 与 canonical member 一一映射。
3. 人工确认：管理员在 UI 中接受候选。

多目标文本中仅凭 LLM 推断“哪个称呼属于哪个 token”不得直接自动落库。

角色、兴趣、风格等作者维度 claim 可以继续使用作者消息证据；alias 需要单独的 target-bound evidence allowlist，不能复用宽泛的 related-member evidence。

### 6.6 人工否决优先

名称记录建议增加最小状态字段：

```text
status = active | suppressed
```

规则：

- 管理员 suppress 某个 normalized alias 后，自动学习可以增加证据计数，但不得重新激活。
- 人工重新启用后才恢复。
- `aliases`、搜索和 prompt 只使用 active 记录。
- revision/rollback 同时覆盖名称状态。

## 七、分阶段落地方案

### 阶段 1：先修正自动别名安全性和名称优先级

目标：不改 sidecar 协议、不新增大型 UI，先消除错误写入与旧昵称压过实时昵称。

实施项：

1. 抽取共享的自动名称归一化与 denylist helper，供 learner 和 LLM merger 共用。
2. 为启发式学习增加群体泛称、机器人别名不一致、普通文本无真实 mention、多目标保护测试。
3. LLM alias 只允许使用“作者自身证据”或“唯一非机器人目标消息”的 alias evidence；多目标消息不自动应用 alias。
4. `merge_learned_aliases()` 和 LLM merger 不再用 alias 持久化填充 `primary_nickname`。
5. 集中实现一个有效名称计算入口，主昵称改为：人工主昵称 > 当前群观察名 > 有来源的存量观察名 > alias 兜底。
6. `reply_name` 改为人工主昵称 > 有效主昵称；普通 aliases 不参与随机首选。
7. `archive.list_members()` 的有效上限与调用方一致，或新增按 `stable_member_id` 精确查询最近名称的方法，避免扫描/截断 100 人。
8. 增加实际新增、证据刷新和拒绝原因计数，不再把所有 accepted claims 都叫新增别名。

预计修改：

- `channel/wechat_group/wechat_group_profile_service.py`
- `channel/wechat_group/wechat_group_profile_store.py`
- `channel/wechat_group/wechat_group_learner.py`
- `channel/wechat_group/wechat_group_profile_evolution_executor.py`
- `channel/wechat_group/wechat_group_profile_evolution_merger.py`
- `channel/wechat_group/wechat_group_archive.py`
- 对应 `tests/test_wechat_group_profile_*`、`tests/test_wechat_group_learner.py`、`tests/test_wechat_group_context.py`

### 阶段 2：补齐名称来源、人工治理和当前群同步

目标：让管理员看得懂名称从哪里来，并能真正修正错误自动别名。

实施项：

1. 名称记录增加 `status`，兼容迁移统一回填 `active`。
2. Profile API 分别返回：
   - `manual_preferred_name`
   - `observed_room_name`
   - `manual_aliases`
   - `learned_aliases`
   - `effective_aliases`
   - `reply_name`
3. Web 表单把“主昵称”改为“首选称呼”，把人工别名与自动识别别名分区展示。
4. 自动别名显示来源、置信度、证据数量、最近出现时间和状态。
5. 增加管理员 suppress/restore 操作；普通成员仍无画像写权限。
6. 从 active identity member alias 读取最新 `room_alias`，归档名称只做兜底。
7. 群成员刷新时只在名称变化时更新 observed name，避免每条消息重复写数据库。

默认只修改 Web 控制台，不修改 `desktop/`。

### 阶段 3：可选的结构化 mention 与普通文本别名召回

该阶段需要单独确认，不作为前两阶段的阻塞项。

结构化 mention：

1. sidecar 把 `mentionList()` 扩展为 `mentions=[{id,name}]`。
2. 更新 JSON Lines 事件协议、Python message、archive metadata 和测试。
3. 服务端逐个解析 stable member，建立 display name 与 member token 的确定映射。
4. LLM 只负责补充语义，显式 mention 别名由服务端直接判定。

普通文本召回：

1. 默认仍只使用真实 `at_list`。
2. 若后续需要支持“张总是谁”，只允许当前群 active alias 的唯一精确命中。
3. 同一 alias 命中多个成员时不注入任何画像，并返回 `ambiguous_alias` 诊断。
4. 不做跨群、拼音、模糊或 LLM 自由匹配。

### 阶段 4：修正学习调度和可观测性

实施项：

1. pending 数量改为数据库按当前 stable room 统计 `id > cursor` 的真实消息数。
2. backlog 超过 batch limit 时，在受控上限内继续排空，而不是等待下一条新消息。
3. 明确 `wechat_group_learning_enabled`：要么接入启发式自动调度，要么删除误导性的开关，仅保留“手动运行”。
4. UI 明确首次 baseline 语义，并提供显式、管理员确认的“从指定时间回放”能力，而不是默认重放全部历史。
5. 运行详情展示 alias inserted/refreshed/rejected/suppressed 数量及拒绝原因。

## 八、建议测试矩阵

### 8.1 名称来源与优先级

- 人工首选称呼压过当前群名片。
- 没有人工首选时，最新群名片压过旧画像主昵称。
- 当前群名片缺失时使用联系人昵称或 observed 名称。
- 自动 alias 不会成为 `reply_name`。
- A 群和 B 群的当前名、人工称呼、aliases 完全隔离。
- 超过 100 人的群仍能按 stable member 精确取得当前名称。

### 8.2 启发式别名

- 单目标、单显式称呼正确入库。
- 多目标不学习。
- 普通文本昵称不学习。
- 只有机器人 mention 不学习。
- `@所有人/@大家/@all/@everyone/@here` 不学习。
- 机器人联系人名与群名片不一致时，仍能正确排除机器人 mention。
- runtime sender 变化后仍写同一 canonical profile。
- 未锚定成员不自动创建正式画像。

### 8.3 LLM 画像进化

- opaque token、当前群和 evidence allowlist 继续有效。
- 多目标消息中的 alias 不自动落库。
- 跨成员 evidence 被拒绝。
- 同一 alias 重复出现只刷新证据，不重复计算新增数。
- suppress 的 alias 不会被后续 evolution 重新激活。
- HTTP 408/429/5xx 不推进 cursor。
- rollback 恢复名称状态、claims 和画像主体。

### 8.4 Prompt 召回

- speaker profile 使用 canonical stable member ID。
- 真实 runtime mention 能解析当前群画像。
- 不注入机器人自身或说话人作为 mentioned profile。
- 不跨群召回同名 alias。
- 可选普通文本 alias 唯一命中时才注入；歧义时拒绝。
- prompt 中 `reply_name` 与服务端有效名称计算结果一致。

### 8.5 Web 管理端

- 只编辑人工 aliases，不会把自动 aliases 复制为 manual 来源。
- suppress/restore 后列表、详情、搜索和 prompt 同步变化。
- 来源、置信度、证据数和最近出现时间展示正确。
- 人工首选称呼为空时回退当前群观察名。

## 十一、验收标准

全部满足后才能认为昵称优化完成：

1. 每个名称都能回答“来自哪个群、哪个成员、哪种来源、有哪些证据、当前是否有效”。
2. 自动 alias 不会无条件成为主昵称或回复称呼。
3. 群名片变化后，在当前群能够得到新显示名，且不影响其他群。
4. `@所有人`、机器人群别名不一致和多人 mention 不会产生错误成员 alias。
5. LLM alias evidence 能服务端证明属于具体目标成员，而不仅是与目标出现在同一消息。
6. 管理员可以真正否决错误自动 alias，后续学习不会静默恢复。
7. 真实 mention、speaker profile 和 member redirect 始终解析到 canonical stable member。
8. 当前群超过 100 人时，昵称解析不因成员列表截断失效。
9. Web 展示和 prompt 中的 `primary_nickname/reply_name/aliases` 使用同一服务端规则。
10. 聚焦回归、微信群通道回归和真实链路检查均通过。
