# 微信群思考泄漏根因修复设计方案

> **状态：** 已实施并完成本地验证
> **创建日期：** 2026-07-30
> **代码基线：** `aef72e63`
> **问题范围：** 微信群 Agent 回复中的内部分析、思考标签和发送协议标签泄漏
> **关联提交：** `44ed6819`、`44677650`、`54460cb1`、`d88b80ba`、`c3976b7d`、`1c3d63aa`

## 1. 设计结论

本问题不采用“整体回退到 7 月 29 日修改前”的方案，也不恢复自然语言思考正则。

推荐方案由四个相互独立、可以分别验证和回退的部分组成：

1. **选择性恢复旧上下文边界**：新 thread 的群聊 Prompt 不再注入历史机器人正文；续聊只从当前成员的已确认 thread 恢复机器人答复。
2. **修复 Provider 真实请求控制**：微信群的禁思考要求必须落实到最终 HTTP payload；不再以 FakeBot 收到 `thinking=disabled` 视为完成。
3. **建立严格最终答复协议**：微信群模型候选只有提供明确结构化最终答复边界，才允许进入 Agent 历史和发送链路；裸文本不再默认视为可发送正文。
4. **隔离既有污染**：含历史机器人事件的 rolling summary 不再注入，新协议上线前创建的 active thread 不再自动续接。

该方案保留当前已经验证有效的候选请求快照、候选完整缓冲、工具协议校验和 `pending -> send_result -> confirmed` 两阶段提交，不回退这些安全能力。

## 2. 用户反馈样本

当前反馈已经包含多种不同形态，不能继续当成同一种正则问题处理。

### 2.1 带发送协议标签

```text
</thinking>
<send>
<message>
锐评：……
</message>
</send>
我直接用了「锐评」这个梗接上啦……
```

该样本同时包含：

- 未被识别的 `</thinking>`；
- 可确定识别的 `<send><message>...</message></send>` 最终消息边界；
- 发送协议之外不应交付的解释文本。

### 2.2 不可用技能的内部检查式答复

```text
我看了一下，这个 image-generation 技能需要配置 API 密钥才能使用……
不过我注意到用户提供的 Moviepilot 需求是清晰的……
需要我先确认……
```

该样本不一定全部属于模型思考。现有 `<unavailable_skills>` 明确要求模型在相关场景指导用户完成配置，模型可能把内部技能状态组织成了面向用户的最终答复。但“我看了一下”“我注意到用户提供的需求”等内部检查口吻不应出现在群聊正文。

### 2.3 无标签内部分析加最终答复

```text
用户要求生成……
我需要特别注意……
我应该用自然、幽默的方式回绝……
回复控制在50字以内……
哈哈，这个我可能没法直接生成哦……
```

该样本没有可靠的结构化边界。服务端不能仅凭“用户要求”“我应该”等中文句式证明哪一段是思考、哪一段是正常技术说明。

### 2.4 带 Provider 内部路径的 JSON 发送协议

```text
小米龙甲电池这套路……
</thinking>
<send>
{"path":"/mnt/data/tmp/image.png","message":"小米龙甲电池：……"}
</send>
```

该样本证明 `<send>` 内部不只有 `<message>` 子标签，还可能是 JSON 对象。服务端只允许读取字符串 `message` 作为候选最终文本；`path`、URL 和其他字段均属于不可执行的 Provider 数据，不得访问、下载、映射为本地文件或进入渠道媒体发送。只有 `path` 而没有有效 `message` 时必须拒绝候选。

### 2.5 空的文本化工具协议

```text
@小灯在呢～有事直说！
</thinking>
<tool_calls>
</tool_calls>
```

`<tool_calls>` 是 Provider 输出到普通 content 的内部协议，不是 OpenAI/Claude 流中的原生工具调用结构。服务端不得执行、发送或从标签前的自然语言猜测最终答复。该候选没有结构化最终答复边界，应整体丢弃并切换备用模型。

## 3. 已验证事实

### 3.1 历史版本回放

将当前全部新样本回放到以下历史版本，均会作为正文通过：

| 版本 | 当时能力 | 新样本结果 |
|---|---|---|
| `172d6f69` | 首次流式思考修复前 | 当前样本均通过 |
| `44ed6819` / `v2.1.19` | 识别 `<think>...</think>` | 当前样本均通过 |
| `44677650` / `v2.1.20` | 增加特定无标签中文正则 | 当前样本均通过 |
| `54460cb1` | 删除无标签正则，保留结构化隔离 | 当前样本均通过 |
| `d88b80ba` 之后 | V2 thread 与 room timeline | 当前样本均通过 |
| 当前 `aef72e63` | 候选缓冲与协议残片校验 | 当前样本均通过 |

因此，整体回退不能修复本次反馈样本。它只会同时撤销后续已经解决的跨分片 `<think>`、候选污染、坏工具调用和未确认发送持久化等问题。

### 3.2 当前输出链路回放

当前代码对这些样本的回放结果一致：

```text
流式结构化解析：原样保留
微信群候选校验：接受
发送前 cleanup：保留内部分析前缀
```

原因是：

- `agent/protocol/agent_stream.py` 只识别 `<think>` / `</think>` 和标准 `reasoning_content`；
- `bridge/agent_bridge.py` 只拒绝当前已知的 `</arg_value>`、`<function_calls_output>`、`<wechat-sticker-copied>` 等协议残片；
- `channel/wechat_group/wechat_group_reply_cleanup.py` 只处理群聊 Prompt 块、Markdown、固定开场和尾部追问，不负责识别模型内部协议。

### 3.3 禁思考参数没有进入通用 OpenAI 兼容请求体

当前 `AgentLLMModel` 会给微信群候选设置：

```python
thinking={"type": "disabled"}
```

但 `models/openai_compatible_bot.py` 构造最终请求时没有转发该字段。wire-level 回放确认最终 HTTP payload 中：

```text
thinking: absent
reasoning_effort: absent
```

现有单元测试只断言 FakeBot 收到了 `thinking=disabled`，没有检查最终 HTTP 请求体。因此测试通过不能证明 Provider 的思考模式已经关闭。

该缺陷早于 7 月 29 日存在，不能单独解释“最近才集中出现”，但它解释了为什么后续增加的微信群禁思考逻辑没有形成实际请求约束。

### 3.4 V2 引入了可确认的放大路径

`d88b80ba` 之前，普通直聊 recent context 使用 `get_recent_messages()`，只读取群成员入站消息。V2 改为统一调用 `get_recent_conversation_messages()`，会同时读取机器人已发送回复。

隔离临时数据库回放结果：

```text
new_thread recent context 包含上一条已发送机器人正文：是
resume_thread recent context 重复包含同一机器人正文：否
resume_thread 的 thread 历史包含该机器人正文：是
```

因此当前不是“同一次续聊重复注入两遍”，而是：

- 新话题通过 recent timeline 看到历史机器人回复；
- 续聊通过自己的 thread 历史看到机器人回复；
- rolling summary 目前也可能总结机器人回复。

第一次泄漏一旦确认发送，就会成为后续模型可见文本，从而强化相同的内部分析口吻。这是 7 月 29 日后真实存在的行为变化，也是用户“修改前没有连续出现”这一观察中有代码证据支持的部分。

## 4. 完整因果链

```text
Provider 默认或未关闭的思考/内部发送协议
        |
        v
普通 content 中出现 thinking、send/message 或裸分析
        |
        v
候选缓冲只校验坏工具与少量已知协议残片
        |
        v
<think> 解析器和发送前 cleanup 均无法识别
        |
        v
sidecar 确认 sent，正文进入群归档与成员 thread
        |
        +------------------------+
        |                        |
        v                        v
new_thread recent timeline      resume_thread 历史
        |                        |
        +------------+-----------+
                     v
              后续模型再次看到泄漏文本
```

结论是：输出过滤并非唯一根因。若只继续增加标签或中文正则，仍会保留 Provider 请求未受控和历史回灌两个入口。

## 5. 方案比较

| 方案 | 优点 | 主要问题 | 结论 |
|---|---|---|---|
| 整体回退到 7 月 29 日前 | 操作直观 | 当前新样本仍会通过；同时撤销多项已验证安全修复 | 拒绝 |
| 恢复并扩展无标签中文正则 | 改动较小 | 无法证明语义边界，会误删正常多段技术回答 | 拒绝 |
| 只增加 `thinking/send` 标签过滤 | 可解决第一个样本 | 第二、第三个裸文本样本仍会发送，Provider 与历史回灌不变 | 不完整 |
| 第二个 LLM 裁判重写答案 | 可做语义判断 | 增加成本、延迟和新的泄漏/拒绝风险，裁判自身也不可靠 | 拒绝 |
| 选择性回退上下文 + 真实请求控制 + 严格最终答复协议 | 同时封住请求、输出和回灌路径；无需中文语义猜测 | 需要验证各候选遵守最终答复协议 | 推荐 |

## 6. 设计目标与非目标

### 6.1 目标

- 微信群不发送、持久化或回灌模型内部分析、思考标签和 Provider 发送协议残片。
- 主模型与每个备用模型的禁思考要求能够在最终 HTTP payload 或 Provider 原生请求结构中验证。
- 无标签裸文本没有结构化最终答复边界时 fail closed，不从中猜测并截取最后一段。
- 工具调用轮次继续只交付工具协议，不发送中间自然语言。
- 已确认 thread 继续保留用户原文和最终助手文本，保持真实续聊能力。
- Web 的标准 `reasoning_content` 展示行为不受微信群严格协议影响。

### 6.2 非目标

- 不整体回退 V2 context/thread、候选快照、候选缓冲或两阶段提交。
- 不恢复任何基于“用户要求”“我应该”等句式的自然语言截取规则。
- 不引入第二个模型裁判。
- 不借本次任务重构通用 Agent loop、工具系统或所有渠道输出协议。
- 不自动删除群归档、历史消息或用户数据。
- 不连接、更新或重启远端 Docker 环境。

## 7. 详细设计

### 7.1 先建立失败回归基线

在修改实现前，先加入当前必然失败的回归测试：

1. 全部用户反馈样本分别通过候选缓冲、AgentStream 和发送前 cleanup 的组合测试。
2. 通用 OpenAI 兼容 Bot 的 HTTP payload 捕获测试，断言微信群请求真实携带禁思考控制。
3. `new_thread` 不应看到上一条机器人正文的上下文测试。
4. rolling summary 含 `assistant:*` 来源时不得继续注入的测试。
5. 新协议上线前创建的 active thread 不得被新请求自动续接的测试。

RED 阶段必须证明：当前反馈样本可进入发送正文、通用 HTTP payload 缺少思考控制、机器人正文可进入新 thread Prompt。

### 7.2 微信群严格最终答复协议

微信群候选已经在路由层完整缓冲，因此在任何分片进入 `AgentStreamExecutor` 前增加确定性的候选归一化边界。

#### 7.2.1 模型请求约束

将 `_WECHAT_GROUP_FINAL_ONLY_PROMPT` 改为明确的机器可校验协议：

```text
需要工具时只返回原生 tool_calls，不输出过程说明。
不需要继续调用工具时，将唯一可发送正文放入：
<final_response>...</final_response>
标签外不得放置面向用户的正文。
```

该协议只影响微信群候选，不改变 Web、CLI 和其他 IM 渠道。

#### 7.2.2 候选接受规则

无工具调用的模型候选只接受以下两种完整结构：

1. 新协议：`<final_response>...</final_response>`；
2. 已在真实反馈中出现的 Provider 协议：`<send><message>...</message></send>`；
3. JSON 发送协议：`<send>{"message":"...", ...}</send>`。

归一化规则：

- 恰好提取一个完整最终正文块；
- JSON 发送协议必须通过 `json.loads()` 解析且 `message` 必须是非空字符串；`path` 及其他字段只忽略，绝不执行；
- 找到唯一完整最终正文块时，块外文本和块外孤立思考标签一律视为不可交付的模型内部内容，不进入正文、事件或历史；
- 多个最终正文块、空正文、嵌套损坏或未闭合标签均拒绝当前候选并切换备用模型；
- 找不到完整最终正文块时，任何孤立 `thinking/send/message/final_response` 标签都直接导致候选拒绝；
- 全部候选不合格时返回系统生成的安全错误，不回放任何模型裸文本；
- 归一化成功后只向 `AgentStreamExecutor` 交付一个干净的正文 chunk。

工具调用候选继续沿用当前严格规则：

- 工具名非空且存在于当前 schema；
- 参数是完整 JSON object；
- 工具轮次中的普通 content 不发送、不持久化；
- `reasoning_content` 不进入最终正文。

#### 7.2.3 思考标签兼容

结构化思考解析增加明确协议别名：

- `<think>...</think>`；
- `<thinking>...</thinking>`。

仅按完整标签状态机处理，不按自然语言内容识别。存在唯一完整最终正文块时，块外孤立思考标签随其他块外内容一起丢弃；不存在完整最终正文块时，孤立结束标签、损坏标签或标签冲突在候选缓冲层直接导致拒绝，不把残片交给发送前 cleanup。

#### 7.2.4 反馈样本的预期结果

| 样本 | 预期处理 |
|---|---|
| `</thinking><send><message>答复</message></send>解释` | 仅交付 `<message>` 内的答复 |
| “我看了一下 image-generation……”裸文本 | 候选不满足最终答复协议，丢弃并切换 |
| “用户要求……我应该……最终答复”裸文本 | 候选不满足最终答复协议，丢弃并切换 |
| `<send>{"path":"/mnt/data/...","message":"答复"}</send>` | 仅交付 `message`，忽略且不访问 `path` |
| `正常句子</thinking><tool_calls></tool_calls>` | 文本化工具协议无效，整体丢弃并切换 |

### 7.3 Provider 禁思考控制必须落实到 wire level

新增一个最小的 Adapter 能力边界，区分三类情况：

1. **Provider 原生支持禁思考**：由现有 DeepSeek、MiMo、DashScope、Moonshot 等原生适配器映射成其官方请求字段。
2. **Provider 按 API 契约不暴露思考正文**：保留其标准请求，但仍必须遵守微信群最终答复协议。
3. **通用自定义 OpenAI 兼容端点**：把当前已经传到 Bot 的 `thinking={"type":"disabled"}` 真正写入该候选 HTTP payload。

实施约束：

- 第三方字段名称和取值必须先依据对应 Provider 官方文档或现有原生适配器验证，禁止根据模型名猜测。
- 自定义 OpenAI 兼容端点若明确返回“不支持 thinking 参数”的 400，不得在微信群中无控制重试同一候选；应将该候选判为协议不兼容并切换备用模型。
- 不允许为了提高可用率，在去掉禁思考控制后继续接受该候选裸文本。
- 最终答复协议始终作为第二道边界，即使 Provider 声称已关闭思考也不直接信任任意裸 content。

wire-level 测试必须捕获最终交给 `OpenAIHTTPClient.chat_completions()` 的 payload，而不是只检查 `_build_call_kwargs()` 或 FakeBot 参数。

### 7.4 选择性恢复 V2 上下文边界

不删除 room timeline，也不回退 stable room/member、thread 或 room revision。只调整“哪些事件可以渲染进模型 Prompt”。

#### 7.4.1 recent timeline

- `new_thread`：recent block 只渲染群成员公开消息，不渲染历史机器人正文；恢复 7 月 29 日前普通直聊的输入边界。
- `resume_thread`：机器人历史只来自当前成员、当前 thread 的已确认文本；room recent block 继续只补充群成员公开消息。
- `observe_only`：收件人判断仍可使用 timeline 元数据，但生成 Prompt 不直接注入历史机器人正文。
- quoted reply：通过当前消息的 quote excerpt 和 thread 关联恢复被回复内容，不依赖全量机器人 recent 文本。

room revision、single-flight 和 stale 判断仍可继续统计 assistant cursor；本次只改变 Prompt 投影，不改变协调语义。

#### 7.4.2 rolling summary

rolling summary 只总结本群成员的安全公开消息，不再把机器人答复作为摘要原料。

现有 summary 已保存 `assistant_cursor`，新版本还保存 `source_event_ids_json`，因此无需数据库迁移：

- 读取时发现 `assistant_cursor > 0` 或任意 `assistant:*` 来源，立即视为旧策略派生数据，不注入 Prompt；
- 后台按新规则重新生成；
- 原 summary 最长一小时自然过期，失败时继续保持不注入，而不是回退使用旧摘要。

#### 7.4.3 旧 thread 隔离

为新建 thread 的 metadata 增加输出协议版本，例如 `output_protocol_version=2`。

- 只续接协议版本匹配的 active thread；
- 修复上线前创建、没有版本字段的 thread 视为旧 thread，创建新 thread；
- 不删除旧 thread 和消息，等待现有 TTL 自然过期；
- 避免上线前已经确认发送的裸分析继续从 thread 回灌。

### 7.5 不可用技能提示改为最终答复语义

调整 `<unavailable_skills>` 的系统提示措辞：

- 该块是系统提供的能力状态，不要求模型描述“检查过程”；
- 相关请求确实依赖不可用技能时，只输出面向用户的简短能力结果和必要配置项；
- 不得使用“我看了一下”“用户提供的需求”“我需要先确认”等内部路由口吻；
- 不得声称读取了不存在的 `config.json`，只能陈述结构化 `<missing>` 中真实提供的信息；
- 最终内容仍必须进入微信群最终答复协议。

这不是自然语言输出过滤，而是修正当前系统提示对模型行为的错误引导。

### 7.6 诊断日志

新增不包含正文的结构化诊断字段：

```text
candidate provider/model
route source 和 attempt count
reasoning control mode
final protocol kind
candidate rejection reason
raw/normalized character count
thread action
recent member/assistant event count
```

日志不得记录完整 Prompt、模型裸分析、API Key、请求头或用户媒体路径。这样再次出现问题时，可以判断是请求控制未生效、最终协议不合格还是历史上下文来源异常，而不需要先读取群聊私密正文。

## 8. 预计修改范围

## 10. 验证矩阵

### 10.1 输出协议

- `<think>`、`<thinking>` 的开闭标签及标签名跨任意 SSE 分片。
- 标准 `reasoning_content` 不进入微信群正文、事件或 thread。
- `<send><message>` 完整结构只交付 message 内容。
- `<send>{JSON}</send>` 只交付字符串 `message`，不访问或发送 `path`。
- JSON 只有 `path`、`message` 非字符串或 JSON 损坏时拒绝候选。
- `<tool_calls>` 等文本化工具协议不得转换为可执行工具，也不得发送标签前文本。
- 标签外存在分析、解释或重复正文时不交付标签外内容。
- 裸内部分析加最终答复不满足协议时切换候选。
- 多个 message、空 message、未闭合或嵌套损坏时拒绝候选。
- 正常多段答复放在 `<final_response>` 内时完整保留，不按段落截断。
- 用户讨论 XML 标签本身时，不得意外把普通代码示例当成外层交付协议。

### 10.2 工具与故障转移

- 工具调用轮次中间正文继续丢弃。
- 空/未知工具名、损坏参数和既有 Provider 协议残片继续切换候选。
- 主候选协议不合格后，备用候选从同一不可变请求源重新创建请求。
- 全部候选协议不合格时只返回系统安全错误。
- safety/content-filter 结果不通过备用模型绕过。

### 10.3 Provider 请求

- 微信群主模型及每个备用模型的最终 payload 均能证明思考关闭或 Provider 按契约不暴露思考正文。
- 通用自定义端点请求真实包含禁思考字段。
- Provider 明确拒绝该字段时，不进行无控制重试。
- 非微信群渠道保持当前思考开关与 Web 展示语义。

### 10.4 上下文与持久化

- `new_thread` Prompt 不含历史机器人正文。
- `resume_thread` 只从当前 thread 恢复已确认最终答复。
- 其他群、其他成员私有 thread 不得进入当前请求。
- 含 `assistant:*` 来源的旧 rolling summary 不注入。
- 未确认发送、清洗为空、静默和 stale 抑制继续丢弃 pending turn。
- 只有归一化后的最终正文才能进入群归档和 thread。

## 11. 验收标准

同时满足以下条件才视为修复完成：

1. 全部反馈样本均不能把内部分析、原始标签、文本化工具协议或 Provider 内部路径发到群里。
2. 带 `<message>` 的样本最多只发送其中一条最终答复；JSON `<send>` 样本最多只发送 `message` 字段。
3. 第二个样本只能产生面向用户的简短能力状态，不出现检查、路由和用户需求分析口吻。
4. 第三个样本只能发送最终安全答复；无法取得结构化最终答复时宁可安全失败，不截取最后一段猜测发送。
5. wire-level 测试能证明微信群候选的禁思考控制已进入真实请求结构。
6. 新 thread、rolling summary 和旧 thread 都不能重新注入修复前的机器人泄漏正文。
7. 工具调用、主备切换、正常多段答复和 Web 思考展示无回归。
8. 定向测试、全量回归、语法检查和 `git diff --check` 全部通过。

## 12. 回退方案

本设计不迁移或删除用户数据，回退只涉及运行时代码：

- 最终答复协议与候选归一化可作为一个原子改动回退；
- Provider wire 控制可按适配器单独回退；
- recent/summary/thread 投影策略可独立恢复；
- 不可用技能提示可独立恢复。

若严格最终答复协议导致某个候选持续不兼容，应先从候选链中安全跳过并记录诊断，不得直接恢复“任意裸 content 均可发送”的旧行为。需要放宽协议时必须基于该 Provider 的正式结构化输出能力另行设计和验证。

## 13. 剩余风险

- 任何模型都可能把不恰当内容放进最终答复块，结构化协议只能保证“交付边界”，不能证明语义质量。
- 某些第三方 OpenAI 兼容端点可能静默忽略禁思考字段，因此仍需最终答复协议作为独立保护。
- 不同 Provider 对 XML 指令的遵循度可能不同，必须在发布前对当前主备候选逐一做真实 canary；不合格候选应 fail closed。
- 修复前归档仍保留历史泄漏文本，但新 Prompt 投影、summary 失效和 thread 版本隔离会阻止其继续进入模型上下文，不需要破坏性清库。

这些风险不通过自然语言正则规避，而通过结构化边界、候选隔离、上下文来源控制和真实链路验收降低。
