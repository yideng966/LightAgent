# 微信群模型请求重组与输出隔离最终开发计划

> **状态：** 已完成
> **创建日期：** 2026-07-30
> **代码基线：** `d88b80ba`（`v2.1.22`）
> **关联提交：** `44ed6819`、`44677650`、`54460cb1`

## 1. 问题结论

远端只读日志确认了三种现象：

1. 模型返回空工具名，系统仍执行并产生 `Tool '' not found`，错误工具轮次污染后续 Agent 上下文，最终泄漏 `</arg_value></function_calls_output>`。
2. 模型正文生成 `<wechat-sticker-copied>URL</wechat-sticker-copied>`，原始标签被发送，URL 又触发媒体提取。
3. 备用模型把无标签自然语言分析和最终答复一起写入普通 `content`。

当前 `54460cb1` 只深拷贝已经组装完成的 `LLMRequest`。它可以防止 Provider 原地修改同一个 Python 对象，但没有建立明确的“请求源”，也不允许微信群在候选已返回分片后整体丢弃并切换。

本次不整提交回退历史版本，只替换运行时实现。`v2.1.22` 已有的 room timeline、V2 thread、room single-flight 和 `pending -> send_result -> confirmed` 两阶段提交全部保留。

## 2. 开发范围

本次只完成两条主链路：

1. 主模型和每个备用模型都从候选调用前冻结的规范化源快照重新创建 `LLMRequest`，不得复用前一候选请求或响应。
2. 微信群候选响应在路由层完整缓冲。传输失败、空/未知工具名、损坏工具参数或已知协议残片出现时，整个候选丢弃，再从同一源快照创建下一候选；失败候选不得进入 Agent 历史或工具执行。

继续保留：

- 标准 `reasoning_content` 与最终正文分离。
- `<think>...</think>` 跨 SSE 分片有状态解析。
- 微信群禁用思考并要求只输出最终答复。
- Web 已展示任意流式分片后不切换模型。
- V2 仅在 sidecar 确认 `sent` 后提交 thread 与 timeline。

明确不做：

- 不恢复自然语言思考正则。
- 不增加“微信群兼容”或“可信模型”配置。
- 不引入第二个 LLM 裁判或强制所有 Provider 使用新的最终答复工具。
- 不在本次重构通用媒体发送事务。
- 不在本次实现实时新闻证据门禁，这属于独立事实可靠性问题。
- 不修改远端 Docker 配置、容器或真实群数据。

## 3. 请求源快照

在 `agent/protocol/models.py` 增加轻量 `LLMRequestSourceSnapshot`，保存候选调用前的 canonical 请求原料：

```text
messages
tools
system
model / temperature / max_tokens / stream
request_options 及其他请求级属性
请求级 source metadata（仅诊断，不发给 Provider）
```

规则：

1. 快照创建时深拷贝嵌套值，内部不暴露可变引用。
2. `build_request()` 每次都从内部源重新创建新的 `LLMRequest` 和嵌套对象。
3. `AgentStreamExecutor` 在发起路由前创建快照；微信群用户原文继续从现有 `wechat_group_user_content` 获取，只放入请求级 metadata，不新增持久化副本。
4. `TextModelRouter.complete()` 同样创建源快照，保持同步文本任务的主备语义一致。
5. 对尚未显式提供源快照的兼容调用，路由入口从传入的 canonical `LLMRequest` 冻结一次源快照。
6. 候选 Bot 只接收 `build_request()` 的结果，Provider 格式转换和请求体均为当前候选私有。

这里的“重新组装”是从同一份冻结 canonical 源重新创建请求，不是在候选间重新查询 live 数据库。否则同一用户请求会因群里新增消息或历史变化而得到不同上下文。

## 4. 微信群候选隔离

微信群 `call_stream()` 调整为：

```text
source snapshot
  -> build_request(primary)
  -> 缓冲 primary 全部分片
  -> 校验
       -> 通过：一次性向 AgentStreamExecutor 交付
       -> 失败：丢弃全部分片
  -> build_request(fallback-1)
  -> 重复上述流程
```

校验范围保持最小：

- 任意位置出现 408、429、5xx 或连接类临时错误，丢弃该候选已缓冲内容并切换。
- 工具名必须非空且存在于当前请求的工具 schema。
- 工具参数必须是完整 JSON object；微信群严格路径不把坏 JSON 修复成可执行调用。
- 精确识别本次线上出现的内部协议残片：`</arg_value>`、`<function_calls_output>`、`</function_calls_output>`、`<wechat-sticker-copied>`。
- 空正文且无工具时切换候选；明确 safety/content-filter 结束原因不通过备用模型绕过。
- 全部候选失败时返回服务端安全错误，不回放任何候选正文。

候选通过校验前，路由层不向 `AgentStreamExecutor` yield 分片，因此不会：

- 追加 assistant/tool_use 历史。
- 执行工具或产生 `tool_result`。
- 发送微信群 `message_update`。
- 写入 V2 pending、thread、timeline 或 continuation。

非微信群渠道保持现有流式语义。尤其 Web 一旦显示首个分片，仍禁止切换模型。

## 5. 无标签思考的边界

请求重组可以消除候选之间的对象、响应和历史污染，但无法从语义上证明裸 `content` 中哪句话是思考。服务端在不使用自然语言正则、第二模型裁判或 Provider 人工信任标记的前提下，不能百分之百无损识别无标签思考。

本次采取的边界是：

- 继续在请求源头禁用思考并强化最终答复提示。
- 标准 reasoning 和显式 think 块确定性隔离。
- 已知 Provider 协议残片按精确 token 拒绝。
- 不再用句式猜测并截断正常多段回答。

若真实群仍出现“纯自然语言分析被放进最终 content”，应基于该 Provider 官方结构化输出能力另开小范围方案，不能把不可靠正则重新加回来。

## 8. 验证矩阵

- 主候选修改 messages、tools、system 和 options 后失败，备用候选仍收到源快照内容。
- 传入成品 `LLMRequest` 被污染但附带干净源快照时，所有候选只使用源快照。
- 主模型熔断时，首个备用候选仍独立构造完整请求。
- 微信群主候选先输出正文再 429，正文被整体丢弃，群里只看到备用候选。
- Web 主候选先输出正文再失败，不调用备用候选。
- 空工具名、未知工具名、坏 JSON 参数均不进入 Agent 历史、不执行工具，并切换备用候选。
- `</arg_value></function_calls_output>` 和伪 sticker 标记触发候选丢弃。
- 合法工具调用、普通多段正文、标准 reasoning 和显式 think 行为不回归。
- 全候选失败只产生安全错误，V2 不确认 pending。

## 10. 实施回写区

### 10.1 实际改动

- 在 `agent/protocol/models.py` 新增 `LLMRequestSourceSnapshot`，内部深拷贝 canonical 请求源，每次 `build_request()` 都返回嵌套对象独立的新请求；兼容调用会在路由入口从现有 `LLMRequest` 冻结一次。
- `AgentStreamExecutor` 在发起路由前冻结消息、工具、系统提示和微信群用户原文 metadata；取消信号作为运行时控制单独传递，不进入可深拷贝请求源。
- `TextModelRouter` 的同步与流式候选统一从源快照创建请求。微信群流式候选在路由层完整缓冲，校验通过后才向 Agent 交付；Web 和其他渠道继续使用原流式路径。
- 微信群候选前置校验空/未知工具名、JSON object 参数、空响应和已知 Provider 协议残片；明确 safety/content-filter 结束原因转换为服务端固定拒绝，不调用备用模型。
- 未新增 Provider 信任配置、最终答复虚拟工具、ConversationStore schema、Web 配置或 sidecar 协议。

- 媒体通用发送事务和实时新闻证据门禁已从本次范围移出，分别作为独立问题处理。
