# 微信群自由回复并发丢失修复计划

## 任务背景

微信群 Context Engine V2 在自由回复发送前比较 room revision。实际日志显示，请求已经生成回复并进入发送阶段，但生成期间同群新增两条入站消息后，被记录为 `stale ambient reply suppressed`，最终没有交给 sidecar：

```text
before={'inbound_cursor': 7878, 'assistant_cursor': 683}
after={'inbound_cursor': 7880, 'assistant_cursor': 683}
```

当前 `_should_suppress_stale_ambient()` 只检查 `wechat_group_is_free_reply`，把所有自由回复都当成 ambient。它没有区分明确面向机器人的 `new_thread` / `resume_thread` 与仅参与群聊环境话题的 `observe_only`，因此多人连续触发机器人时，仍然有效的已生成回复会被误丢弃。

## 行为边界

| 请求类型 | V2 session action | room revision 变化后的行为 |
|---|---|---|
| 明确面向机器人但未显式 `@` | `new_thread` | 保留回复，按 room single-flight 顺序确认发送 |
| 对机器人上一条回复的自然追问 | `resume_thread` | 保留回复，按 room single-flight 顺序确认发送 |
| 面向全群的环境接话 | `observe_only` | 保持现有 stale 抑制，避免迟到插话 |
| 显式 `@` / 引用机器人 | 非自由回复 | 保持现有行为，不执行 ambient stale 抑制 |

缺少 `wechat_group_session_action` 的异常上下文不再默认按 ambient 丢弃，避免分类元数据缺失时静默吞回复；正常 V2 请求仍由 `WechatGroupSessionPolicy` 明确产生 action。

## 验收标准

1. 多名成员连续触发明确面向机器人的自由回复时，先生成的有效回复不会仅因新增群消息而被丢弃。
2. 同群回复仍由 room single-flight 串行生成和发送，不出现并发乱序。
3. 真正 `observe_only` 的环境接话在 room revision 变化后仍会被抑制。
4. 所有 V2 回复继续遵守 `pending -> send_result=sent -> confirmed` 两阶段提交边界。
5. 失败、未知、超时、清洗为空、静默及真正 stale 的请求仍不进入助手 timeline、Agent thread 或 continuation。

## 回退方式

恢复 `_should_suppress_stale_ambient()` 对自由回复的原始判断，并还原对应测试即可；不涉及配置、数据库或归档结构迁移。

## 实施结果

已完成。

实际改动：

- `_should_suppress_stale_ambient()` 先读取 `wechat_group_session_action`，仅 `ACTION_OBSERVE_ONLY` 继续执行 room revision 比较。
- `new_thread`、`resume_thread` 和缺少 action 的自由回复在发送前不再被 ambient stale 规则误抑制。
- stale 抑制日志新增 `action=observe_only`，保留 room、前后游标和 request ID。
- 未恢复 Legacy 调度，未修改 sidecar 协议、配置默认值、worker 防抖和队列策略。
