# 修复镜像发布版本覆盖计划

## 背景

`v2.1.10` 标签在 2026-07-28 08:35（Asia/Shanghai）触发 Docker 发布并正确生成版本镜像。随后在 10:37 从 `master` 手动运行 `deploy-image.yml`，工作流读取仓库中仍为 `2.1.2` 的 `cli/VERSION`，又无条件写入 `latest` 与 `skills-full`，导致 Web 控制台左下角显示 `V2.1.2`。

远端元数据确认，`v2.1.10` 对应提交 `7aeaedd3`，被覆盖后的 `latest` 对应提交 `5ea5a9d9`。版本化镜像没有被移动，问题只影响浮动标签。

首次修复通过 `v2.1.11` 发布后，远端验证又发现 `docker/metadata-action@v5` 在标签事件中默认以 `latest=auto` 生成隐式 `latest`。因此后完成的 `skills-full` 矩阵会把基础版 `latest` 覆盖为完整技能镜像；该标签保持不动，最终修复使用 `v2.1.12` 发布。

## 目标

- 正式 Docker 镜像只能由 `v*` 标签推送触发。
- 镜像内版本只能从当前发布标签派生，不再读取仓库中的旧版本文件作为发布输入。
- Web、CLI 和 Python 包元数据在最终镜像中显示当前发布版本。
- `latest` 只指向基础镜像，`skills-full` 只指向完整技能镜像，两个矩阵不得隐式生成对方标签。
- 用合同测试阻止手动发布入口和旧版本回退重新出现。
- 发布并验证 Docker Hub、GHCR 与 GitHub Release 的最终补丁版本产物。

## 修改边界

- 不移动或覆盖 `v2.1.10` 及更早标签。
- 不改变 Dockerfile、镜像依赖、能力包或运行时业务逻辑。
- 不操作任何远端部署容器或用户数据。
- 仅通过推送新的补丁标签触发正式发布。

## 当前状态

`v2.1.12` 修复已同步到包含 PR #23 的最新主分支并通过本地验证，等待提交和标签发布。

## 实际改动

- 删除 `deploy-image.yml` 的 `workflow_dispatch`，正式镜像只能由 `v*` 标签推送触发。
- 发布 Job 增加 `refs/tags/v` 引用门禁，构建版本只使用 `${GITHUB_REF_NAME#v}`，不再读取 `cli/VERSION` 作为发布输入。
- 新增发布合同测试，固定 Tag-only、标签版本派生和版本同步先于 Docker 打包的约束。
- 为 metadata-action 设置 `latest=false`，禁止标签事件自动生成隐式浮动标签；基础版和完整技能版只发布矩阵显式声明的标签。
- 将 `cli/VERSION` 与 `pyproject.toml` 同步为最终补丁版本，并更新协作规则、变更记录及版本化发行说明。
