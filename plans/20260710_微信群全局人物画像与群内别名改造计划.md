# 微信群全局人物画像与群内别名改造计划

> 状态：已被 `plans/20260720_群友画像功能复盘与架构建议.md` 取代，不再实施。
>
> 执行要求：实施时必须使用测试驱动方式逐项推进；优先使用隔离工作区；每完成一项回写本计划的实际改动与验证结果。

## 一、目标

把当前语义混合的“微信群全局画像”改造成明确的两层模型：

1. 同一个已验证人物在同一 `stable_account_id` 下只有一份全局人物画像，跨群累积有证据的稳定观察，不再被某一群或某一批消息整体覆盖。
2. 群昵称、群内称呼和回复称呼严格按当前 `stable_room_id` 保存和选择，不把其他群叫法带入当前群。
3. LLM 不再只做零散字段提取，而是基于服务端验证通过的证据生成较全面、可追溯、带不确定性说明的人物总结。
4. Prompt、Agent 工具和 Web 控制台都使用同一套全局画像与当前群名称投影，避免稳定 ID、运行时 ID 和画像 ID 混用。
5. 保留迁移、审计和回滚能力；不删除旧数据库数据，不靠昵称或 LLM 自动合并跨群人物。

## 三、当前实际逻辑链路

```text
微信群消息
  -> sidecar 上报 runtime_room_id / runtime_sender_id / at_list
  -> WechatGroupChannel 解析 stable_room_id / stable_member_id
  -> WechatGroupArchive 同时保存 stable/runtime 快照
  -> profile evolution 按 stable_room_id 记录信号
  -> executor 读取当前群增量消息
  -> LLM extractor 在消息文本中仍展示 runtime sender_id
  -> merger 直接按 LLM 返回的 sender_id 写画像
  -> wechat_group_global_profiles 以 sender_id 为唯一主键
  -> name records 另存 room_id + display_name
  -> 当前回复按 stable room/member 构造画像上下文
  -> 入站 at_list 仍是 runtime ID，直接交给画像查询
  -> 服务端生成 reply_name 后交给 LLM 自行遵守
  -> 出站真实 mention 默认只 mention 本轮发送者
```

当前存储与调用同时存在三种不一致语义：

- 旧画像表认为 `sender_id` 是全局人物键。
- 稳定身份层规定 `stable_member_id` 按 `stable_room_id` 隔离。
- LLM 与 sidecar 仍在部分位置使用 runtime sender ID。

## 四、已确认问题

### P0-1：没有真正的跨群全局人物主键

- `wechat_group_global_profiles` 只有 `sender_id` 主键，没有 room 维度。
- 新学习链路优先用 `stable_member_id` 写画像。
- `stable_member_id` 在身份模型中隶属于单个 `stable_room_id`。

因此，同一真人在 A、B 两群会形成两个画像主体；旧 runtime 画像和新 stable 画像还可能并存。当前“全局画像”只是表名和旧 sender 语义，不是可靠的全局人物画像。

### P0-2：LLM 演进仍会写出 runtime 孤儿画像

`WechatGroupProfileLlmExtractor._build_prompt()` 使用消息的 `sender_id`，没有优先使用 `stable_member_id`。LLM 返回后，merger 也没有把返回 ID 映射、约束到当前批次可证明的 stable member/person。

结果可能是：

- 现有画像以 `stable_member_id` 保存；
- LLM 新结果又以 runtime sender ID 新建一行；
- 重登后 runtime ID 变化，再产生第三行。

### P0-3：全局画像字段是“最后一次覆盖”，不是全面总结

`merge_learned_profile()` 会用最新批次的 `speak_style`、`interests`、`common_words` 直接覆盖已有值；现有测试明确断言 A 群数据会被 B 群最后一次学习覆盖。

这会导致：

- 单一群、单一时间窗口主导全局结论；
- 旧的有效特征丢失；
- 玩笑、短期话题或一次异常批次改变长期画像；
- 无法表达冲突、置信度和时间演变。

### P0-4：当前群读取边界没有真正限制全局画像来源数据

`get_profile(sender_id, room_id)` 会先按全局 ID 取画像，再调整名称，并不验证该人物是否属于当前群。`list_profiles(room_id=...)` 虽会筛选当前群成员，但返回对象仍携带该人物全部 `name_records` 和 `room_summaries`；executor 又把整个对象 JSON dump 给当前群 LLM。

因此当前实现可能把其他群名称、别名来源和画像来源摘要带入当前群演进 Prompt。新目标允许复用脱敏后的全局人物总结，但不允许把其他群名称、消息证据或群内私有事实原样带入。

### P1-1：当前 LLM 链路不是完整画像总结

当前 LLM schema 虽声明 `role_hints`、`interests`、`speak_style`、`common_terms`、`catchphrases`，但实际 merger：

- 不保存 `role_hints`；对应计数始终为 0。
- 不应用 LLM 返回的新 `speak_style`。
- 把 `common_terms` 和 `catchphrases` 混入旧 `common_words`。
- 没有 `profile_summary` 或等价的全局人物总结字段。
- 没有字段级证据、来源群、首次/最近确认时间、冲突状态。

所以当前实现是“部分字段抽取”，不是“比较全面、比较真实的人物总结”。

### P1-2：证据门禁可被绕过

当前只对字典形式的部分字段检查 `evidence_message_ids`；字符串形式的兴趣和角色可以无证据通过。`common_terms`、`catchphrases` 也没有统一的证据和置信度校验。

服务端还没有验证：

- LLM 返回的成员是否属于当前批次和当前群。
- evidence ID 是否真实存在于当前批次、当前 room。
- 证据是否与目标成员有关。
- 是否错误包含机器人自身、原始 ID、随机 ID、群体泛称。
- 新结论是否和已有高置信结论冲突。

### P1-3：当前群称呼仍可能被全局 alias 抢占

当前服务会把当前群昵称选为 `primary_nickname`，但 `reply_name` 又固定优先取 `aliases[0]`。当 alias 来自空 room 的全局记录时，会出现：

```text
primary_nickname: 当前群别名
aliases: 其他全局叫法
reply_name: 其他全局叫法
```

这与“BOT 在当前群提到成员时使用该成员在当前群内的叫法”不一致。

### P1-4：入站真实 @ 的 runtime/stable 映射没有闭环

`_build_memory_context_block()` 使用 stable room/sender，却把 sidecar 的 runtime `at_list` 原样交给画像服务。画像服务随后按这些 ID 直接查画像，因此稳定身份启用后，被 @ 的第三方成员画像通常无法命中。

### P1-5：文本称呼与真实 mention 是两条链路

- LLM 文本中提到第三方，只受 `reply_name` Prompt 约束，不会自动成为真实 @。
- 当前 `_build_reply_mentions()` 只返回本轮发送者 runtime ID。
- 对本轮发送者的真实 @，sidecar 会优先读取当前 `room.alias(contact)`，这一段逻辑基本正确。
- sidecar 在部分 puppet 降级路径只能发送可见 `@昵称` 文本，不能保证微信协议层真实 mention。

本计划只保证“自然语言提到成员时使用当前群叫法”，不自动扩大第三方真实 @，避免机器人无意通知群成员。若需要主动真实 @ 第三方，应单独确认通知策略。

### P1-6：回滚不完整

当前画像回滚只恢复主画像字段，不清理本次 LLM 新增的 name records，并明确返回 `name_record_rollback = not_pruned`。新建画像的回滚也缺少恢复为“不存在”的完整语义。

### P1-7：增量游标可能让证据永久漏学

启发式 learner 在某成员单批消息不足阈值时会跳过该成员，但群级 cursor 仍整体推进；被跳过的消息以后不会再次参与画像。LLM 演进一次只处理 `batch_message_limit`，触发器却可能把本次 latest observed 标记为已触发；当积压超过一批且之后没有新消息时，剩余 backlog 不一定继续自动排空。

这会让“全面画像”在数据层面先天不完整，必须把成员级累积窗口和 backlog drain 纳入同一处理闭环。

### P2：自动学习默认关闭且触发覆盖不足

`wechat_group_profile_evolution_enabled` 当前默认 `false`。即使代码存在，不启用也不会持续形成画像。

现有触发测试未覆盖最大间隔、重启恢复、并发、仅选中 stable room、跨群归档行号交错等情况。默认关闭应继续保留，避免升级后静默产生模型费用；但 Web 必须明确提示“未启用时不会自动总结”。

另外，当前 profile list 先截取全局最近 200 条再按 room 过滤，归档成员聚合也存在最多 100 人的内部上限；大群旧成员可能静默漏召回。读取画像时还会触发昵称修复写回，导致只读请求产生持久化副作用。

## 五、目标语义

### 5.1 全局人物画像

全局范围定义为：同一个 `stable_account_id` 下，经确定性身份依据绑定到同一个 `stable_person_id` 的成员。

允许进入全局画像的内容：

- 综合人物摘要。
- 有证据的兴趣和长期关注主题。
- 有证据的能力/角色线索，必须以“观察线索”表达，不当作现实身份事实。
- 沟通与协作风格。
- 稳定偏好、常见表达和反复出现的行为模式。
- 置信度、证据数、来源群数量、首次/最近观察时间和不确定性说明。

禁止进入全局画像的内容：

- 未经证据支持的现实身份推断。
- 敏感属性、隐私属性或本地路径、XML、base64、原始 payload。
- 只属于某个群的群规、项目秘密、成员关系和群内上下文原文。
- 其他成员的事实。

### 5.2 当前群名称投影

以下内容必须按 `stable_person_id + stable_room_id + stable_member_id` 保存和读取：

- 当前群群昵称。
- 当前群人工指定的首选称呼。
- 当前群有证据的口语别名。
- 当前群最近观察到的显示名。
- 当前群对应的 active runtime sender ID，仅用于真实 mention。

`reply_name` 由服务端确定，不由 LLM 在多个跨群别名中自行挑选。

建议优先级：

1. 当前群人工设置的 `preferred_reply_name`。
2. 当前群高置信、有证据的口语别名。
3. 当前群 live `room_alias` / 群昵称。
4. 当前群最近观察到的有效显示名。
5. 全局 canonical display name，仅在当前群没有任何可用名称时兜底。
6. 全部缺失时不输出称呼；禁止把 stable/runtime sender ID 当名字。

## 六、方案比较

| 方案 | 做法 | 优点 | 主要问题 | 结论 |
| --- | --- | --- | --- | --- |
| A. 继续用 sender_id 打补丁 | 保留现表，以 runtime/wechat ID 当全局人物键，只修 LLM 和 alias 优先级 | 改动最少 | 重登、跨账号、stable 身份下仍会分裂；无法可靠迁移 | 不推荐 |
| B. 全局 person + 群 membership/name projection | 新增 `stable_person_id`，stable member 继续负责群内权限和 membership；画像按 person，全局总结与群名分层 | 语义清晰，满足用户目标，权限和称呼不会串群 | 需要身份映射和一次安全迁移 | 推荐 |
| C. 保留每群画像，读取时动态聚合 | 不新增人物主键，查询时把疑似同一人的多份画像交给 LLM 合并 | 写入改动较小 | 无法可靠判断同一真人；每次读取成本高；容易误合并和泄露 | 不推荐 |

本计划采用方案 B。

## 七、目标架构

```text
runtime contact / wechat_id（确定性指纹）
  -> stable_member_id（群内成员、权限边界）
  -> stable_person_id（同一 stable_account 下的全局人物）

当前群增量归档
  -> stable member/person 映射
  -> LLM 只提出结构化 claim 候选
  -> 服务端校验成员、证据、置信度、噪声和冲突
  -> accepted claims 全局累积
  -> 仅在 claims 变化时生成/更新全局 summary

回复上下文
  -> 读取全局 person summary
  -> 读取当前 room 的 name projection
  -> 服务端计算唯一 reply_name
  -> Prompt 不注入其他群名称和证据原文
```

## 八、数据模型与迁移原则

### 8.1 身份层

在 identity DB 增加：

- `wechat_group_identity_persons`
  - `stable_person_id`
  - `stable_account_id`
  - `canonical_display_name`
  - `status` / `confidence`
  - `created_at` / `updated_at` / `confirmed_at`
- `wechat_group_identity_person_memberships`
  - `stable_person_id`
  - `stable_room_id`
  - `stable_member_id`
  - 最近 runtime sender 快照
  - 可验证的 wechat ID/指纹快照
  - 绑定来源和审计信息

自动绑定只允许：

- 同一 `stable_account_id` 下完全相同且非空的可靠 wechat ID；或
- 同一 active 登录态下完全相同的 runtime contact ID，并保留来源；或

禁止：

- 仅按昵称、群昵称、头像或 LLM 判断自动合并。
- 跨 `stable_account_id` 自动合并。
- 存在多个候选时选择“最像”的一个。

### 8.3 迁移

新增 `scripts/migrate_wechat_group_profiles.py`，默认 dry-run，显式 `--apply` 才写入。

迁移规则：

1. 用 identity membership 唯一映射旧 runtime/stable sender 到 `stable_person_id`。
2. 唯一可证明的旧全局画像迁入 person profile。
3. 旧 name records 按 room/member 映射迁入当前群名称记录。
4. 无法唯一映射、同名冲突、跨账号冲突全部输出报告，不自动合并。
5. 使用 SQLite transaction 和 schema version；apply 前通过 SQLite backup API 生成备份。
6. 不删除旧表；新服务优先读 v2，迁移期可只读 fallback 到旧表。
7. 重复执行必须幂等。

## 九、LLM 总结与证据策略

### 9.1 两阶段处理

第一阶段：LLM 只提取 claim 候选。

- 输入只含当前 stable room 的脱敏消息、允许的 stable member/person token 和已有摘要精简版。
- 输出每个非平凡字段都必须包含 `value`、`confidence`、`evidence_message_ids`。
- LLM 不负责决定跨群人物绑定。

第二阶段：服务端验证后生成全局 summary。

- 只把 accepted claims 和必要的脱敏证据摘录交给 summarizer。
- 合并跨群、跨时间的稳定观察，保留冲突和不确定性。
- 单一批次不得直接覆盖完整画像。
- 新证据不足时保留旧结论并降低/维持置信度，不强行重写。

### 9.2 强制校验

服务端必须验证：

- 输出 person/member 在本次允许集合内。
- 每个 evidence ID 存在于本批次、当前 stable room。
- 证据文本经过路径和 payload 脱敏。
- alias 证据能唯一指向目标成员。
- 字段置信度达到配置阈值。
- 机器人自身、群体泛称、原始 ID、长随机 ID、敏感推断被拒绝。
- 冲突 claim 不静默覆盖，转为 contradicted/uncertain。

### 9.3 启发式学习边界

旧 `WechatGroupLearner` 继续负责低成本统计和兜底：

- 消息数、活跃度、最近出现时间。
- 当前群观察名。
- 经过严格唯一目标验证的显式 @ 别名。

## 十一、验收标准

### 自动化验收

- 同一已验证人物跨两个群只产生一个 `stable_person_id` 和一份全局画像。
- stable member 仍按群隔离，管理员和真实 mention 不受 person 合并影响。
- A/B 群不同叫法绝不串用；当前群可用名称存在时不回退其他群/global alias。
- LLM 输出任意 sender、伪造 evidence、无证据字符串、机器人画像和群体泛称时均被拒绝并记录原因。
- 当前群 LLM 输入不包含其他群名称、别名记录、room summary 或消息原文。
- 单批次学习不会整体覆盖旧画像；summary 能综合多群、多时间 accepted claims，并表达不确定性。
- 不足阈值的成员消息能跨批累积，超过 batch limit 的 backlog 能自动排空。
- runtime at_list 能在当前群转换并命中正确 stable member/person 画像。
- rollback 后主画像、claims、summary 和本 run name records 全部恢复。
- dry-run 不写库；apply 迁移可备份、可幂等、冲突不自动合并。
- 当前群画像列表不受全局 top-200 或群成员 top-100 截断，读取接口不会修改数据库。

### 真实链路验收

1. 同一个人存在于两个已选微信群，两个群分别设置不同群昵称/常用叫法。
2. 两群积累不同但互补的聊天证据并启用画像自动学习。
3. Web 全局画像只显示一份综合人物画像，能看到多来源统计但不暴露其他群原文。
4. 在 A 群询问/提到该成员，BOT 使用 A 群叫法；在 B 群使用 B 群叫法。
5. 在 A 群真实 @ 该成员后询问，Prompt 能命中其全局画像；回复不会错误 @ 第三方。
6. 回滚最近一次画像学习后，画像和本次新增群内别名都恢复。

## 十二、明确不做项

- 不用 LLM、昵称或相似文本决定跨群人物合并。
- 不把群内私有事实、群关系或聊天原文作为全局资料注入其他群。
- 不改变管理员权限的 `stable_room_id + stable_member_id` 边界。
- 不把 `stable_person_id` 传给 sidecar 发送。
- 不自动真实 @ LLM 文本中提到的第三方成员。
- 不同步修改 Electron 桌面端。
- 不删除旧画像表或在没有 dry-run 报告时覆盖历史数据库。

## 十三、待用户确认的默认决策

本计划按以下默认决策编写：

1. “全局”限定在同一 `stable_account_id` 下；跨机器人微信账号不自动合并。
2. 全局画像复用的是脱敏、证据化的人物总结，不复用其他群别名和群内私有事实。
3. 当前群称呼由服务端确定；优先当前群人工称呼/高置信别名/群昵称。
4. LLM 自动总结开关继续默认关闭，管理员启用后自动运行。
5. 本次只保证自然语言称呼正确，不增加主动真实 @ 第三方。
6. UI 只改 Web 控制台，不改桌面端。
