# 微信群表情包回复内部过程泄露修复实施计划

> **供执行 Agent 使用：** 实施时必须使用 `superpowers:test-driven-development`；如按任务拆分执行，可使用 `superpowers:subagent-driven-development` 或 `superpowers:executing-plans`。所有步骤使用复选框跟踪，开发完成后必须回写本计划的实施状态、实际改动和验证结果。

**目标：** 微信群发送表情包时，只允许发送表情包本身以及工具参数中显式声明的用户可见短文案，不再把“回了个……”“表情包已发出”等 Agent 工具完成说明发送到群里。

**架构：** 保留现有 `wechat_group_sticker_search` → `wechat_group_sticker_send` → `file_to_send` → `AgentBridge` → `ChatChannel` → 微信群 sidecar 主链路，不新增回复引擎，也不修改 JSON Lines 协议。在表情包工具结果中增加一个仅表示“用户可见文案”的显式字段；`AgentBridge` 对微信群表情包回复只读取该字段，并忽略工具完成后模型生成的收尾文本。普通图片、文件和其他渠道继续使用现有 `text_response` 伴随文本逻辑。

**技术栈：** Python、`unittest`、CowAgent Agent 工具系统、`AgentBridge`、`ChatChannel`、个人微信群通道。

- 不修改：sidecar 协议、微信真实发送实现、表情包搜索与下载、自由回复判定、Web/桌面 UI、配置默认值。

  - 微信群带工具调用的中间进度继续由 `AgentEventHandler` 抑制。

## 二、证据链与根因

### 2.1 日志证据

`run.log` 中 2026-07-10 17:34 左右的同一轮执行顺序为：

1. `run.log:112800`：模型调用 `wechat_group_sticker_search`。
2. `run.log:112826`：模型调用 `wechat_group_sticker_send`，工具参数里已经包含自然群聊文案。
3. `run.log:112827-112828`：表情包作为 `file_to_send` 成功进入发送队列。
4. `run.log:112829-112832`：Agent 仍进入下一轮，生成“回了个大佬请坐，礼尚往来[吃瓜]”。
5. `run.log:112834-112835`：`AgentBridge` 随后组装并发送表情包图片。

同类现象不止一次：日志中还出现过“表情包已发出 🎉”“发了个呲牙表情回了～”等工具完成后的说明文字，说明这是稳定的数据流缺陷，不是单次模型随机输出。

### 2.2 代码数据流

```text
wechat_group_sticker_send 成功
        ↓
AgentStreamExecutor 把 file_to_send 放入 files_to_send，但继续下一轮 LLM
        ↓
下一轮 LLM 生成工具完成说明，成为 response
        ↓
AgentBridge._create_file_reply(file_info, response, context)
        ↓
response 被写入 IMAGE_URL Reply.text_content
        ↓
ChatChannel._send_reply() 先发送 text_content，再发送图片
```

关键代码位置：

- `agent/protocol/agent_stream.py:796-802`：工具结果为 `file_to_send` 时只入队，没有终止 Agent loop。
- `bridge/agent_bridge.py:672-684`：发现待发送文件后，把最终 `response` 原样传给 `_create_file_reply()`。
- `bridge/agent_bridge.py:810-818`：图片回复只要 `text_response` 非空，就写入 `reply.text_content`。
- `channel/chat_channel.py:337-344`：`IMAGE_URL` 带 `text_content` 时，固定先发文字、再发图片。
- `bridge/agent_event_handler.py:66-78`：现有防护只抑制“同一轮带 `tool_calls` 的中间文字”；工具完成后的最后一轮没有 `tool_calls`，不在该防护范围内。

### 2.3 已确认的根因

根因不是 sidecar 重复发送，也不是模型的隐藏 reasoning token 被直接透传，而是回复组装层混淆了两类文本：

- `wechat_group_sticker_send.message`：模型显式声明、应当允许作为用户可见表情包短文案的内容。
- Agent 工具完成后的最终 `response`：常见内容是“我发了什么”“工具已完成”等收尾说明，不应自动成为群消息。

当前 `WechatGroupStickerService` 会把工具 `message` 放入通用 `Send` 结果，但 `AgentBridge` 没有把它定义为明确的公开文案，反而使用后续 LLM 的 `response` 作为伴随文字。因此，即使 2026-07-07 已经修复了“工具调用中间进度泄露”，表情包完成后的收尾说明仍会通过另一条路径发到群里。

### 2.4 诱发条件

- 2026-07-08 增强自然接梗和表情包工具调用后，表情包使用频率上升，旧的通用文件伴随文本行为更容易暴露。
- 内置 persona 已要求“不汇报内部工具过程”，但 prompt 只能降低概率，不能提供确定性边界。
- 当前没有覆盖“表情包工具成功 + 最后一轮产生说明文本 + 群里只应收到表情包/显式短文案”的跨层回归测试。

## 三、方案比较

### 方案 A：只加强 prompt

- 做法：要求模型成功发送表情包后不要再解释。
- 优点：改动最小。
- 缺点：模型行为不确定；现有 persona 已有类似要求，日志仍能复现。
- 结论：只能作为辅助约束，不能作为修复主体。

### 方案 B：按关键词清洗“回了个”“已发出”等文字

- 做法：在 `wechat_group_reply_cleanup.py` 增加正则过滤。
- 优点：实现快。
- 缺点：容易漏掉新说法，也可能误删正常回答；这是处理症状而不是修复数据来源。
- 结论：不采用。

### 方案 C：显式区分公开文案与 Agent 收尾文本（推荐）

- 做法：表情包工具结果增加 `wechat_group_sticker_caption`；该字段只来自工具调用时的原始 `message`。`AgentBridge` 识别微信群表情包后，仅把该字段作为 `reply.text_content`，无论最终 `response` 内容是什么都不采用。
- 优点：确定性强、范围仅限微信群表情包、保留显式短文案、不会改变其他媒体和渠道。
- 缺点：需要同时修改工具说明、表情包服务、回复组装和测试。
- 结论：采用。

### 方案 D：把表情包发送工具改成 Agent 终止工具

- 做法：工具成功后直接结束 Agent loop，不再请求最后一轮 LLM。
- 优点：还能减少一次模型请求和延迟。
- 缺点：需要改动通用 Agent 执行协议，或者让通用执行器识别微信群专属工具；影响面明显大于当前缺陷。
- 结论：本次不做。若后续要优化表情包延迟和 token，再单独评估通用“终止型工具”契约。

## 四、推荐方案的数据契约

表情包工具成功结果增加以下字段：

```python
{
    "type": "file_to_send",
    "file_type": "image",
    "path": "...",
    "sticker_id": "...",          # 本地表情包时存在
    "online_id": "...",           # 在线表情包时存在
    "wechat_group_sticker_source": "local|online",
    "wechat_group_sticker_caption": "自然群聊短文案或空字符串",
}
```

字段规则：

1. `wechat_group_sticker_caption` 只能来自 `wechat_group_sticker_send` 的原始 `message` 参数。
2. `message` 为空时，该字段必须是空字符串，不能使用 `Send` 自动生成的“正在发送文件”或“发送表情包 文件名”作为公开文案。
3. 微信群表情包回复无论最终 Agent `response` 是“回了个……”、正常短句还是其他内容，都不能把它自动附加到图片。
4. `wechat_group_sticker_caption` 非空时，仍沿用 `ChatChannel` 的既有顺序：先发送这条显式短文案，再发送表情包。
5. 普通图片/文件没有表情包元数据时，继续使用原 `text_response`，防止跨渠道回归。

```python
@staticmethod
def _resolve_file_reply_text(file_info: dict, text_response: str, context: Context = None) -> str:
    is_wechat_group_sticker = bool(
        context
        and context.get("channel_type") == const.WECHAT_GROUP
        and (
            file_info.get("sticker_id")
            or file_info.get("online_id")
            or file_info.get("wechat_group_sticker_source")
        )
    )
    if is_wechat_group_sticker:
        return str(file_info.get("wechat_group_sticker_caption") or "").strip()
    return text_response
```

## 六、验收标准

以下条件必须同时满足：

1. 日志中即使仍出现模型生成的“回了个……”“表情包已发出”等收尾文本，微信群出站命令中也不能出现对应 `send_text`。
2. 无显式 `message` 的本地、在线表情包都只发送图片。
3. 有显式 `message` 时，只发送该短文案一次，再发送表情包一次。
4. 普通图片/生成图片的说明文字不丢失。
5. 非微信群渠道行为不改变。
6. 现有工具中间进度抑制、表情包群隔离、在线 URL 脱敏、冷却和日限测试全部通过。
7. 不修改 sidecar JSON Lines 协议，不新增配置项或依赖。

## 七、风险与回退

- 风险：部分历史行为可能依赖最终 `response` 作为表情包配文。
  - 控制：显式使用工具 `message` 作为唯一公开 caption，并通过 prompt/schema 告知模型。
- 风险：把普通图片误识别为表情包后丢失说明文字。
  - 控制：必须同时满足 `channel_type=wechat_group` 和 `sticker_id` / `online_id` / `wechat_group_sticker_source` 元数据条件。
- 风险：使用通用 `Send.message` 会把默认文件名说明暴露到群里。
  - 控制：公开字段只从原始工具参数 `message` 生成，禁止从 `payload["message"]` 回填。
- 回退：撤回 `wechat_group_sticker_caption` 映射及 `_resolve_file_reply_text()` 调用即可恢复旧行为；不涉及数据库结构、配置迁移或 sidecar 协议回退。
