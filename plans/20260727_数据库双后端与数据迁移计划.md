## 复查结论

2026-07-27 对照当前代码、Docker 入口和桌面打包链完成第三次复查。原计划“SQLite 默认兼容、PostgreSQL 全量承载、停机迁移、禁止静默回退”的主方向保留，以下遗漏或不合理点已在本文修正：

1. **Schema 归属不合理：** 不再把 47 张业务表集中塞入 `common/database/schema.py`；公共层只提供连接、事务、元数据协议和 registry，表定义由会话/记忆、微信群和 Webhook 各业务域负责。
2. **启动失败可能被吞掉：** 当前 `app.run()`、Agent memory 初始化和渠道线程存在捕获异常后继续运行的路径；PostgreSQL 配置、连接、权限或 schema 初始化失败必须在启动任何后台线程和渠道前失败，并让进程以非零状态退出。
3. **源库路径与 schema 漂移未覆盖：** 微信群库在未设置 `LIGHTAGENT_DATA_DIR` 时实际回落到 `~/.lightagent`，并可能残留 legacy 库。迁移必须检查所有明确登记的候选路径；同一逻辑库出现多个非空副本、未知表、未知列或更新版本 schema 时失败闭合，不能按时间任选。
4. **SQLite 宽松类型风险：** 除 embedding 外，还需检查整数溢出、文本落入整数列、非法布尔值、重复唯一键和孤儿外键；PostgreSQL 的 32 位 `INTEGER` 不能直接承接所有 SQLite 64 位整数。
5. **数据库预置和权限未说明：** 数据库 `lightagent` 与运行角色必须由管理员预先创建；迁移工具不申请 `CREATEDB`/超级用户权限，也不自动创建数据库或安装扩展。
6. **Docker 迁移命令缺少落点：** 当前 entrypoint 忽略 Compose 的普通 `command`，只执行 `CHATGPT_ON_WECHAT_EXEC`；迁移 profile 必须通过固定的 `CHATGPT_ON_WECHAT_EXEC` 调用 CLI，或另行安全改造 entrypoint，不能假设 `command` 会生效。
7. **桌面后端打包遗漏：** SQLAlchemy 和 PostgreSQL dialect 为运行时依赖，必须同步 `desktop/build/requirements-desktop.txt`、PyInstaller hidden imports 和 release 构建验证；不修改桌面 UI。
8. **备份门禁不足：** 增加可用空间、备份目录权限、停机静默窗口下的全源写锁、临时目录完成标记和“不自动删除备份”规则。
9. **查询语义差异未完整覆盖：** 除 FTS 外，还要审计 `LIKE` 大小写、NULL 排序、`rowcount`、partial unique index、服务端默认值和确定性排序。
10. **Python/驱动承诺过早：** 不再直接承诺用旧版二进制驱动覆盖 Python 3.7–3.8；SQLite 继续支持项目现有版本范围，PostgreSQL 的最低 Python 版本须先通过驱动安全与打包矩阵确认，推荐以 Docker 当前 Python 3.10 为最低支持线。
11. **SQLite 锁与备份连接不能复用：** 实验确认同一连接在持有 `BEGIN IMMEDIATE` 时调用 `backup()` 会阻塞；每个源库必须使用独立 guard 连接持有写锁，再由另一条只读连接执行快照备份，并在全部快照完成前保持所有 guard 锁。
12. **WAL 文件哈希不能代表逻辑数据：** WAL 恢复或 checkpoint 可能改变 `.db`/`-wal` 的物理字节但不改变业务数据；原始文件哈希只作审计信息，幂等、receipt 和迁移校验统一使用按表规范化计算的逻辑指纹。

## 一、目标

在不改变现有 SQLite 默认行为、不丢失历史数据的前提下，为 LightAgent 增加 PostgreSQL 后端，并提供 Docker Compose 场景下可执行的一条命令迁移方案。

交付后应满足：

1. `DB_TYPE=sqlite` 继续作为默认值，现有源码、桌面端和 Docker 用户无需改配置即可升级。
2. `DB_TYPE=postgresql` 时，项目当前所有运行时业务持久化统一使用 PostgreSQL，不出现会话在 PostgreSQL、微信群数据仍写 SQLite 的混合状态。
3. Docker Compose 明确展示 PostgreSQL 连接变量，并通过同目录 `.env` 注入实际值，不在仓库中保存真实密码。
4. 已有 SQLite 用户可以先预检、自动备份，再通过一条命令迁移全部已知业务库；迁移完成后自动核对表结构、行数、关键主键和内容摘要。
5. 迁移写入或提交前校验失败时 PostgreSQL 目标事务整体回滚；迁移工具不对源库执行业务 DML/DDL，不删除或移动源文件，源 SQLite 逻辑数据保持不变，切流前可以直接切回 SQLite。
6. PostgreSQL 连接失败、配置错误或 schema 不兼容时必须显式失败，禁止静默回退 SQLite，以免产生数据分叉。
7. PostgreSQL 模式只使用一个名为 `lightagent` 的 Database 和一个可配置 schema；12 个 SQLite 文件对应的逻辑域不拆成 12 个 PostgreSQL Database。

## 二、当前事实与影响范围

### 2.1 当前不是单一 SQLite 数据库

代码盘点确认，当前运行时共有 12 个物理 SQLite 文件、47 张普通业务表，另有两张可重建的 FTS5 虚拟表。默认路径会分别落在 `agent_workspace` 与 `LIGHTAGENT_DATA_DIR`。

| 逻辑域 | 默认 SQLite 文件 | 普通表数 | 主要数据 |
| --- | --- | ---: | --- |
| 会话与长期记忆 | `agent_workspace/memory/long-term/index.db` | 5 | `sessions`、`messages`、`chunks`、`files`、`_meta` |
| 微信群归档 | `LIGHTAGENT_DATA_DIR/wechat_group/wechat_group_archive.db` | 5 | 群消息、机器人回复、生图额度、记忆提炼任务与候选 |
| 微信群稳定身份 | `LIGHTAGENT_DATA_DIR/wechat_group/wechat_group_identity.db` | 8 | 账号、群、成员、运行时别名、绑定事件与重定向 |
| 微信群画像 | `LIGHTAGENT_DATA_DIR/wechat_group/wechat_group_profiles.db` | 6 | 画像、昵称、声明、revision、run 与学习游标 |
| 微信群知识 | `LIGHTAGENT_DATA_DIR/wechat_group/wechat_group_knowledge.db` | 3 | 群记忆、学习游标与学习任务 |
| 微信群报告 | `LIGHTAGENT_DATA_DIR/wechat_group/wechat_group_reports.db` | 8 | 设置、任务、报告、预览、确认与投递分片 |
| 微信群焦点 | `LIGHTAGENT_DATA_DIR/wechat_group/wechat_group_focus.db` | 2 | 焦点栈与消息引用 |
| 微信群情绪 | `LIGHTAGENT_DATA_DIR/wechat_group/wechat_group_emotion.db` | 1 | 群情绪状态 |
| 微信群表情包 | `LIGHTAGENT_DATA_DIR/wechat_group/wechat_group_sticker.db` | 2 | 素材与使用记录 |
| 微信群风格 | `LIGHTAGENT_DATA_DIR/wechat_group/wechat_group_style.db` | 1 | 群风格卡片 |
| 微信群技能权限 | `LIGHTAGENT_DATA_DIR/wechat_group/wechat_group_skill_access.db` | 5 | 策略、授权、审计、模板与元数据 |
| GitHub Webhook 去重 | `agent_workspace/github/webhook_deliveries.db` | 1 | delivery 去重与投递状态 |

补充说明：

- `index.db` 同时承载 Agent 会话和长期记忆，不是两个独立数据库。
- `chunks_fts`、`chunks_fts_trigram` 及其 shadow 表、触发器属于派生索引，不作为业务数据迁移，目标端应从 `chunks` 重建检索能力。
- 已废弃的 `wechat_group_topics.db` 按现有项目规则不迁移。
- 数据库中保存的图片、语音、表情包和报告资源主要是文件路径；迁移只迁移记录，不搬动媒体文件，原有 `./config`、`./data` 挂载必须继续保留。
- 微信群库的当前默认回退路径是 `~/.lightagent/wechat_group`，并不等同于源码模式下 `config.py.get_data_root()` 的仓库根目录；源库发现必须复用各 Store 的真实路径规则并显式处理 legacy 候选，不能只拼接一个根目录。
- 桌面端通过 `desktop/build/requirements-desktop.txt` 和 PyInstaller spec 独立打包后端；新增数据库依赖若只写入根 `requirements.txt`，桌面后端会在运行时缺包。

### 2.2 当前存在大量 SQLite 专属实现

当前持久化代码约有 386 处 `execute()` 调用，直接依赖以下 SQLite 行为：

- `sqlite3.Row`、`?` 参数占位符和连接级 `row_factory`。
- `PRAGMA journal_mode=WAL`、`busy_timeout`、`integrity_check`、`table_info`。
- `INTEGER PRIMARY KEY AUTOINCREMENT`、`cursor.lastrowid` 和隐式 `rowid`。
- `INSERT OR IGNORE`、`INSERT OR REPLACE`。
- FTS5、`bm25()`、trigram tokenizer、shadow 表和同步触发器。
- SQLite 动态类型：`chunks.embedding` 声明为 `TEXT`，实际新记录可能写入二进制 float32 数据。
- 进程内 `threading.Lock` 保护的读改写逻辑；该锁不能保护多个 PostgreSQL 客户端或多个 LightAgent 实例。

因此不能采用“替换连接字符串”或正则改写 SQL 的方式。必须保留现有 Store 公共接口，在 Store 内部引入可验证的数据库抽象、显式 schema 和后端方言处理。

## 三、范围与非目标

### 3.1 本次范围

1. 配置中心、环境变量校验、敏感信息脱敏和启动健康检查。
2. SQLite/PostgreSQL 逻辑数据库注册、连接池、事务和 schema 版本管理。
3. 上述 12 个物理 SQLite 文件所对应的全部运行时 Store。
4. 长期记忆关键词检索在两个后端上的等价可用实现。
5. 表情包批量理解、画像重置、旧聊天导入和稳定身份维护等直接访问 SQLite 的运维入口。
6. SQLite 到 PostgreSQL 的预检、备份、迁移、校验、幂等保护和迁移报告。
7. CLI、Docker Compose、跨平台迁移包装脚本、自动化测试和用户文档。
8. 桌面端 Python 后端的数据库依赖与 PyInstaller 打包兼容；不增加桌面数据库设置 UI。

### 3.2 非目标

1. 不把 PostgreSQL 设为默认数据库。
2. 不在默认 Compose 中捆绑或代管 PostgreSQL 服务；首版连接用户显式提供的外部 PostgreSQL。
3. 不新增 Web 控制台数据库管理页面或桌面端 UI。
4. 不实现 SQLite/PostgreSQL 双写，也不实现在线无停机迁移。
5. 不实现 PostgreSQL 到 SQLite 的反向迁移。正式开放流量后如需回退，必须另行处理 PostgreSQL 新增数据。
6. 不引入 `pgvector`，现有 embedding 继续由应用层计算相似度。
7. 不迁移 SQLite 内部表、FTS5 派生表或已废弃的微信群 topic 数据。
8. 不扫描和迁移未知 `.db` 文件，只处理版本控制中登记的逻辑数据库清单。
9. 不自动创建 PostgreSQL Database、用户或安装 `pg_trgm`；管理员先完成 `lightagent` 数据库和最小权限角色的配置。

## 四、选定设计

### 4.1 配置合同

新增并统一使用以下变量：

```dotenv
# sqlite（默认）或 postgresql
DB_TYPE=postgresql

# DB_TYPE=postgresql 时 host/username/password 必填
DB_POSTGRESQL_HOST=192.168.3.150
DB_POSTGRESQL_PORT=5432
DB_POSTGRESQL_DATABASE=lightagent
DB_POSTGRESQL_USERNAME=xxxxxxx
DB_POSTGRESQL_PASSWORD=replace-with-a-strong-password

# 可选；首版默认值如下
DB_POSTGRESQL_SCHEMA=public
DB_POSTGRESQL_SSLMODE=prefer
```

约束：

- 未配置或留空 `DB_TYPE` 时按 `sqlite` 处理；非空值仅接受 `sqlite`、`postgresql`，非法值启动失败。
- PostgreSQL 首版支持范围定为 14–18；启动和迁移预检读取服务端版本并给出明确错误。
- `host`、`database`、`username`、`password` 按不透明字符串处理；`port` 做 1–65535 整数校验；`schema` 做 PostgreSQL 标识符白名单校验。
- `sslmode` 仅接受 libpq 的 `disable`、`allow`、`prefer`、`require`、`verify-ca`、`verify-full`；选择证书校验模式时必须验证所需证书路径可读。
- 环境变量优先于 `config.json`。`config-template.json` 中 `db_type=sqlite`、database=`lightagent`、port=`5432`、schema=`public`、sslmode=`prefer`，host/username/password 保持空值。
- 使用 SQLAlchemy `URL.create()` 组装连接信息，不手工拼接 DSN，避免密码中的 `@`、`/`、`:` 等字符被错误解析。
- 日志、异常、Web 配置响应和迁移报告不得出现原始密码或完整 DSN。
- `config.py` 当前环境变量覆盖日志会直接打印值，敏感键识别也未包含 `password`；实施时必须先补齐 `password`、`token`、`credential` 等脱敏规则，并为数据库字符串绕开通用 `eval()` 解析。短密码也必须完全隐藏，不能因长度不足原样输出。
- 首版固定采用保守连接参数：connect timeout 10 秒、pool size 5、max overflow 5、pool timeout 30 秒、`pool_pre_ping=True`；先不扩大 Compose 配置面，确有压测依据时再开放调优变量。
- `lightagent` Database 必须预先存在且使用 UTF-8；应用只负责指定 schema 内的表和版本迁移，不尝试连接 `postgres` 管理库创建 Database。

### 4.2 数据库基础层

物理拓扑固定为：

```text
PostgreSQL Database: lightagent
  Schema: public（可配置）
    47 张现有普通业务表
    lightagent_schema_migrations
    lightagent_data_migrations
```

在 `common/database/` 增加跨 Agent、Channel、Web 共用的基础层，但不把业务表定义放进公共层：

```text
common/database/
  settings.py          # 配置读取、类型校验和安全 URL 构造
  errors.py            # 可识别且可安全输出的数据库异常
  manager.py           # Engine 生命周期、逻辑库绑定、事务与健康检查
  metadata.py          # 命名约定、共享类型和 DomainSpec 协议
  registry.py          # 显式登记逻辑域、表、源路径和迁移版本
  migrations.py        # 有序 schema migration 与版本台账
  sqlite_inventory.py  # 已知 SQLite 源库和表清单
```

业务 schema 由所属模块维护，例如会话/记忆放在 `agent/memory/`，微信群表放在 `channel/wechat_group/`，Webhook 表放在 `channel/web/`。每个逻辑域导出受测试的 `DomainSpec`，公共 registry 显式汇总；禁止依赖 import 副作用或扫描文件自动注册。

核心规则：

1. 使用 SQLAlchemy 2.0 Core，不引入 ORM，不改变现有 Store 对外返回的 `dict`/列表结构。
2. SQLite 模式下，每个逻辑域继续绑定当前物理文件，路径和数据隔离保持不变。
3. PostgreSQL 模式下，所有逻辑域共享一个进程级 Engine/连接池和同一 schema，避免每个 Store 创建独立连接池。
4. Store 构造函数继续兼容现有 `db_path` 测试注入；显式传入路径时强制使用隔离 SQLite，不读取全局 PostgreSQL 配置。
5. Engine 在 `load_config()` 完成后惰性创建，禁止模块 import 时连接数据库；测试必须能显式 reset/dispose 全局实例。
6. 每次操作从 Engine 获取独立连接或事务，不跨线程长期持有 SQLAlchemy Connection。
7. SQLite 每个物理文件使用受控连接策略，并通过 connect hook 在每条连接上恢复该 Store 需要的 `foreign_keys`、WAL、synchronous 和 busy timeout；不能只在初始化连接执行一次 PRAGMA。
8. PostgreSQL 使用 `READ COMMITTED` 基线隔离；需要“检查后更新”的路径使用单条条件 UPDATE、乐观版本或 `SELECT ... FOR UPDATE`，不能继续只依赖 `threading.Lock`。
9. PostgreSQL 的 schema 必须显式限定或使用受控 `search_path`，所有动态标识符均来自已验证配置；SQLAlchemy Engine 设置 `hide_parameters=True`，异常再经过统一脱敏。
10. schema 初始化使用数据库级迁移锁；SQLite 依赖文件事务，PostgreSQL 使用同一命名空间的 advisory transaction lock，避免迁移工具和多个实例并发升级。
11. `app.run()` 在同步内置技能、MCP、scheduler 和任何渠道线程启动前完成数据库配置、连接、权限和全部 domain schema 预检。失败必须以非零进程状态退出，不能被 memory/channel 的宽泛异常处理降级成“部分可用”。
12. PostgreSQL 不可达时显式失败，不自动创建或写入本地 SQLite；运行中断线可以由连接池重连，但失败写入不得伪装成功。
13. PostgreSQL 启动时若发现本地存在非空 SQLite 业务数据、但目标端没有匹配的已完成迁移 receipt，则拒绝启动并提示先运行 `lightagent db migrate`；新安装且没有源数据时可直接初始化空 PostgreSQL。
14. 应用正常退出和启动失败清理路径都调用 `dispose()`；桌面后台线程与渠道重启不得各自创建新的全局 Engine。

### 4.3 依赖兼容策略

项目当前声明支持 Python 3.7–3.13，但当前 Psycopg 3 官方支持 Python 3.10+。为了避免给 EOL Python 自动安装过期的 `psycopg2-binary`，兼容合同拆分为：

- SQLite 模式继续覆盖项目现有 Python 3.7–3.13，不因本功能降低既有兼容范围。
- PostgreSQL 模式推荐并默认支持 Python 3.10–3.13，与 Docker 的 Python 3.10 基线一致，使用 `psycopg[binary]>=3,<4`。
- 不在默认依赖中为 Python 3.7–3.8 固定旧版二进制驱动。若业务明确要求旧 Python 也运行 PostgreSQL，必须在实施前单独确认驱动、安全更新、Windows/Linux wheel 和 PyInstaller 可用性。
- `SQLAlchemy>=2.0,<2.1` 作为双后端 Core；业务 Store 只依赖 SQLAlchemy，不散落 psycopg 专属调用。
- PostgreSQL 驱动按 Python marker 安装并延迟导入；不满足 PostgreSQL 运行版本时，SQLite 仍可启动，只有显式选择 `DB_TYPE=postgresql` 才返回清晰的版本/驱动错误。
- 依赖同步检查 `requirements.txt`、`pyproject.toml`、`desktop/build/requirements-desktop.txt`、Docker 构建和 release workflow。
- PyInstaller 显式收集 `common.database`、SQLAlchemy SQLite/PostgreSQL dialect 和 psycopg；冻结包分别验证 SQLite 默认启动与 PostgreSQL 连接失败的安全错误，避免打包成功但运行期缺模块。

实施前先完成 Python 3.7/3.9 的 SQLite 安装回归，以及 Python 3.10/3.13 的 PostgreSQL 安装与连接回归。PostgreSQL 是否必须下探 Python 3.7–3.9 保留为实施前确认项，未确认前不通过旧驱动猜测解决。

### 4.4 Schema 与 SQL 方言

1. 将 47 张普通业务表按业务域定义为 SQLAlchemy Core `Table`，由 registry 汇总为统一 metadata 和 inventory，保留现有表名、列名、唯一约束、索引和默认业务语义。
   各业务域拥有本域表定义，公共层只维护协议和汇总入口；这些定义共同构成消除运行时字符串 DDL 的单一事实来源，不放进一个公共大文件。
2. JSON 字段首版继续使用 `TEXT` 并由现有代码序列化，避免切换为 JSONB 后返回类型、键顺序和历史校验发生变化。
3. 时间字段继续保留当前整数或浮点 Unix 时间语义，不在本次改造成时区时间列。
4. embedding 规范为 `LargeBinary`：SQLite 对应 BLOB，PostgreSQL 对应 BYTEA；迁移时兼容历史 JSON 字符串和现有 float32 bytes。
5. SQLite 的 `INTEGER` 是 64 位，而 PostgreSQL `INTEGER` 是 32 位。时间、游标、计数、文件大小、自增 ID 等先扫描历史最小/最大值，再映射到 `BIGINT`；仅 0/1 标志或明确有界值使用 `SMALLINT`/`BOOLEAN`。SQLite 自增兼容使用 `BigInteger().with_variant(Integer, "sqlite")` 或等价显式定义。
6. `AUTOINCREMENT` 使用显式自增主键定义；依赖 `lastrowid` 的写入改为 SQLAlchemy 返回主键或 PostgreSQL `RETURNING`。
7. 清除业务语义对隐式 `rowid` 的依赖：
   - 画像 evolution run 的“只能回滚最新一次”改用显式单调顺序键，并从旧 `rowid` 回填。
   - 身份绑定事件使用显式稳定排序键。
   - FTS 索引以 `chunks.id` 作为业务关联键，不把 PostgreSQL 不存在的 `rowid` 带入共享逻辑。
8. `INSERT OR IGNORE/REPLACE` 改为显式 `ON CONFLICT DO NOTHING/DO UPDATE`，由 SQLAlchemy 的 SQLite/PostgreSQL dialect 构造，不做字符串替换；partial unique index 的 conflict target 单独覆盖。
9. `PRAGMA table_info` 改为 SQLAlchemy Inspector；`PRAGMA integrity_check` 仅保留在 SQLite 健康检查，PostgreSQL 使用 schema、约束和查询验证。
10. 所有返回值统一经过 `RowMapping -> dict` 适配，BYTEA 的 `memoryview` 归一为 bytes；不得让 Store 调用方感知驱动行对象差异。
11. 审计全部 `LIKE`：现有应不区分大小写的搜索统一表达为 `lower(column).like(lower(pattern))` 或受控 `ilike()`；JSON 文本包含查询保持参数化。所有分页查询补足稳定 tie-breaker，并显式固定需要的 NULL 排序，避免两个后端顺序漂移。
12. 审计 `cursor.rowcount`、服务端默认值、`REAL`/DOUBLE、空字符串与 NULL、布尔整数、事务内 sequence 行为；共享合同测试不得只覆盖成功 CRUD。
13. 主键、唯一约束、外键和索引使用确定且不超过 PostgreSQL 63 字节限制的显式名称，CI 检查截断后碰撞；不趁本次改造增加现有业务未声明的新外键。
14. 进程锁可以继续保护单实例内存状态，但跨连接一致性必须由唯一约束、原子 upsert、乐观版本或行锁保证。

### 4.5 Schema 版本管理

新增 `lightagent_schema_migrations` 表，以 `domain + version` 记录有序迁移：

- 新数据库按当前 metadata 创建完整 schema 后写入基线版本。
- 已有 SQLite 先通过 Inspector 识别现状。正式跨库迁移时，先备份原文件，再只在备份快照上执行受支持的 schema 归一化；原 SQLite 不因迁移工具升级而被修改。
- 已登记的旧列缺失可按有序 migration 补齐；出现未知业务表、未知列、重复表来源或高于当前工具的 schema 版本时阻断 apply，并在 dry-run 报告中列出，不得静默忽略。
- PostgreSQL schema 升级在事务和迁移锁内执行。
- 禁止启动时执行删表、清空数据或无法回滚的隐式重建。
- 不额外引入 Alembic；首版使用项目内小型、有序、受测试的 migration registry，避免增加第二套 CLI 和配置体系。

### 4.6 长期记忆检索

`chunks` 是长期记忆的唯一业务数据源，全文索引只是派生能力：

- SQLite 继续保留现有 FTS5、trigram 和 `LIKE` 回退行为。
- PostgreSQL 基线实现复用现有 CJK/ASCII token 提取、OR 命中和 Python 动态评分，只把过滤查询改为参数化大小写不敏感匹配，保持中文、混合文本和短词均可检索，不要求数据库管理员安装扩展。
- 若目标库已由管理员安装 `pg_trgm` 且当前用户具备建索引权限，则为 `chunks.text` 创建受控 GIN trigram 索引以加速包含查询；应用不得在启动或迁移时自行执行 `CREATE EXTENSION`。
- 未安装 `pg_trgm` 时只记录一次性能提示，不影响启动和正确性。
- PostgreSQL 与 SQLite 的 BM25 数值不要求相同，但作用域过滤、命中集合、相关结果优先级和 `min_score` 行为必须通过共享合同测试。
- 迁移不复制 FTS5 虚拟表、触发器和 `_meta.trigram_backfill_done`，目标端从 `chunks` 重建派生索引。

### 4.7 PostgreSQL 预置与最小权限

数据库管理员在启用 PostgreSQL 前完成一次性预置：

1. 创建 UTF-8 Database `lightagent` 和独立运行角色，不使用 `postgres` 超级用户运行应用。
2. 运行角色具备目标 Database 的 CONNECT、目标 schema 的 USAGE/CREATE，以及本项目表、索引和 sequence 所需的 SELECT/INSERT/UPDATE/DELETE/DDL 权限。
3. 运行角色不需要 CREATEDB、CREATEROLE、SUPERUSER，也不需要安装 extension 的权限。
4. 使用非 `public` schema 时，由管理员预先创建并授权，或明确允许应用角色创建该 schema；迁移预检必须区分“Database 不存在”“认证失败”“schema 无权限”和“DML 无权限”。
5. `pg_trgm` 由管理员选择安装；未安装不影响功能正确性，只影响大数据量包含查询性能。

文档提供不含真实密码的示例 SQL，但一条命令迁移的前提是 Database 和角色已经存在。工具不会为了“自动化”扩大到管理库权限。

### 4.8 启动与运行时失败策略

1. `load_config()` 后立即执行 `initialize_database()`，完成驱动版本、连接、server encoding、PostgreSQL 版本、权限、schema 版本和本地未迁移数据检查。
2. 只有初始化成功后才允许同步技能、预热 MCP/scheduler、创建 Web/微信群等渠道线程。
3. 配置或数据库初始化错误必须传播到 `app.py` 顶层并返回非零退出码；Docker `restart: unless-stopped` 才能正确重试，不能记录日志后以 0 退出。
4. Agent memory 当前的“不可用则降级”和微信群部分能力的宽泛异常捕获只能处理功能级异常；统一数据库初始化失败不得被这些路径吞掉。
5. 运行期间 PostgreSQL 暂时断开时，连接池可重连；当次事务必须回滚，写操作返回明确失败并记录可诊断但已脱敏的错误，不得转写 SQLite 或伪造成功。
6. `lightagent db status` 只读且无建表副作用；`migrate --dry-run` 允许在回滚事务中验证权限，但不得留下 schema、锁表或迁移 receipt。

## 五、SQLite 到 PostgreSQL 迁移方案

### 5.1 用户入口

新增 CLI 命令：

```powershell
# 查看当前后端、连接、schema 版本和已发现的 SQLite 源库
lightagent db status

# 默认只做预检，不写 PostgreSQL
lightagent db migrate --dry-run

# 正式迁移；非交互环境使用 --yes
lightagent db migrate --apply --yes

# 独立复核最近一次迁移
lightagent db verify
```

Docker 增加 `migration` profile 下的一次性 `db-migrate` 服务，并提供：

- `docker/migrate-to-postgresql.ps1`
- `docker/migrate-to-postgresql.sh`

包装脚本执行顺序固定为：停止 `lightagent` -> 运行预检 -> 运行备份和迁移 -> 运行校验 -> 校验通过后重新启动 `lightagent`。任何一步失败都保持主服务停止并返回非零状态，禁止带着不确定数据自动启动。

当前 `/entrypoint.sh` 不使用 Compose `command`，而是执行 `CHATGPT_ON_WECHAT_EXEC`。因此 `db-migrate` 服务明确设置固定的 `CHATGPT_ON_WECHAT_EXEC="lightagent db migrate ..."`，包装脚本分别覆盖为 dry-run、apply 和 verify；首版不为此改写 entrypoint 的降权与密码初始化逻辑。PowerShell 使用 `$PSScriptRoot`、Shell 使用脚本自身目录定位 `docker-compose.yml` 和 `.env`，从任意当前目录执行都指向同一 Compose project。

用户最终只需在 `docker/.env` 填好连接参数后执行一条命令：

```powershell
.\docker\migrate-to-postgresql.ps1
```

Linux/macOS 对应：

```bash
./docker/migrate-to-postgresql.sh
```

CLI 保留 dry-run 和逐步执行方式，便于生产环境先审计报告再切换；包装脚本不替代底层安全门禁。dry-run 的成功结果不作为后续 apply 的授权或缓存，apply 必须重新执行全部门禁并取得一组新的 guard 锁，避免两次命令之间源库发生变化。

### 5.2 迁移前置门禁

正式迁移前必须全部通过：

1. `DB_TYPE=postgresql` 且必填连接参数完整，database 必须为已确认的 `lightagent`；日志中只显示 host、port、database、schema，不显示密码。
2. PostgreSQL 版本、UTF-8 server encoding、目标 schema 和最小权限均符合 4.7；数据库不存在时给出管理员预置提示，不尝试自动创建。
3. LightAgent 主进程已停止。Docker 包装脚本负责停止本 project 的服务；源码 CLI 需要显式确认服务已停。每次 dry-run/apply 都按固定顺序为全部源库建立独立 guard 连接并执行 `BEGIN IMMEDIATE`；任一源库无法取得写锁时，回滚并关闭全部已持有 guard 后拒绝迁移，不能只依赖可能过期的 PID 文件。dry-run 输出报告后释放 guard；apply 将同一组 guard 持有到 5.3 的快照完成，不在门禁与备份之间释放重取。
4. 源库 registry 为每个逻辑域列出当前路径与经代码/历史确认的 legacy 候选。若同一逻辑域发现多个非空副本，报告路径、表数和哈希后阻断，禁止按修改时间或文件大小自动选择。
5. 对 12 个当前物理 SQLite 文件及已登记的 legacy 候选做存在性、源文件与父目录访问/加锁能力和 `PRAGMA integrity_check`；不存在的可选库记为“无数据”，无法加锁或损坏的库直接阻断。
6. 检查源库 schema：缺少受支持旧版本列可在快照上升级；未知普通表、未知列、重复唯一键、孤儿外键或高于迁移工具版本的 schema 阻断 apply。SQLite/FTS 内部表和明确废弃表按 allowlist 排除。
7. 按目标类型扫描 `typeof()`、NULL、整数范围、布尔值、REAL、UTF-8 文本和 embedding，先输出不可迁移主键清单；不得等批量写到一半才发现脏数据。
8. 计算全部源库快照与报告所需空间，并确认备份卷有“源库总大小 + manifest/临时开销 + 20% 安全余量”的可用空间。
9. 盘点每个源表的列、行数、主键范围和源文件大小，记录 `.db`/`-wal` 的审计哈希；dry-run 从 guard 锁定的只读视图计算预检逻辑指纹，apply 从完成并归一化的快照按稳定键计算权威的版本化表级哈希和整体 `source_fingerprint`，registry 同时检查 47 个表名无碰撞。
10. 目标允许为空 schema，或只包含本工具创建且没有业务行的当前 schema；目标已有未知表或业务数据时拒绝覆盖。
11. 重复 apply 仍须重新取得全源锁并生成完成快照；其 `source_fingerprint`、目标 Database/schema 和 receipt 均匹配时返回“已完成并校验通过”。仅原始文件哈希变化不能判定为新数据，逻辑指纹不同或目标仅部分存在时拒绝自动合并。

### 5.3 停机静默窗口备份

1. 备份目录固定为 `agent_workspace/backups/database-migration/<时间戳>/`，Docker 下落在持久化的 `./data/backups/`；目录采用仅当前运行用户可读写的权限，且被 Git/Docker build context 排除。
2. 复用本次 apply 在 5.2 取得的全部 guard 连接；guard 只持有 `BEGIN IMMEDIATE` 写锁，不执行 `backup()`、业务 DML、DDL 或 PRAGMA 模式切换。不得释放后重新获取，也不得复用之前 dry-run 已释放的连接。
3. 全部 guard 锁取得后，为每个源库另开一条 URI `mode=ro` 只读连接作为 backup source，再调用 Python `sqlite3.Connection.backup()` 写入新快照。不能使用 `immutable=1`，否则可能漏读未 checkpoint 的 WAL 内容。
4. 备份期间始终保持全部 guard 连接；所有 snapshot 连接关闭、快照 `integrity_check` 和逻辑指纹完成后，才按逆序 rollback/close guard。已用临时库验证该模式在 SQLite `DELETE` 与 `WAL` 日志模式下均能完成备份并阻止并发写入。
5. 12 个 SQLite 文件没有跨文件事务，因此这里保证的是“主服务已停止且全部写锁同时持有期间”的独立快照集合，不宣称数据库级跨文件原子快照。只要无法建立完整静默窗口就失败，不降级为在线或逐库边迁移边释放锁。
6. 快照先写入带 `.incomplete` 标记的临时目录。全部 backup、close、持久化刷新、integrity check 和哈希完成后再原子写入完成 manifest；中断目录不得被后续 migrate 当作有效备份。
7. 对受支持的旧 schema，只在备份快照上执行有序归一化，再从归一化快照迁移；迁移工具不对原 SQLite 执行业务 DML/DDL，也不删除或移动原 `.db`/`-wal`/`-shm`。SQLite 打开、WAL 恢复或关闭连接可能触发 checkpoint 并改变物理文件布局，因此不承诺源文件字节哈希恒定，只承诺源业务 schema 和逻辑数据不变。
8. `manifest.json` 记录原文件路径、快照路径、大小、审计文件哈希、schema 版本、表清单、行数、表级规范化哈希和 `source_fingerprint`，但不得包含 PostgreSQL 密码、完整 DSN、Webhook Secret 或其他项目密钥。
9. 后续迁移只读取完成快照，不读取原始 SQLite。工具不自动删除成功或失败备份；文档说明磁盘占用和人工保留策略。

### 5.4 数据转换和写入

迁移在 PostgreSQL 单个外层事务中执行，步骤如下：

1. 获取 migration lock，创建或升级目标 schema。
2. 按逻辑域与外键依赖顺序迁移普通业务表。
3. 使用 SQLAlchemy 批量参数写入，SQLite 端固定批次读取，PostgreSQL 端使用 executemany/受控流式结果，禁止一次加载整表、拼接用户数据或自行生成 CSV SQL。
4. 按 DomainSpec 做类型感知转换：保留业务主键、Unix 时间、Unicode 文本、NULL 和路径字符串；64 位整数写 BIGINT，布尔字段只接受登记的 0/1/true/false，REAL 写 DOUBLE PRECISION。
5. 将 SQLite 自增主键导入后，把 PostgreSQL identity sequence 调整到 `MAX(id) + 1`。
6. 对依赖隐式 `rowid` 的表写入显式顺序值，迁移后不再引用 PostgreSQL 不存在的 rowid。
7. embedding 转换规则：bytes 原样写 BYTEA；历史 JSON 数组解析为 float32 bytes；无法解析的记录列出主键并阻断迁移，不静默置空。
8. 写入前完成唯一键和现有外键检查；不使用 `ON CONFLICT DO NOTHING` 掩盖源数据重复或表映射错误。
9. 跳过 `sqlite_%`、FTS5 虚拟表、shadow 表、FTS 触发器和已废弃 topic 表。
10. 业务表全部写入后创建普通索引和可选 PostgreSQL 检索索引。
11. 写入 `lightagent_data_migrations` 完成记录，包含 migration id、`source_fingerprint`、源 manifest 哈希、目标 Database/schema、表级统计、开始/结束时间和工具版本。
12. 任一表写入、提交前校验或索引创建失败，整个 PostgreSQL 事务回滚。
13. migration receipt 与业务数据在同一事务提交。若客户端在 `COMMIT` 时断线并出现“提交结果未知”，工具必须重连并按 migration id 查询 receipt：receipt 存在则进入只读复核，receipt 不存在才允许重试，禁止盲目重复导入。

### 5.5 校验标准

提交事务前执行完整数据校验，提交后再做一次只读复核：

- 每张普通业务表源/目标行数相等。
- 每张表按稳定主键顺序和目标类型流式计算规范化 SHA-256；文本、NULL、BIGINT、DOUBLE、布尔整数和二进制使用版本化编码规则，避免驱动返回类型不同造成假差异。
- 表、列、类型、NULL/default、主键、唯一键、现有外键和关键索引与 DomainSpec 一致，约束/索引名无 63 字节截断碰撞。
- 自增表插入一条事务内测试记录时不会与历史 ID 冲突，测试事务随后回滚。
- `sessions/messages` 恢复一组会话，长期记忆能按 scope 查询一组 chunk。
- 微信群稳定身份、归档、画像、群记忆、报告、表情包、技能 ACL 与 GitHub delivery 各执行一组只读语义抽查。
- 迁移前后本地媒体路径字符串一致，随机抽查存在文件仍可访问；迁移工具不要求所有历史媒体都存在。
- 对 guard 锁定后的源快照、归一化迁移输入和 PostgreSQL 目标分别计算版本化逻辑指纹；目标必须与迁移输入一致。测试另外确认迁移工具未对源库执行 DML/DDL，允许 SQLite 合法 checkpoint 导致物理文件哈希变化；PostgreSQL 模式冒烟期间监控数据根目录，确认没有创建或更新业务 `.db`。
- 校验报告同时输出机器可读 JSON 和简体中文摘要，失败时包含逻辑域、表和主键，但不包含敏感连接信息。

提交前校验失败会回滚整个目标事务；提交后复核失败或数据库暂时不可达时，目标数据不再被自动删除，迁移工具标记为“待复核”并保持 LightAgent 停止，后续通过 `lightagent db verify` 和同事务 receipt 判断最终状态。

### 5.6 切换与回滚

安全切换窗口：

1. 停止主服务并禁止外部写入。
2. 完成 SQLite 快照、PostgreSQL 迁移和双重校验。
3. 保持 `DB_TYPE=postgresql` 启动 LightAgent，执行启动健康检查和最小人工冒烟。
4. 冒烟通过后再恢复外部流量，并保留 SQLite 快照和迁移报告。

回滚边界：

- 在 PostgreSQL 尚未接收新业务写入前，停止服务、改回 `DB_TYPE=sqlite` 并启动即可；源 SQLite 的业务 schema 与逻辑数据未被迁移工具修改。WAL checkpoint 可能改变物理文件布局，但不影响该回滚路径。
- PostgreSQL 开始接收新写入后，直接切回 SQLite 会丢失切换后的新数据。本计划不通过双写掩盖这一事实；如切流后需要回退，必须先停止写入并另行导回增量数据。

## 六、Docker Compose 设计

`docker/docker-compose.yml` 的 `lightagent.environment` 明确加入：

```yaml
DB_TYPE: "${DB_TYPE:-sqlite}"
DB_POSTGRESQL_HOST: "${DB_POSTGRESQL_HOST:-}"
DB_POSTGRESQL_PORT: "${DB_POSTGRESQL_PORT:-5432}"
DB_POSTGRESQL_DATABASE: "${DB_POSTGRESQL_DATABASE:-lightagent}"
DB_POSTGRESQL_USERNAME: "${DB_POSTGRESQL_USERNAME:-}"
DB_POSTGRESQL_PASSWORD: "${DB_POSTGRESQL_PASSWORD:-}"
DB_POSTGRESQL_SCHEMA: "${DB_POSTGRESQL_SCHEMA:-public}"
DB_POSTGRESQL_SSLMODE: "${DB_POSTGRESQL_SSLMODE:-prefer}"
```

同时：

1. `docker/.env.example` 增加相同字段和中文说明，密码只放占位值。
2. `.dockerignore` 继续排除 `docker/.env`，并增加合同测试防止真实连接信息被构建进镜像。
3. `db-migrate` profile 服务复用同一镜像、环境变量和 `./config`/`./data` 挂载，不映射端口、不设置自动重启；通过固定 `CHATGPT_ON_WECHAT_EXEC` 执行 CLI，不依赖当前 entrypoint 会忽略的 Compose `command`。
4. 默认 `docker compose up -d` 不启动迁移服务。
5. PowerShell/Shell 包装脚本都以自身目录作为 Compose project directory，显式使用 `docker/docker-compose.yml` 和 `docker/.env`，并检查 `DB_POSTGRESQL_DATABASE=lightagent`。
6. 不增加内置 PostgreSQL 容器和默认数据库密码，避免替用户承担数据库备份、升级与高可用职责；文档先给出外部 Database/角色预置步骤。
7. 明确提示 Docker 环境变量可被有宿主机 Docker 权限的管理员通过 inspect/config 查看；应用日志和 Web API 仍不得回显密码。

## 十、风险与控制

| 风险 | 控制措施 |
| --- | --- |
| 只迁移部分 SQLite，形成混合持久化 | 以逻辑库 registry 和 47 表 inventory 作为测试合同；PG 模式下运行时 Store 不得创建 `.db` |
| SQL 方言转换遗漏 | SQLAlchemy Core 显式构造查询；禁止正则替换占位符；每个 Store 跑双后端合同 |
| `rowid`/自增语义变化 | 先增加显式键并回填；迁移后校准 sequence；回归最新 run 和游标逻辑 |
| SQLite 64 位整数写入 PostgreSQL 32 位 INTEGER 溢出 | 预扫历史范围；时间、ID、计数和文件大小默认映射 BIGINT；覆盖边界测试 |
| embedding 类型不兼容 | 迁移前识别 bytes/JSON；统一转 float32 bytes；异常记录阻断而非置空 |
| PostgreSQL 全文检索中文退化 | ILIKE 保证正确性，pg_trgm 仅做可选加速；以命中语义测试而非绑定 BM25 数值 |
| LIKE、NULL 排序和 collation 改变查询结果 | 显式大小写策略、NULL 顺序和稳定 tie-breaker；双后端共享合同覆盖分页/搜索 |
| 多实例并发初始化或读改写竞争 | schema advisory lock、数据库事务、唯一约束、原子 upsert/乐观版本，不依赖单进程锁 |
| 迁移期间仍有 SQLite 写入 | 包装脚本先停服务；全部独立 guard 连接取得 `BEGIN IMMEDIATE` 写锁后才由分离的只读连接备份；任一锁失败即退出 |
| 把 12 个 SQLite 文件误当成一个原子快照 | 明确只支持停机静默窗口；全部 guard 同时持锁后生成独立快照集合，不宣称跨文件事务原子性 |
| WAL checkpoint 导致原始文件哈希变化或误判重复迁移 | 文件哈希仅供审计；幂等、receipt 和源/目标校验使用版本化表级逻辑指纹与 `source_fingerprint` |
| 同一逻辑库在多个历史路径有非空副本 | registry 枚举 current/legacy 候选并失败闭合，要求人工明确源，不按时间任选 |
| 源库含未知表、未知列或宽松类型脏数据 | dry-run 做 schema/type/唯一键/外键预检；只在备份快照归一化受支持旧版本 |
| 备份卷空间不足或备份泄露聊天数据 | 迁移前空间门禁、私有权限、incomplete 标记、构建排除且不自动删除 |
| 目标库已有数据被覆盖 | 非空目标默认拒绝；`source_fingerprint`、目标 Database/schema 和迁移 receipt 完全匹配时才允许幂等复核 |
| 数据库密码泄露 | DB 专属不透明解析、日志/API/报告脱敏、`.env` 排除和安全回归测试 |
| PostgreSQL 故障时悄悄写回 SQLite | 明确禁止自动回退，启动失败并给出不含密码的诊断 |
| `app.py` 吞掉启动异常导致容器看似成功 | 数据库预检前置；致命错误非零退出；负向 Docker/进程测试 |
| Compose migration `command` 被 entrypoint 忽略 | profile 固定通过 `CHATGPT_ON_WECHAT_EXEC` 运行 CLI，并增加合同测试 |
| 桌面冻结包缺 SQLAlchemy dialect/驱动 | 同步 desktop requirements、PyInstaller hidden imports 和 release 产物冒烟 |
| 切流后回滚丢新增数据 | 明确切流前回滚点；不承诺双写；正式流量恢复前完成冒烟 |
| EOL Python 缺少安全 PostgreSQL 驱动 | SQLite 保持原兼容范围；PostgreSQL 默认以 Python 3.10+ 为基线，旧版本另行确认 |

## 十一、实施前确认项

本计划按以下默认决策编写，开始编码前需要用户确认：

- [x] PostgreSQL 数据库名使用 `lightagent`。
- [x] 未配置或留空 `DB_TYPE` 时默认使用 SQLite。
- [x] `DB_TYPE=postgresql` 时全部 47 张运行时业务表统一进入一个 PostgreSQL Database，不保留业务 SQLite 混合运行。
