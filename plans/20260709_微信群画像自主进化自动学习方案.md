# 微信群画像自主进化自动学习方案

> 状态：方案待确认，尚未进入代码实施。
> 背景：用户明确要求采用方案 C，复用现有自动学习/自主进化能力，并在此基础上实现微信群画像隔离；画像学习必须自动运行，不希望人工审核。

## 目标

把当前“手动触发 + 启发式抽取 + 直接覆盖画像”的微信群画像学习，升级为“自主进化触发 + LLM 结构化提炼 + 服务端自动合并 + 群级隔离 + 可追溯可回滚”的自动学习闭环。

核心目标：

1. 群画像自动学习：无需人工点击学习按钮，也不要求人工审核候选。
2. 复用自主进化机制：沿用现有 idle trigger、并发限制、运行记录、备份/回滚思想，避免再造一套完全独立调度系统。
3. 严格群隔离：画像读写必须绑定 `room_id + sender_id`；不得把 A 群别名、角色、称呼注入 B 群。
4. 提升画像质量：通过 LLM 识别别名、角色线索、发言风格、兴趣主题、常用表达，并用服务端规则防止一次误判永久污染画像。
5. 可验证可回退：每次自动画像演进都有 run 记录、输入摘要、输出 JSON、合并 diff、证据消息 ID 和回滚点。

## 当前问题判断

### 1. 自动学习没有真正自动运行

当前 `WechatGroupLearner.run_once(room_id, mode)` 只在 Web API 或测试中被显式调用。`wechat_group_learning_enabled` 虽然存在配置项，但没有形成后台自动调度。

现状影响：

- 群消息会被归档，但不会自然沉淀成画像。
- 画像质量依赖管理员手动点击学习。
- 高活跃群反而更容易积累大量未处理归档。

### 2. 当前画像质量上限低

当前 `_learn_profiles()` 主要依赖启发式规则：

- 按 `sender_id` 聚合文本消息。
- 选择最近可用昵称。
- 用正则和词频抽取 `common_words`。
- 用少量关键词推断 `interests`。
- 用平均长度和列表标记推断 `speak_style`。

这类规则适合做低成本兜底，但不适合判断：

- 成员在群内的稳定角色。
- 群内常用称呼和别名。
- 成员真实关注领域。
- 发言风格中的表达习惯、边界和偏好。
- 多轮上下文里的隐含关系。

### 3. 别名生成少是当前规则过窄导致的

现有别名学习只处理“唯一非机器人 mention 目标 + 唯一显式 @ 称呼”的场景。这降低误学概率，但召回率很低。

典型漏学场景：

- 群成员直接称呼“张总你看下”，但没有真实 @。
- 引用某人消息时使用昵称。
- 群昵称变化，但没有进入显式 alias 学习链路。
- 多轮对话里稳定出现“老王/王工/产品大哥”等称呼。

### 4. 直接让 LLM 覆盖画像风险过高

用户要求自动，不做人工审核。这个方向可以接受，但必须把“自动审核”放在服务端规则中，而不是完全相信 LLM。

原因：

- LLM 可能把玩笑误判为角色。
- LLM 可能把临时话题当作长期兴趣。
- LLM 可能把其他群学到的称呼泛化到当前群。
- LLM 可能输出无证据的身份判断。

因此本方案采用：LLM 负责结构化提炼，服务端负责证据校验、置信度门禁、字段级合并和回滚。

## 方案选择

采用方案 C，但做边界修正：

不直接复用现有 `agent.evolution.executor.run_evolution_for_session()` 去编辑群画像。现有 executor 的目标是编辑 workspace 内的 `MEMORY.md`、daily memory、skills、knowledge 等文件；微信群画像存储在 `~/.cow/wechat_group/wechat_group_profiles.db`，并且要求按 `room_id + sender_id` 隔离。

正确复用方式：

- 复用 `agent.evolution.trigger` 的 idle 扫描思想。
- 复用自主进化的“空闲后处理”“每轮计数”“并发上限”“运行记录”“备份回滚”模式。
- 新增微信群画像专用 executor，不允许它使用通用 `write/edit/bash` 改 workspace。
- 新增受限画像工具或服务接口，只能读当前群归档、写当前群画像记录。
- 群画像自动演进结果仍写微信群画像存储，不写入全局 `MEMORY.md`。

## 总体架构

新增一条专用链路：

```text
WechatGroupChannel 收到群消息
  -> 归档消息到 WechatGroupArchive
  -> 记录 room_id 维度的画像学习活动状态
  -> 自主进化 idle scanner 发现群满足条件
  -> 调用 WechatGroupProfileEvolutionExecutor
  -> 读取当前 room_id 的新增归档消息
  -> 组装成员级证据包
  -> 调用 LLM 输出严格 JSON
  -> 服务端校验 JSON / 证据 / 置信度 / 当前群成员关系
  -> 自动合并到 WechatGroupProfileService
  -> 记录 run、diff、snapshot、evidence
  -> 下一轮回复通过 <wechat-group-memory> 注入当前群画像
```

## 组件设计

### 1. 群画像自主进化触发器

建议新增：

- `channel/wechat_group/wechat_group_profile_evolution_trigger.py`

职责：

- 接收微信群消息活动信号。
- 按 `room_id` 维护最后活跃时间、累计新消息数、是否正在学习。
- 每分钟或复用现有 evolution scan tick 检查是否满足学习条件。
- 满足条件后提交给画像专用 executor。

触发条件建议：

- `wechat_group_profile_evolution_enabled = true`
- 当前群在 `wechat_group_room_ids` 范围内。
- 当前群距离最后一条消息空闲超过 `wechat_group_profile_evolution_idle_minutes`，默认 `10`。
- 当前群自上次画像学习后新增消息数达到 `wechat_group_profile_evolution_min_messages`，默认 `30`。
- 或距离上次成功学习超过 `wechat_group_profile_evolution_max_interval_minutes`，默认 `1440`，用于低频兜底。
- 全局并发不超过 `wechat_group_profile_evolution_max_concurrent`，默认 `1`。

为什么按群触发而不是按 session 触发：

- 现有自主进化是按 Agent session 扫描。
- 微信群如果 `group_shared_session = true`，多个群可能共享或影响 session 语义。
- 群画像必须严格以 `room_id` 为边界，所以触发状态必须独立于 Agent session。

### 2. 群画像专用 executor

建议新增：

- `channel/wechat_group/wechat_group_profile_evolution_executor.py`

职责：

- 从 `WechatGroupArchive.get_messages_after_row_id(room_id, cursor)` 读取新增消息。
- 按成员聚合证据。
- 过滤无效消息、机器人消息、纯表情、撤回/XML/低信息噪声。
- 构造 LLM 输入。
- 调用当前 Agent 使用的模型或 Bridge 统一模型实例。
- 解析 LLM JSON。
- 调用自动合并器落库。
- 记录 run 结果。

重要边界：

- executor 只能处理一个 `room_id`。
- LLM prompt 中不得放入其他群消息。
- media_path、本机路径、XML、base64 不进入 prompt。
- executor 不使用 `write/edit/bash`。
- executor 不直接改 `MEMORY.md`、knowledge 或 skills。

### 3. LLM 画像提取器

建议新增：

- `channel/wechat_group/wechat_group_profile_llm_extractor.py`

输入：

- `room_id`
- `room_name`
- 当前批次消息摘要
- 成员样本，按 `sender_id` 聚合
- 当前已有画像精简版
- 当前群成员 name records

输出必须是严格 JSON，例如：

```json
{
  "profiles": [
    {
      "sender_id": "wxid_xxx",
      "primary_nickname": "",
      "aliases": [
        {
          "value": "张总",
          "confidence": 0.92,
          "evidence_message_ids": ["m1", "m7"],
          "reason": "多人在当前群用该称呼指向该成员"
        }
      ],
      "role_hints": [
        {
          "value": "经常协调发布排期",
          "confidence": 0.84,
          "evidence_message_ids": ["m2", "m8"]
        }
      ],
      "interests": [
        {
          "value": "发布排期",
          "confidence": 0.78,
          "evidence_message_ids": ["m2"]
        }
      ],
      "speak_style": {
        "value": "偏短句，常直接给结论",
        "confidence": 0.81,
        "evidence_message_ids": ["m3", "m4", "m9"]
      },
      "common_terms": ["发布", "回归", "上线"],
      "catchphrases": ["收到", "我看下"],
      "confidence": 0.82
    }
  ]
}
```

字段原则：

- `primary_nickname` 不由 LLM 主导，仍优先来自当前群成员昵称和归档昵称。
- `aliases` 必须有证据消息。
- `role_hints` 命名为“角色线索”，避免把推断当事实。
- `common_terms` 和 `catchphrases` 分开，避免当前 `common_words` 语义混乱。
- 不允许 LLM 输出跨群 ID、跨群称呼或无法在当前批次/当前群证据中定位的结论。

### 4. 自动合并器

建议新增：

- `channel/wechat_group/wechat_group_profile_evolution_merger.py`

职责：

- 校验 LLM 输出。
- 做字段级自动合并。
- 生成 diff。
- 保存合并前快照。
- 写入画像服务。

自动合并规则：

- `aliases`：当前群证据不少于 2 条或置信度高于阈值时自动写入 `name_records`，`source_kind = llm_evolution`。
- `role_hints`：写入新增字段或扩展画像 content，但标记为 hints，不作为强身份事实。
- `interests`：合并为去重后的短标签，低置信度不写。
- `speak_style`：不单批硬覆盖；使用最近多次结果加权，或仅在当前字段为空时写入。
- `common_terms`：过滤停用词、XML/HTML 噪声、过短 token、纯数字、无意义高频词。
- `catchphrases`：只保留短表达，不混入技术词。
- `msg_count`、`activity_score`、`last_seen_at` 仍由服务端计算，不由 LLM 决定。

保护规则：

- 不允许写机器人自己的画像。
- 不允许把发言人自己的昵称学成别人的 alias。
- 不允许把 `所有人`、`大家`、`all`、`here` 等群体称呼写成个人 alias。
- 不允许把 `wxid_...`、原始 sender id、长随机 ID 写成昵称。
- 不允许跨 `room_id` 复用别名。

### 5. 存储结构扩展

当前 `wechat_group_global_profiles` 字段偏少，建议增量扩展，避免破坏既有 UI 和 prompt：

新增字段可选：

- `role_hints_json`
- `common_terms_json`
- `catchphrases_json`
- `profile_summary`
- `confidence`
- `last_evolved_at`

也可以不立即改主表，而是新增表：

- `wechat_group_profile_evolution_runs`
- `wechat_group_profile_evolution_diffs`
- `wechat_group_profile_snapshots`

推荐做法：

第一阶段新增 run/diff/snapshot 表，同时继续把兼容字段写回现有 profile 表。这样现有 `WechatGroupContextService` 和 Web UI 不会大改。

建议表：

```sql
CREATE TABLE wechat_group_profile_evolution_runs (
  run_id TEXT PRIMARY KEY,
  room_id TEXT NOT NULL,
  batch_start_row_id INTEGER NOT NULL,
  batch_end_row_id INTEGER NOT NULL,
  batch_message_count INTEGER NOT NULL,
  profile_update_count INTEGER NOT NULL,
  status TEXT NOT NULL,
  failed_reason TEXT NOT NULL DEFAULT '',
  started_at INTEGER NOT NULL,
  finished_at INTEGER NOT NULL DEFAULT 0
);

CREATE TABLE wechat_group_profile_evolution_diffs (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  run_id TEXT NOT NULL,
  room_id TEXT NOT NULL,
  sender_id TEXT NOT NULL,
  before_json TEXT NOT NULL,
  after_json TEXT NOT NULL,
  evidence_message_ids_json TEXT NOT NULL DEFAULT '[]',
  created_at INTEGER NOT NULL
);
```

快照可以存在 diff 的 `before_json` 中，回滚时按 run 恢复。

### 6. 回滚能力

复用自主进化“可撤销”的理念，但不能直接复用文件级 backup。

原因：

- 自主进化当前回滚是恢复 workspace 文件。
- 群画像在 SQLite 中。

应新增数据库级回滚：

- `rollback_profile_evolution_run(run_id)`
- 根据 `wechat_group_profile_evolution_diffs.before_json` 恢复每个 sender 的画像主体。
- 对本 run 新增的 name records，可通过 `source_kind = llm_evolution` 和 `run_id` 标记删除或禁用。

如果要让主 Agent 能响应“撤销刚才群画像学习”，可以扩展 `evolution_undo` 或新增 `wechat_group_profile_evolution_undo`，但工具必须绑定当前 `room_id`。

## 和现有自主进化的关系

### 可以复用

- idle 后再学习的理念。
- `start_evolution_trigger()` 的进程级后台线程模式。
- `min_turns` / `idle_minutes` / context pressure 的触发思路。
- 并发上限 `_MAX_CONCURRENT` 的设计。
- run 记录、summary、undo 的产品语义。
- 使用当前 Agent 模型配置，而不是新增模型配置。

### 不应直接复用

- 不直接使用现有 evolution review agent 去编辑群画像。
- 不允许画像学习 agent 拿到 `write/edit/bash`。
- 不把微信群画像写入 `MEMORY.md`。
- 不把群画像演进结果主动推送到群，避免打扰。
- 不复用全局 session 作为画像隔离边界。

### 需要新增的复用适配

- 在 `note_user_turn()` 之外，为微信群增加 `note_wechat_group_profile_signal(room_id, message_id)`。
- 或在 `WechatGroupChannel._record_inbound_message()` 后记录群画像演进信号。
- 在 AgentBridge 已有 idle trigger 启动时，同时启动微信群画像 evolution trigger。
- 将微信群画像 evolution 的运行记录接入 Web 控制台“群记忆/画像”页面。

- 如果后续要完全替代旧 `wechat_group_learning_enabled`，需要迁移配置语义。

## Web 控制台 UI 方案

原则：尽可能把新增配置项、内部状态、自动学习结果和异常原因暴露到 Web 控制台，避免自动后台学习变成不可观察的黑盒。但 UI 只做配置、观察、回滚和手动触发，不做人工审核队列。

现有入口基础：

- `群聊设置 -> 个人微信群 -> 永久记忆` 已有“记忆维护 / 学习运行”页签。
- `群聊设置 -> 个人微信群 -> 全局画像` 已有画像列表、群过滤、详情和手动修正。
- 现有 `学习运行` 仍面向旧 `WechatGroupLearner`，需要升级为“自主进化学习”视角。

### 1. 群记忆页面：学习运行页签

在现有“学习运行”页签中改造为“自动学习控制台”，展示当前选中群的画像自主进化状态。

需要展示的配置项：

- `wechat_group_profile_evolution_enabled`：启用群画像自主学习。
- `wechat_group_profile_evolution_idle_minutes`：群聊空闲多少分钟后允许学习。
- `wechat_group_profile_evolution_min_messages`：新增消息数达到多少后触发学习。
- `wechat_group_profile_evolution_max_interval_minutes`：最长兜底学习间隔。
- `wechat_group_profile_evolution_batch_message_limit`：单次最多处理消息数。
- `wechat_group_profile_evolution_max_members_per_run`：单次最多分析成员数。
- `wechat_group_profile_evolution_min_confidence`：通用字段自动合并最低置信度。
- `wechat_group_profile_evolution_alias_min_confidence`：别名自动合并最低置信度。
- `wechat_group_profile_evolution_max_concurrent`：全局并发上限。
- `wechat_group_profile_evolution_notify`：是否通知学习结果，默认关闭。

需要展示的运行状态：

- 当前群是否启用自动学习。
- 当前群最近活跃时间。
- 当前群距离上次学习后的新增归档消息数。
- 当前群当前是否正在学习。
- 下次可能触发原因：`idle_waiting`、`message_threshold_pending`、`ready`、`disabled`、`running`。
- 最近一次成功学习时间。
- 最近一次失败原因。
- 当前学习 cursor：`last_archive_row_id`，用于诊断增量消费是否推进。

需要提供的操作：

- 保存配置。
- 立即运行一次当前群画像自主学习。
- 重置当前群画像学习 cursor，仅管理员可见，默认折叠到“高级诊断”。
- 暂停当前群自动画像学习，不影响其他群。

### 2. 学习运行记录

运行记录列表从旧的 `learn/runs` 扩展为 profile evolution runs，默认展示当前群最近 20 次。

每条 run 展示：

- 状态：`success`、`failed`、`skipped`、`running`。
- 触发来源：`idle`、`message_threshold`、`max_interval`、`manual`。
- 开始和结束时间。
- 处理消息数。
- 分析成员数。
- 更新画像数。
- 新增别名数。
- 更新角色线索数。
- 更新常用词/口头禅数。
- LLM 调用耗时和失败原因。
- `run_id`，用于诊断和回滚。

点击 run 后展示详情：

- 本次输入消息范围：`batch_start_row_id -> batch_end_row_id`。
- LLM 输出 JSON 的精简预览。
- 服务端丢弃字段及原因，例如 `low_confidence`、`missing_evidence`、`cross_room_sender`、`ambiguous_alias`。
- 自动合并 diff 列表。
- 回滚按钮。

### 3. 全局画像页面：画像详情增强

在“全局画像”详情区补充自动学习来源与字段质量信息。

详情页新增只读区：

- `画像摘要 profile_summary`
- `角色线索 role_hints`
- `常用主题 common_terms`
- `口头禅 catchphrases`
- `画像置信度 confidence`
- `最近自动学习时间 last_evolved_at`
- `最近自动学习 run_id`

房间来源区增强：

- 当前群称呼优先级说明。
- 每个 name record 展示 `source_kind`：`manual`、`learning`、`llm_evolution`。
- 每个别名展示来源群、证据数量和最近出现时间。

手动修正区调整：

- 继续保留手动修正，但定位为“覆盖自动学习错误”。
- 手动保存的字段优先级高于自动学习字段。
- UI 标记“手动修正字段不会被低置信自动学习覆盖”。

### 4. 自动合并 diff 视图

新增“自动更新记录”区，可放在画像详情页下方，也可作为 run 详情的一部分。

每条 diff 展示：

- 字段名：`aliases`、`role_hints`、`interests`、`speak_style`、`common_terms`、`catchphrases`。
- 更新前。
- 更新后。
- 置信度。
- 证据消息 ID 数量。
- 来源 run。
- 是否可回滚。

展示策略：

- 默认只显示摘要，点击后展开 JSON。
- 不显示完整群聊原文，避免泄露聊天内容；只显示证据消息 ID 和脱敏摘录。
- 不显示 media_path、本机路径、XML、base64。

### 5. 回滚 UI

用户不想人工审核，但自动学习必须可回滚。

入口：

- run 详情页：回滚整次 run。
- 画像详情页：回滚该成员最近一次自动更新。

回滚前展示：

- 将影响的成员数。
- 将恢复的字段列表。
- 将移除或禁用的本 run 新增别名记录数。
- 明确只影响当前群相关画像来源，不影响其他群。

回滚后展示：

- 回滚状态。
- 回滚时间。
- 回滚 run_id。
- 可再次刷新画像详情确认结果。

### 6. 诊断与可观测性

新增“高级诊断”折叠区，默认收起。

建议展示：

- 最近一次 extractor 输入统计：消息数、成员数、字符数。

- 最近一次合并耗时。

这些信息用于排查“为什么没有自动学习”“为什么画像没更新”“为什么别名没生成”。

## LLM Prompt 约束

系统 prompt 要求：

- 你是微信群画像提取器，不是聊天助手。
- 只基于当前 `room_id` 的证据。
- 不要推断现实身份，只输出群内行为线索。
- 没有证据就省略字段。
- 输出严格 JSON。
- 所有结论必须附 `evidence_message_ids`。
- 禁止输出本机路径、XML、base64、message raw payload。
- 禁止把玩笑、讽刺、临时情绪当长期画像。

用户消息结构：

```text
<current-room>
room_id: ...
room_name: ...
</current-room>

<existing-profiles>
...
</existing-profiles>

<messages>
[m1] 10:01 Alice(wxid_a): ...
[m2] 10:02 Bob(wxid_b): ...
</messages>

Return JSON only.
```

## 数据流细节

### 消息进入

1. `WechatGroupChannel` 收到 sidecar 消息。
2. 消息按现有逻辑写入 `WechatGroupArchive`。
3. 记录当前 `room_id` 有新画像学习信号。
4. 正常回复链路不等待画像学习。

### 空闲扫描

1. 后台线程每 60 秒扫描启用的群。
2. 若群仍在活跃，等待空闲。
3. 若满足新增消息阈值或兜底间隔，启动 executor。
4. 同一群学习期间不重复启动。

### LLM 提取

1. executor 读取当前群新增归档。
2. 按 sender 聚合，过滤低信息成员。
3. 构造上下文，控制 token。
4. 调用 LLM。
5. JSON parse 失败则本 run 失败，不写入画像。

### 自动合并

1. merger 校验 sender 是否属于当前群证据。
2. 按字段置信度合并。
3. 写 profile store 和 name records。
4. 记录 diff 和 run 状态。
5. 更新学习 cursor。

### 回复注入

不改变当前注入路径：

- `WechatGroupContextService.preview_context()` 仍负责读取画像。
- `<wechat-group-memory>` 仍按当前 `room_id` 注入。
- `wechat_group_profile_get` 工具仍由服务端绑定当前群。

## 实施阶段

### 阶段 1：复用自主进化触发模型，打通自动运行

- 新增微信群画像 evolution trigger。
- 监听归档后的群消息活动。
- 按 `room_id` 维护 idle、新增消息数、运行中状态。
- 触发后先调用现有 `WechatGroupLearner.run_once(room_id, mode="profile")`。
- 目标是先实现“自动跑”，不引入 LLM。
- Web UI 增加配置项、当前群状态卡、运行记录列表和“立即运行”入口。

验证：

- 新消息累计达到阈值后，空闲扫描会触发学习。
- 未启用配置时不会触发。
- 同一群不会并发运行两次。
- 不同群互不影响。
- UI 能保存配置并展示当前群状态。

### 阶段 2：新增 LLM 画像提取器

- 新增 `WechatGroupProfileLlmExtractor`。
- 定义严格 JSON schema。
- 增加 JSON 解析和失败降级。
- 保留旧启发式 learner 作为 fallback。
- UI run 详情展示 LLM parse 状态、丢弃原因和精简输出预览。

验证：

- LLM 返回合法 JSON 时生成结构化候选。
- 非法 JSON 不写画像。
- 输出包含跨群或无证据 sender 时被拒绝。
- UI 能展示失败原因，不只显示“失败”。

### 阶段 3：自动合并和质量治理

- 新增 merger。
- 拆分 `common_terms` 和 `catchphrases`。
- 支持 `role_hints`。
- 增加字段级置信度门禁。
- 调整 prompt content 格式，让回复能使用更高质量画像。
- 全局画像详情展示 `role_hints`、`common_terms`、`catchphrases`、`confidence` 和最近自动学习来源。

验证：

- 高置信别名自动写入当前群 name records。
- 群体称呼不写入个人 alias。
- 身份角色以 role hints 进入，不作为硬事实。
- 低置信字段跳过。
- UI 能按字段看到自动更新结果和来源。

### 阶段 4：运行记录、diff 和回滚

- 新增 evolution run/diff 表。
- 每次合并保存 before/after。
- 支持按 run 回滚。
- Web UI 展示最近自动学习记录。
- Web UI 支持 run 详情、成员 diff 和回滚操作。

验证：

- 自动学习后可看到 run。
- 回滚 run 后画像恢复。
- 回滚只影响当前 run 和当前群相关记录。
- UI 回滚后刷新画像详情能看到恢复结果。

- Web 手动“学习”按钮改为触发同一个 profile evolution executor。
- 旧启发式 `WechatGroupLearner` 降级为 fallback 或仅用于群永久记忆。
- `wechat_group_learning_enabled` 与新配置关系明确化。
- UI 将旧“学习运行”文案升级为“画像自主学习”，旧启发式学习入口移动到高级诊断或隐藏。

## 风险与约束

### 模型成本

自动学习会产生后台 LLM 调用。必须通过 idle、消息阈值、批量限制、并发限制控制成本。

### 误学风险

用户不希望人工审核，因此必须用服务端规则替代人工审核。所有自动合并都必须有证据、置信度和 diff。

### 跨群泄露

这是最高优先级风险。任何 extractor、merger、tool、prompt 注入都必须以 `room_id` 过滤。

### 主链路延迟

画像学习必须异步后台运行，不阻塞微信群消息回复。

### 与全局自主进化边界

微信群画像 evolution 不能编辑 workspace 文件，不能写全局 memory，不能把群内成员画像变成全局事实。

## 推荐结论

采用方案 C 是可行的，但落地方式应是“复用自主进化框架思想 + 新增微信群画像专用执行链路”，而不是直接让现有自主进化 review agent 去写群画像。

推荐第一版交付范围：

1. 自动触发器接入，配置开启后自动跑。
2. LLM 结构化画像提取。
3. 服务端自动合并别名、角色线索、兴趣、发言风格、常用表达。
4. run/diff/snapshot 记录。
5. 当前群隔离和回滚能力。

不建议第一版做：

- 人工审核 UI。
- 主动向群里汇报画像学习结果。
- 把群画像写进 `MEMORY.md`。
- 让 LLM 自由编辑 SQLite 或 workspace 文件。
- 跨群合并同一 `sender_id` 的称呼和角色。
