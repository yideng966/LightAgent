## 问题确认

issue #17 当前仍为 Open，标题是“微信群全局画像缺失群名时应在同步后补齐房间名”。issue 描述中提到 PR #1 / PR #2 已修复，但本地核验显示这两个 PR 描述与画像群名持久化补齐没有直接对应关系。

当前代码已经完成了 20260705 计划中的展示/读取兜底：

- `WechatGroupProfileService._build_room_summaries()` 会在 `room_summaries.room_name` 为空时从 `WechatGroupArchive.find_room_name()` 读取归档群名。
- `WechatGroupMemoriesHandler._enrich_profile_room_names()` 会在 Web 画像 API 返回前，优先用配置、运行中房间列表或归档给 `room_summaries` 补群名。

但临时数据库复现显示，当前只是读取/展示层补齐，历史 `wechat_group_profile_name_records.room_name` 仍为空，`repair_historical_profile_names()` 也只修复画像主昵称，不修复 name records 的群名：

```text
before_record_room_name=
listed_summary_room_name=Product Launch Group
repair_result={'total': 1, 'repaired': 0}
after_record_room_name=
```

现有相关测试已通过：

```powershell
python -m unittest tests.test_wechat_group_profile_service tests.test_wechat_group_web
# Ran 56 tests, OK
```

结论：issue #17 的“后台展示可读性”部分已有兜底修复；“同步后补齐房间名”仍缺少持久化修复，问题成立。

## 目标

在微信群房间列表同步后，用已知 `room_id -> room_name` 映射补齐历史画像 name records 中缺失的 `room_name`，并保留现有展示兜底作为防御层。

## 方案选型

推荐方案：在房间列表同步事件后触发服务层持久化修复。

- 优点：符合 issue 中“同步后补齐”的触发语义；只修改微信群通道、画像服务和存储层；不会让 Web GET 接口产生隐式写入。
- 风险：只有 sidecar 上报 rooms 或手动刷新房间列表后才会触发；未启动微信群通道时仍依赖现有展示兜底。

备选方案一：在 Web 画像列表 GET 时顺手持久化补齐。

- 优点：用户打开后台即可修复。
- 风险：GET 接口产生写副作用，不符合当前 Web 查询接口习惯。

备选方案二：只关闭 issue，不做代码变更。

- 优点：当前展示层已有兜底，改动为零。
- 风险：issue 明确说“同步后补齐”，且复现证明底层 name records 没有被补齐，关闭依据不足。
