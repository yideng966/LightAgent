# 微信群音频格式误判修复方案

## 背景

2026-07-12 22:20:34，微信群音频消息触发 `chat_channel.py` 日志：

```text
[chat_channel] silk to wav conversion failed; asr skipped, error_type=ValueError
```

随后群内出现：

```text
@凌 [ERROR]
Silk 语音转换失败，无法进行语音识别，请稍后重试。
```

已确认当前环境安装了 `pysilk-mod 1.6.4`，因此本次不是 2026-07-10 已修复的缺依赖问题。

## 根因

归档库中对应音频记录为 `message_id=7008804048363399943`，媒体路径为 `.sil`，但处理失败后原文件已被通用语音清理逻辑删除，无法复验该文件头。

同一发送者更早保留的 `.sil` 音频文件头为：

```text
ff f3 38 c4 ...
```

这是 MPEG/MP3 音频帧特征，不是 Silk 常见头 `#!SILK_V3`。当前 `voice/audio_convert.py` 仅按扩展名判断 `.sil/.silk/.slk`，导致真实 MP3/MPEG 内容被送入 `pysilk.decode_file()`，从而抛出 `ValueError`。`ChatChannel` 又把它当作 Silk 转换失败直接返回错误，没有给 ASR 直接处理 MP3 的机会。

另一个伴随问题是：微信群 sidecar 媒体文件位于 `~/.cow/wechat_group/media` 并被归档库引用，但 `ChatChannel` 语音处理完成后会删除原始输入文件。失败时这会破坏诊断证据，也让归档 `media_path` 失效。

## 修复方案

1. 在 `voice/audio_convert.py` 增加轻量文件头识别：
   - `#!SILK` -> `silk`
   - `RIFF....WAVE` -> `wav`
   - `ID3` 或 MPEG frame sync -> `mp3`
   - 兼容 `amr`、`ogg`、`flac`、`m4a`
2. `any_to_wav()` 对 `.sil/.silk/.slk` 先看文件头：
   - 文件头确认为 Silk 或无法识别时，保持原 Silk 解码路径，兼容无头 Silk 数据。
   - 文件头确认为 MP3/WAV 等非 Silk 时，按真实格式走通用音频路径，不再误报 Silk。
3. `ChatChannel` 在转换失败时：
   - 只有“扩展名为 Silk 且文件头确认为 Silk 或未知”才返回 Silk 错误并停止 ASR。
   - `.sil` 但文件头是 MP3/WAV 等格式时，创建正确扩展名的临时别名交给 ASR，保留已有“下游可直接接收原格式”的兼容策略。
4. 微信群 sidecar 归档媒体文件不作为通用临时文件删除；只清理转换生成的 WAV 和临时别名。

## 实际改动

- 更新 `voice/audio_convert.py`：新增 `sniff_audio_format()` 和 `audio_extension_for_format()`，在 `any_to_wav()` 中优先按文件头识别 WAV、Silk、MP3/MPEG、AMR、OGG、FLAC 和 M4A；`.sil/.silk/.slk` 只有在真实 Silk 或无法识别时才进入 Silk 解码。
- 更新 `channel/chat_channel.py`：语音分支先识别真实音频格式；`.sil` 但内容为 MP3/MPEG 时不再返回 Silk 错误，转换失败后会创建 `.mp3` 临时别名交给 ASR；微信群 sidecar 归档媒体源文件不再被通用临时文件清理删除。
- 更新 `tests/test_audio_convert.py` 与 `tests/test_chat_channel_voice.py`：覆盖误标 `.sil` 的 MP3/MPEG 文件、ASR 临时别名和微信群归档源文件保留。
- 代码审查后加固：ASR 临时别名改为唯一临时文件，避免覆盖同目录已有媒体；归档源文件保留判断使用 `os.path.samefile()` 与 Windows 友好的 `normcase(abspath())` 兜底。
