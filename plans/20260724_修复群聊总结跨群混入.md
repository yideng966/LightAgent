# 修复群聊总结跨群混入开发计划

## 背景

GitHub Issue #1 反馈：在 A 群请求“总结一下昨天的聊天纪要”时，回复混入了其他群的内容。预期所有聊天记录检索和总结上下文都必须严格限定在当前群。

## 原因分析

微信群归档已经同时保存稳定群 ID（`stable_room_id`）与历史兼容群 ID（`room_id` / `runtime_room_id`），当前查询统一使用：

```sql
stable_room_id = ? OR room_id = ?
```

该条件没有约束 `room_id` 兼容分支只能匹配尚未绑定稳定身份的历史记录。当另一群已绑定稳定身份，但其历史 `room_id` 与当前群的稳定 ID 发生值碰撞时，这条记录仍会通过 `room_id = ?` 被选中。群聊总结会同时注入归档证据、本地抽取摘要、最近聊天记录和焦点消息，因此底层误选会沿多条上下文链路进入 LLM 请求。

## 解决方案

1. 将归档查询的群作用域条件收紧为：
   - 优先且严格匹配 `stable_room_id = 当前群`；
   - 仅当记录的 `stable_room_id` 为空时，才允许通过历史 `room_id = 当前群` 兼容读取。
2. 将同一约束应用到消息检索、精确消息读取、蒸馏、增量读取、成员读取、房间名称与相关归档统计，避免其他归档消费者保留同类越界路径。
3. 增加回归测试，构造“B 群 runtime/legacy room_id 等于 A 群 stable_room_id”的碰撞数据，验证 A 群的 recent、search、distill 和最终总结上下文均不包含 B 群内容，同时保留无稳定 ID 历史数据的兼容读取。
4. 更新 `AGENTS.md` 与 `CHANGES.md`，记录群归档隔离约束、实际改动和验证结果。
