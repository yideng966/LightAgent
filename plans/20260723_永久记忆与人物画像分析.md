# 永久记忆与人物画像功能分析方案

> 状态：分析完成，待确认是否进入重构实施计划。
> 日期：2026-07-23
> 范围：当前 LightAgent 仓库内的通用永久记忆、个人微信群群永久记忆、群友人物画像、画像进化、Prompt 注入、Agent 工具和 Web 管理入口。
> 说明：本轮未提供外部参考项目代码，因此本文以当前仓库内部的两套设计做对比：`agent.memory` 通用长期记忆 vs `channel.wechat_group` 的群记忆/群友画像扩展。若后续需要对比外部项目，应补充外部仓库、分支或提交号后再做二次调研。

## 一、结论先行

当前项目已经同时存在三类“长期上下文”能力：

1. 通用永久记忆：`agent.memory`，面向所有 Agent 会话和知识库，底层是 SQLite chunks、FTS5/trigram、可选向量检索、文件同步与 `MemoryScope` 作用域隔离。
2. 微信群群永久记忆：`WechatGroupKnowledgeStore/Service`，面向当前微信群，独立 SQLite 表保存群规、群偏好、历史约定等，按 `room_id` 强隔离，但检索主要是 LIKE 和倒序列表。
3. 微信群人物画像：`WechatGroupProfileStore/Service`，面向 `stable_room_id + stable_member_id` 的群友画像，独立 SQLite 表保存 profile、name records、claims、runs、revisions、learning state，并支持 LLM 画像进化和回滚。

整体判断：

- 可以参考当前微信群画像的设计来重构本项目，但只能“选择性参考”，不建议整套照搬到通用永久记忆。
- 最值得复用的是：稳定身份作用域、服务端绑定作用域工具、证据化 claims、修订/回滚、LLM 输出白名单校验、普通成员写入门禁。
- 最需要修正的是：群永久记忆与通用 `MemoryManager` 分裂、群记忆 LIKE 检索能力弱、画像主表字段过于扁平、Prompt 注入暴露过多内部字段、自动画像准入/游标推进在真实 WeChaty 环境下可能造成零产出。
- 推荐重构方向不是“把所有画像塞进 MemoryManager”，而是“统一作用域和检索入口，保留画像结构化存储”。群记忆更适合逐步迁入或适配到通用 MemoryScope；人物画像则继续保留结构化 profile store，但改为 claims-first、证据-first、Prompt 摘要-first。

## 三、当前逻辑梳理

### 3.1 通用永久记忆链路

通用记忆的核心抽象是 `MemoryScope`：

```text

shared
user(user_id)
session(session_id, user_id)
wechat_group(room_id)
wechat_group_member_profile(room_id, sender_id)
wechat_group_member_profiles(room_id)
```

写入路径：

```text
MEMORY.md / memory/*.md / knowledge/*.md
  -> MemoryManager.sync()
  -> chunker
  -> optional embedding
  -> MemoryStorage.chunks
  -> FTS5/trigram/LIKE + vector index

MemoryManager.add_memory(content, memory_scope=...)
  -> chunker
  -> optional embedding
  -> chunks with scope_type/scope_id/channel_type/subject_id/status
```

检索路径：

```text
MemorySearchTool.execute()
  -> MemoryManager.search()
  -> vector search if embedding provider exists
  -> keyword search
  -> merge + temporal decay

scoped search
  -> MemoryStorage._scope_filter_sql(memory_scope)
  -> exact scope_type/scope_id/channel_type/subject_id/status filter
```

特点：

- 通用、可跨渠道复用。
- 支持 hybrid search，并对中文/混合文本提供 trigram FTS5 或 LIKE fallback。
- `MemoryScope` 已经具备微信群和群友画像作用域表达能力。
- 数据主要是非结构化文本 chunk，适合事实、偏好、知识页、历史摘要，不适合直接承载复杂画像生命周期。
- 通过 `status` 可以停用 chunk，但缺少画像级 claims、证据、修订和回滚语义。

### 3.2 微信群群永久记忆链路

群永久记忆当前不直接使用 `MemoryManager`，而是独立存储：

```text
WechatGroupKnowledgeStore
  -> wechat_group_group_memories
  -> memory_id, room_id, content, source_kind, evidence_message_ids, evidence_text, status
  -> wechat_group_learning_cursors
  -> wechat_group_learning_runs
```

写入入口：

```text
Web POST /api/wechat-group/memories/group
  -> WechatGroupKnowledgeService.add_group_memory()
  -> WechatGroupKnowledgeStore.add_group_memory()

WechatGroupLearner
  -> 从 archive 增量提炼群记忆候选或直接写入
```

召回入口：

```text
WechatGroupChannel._build_memory_context_block()
  -> WechatGroupContextService.preview_context()
  -> WechatGroupKnowledgeService.search_group_memories(room_id, query)
  -> <wechat-group-memory>[group_memory]

AgentBridge
  -> create_wechat_group_memory_tools()
  -> wechat_group_memory_search
  -> 服务端绑定当前 room_id
```

特点：

- `room_id` 隔离清晰，适配微信群业务快。
- Web 管理、停用、预览、学习运行记录比较完整。
- 检索能力弱于通用记忆，主要是 room 内列表 + 简单包含匹配，不利用通用向量/FTS。
- 与 `MemoryScope.wechat_group(room_id)` 存在职责重复，形成两套长期记忆来源。
- `WechatGroupContextService` 曾尝试挂 `memory_manager`，但当前群记忆召回并没有真正走通用 memory search。

### 3.3 微信群人物画像链路

人物画像当前是结构化系统，不是普通 memory chunk。

主存储：

```text
WechatGroupProfileStore
  -> wechat_group_member_profiles
  -> wechat_group_member_profile_names
  -> wechat_group_member_profile_claims
  -> wechat_group_member_profile_revisions
  -> wechat_group_member_profile_runs
  -> wechat_group_member_profile_learning_state
```

核心主键语义：

```text
stable_room_id + stable_member_id
```

主要能力：

- 手工维护 profile：`upsert_manual_profile()`。
- 自动合并启发式画像：`merge_learned_profile()`、`merge_learned_aliases()`。
- LLM 画像进化：archive 增量消息 -> opaque member token -> LLM JSON -> merger 白名单校验 -> `apply_evolution_profile()`。
- 证据和审计：aliases/claims 带 evidence message IDs，evolution run 有 revisions，可回滚。
- Prompt 注入：`_format_profile_content()` 生成 `reply_name`、aliases、role_hints、speak_style、interests、common_words、msg_count、activity_score、intimacy_score 等内容。

召回入口：

```text
WechatGroupContextService.preview_context()
  -> resolve_profiles_for_prompt()
  -> 当前发言人 profile
  -> 本轮明确 @ 到的 mentioned profiles
  -> <wechat-group-memory>

wechat_group_profile_get
  -> 服务端绑定当前 room_id
  -> 默认读当前 speaker
  -> query/list_all 也限制在当前群
```

特点：

- 作用域和审计能力明显强于通用 memory chunk。
- 画像不是“检索若干文本”，而是“当前成员的一份结构化摘要 + 多条证据化 claim”。
- 已经有避免模型伪造 ID 的 opaque token 方向，这是值得保留的关键设计。
- 当前 profile 主表仍保留较多扁平字段，Prompt 注入也直接暴露计数和稳定 ID，业务语义不够精炼。
- 自动准入逻辑过严时，会出现消息被消费、cursor 推进但无画像产出的风险；这类问题不适合靠 Prompt 修复，应在服务端生命周期和 cursor 规则上修。

## 四、三类设计对比

| 维度 | 通用永久记忆 | 微信群群永久记忆 | 微信群人物画像 |
| --- | --- | --- | --- |
| 数据形态 | 非结构化文本 chunk | 群级文本条目 | 结构化 profile + name records + claims |
| 作用域 | `MemoryScope` 通用表达 | `room_id` | `stable_room_id + stable_member_id` |
| 检索 | 向量 + FTS5/trigram + LIKE | 简单 query 包含匹配 + 倒序 | 精确读、列表、LIKE 查询 |
| 写入来源 | 文件同步、工具写入、摘要 flush | Web 手工、学习沉淀 | Web 手工、启发式学习、LLM 进化 |
| 证据 | `source_message_ids` 可选 | evidence message IDs/text | claims/name records/revisions/run evidence |
| 回滚 | 无画像语义回滚 | 停用单条记忆 | evolution revisions 支持回滚 |
| Prompt 注入 | 由 Agent 工具按需搜索 | `<wechat-group-memory>[group_memory]` | `<speaker_profile>`/`<mentioned_profile>` |
| 权限 | 通用工具权限依赖 Agent 工具过滤 | Web/API 与通道门禁 | Web/API、通道门禁、Agent 工具绑定 |
| 主要风险 | 非结构化、缺少事实生命周期 | 与通用记忆分裂、检索弱 | 字段扁平、自动准入和 Prompt 摘要需优化 |

关键差异：

1. 群记忆本质上更像 `MemoryScope.wechat_group(room_id)` 下的 scoped memory，不一定需要长期保持独立 store。
2. 人物画像不是普通记忆。它需要名称记录、证据 claim、生命周期、冲突处理、回滚和 Prompt 投影，因此不应直接迁成 chunks。
3. 通用 memory 的搜索能力强，但治理能力弱；画像 store 的治理能力强，但召回/相关性排序弱。
4. 当前项目最缺的不是再新增一个记忆系统，而是把“作用域、证据、检索、生命周期、权限”统一到一套清晰边界里。

## 五、可参考设计点

### 5.1 值得保留并推广的设计

1. 服务端绑定作用域工具。
   - `wechat_group_memory_search` 和 `wechat_group_profile_get` 不暴露 `room_id` 参数。
   - 当前 room/member 从 `Context` 元数据绑定，避免模型跨群读取。

2. 稳定身份优先。
   - 长期配置、权限、画像、群记忆都应优先使用 stable scope。
   - runtime ID 只用于真实发送和 legacy 快照。

3. claims + evidence。
   - 人物画像事实应由 claim 承载。
   - 每条 claim 要有 evidence message IDs、confidence、source_kind、status 和时间边界。

4. opaque token LLM 提取。
   - LLM 不直接看到真实 `stable_member_id`。
   - 服务端维护 token -> member 的白名单映射。
   - merger 只接受当前批次 allowlist 内的 token 和 evidence。

5. 修订与回滚。
   - 自动画像进化必须能按 run 回滚。
   - 这比直接覆盖 profile 主表安全。

6. 写入门禁分层。
   - 普通成员可以查询和问答，但不能触发持久写入、画像写入、配置修改、workspace 写入。
   - 通道层拒绝、Agent 工具过滤、Prompt 权限提示三层都要保留。

### 5.2 不宜照搬的设计

1. 群永久记忆继续独立 LIKE 检索。
   - 它已经和 `MemoryScope.wechat_group(room_id)` 重复。
   - 长期看应接入通用 `MemoryManager` 的 FTS/向量能力，或至少提供统一 adapter。

2. 把 profile 主表扁平字段直接注入 Prompt。
   - `msg_count`、`activity_score`、`intimacy_score` 和稳定 ID 对自然回复帮助有限。
   - 更合适的是生成“对当前回复有帮助的受限摘要”。

3. 用“是否已有画像/是否强身份确认”作为自动画像唯一准入。
   - 这会把无强 ID 但当前群可隔离的成员全部过滤掉。
   - 应区分“当前群观察型画像”和“跨 runtime/权限继承型身份确认”。

4. cursor 在零 eligible 成员时仍推进。
   - 这会造成后续策略修复后历史增量无法自然重试。
   - 应把“消息被读取”和“画像有效消费”分开记录。

5. 群记忆和画像分别有独立 DB，缺少统一索引视图。
   - 对 Web 查询、Agent 工具、诊断和迁移都会增加成本。

## 六、建议重构方向

### 6.1 目标边界

重构目标：

- 统一长期上下文的作用域模型。
- 群记忆接入通用检索能力。
- 人物画像保留结构化治理能力。
- Prompt 注入只注入当前轮必要、可信、可解释的摘要。
- 保留当前 Web/API 兼容入口，避免一次性破坏用户数据。

非目标：

- 不重写独立 Agent loop。
- 不把微信群通道变成独立机器人产品。
- 不做跨群人物合并。
- 不把 runtime ID 当作长期权限主体。
- 不让模型自行决定跨群读取、写入或合并。

### 6.2 推荐目标结构

```text
LongTermContextService
  -> group_memory: MemoryManager + MemoryScope.wechat_group(stable_room_id)
  -> member_profile: WechatGroupProfileService, claims-first
  -> global/shared memory: MemoryManager + MemoryScope.shared()
  -> prompt projection: 当前轮按需摘要

WechatGroupContextService
  -> 只负责微信群上下文装配
  -> 不拥有第二套长期记忆检索逻辑
```

群记忆目标：

```text
group memory write
  -> MemoryManager.add_memory(
       content,
       memory_scope=MemoryScope.wechat_group(stable_room_id),
       metadata={source_kind, evidence, created_by, legacy_memory_id}
     )

group memory search
  -> MemoryManager.search(query, memory_scope=MemoryScope.wechat_group(stable_room_id))
  -> fallback legacy WechatGroupKnowledgeStore during migration
```

人物画像目标：

```text
profile main table
  -> 只保留 stable_room_id, stable_member_id, lifecycle, timestamps, revision, status, materialized_summary

name records
  -> reply_name, primary_nickname, aliases, observed names

claims
  -> dimension, value, confidence, evidence, source_kind, valid_at, invalid_at, expires_at, status

prompt projection
  -> addressing
  -> relevant active claims
  -> current speaker interaction preference/boundary
  -> mentioned members only when explicitly mentioned
```

### 6.3 分阶段实施方案

#### 阶段 0：冻结现状和补齐回归

- 梳理现有 API 行为，新增不改变行为的回归测试。
- 覆盖群记忆 exact room 隔离、画像 exact member 隔离、Agent 工具不暴露 room_id、普通成员写入门禁。
- 增加零 eligible 成员时 evolution run/cursor 的诊断测试。

验收：

```powershell
python -m unittest tests.test_memory_scope tests.test_wechat_group_memory_tools tests.test_wechat_group_permissions
python -m unittest tests.test_wechat_group_profile_service tests.test_wechat_group_profile_evolution_executor
```

#### 阶段 1：给群记忆加通用 MemoryManager adapter

- 新增 `WechatGroupScopedMemoryService` 或等价 adapter。
- 写入时双写 legacy `WechatGroupKnowledgeStore` 和 `MemoryManager` scoped chunks。
- 搜索时优先 scoped `MemoryManager.search()`，失败或无结果时 fallback legacy store。
- Web/API 返回仍保持原结构，避免前端改动扩大。

验收重点：

- 当前群召回不跨群。
- 中文查询能利用 trigram/LIKE fallback。
- 没有 embedding provider 时仍能 keyword-only。

#### 阶段 2：群记忆迁移与去重

- 扫描 legacy `wechat_group_group_memories`，按 `room_id` 迁入 `MemoryScope.wechat_group(room_id)`。
- metadata 保存 `legacy_memory_id` 和 evidence。
- 停用 legacy 记忆时同步更新 chunk `status`。
- 迁移后短期保留 legacy 读 fallback。

验收重点：

- 迁移可重复执行。
- active/inactive 状态一致。
- Web 管理端列表不重复显示。

#### 阶段 3：画像 Prompt 投影瘦身

- 保留现有 profile store。
- 修改 `_format_profile_content()`，不默认注入稳定 ID、原始计数和不透明分数。
- 输出分层摘要：
  - `reply_name`
  - `aliases`
  - `interaction_preferences`
  - `boundaries`
  - `relevant_profile_facts`
  - `recent_valid_context`。
- claims 优先，主表字段只作为兼容 fallback。

验收重点：

- 已有别名/称呼不丢。
- 当前 speaker 的边界和互动偏好优先注入。
- mentioned profiles 仍只处理本轮明确 @ 到的人。

#### 阶段 4：画像自动学习生命周期修正

- 区分 observing / active / privileged 三层：
  - observing：当前群可隔离成员可创建观察记录。
  - active：达到证据门槛后可注入非敏感画像 claim。
  - privileged：跨 runtime 继承、权限、合并仍需强身份或人工确认。
- evolution executor 在没有 eligible output 时不应简单标记 success 并推进消费游标。
- LLM extractor 继续使用 opaque token 和 evidence allowlist。

验收重点：

- 无强 wechat_id 的普通成员不会获得权限继承。
- 当前群内可产生观察型画像。
- cursor 不再静默吞掉无法消费的消息。

#### 阶段 5：统一诊断与 Web 管理入口

- Web 群记忆页展示“来源：scoped memory / legacy fallback”。
- 画像页展示 claims、证据、run 和 revision。
- 增加“重建当前群 scoped memory 索引”和“查看画像学习跳过原因”诊断入口。

验收重点：

- 管理员能看到为什么某群无画像产出。
- 能回滚画像进化 run。
- 能停用群记忆且 Agent 不再召回。

## 七、风险评估

高风险点：

- 群记忆迁移如果不保持 legacy fallback，可能导致现有 Web 列表或 Agent 召回短暂缺失。
- 画像 Prompt 瘦身如果没有保护 `reply_name`/aliases，会影响微信群自然称呼体验。
- 自动画像准入放宽如果和权限继承混在一起，会引入跨成员或跨群权限泄露风险。
- MemoryManager embedding provider 不稳定时，群记忆不能依赖向量作为唯一检索路径。

风险控制：

- 所有迁移先 adapter 双读双写，再切换主读。
- stable scope 必须作为服务端过滤条件，禁止模型传入 room/member 决定作用域。
- 画像自动生成只产生低权限观察型 claims，不影响管理员权限和跨群身份。
- 每个阶段都保留可回滚开关和 legacy fallback。

## 九、最终建议

建议可以参考当前人物画像设计来重构，但重构目标应是：

```text
群记忆归一到通用 scoped memory 检索体系
人物画像保留结构化 store，并升级为 claims-first
上下文注入只做当前轮可信投影
写入和自动学习继续由服务端门禁与证据规则约束
```

不建议做：

```text
直接把人物画像整体迁入 MemoryManager chunks
继续为每个渠道新增独立长期记忆 DB
让 LLM 决定 room_id/member_id 或跨群读取
把 runtime ID 或昵称相同当作长期身份合并依据
一次性删除 legacy store 后再重建
```

如果进入实施，优先做阶段 0 和阶段 1：先补回归和 adapter，不动已有用户数据，不改变 Web/API 表面行为。这样能用最小风险验证“群记忆接入通用检索体系”是否确实提升召回质量，再决定是否继续推进画像 claims-first 重构。
