# 群友画像属性模型调研与重构建议

> 状态：GitHub 同类项目调研和属性模型设计已完成，待用户确认后进入代码实施。
> 日期：2026-07-21。
> CowAgent 代码基线：`77db17c8a0dcc1558a3db78d9ee9ade686fe2d9d`。
> 调研方式：以 2026-07-21 实际拉取的 GitHub 仓库代码为准，引用均固定到具体 commit。
> 范围：群友画像的属性分层、事实维度、证据元数据、时效、统计和 prompt 注入。
> 固定约束：别名必须保留；名称表、别名学习、别名审核和 `reply_name` 选择不在本次属性重构范围内。
> 非目标：本轮不修改业务代码、数据库、配置、Web 页面或正式运行数据。

## 一、结论先行

当前画像字段的问题不是“字段太少”，而是把五种不同性质的数据混在了一行画像里：

```text
称呼信息
  primary_nickname / aliases

人物认知
  role_hints / interests / speak_style / common_words

运行统计
  msg_count / activity_score / intimacy_score

证据和时效
  主要藏在 claims 表，聚合画像看不出事实是否仍有效

生命周期
  status / revision / first_observed_at / last_observed_at
```

这会产生四个直接问题：

1. `interests` 同时承担兴趣、专业领域和最近聊天主题，语义不稳定。
2. `speak_style` 是一个自由文本，无法区分表达风格与机器人应该如何回复。
3. `activity_score` 与 `msg_count` 高度重复；`intimacy_score` 当前只因样本中出现一次 `is_at` 就累加 1，不能表达真实关系。
4. prompt 直接注入 stable ID、计数和不透明分数，却缺少互动偏好、明确边界、稳定事实、关系语境和事实时效。

推荐把群友画像重构为：

```text
称呼层（保持现状）
  reply_name + primary_nickname + aliases + observed names

稳定画像层（可用于个性化回复）
  群内角色、自我描述、擅长领域、兴趣主题、内容偏好、
  互动偏好、明确边界、表达风格、口头禅、关系事实、稳定事实

中期状态层（有有效期）
  正在进行的项目、目标、计划和持续关注事项

事实治理层（每条 claim 自带）
  证据、来源、置信度、首次/最近确认时间、有效期、状态、支持次数

运行统计层（不作为人物事实）
  消息数、活跃天数、与机器人互动次数、最近发言时间、熟悉度等级
```

数据库不应为每个新属性增加一列。建议让现有 `wechat_group_member_profile_claims` 成为画像事实的唯一来源，profile 主表只保存主体、生命周期、时间和必要的物化摘要。

当前正式画像仍为 0，正适合先确定新属性模型，再修复自动生成和回放。若先按旧字段回放 305 条已消费消息，随后再改模型，会产生一次没有业务价值的二次迁移。

## 二、当前实现审计

### 2.1 当前持久化字段

`wechat_group_member_profiles` 当前字段及建议如下：

| 当前字段 | 当前含义 | 主要问题 | 建议 |
| --- | --- | --- | --- |
| `stable_room_id` | 群作用域 | 无 | 保留，只用于服务端过滤，不进入 prompt |
| `stable_member_id` | 群成员主体 | 无 | 保留，只用于服务端过滤，不进入 prompt |
| `primary_nickname` | 主昵称 | 与 name records 有重复 | 兼容保留；称呼逻辑不在本次调整范围 |
| `speak_style` | 说话风格自由文本 | 混入“身份/角色”UI，无法结构化更新 | 由 `expression_style` claims 物化生成 |
| `role_hints_json` | 身份/角色提示 | “hint”含义模糊，可能把推测当事实 | 拆成 `group_role` 与 `self_description` claims |
| `interests_json` | 兴趣 | 混合兴趣、专长和短期话题 | 拆成 `expertise`、`interest`、`content_preference` |
| `common_words_json` | 常用词 | 普通高频词、术语、口头禅混在一起 | 只保留证据化 `catchphrase`；普通词频进入统计 |
| `activity_score` | 活跃分 | 目前基本等同样本消息增量，没有时间窗 | 废弃画像含义，改为窗口化统计 |
| `intimacy_score` | 亲密分 | 当前规则不足以证明亲密关系 | 废弃；以可解释互动数和熟悉度等级替代 |
| `msg_count` | 已学习消息数 | 不是归档真实消息总数 | 移到统计层并明确口径 |
| `first_observed_at` | 首次观察时间 | 无 | 保留 |
| `last_observed_at` | 最近观察时间 | 无 | 保留 |
| `revision/status` | 修订和状态 | 状态语义尚未完整定义 | 沿用 `observing/active/disabled` |

### 2.2 当前学习字段

启发式 learner 当前只会生成：

```text
primary_nickname
speak_style = 短句、列清单、说明式三选一
interests = 前端、发布、测试、架构四类硬编码关键词
common_words = 词频最高的三个词
activity_delta = 本批样本数
intimacy_delta = 本批出现任一 is_at 时加 1
```

这更接近测试用最小启发式，不足以构成真实群友画像。尤其不能据此推断职业、性格、关系亲密度或长期偏好。

LLM extractor 当前比启发式多支持 `role_hints` 和 `catchphrases`，但仍然只有扁平数组，且没有明确区分：

- 本人明确说过的事实。
- 其他群友对他的描述。
- 从长期行为观察出的模式。
- 当前一次对话中的临时状态。
- 已失效或互相冲突的旧事实。

### 2.3 当前 prompt 注入

当前 `_format_profile_content()` 会直接注入：

```text
stable_member_id
primary_nickname
aliases
reply_name
role_hints
speak_style
interests
common_words
msg_count
activity_score
intimacy_score
```

其中 stable ID、原始计数和不透明分数对自然回复没有帮助，反而挤占上下文；真正能改善回复的“用户希望怎么被回复、哪些话题避免、近期持续项目、事实是否可靠”没有被表达。

### 2.4 当前 Web 语义错位

Web 表单中的“身份/角色”实际读写 `speak_style`，“长期偏好”实际读写 `interests`。这说明现有字段已经无法准确承载 UI 想表达的业务含义，继续在原字段上追加标签会进一步扩大歧义。

## 三、GitHub 同类项目调研

### 3.1 MaiBot：最接近群聊拟人画像

调研 commit：`fedfc17513ee64541692d1d9ae8908c220ad6ce9`。

关键实现：

- [结构化人物画像](https://github.com/MaiM-with-u/MaiBot/blob/fedfc17513ee64541692d1d9ae8908c220ad6ce9/src/A_memorix/core/utils/profile_text.py#L8) 把画像分为身份设定、关系设定、稳定了解、相处偏好、近期互动和不确定信息。
- [人物基础数据](https://github.com/MaiM-with-u/MaiBot/blob/fedfc17513ee64541692d1d9ae8908c220ad6ce9/src/common/data_models/person_info_data_model.py#L88) 单独保存人物名称、名称原因、不同群的群名片、记忆点、认识次数和首次/最近认识时间。
- 画像构建限制各段条数，prompt 注入时不默认注入维护备注，并把不确定信息与稳定事实隔开。
- 自动画像保留手工覆盖和 snapshot 过期时间，避免旧画像永久支配回复。

对 CowAgent 的启示：

1. 名称/别名与人物事实必须分离，CowAgent 当前 name records 方向正确，应保留。
2. 画像应至少区分身份、关系、稳定事实、互动偏好和不确定信息。
3. “近期互动”不能直接升格为稳定人物属性。
4. 注入 LLM 的画像应是受限摘要，不是数据库所有字段的转储。

不直接照搬的部分：MaiBot 有跨场景人物资料和全局 person 视角；CowAgent 当前必须继续按 `stable_room_id + stable_member_id` 隔离，不能据此放宽跨群身份合并。

### 3.2 Mem0：记忆层级、时效和个性化维度

调研 commit：`8005e18aec2516ac6fb162c816c7fe9a1870d3bb`。

关键实现：

- [Memory Types](https://github.com/mem0ai/mem0/blob/8005e18aec2516ac6fb162c816c7fe9a1870d3bb/docs/core-concepts/memory-types.mdx#L12) 区分 conversation、session、user、organization memory，并进一步区分 factual、episodic、semantic memory。
- [Companion extraction rules](https://github.com/mem0ai/mem0/blob/8005e18aec2516ac6fb162c816c7fe9a1870d3bb/integrations/openclaw/skills/memory-triage/domains/companion.md#L11) 关注个人偏好、关系、计划目标、习惯模式和重要生活事件，同时跳过寒暄、普通日常流水和瞬时情绪。
- [Memory Decay](https://github.com/mem0ai/mem0/blob/8005e18aec2516ac6fb162c816c7fe9a1870d3bb/docs/platform/features/memory-decay.mdx#L6) 用最近使用时间和强化次数调整召回排序，而不是直接删除旧记忆。
- [Memory Expiration](https://github.com/mem0ai/mem0/blob/8005e18aec2516ac6fb162c816c7fe9a1870d3bb/docs/platform/features/memory-expiration.mdx#L6) 为临时事实增加明确过期时间，过期后停止召回但保留审计记录。

对 CowAgent 的启示：

1. 群友画像只保存跨轮仍有价值的稳定认知；当前对话和最近聊天继续由 transcript/focus 承担。
2. 计划、目标、项目等中期信息必须带有效期，不能永久并入稳定画像。
3. 偏好需要保留方向和原因，不能只存一个孤立关键词。
4. 长期未确认的画像事实应降低召回权重，而不是永远与新事实等权。

不直接照搬的部分：Mem0 的 companion 场景是私人对话，可以保存用户主动分享的健康和重要生活信息；微信群是多人空间，CowAgent 不应自动沉淀健康、政治、宗教、财务等敏感画像。

### 3.3 Graphiti：事实证据、关系和时间边界

调研 commit：`ca4d5e9d8c5d25d45917427b63daec17603a0d3a`。

关键实现：

- [EntityEdge](https://github.com/getzep/graphiti/blob/ca4d5e9d8c5d25d45917427b63daec17603a0d3a/graphiti_core/edges.py#L263) 为每条事实保存自然语言 fact、来源 episodes、`valid_at`、`invalid_at`、`expired_at` 和 `reference_time`。
- [EntityNode](https://github.com/getzep/graphiti/blob/ca4d5e9d8c5d25d45917427b63daec17603a0d3a/graphiti_core/nodes.py#L499) 将实体摘要和结构化 attributes 分开。
- 提取 prompt 要求事实绑定明确实体和当前 episode，禁止从无关事件猜测日期。

对 CowAgent 的启示：

1. 画像的基本单元应该是可审计 claim，而不是不断扩张的字符串数组。
2. 每条 claim 必须携带 evidence message IDs 和时间边界。
3. 新事实与旧事实冲突时，应结束旧事实的有效期，而不是永久并集。
4. 关系是独立事实维度，不能塞进模糊的 `role_hints`。

不直接照搬的部分：本次不引入图数据库，也不实现通用知识图谱；只复用“事实 + 证据 + 有效时间”的最小模型。

### 3.4 chatgpt-mirai-qq-bot：平台资料和成员作用域

关键实现：

### 3.5 nonebot-plugin-learning-chat：统计不是画像

调研 commit：`ee79cc6d5ef06eb7fb00a0b4a8f0f2b6f9feea31`。

[数据模型](https://github.com/CMHopeSunshine/nonebot-plugin-learning-chat/blob/ee79cc6d5ef06eb7fb00a0b4a8f0f2b6f9feea31/nonebot_plugin_learning_chat/models.py#L37) 主要保存群 ID、用户 ID、消息、关键词、时间和出现次数，用于学习群内回复模式和选择候选答案。

## 四、调研归纳

| 设计问题 | 同类项目共同方向 | CowAgent 结论 |
| --- | --- | --- |
| 名称与人物事实是否混存 | 名称、群名片和 alias 独立管理 | 保留现有 aliases/name records，不纳入属性重构 |
| 临时内容是否进入长期画像 | conversation/session/recent 与 stable 分层 | 最近聊天继续走 transcript/focus；只有中期事项进入带过期时间的 claims |
| 画像事实如何审计 | fact 绑定 episode/evidence 和时间 | 现有 claims 表升级为事实源 |
| 冲突事实如何处理 | 失效旧事实、保留历史 | 使用 `invalid_at/status`，不永久做数组并集 |
| 统计是否等于人物属性 | 统计用于排序、频率和调度 | 单独 stats 层，不进入画像正文 |
| 如何避免模型过度推断 | 只接受明确证据，不确定项单独存放 | LLM 输出先成为 candidate，经规则验证后激活 |
| 如何保护隔离 | 按 user/session/group 等 scope 强过滤 | 保持 `stable_room_id + stable_member_id` |
| prompt 应注入多少 | 受限摘要、按需召回 | 称呼始终可用，其余只注入相关 active claims |

## 五、目标属性模型

### 5.1 总体结构

推荐的逻辑返回模型：

```json
{
  "addressing": {
    "reply_name": "王哥",
    "primary_nickname": "王大力",
    "aliases": ["王哥", "老王"]
  },
  "stable_profile": {
    "group_roles": [],
    "self_descriptions": [],
    "expertise_topics": [],
    "interest_topics": [],
    "content_preferences": [],
    "interaction_preferences": [],
    "boundaries": [],
    "expression_styles": [],
    "catchphrases": [],
    "relationship_notes": [],
    "stable_facts": []
  },
  "ongoing_context": {
    "goals_and_projects": []
  },
  "stats": {
    "message_count_total": 0,
    "active_days_30d": 0,
    "bot_interaction_count_30d": 0,
    "familiarity_level": "new",
    "last_observed_at": 0
  },
  "lifecycle": {
    "status": "observing",
    "revision": 1,
    "last_enriched_at": 0
  }
}
```

这只是 service/UI 的逻辑结构，不建议整体作为一个 JSON blob 覆盖写入。称呼来自现有 name records；画像属性来自 claims；stats 来自确定性聚合；lifecycle 来自 profile 主表。

### 5.2 称呼层：完全保留

以下能力保持现状，不因属性模型重构而删除或降级：

- `primary_nickname`。
- `aliases`。
- `name_records` 中的人工名称、观察名称和学习名称。
- `reply_name` 的服务端选择。
- 当前群 speaker/mentioned member 的称呼注入。

别名继续是拟人回复的核心。属性重构时必须做回归保护：即使其他画像 claims 为空，只要成员存在有效别名，LLM 当前轮仍能得到 `reply_name` 和 aliases。

### 5.3 稳定画像维度

| claim dimension | 中文含义 | 可接受证据 | 示例 | 默认注入 |
| --- | --- | --- | --- | --- |
| `group_role` | 当前群内职责或角色 | 本人明确说明、管理员手工确认、明确任命文本 | “负责群内版本发布” | 相关时注入 |
| `self_description` | 本人主动表达的长期身份/背景 | 仅本人明确陈述或人工维护 | “从事前端开发” | 相关时注入 |
| `expertise` | 有稳定证据的擅长领域 | 本人陈述或跨多日高质量内容 | “熟悉 React 性能优化” | 相关时注入 |
| `interest` | 长期感兴趣的话题 | 跨多日重复讨论或本人明确喜欢 | “关注摄影” | 相关时注入 |
| `content_preference` | 对内容、活动或方案的偏好/厌恶 | 明确喜欢、偏好、避免的陈述 | “更喜欢可执行清单” | 相关时注入 |
| `interaction_preference` | 希望机器人如何沟通 | 明确请求或多次稳定反馈 | “回答尽量简洁” | 当前 speaker 优先注入 |
| `boundary` | 明确不希望触碰的互动边界 | 只接受明确陈述或人工维护 | “不要在群里公开提及某事项” | 当前 speaker 强制注入 |
| `expression_style` | 可观察的表达形式 | 足量本人消息统计，不做性格诊断 | “短句、口语化、很少使用表情” | 当前 speaker 可注入 |
| `catchphrase` | 重复出现的个人口头禅 | 至少多条独立本人消息 | “整起” | 需要风格适配时注入 |
| `relationship` | 当前群内明确关系事实 | 明确双主体文本或人工确认 | “与小李共同负责测试” | 涉及对应成员时注入 |
| `stable_fact` | 其他长期且对聊天有帮助的非敏感事实 | 本人明确陈述或人工确认 | “维护项目 A” | 语义相关时注入 |

维度边界：

- “经常聊前端”只能先支持 `interest`，不能自动证明 `expertise`。
- “今天很累”不是 `stable_fact` 或性格，只属于当前上下文。
- “说话很冲”是主观人格判断，不接受；可以记录可测量的“平均短句、较少使用敬语”。
- `group_role` 只是画像事实，绝不能影响管理员权限。
- `boundary` 不能由其他群友代替本人设置。

### 5.4 中期状态维度

`goal_or_project` 用于保存会跨越数天或数周、但不是永久事实的事项，例如：

- “本周在准备 2.0 发布”。
- “计划月底完成搬家”。
- “正在学习 Rust”。

每条必须有：

```text
valid_at
expires_at 或明确结束条件
last_confirmed_at
```

无明确期限时可以使用保守默认 TTL，例如 30 天；后续再次提及时刷新。已结束的事项转为 `invalidated`，不继续注入当前画像。

CowAgent 已有 recent transcript、focus 和 archive evidence，因此不再为“刚才说了什么”新增永久画像字段。

## 六、claim 证据模型

### 6.1 现有字段继续复用

现有 claims 表已经具备：

```text
stable_room_id
stable_member_id
dimension
value / normalized_value
confidence
evidence_message_ids
source_kind
run_id
status
first_seen_at / last_seen_at
```

推荐新增或明确：

```text
evidence_origin     self_statement | direct_observation | third_party | manual
extractor_kind      rule | llm | manual
support_count       独立证据数
valid_at            事实开始生效时间
invalid_at          事实结束时间
expires_at          临时事实停止召回时间
last_confirmed_at   最近一次被新证据确认
```

`source_kind = llm_evolution` 当前混合了“事实来自哪里”和“谁负责抽取”。LLM 只是 extractor，不应因为由 LLM 抽取就被当成事实来源。这个拆分只适用于画像 claims，不改变 alias name records。

### 6.2 状态

建议 claim 状态：

```text
candidate    证据存在但尚未达到自动激活门槛
active       可以进入画像和按需 prompt
suppressed   管理员禁止自动恢复
invalidated  曾经有效，但被新事实或时间边界结束
rejected     违反证据、敏感或维度规则
```

### 6.3 证据优先级

| evidence origin | 默认可信度 | 自动激活原则 |
| --- | ---: | --- |
| `manual` | 1.00 | 直接 active |
| `self_statement` | 0.90 | 非敏感、语义明确时可 active |
| `direct_observation` | 0.70 | 需要跨消息、跨时间重复支持 |
| `third_party` | 0.45 | 默认 candidate，不自动成为稳定事实 |

LLM 给出的 `confidence` 不能覆盖服务端门槛。最终接受分数应由证据来源、独立证据数、时间跨度和维度策略共同决定。

### 6.4 冲突处理

禁止继续对 `interests`、`role_hints` 等字段永久做并集。

```text
新事实与旧事实兼容
  -> 增加 support_count，刷新 last_confirmed_at

新事实明确替代旧事实
  -> 旧 claim.invalid_at = 新事实时间
  -> 旧 claim.status = invalidated
  -> 新 claim active

证据不足但存在冲突
  -> 新 claim candidate
  -> 旧 claim 暂时保留，降低召回权重
```

## 七、运行统计单独建模

推荐保留的确定性统计：

| 字段 | 口径 | 用途 | 是否进入 prompt |
| --- | --- | --- | --- |
| `message_count_total` | 当前群归档去重后的成员消息总数 | 画像成熟度 | 否 |
| `text_message_count_30d` | 最近 30 天可学习文本数 | 学习调度 | 否 |
| `active_days_30d` | 最近 30 天有发言的自然日数 | 活跃度展示 | 否 |
| `bot_interaction_count_30d` | 最近 30 天 @/引用/直接回复机器人次数 | 熟悉度计算 | 否 |
| `last_observed_at` | 最近群内出现时间 | UI 和过期判断 | 否 |
| `familiarity_level` | 根据交互次数和跨度确定性计算 | 调整寒暄程度 | 只注入枚举，不注入分数 |

`familiarity_level` 建议只使用：

```text
new | familiar | regular
```

它表示“机器人与该成员有多少可验证互动”，不表示喜欢、亲密、信任或现实关系。旧 `intimacy_score` 不迁移为情感含义。

## 八、敏感与禁止自动生成的属性

默认禁止自动推断或持久化：

- 性别、年龄、种族、民族、宗教、政治倾向、性取向。
- 健康、疾病、残障、财务、收入、精确住址和实时位置。
- 真实姓名、身份证、电话、邮箱等个人身份信息。
- MBTI、心理诊断、道德评价、攻击性人格标签。
- 根据头像、昵称、表情包或他人玩笑得出的身份结论。

平台 adapter 明确返回的资料也只能作为 platform metadata，不能自动升级为画像 claim。管理员确需保存的敏感信息应走独立、显式、可审计的人工流程，本次不设计该能力。

## 九、自动学习规则

### 9.1 可立即写入 active

- 人工维护的非敏感属性。
- 本人明确表达的互动偏好和 boundary。
- 本人明确表达、语义完整且与当前群有用的稳定事实。
- 服务端确定性观察到的当前群名称；名称仍走现有 name records。

### 9.2 需要重复证据

推荐初始门槛：

| 属性 | 最小证据 |
| --- | --- |
| `expression_style` | 至少 10 条可学习文本，跨 3 个自然日 |
| `catchphrase` | 至少 3 条独立消息，排除引用和转发 |
| `interest` | 至少 3 次相关表达，跨 2 个自然日 |
| `expertise` | 本人明确陈述，或跨多日存在具体、持续的专业内容证据 |
| `relationship` | 明确双主体关系文本；非本人陈述默认 candidate |

这些门槛应配置化并通过真实数据校准，但不能退化为“LLM confidence 高就直接写入”。

### 9.3 永远不应从单条消息自动生成

- 人格判断。
- 情感亲密度。
- 职业、学历、地区等现实身份。
- 负面评价和敏感标签。
- 其他群友带有玩笑、讽刺或争议的描述。

## 十、prompt 注入模型

### 10.1 注入原则

1. 当前 speaker 和明确 mentioned member 的 `reply_name + aliases` 始终优先可用。
2. 当前 speaker 的 `interaction_preference` 和 `boundary` 优先级最高。
3. 角色、专长、兴趣、关系和稳定事实按当前问题相关性选择，不全量注入。
4. `goal_or_project` 只注入仍有效且与当前问题相关的项。
5. candidate、suppressed、invalidated、rejected 不进入 prompt。
6. stable ID、evidence IDs、raw confidence、消息数、活跃分不进入 prompt。

### 10.2 推荐格式

```text
[speaker_profile]
reply_name: 王哥
aliases: 王哥, 老王
group_roles:
- 当前群发布负责人
expertise:
- 熟悉前端构建和版本发布
interaction_preferences:
- 希望先给结论，再给操作步骤
boundaries:
- 不要把未确认的线上故障归因到个人
expression_style:
- 短句、偏直接，常用列表确认事项
relevant_facts:
- 正在推进 2.0 发布，本月底前有效
[/speaker_profile]
```

该块是面向当前请求的物化视图，不是 claims 表完整导出。

## 十一、Web 管理模型

画像详情建议分为四个区域：

1. 称呼：主昵称、别名、观察名称和来源。保持现有能力。
2. 人物认知：按群内角色、擅长领域、兴趣、偏好、互动方式、边界、表达风格、关系和稳定事实分组。
3. 进行中事项：展示有效期、最近确认时间和结束按钮。
4. 数据与审计：统计、证据、来源、candidate、失效历史和手工覆盖。

不要继续用逗号分隔的一行文本编辑所有属性。每一条 claim 应能独立确认、抑制、失效和查看证据。

## 十二、旧字段映射

| 旧字段 | 新位置 | 迁移策略 |
| --- | --- | --- |
| `primary_nickname/aliases/name_records` | 称呼层 | 原样保留，不随画像属性迁移 |
| `role_hints` | `group_role` 或 `self_description` | 只有证据维度明确时迁移，否则 candidate |
| `speak_style` | `expression_style` | 标记旧来源；等待新样本确认 |
| `interests` | `interest` | 不自动提升为 expertise |
| `common_words` | stats 或 `catchphrase` | 满足重复证据才转 catchphrase，否则不进画像 |
| `activity_score` | stats | 不迁移为人物 claim，不再注入 prompt |
| `intimacy_score` | 无直接映射 | 废弃，不保留情感语义 |
| `msg_count` | `message_count_total` | 从 archive 幂等重算，不沿用旧累计值 |

正式画像当前为 0，因此实施时应直接使用新模型创建首批画像；alias/name records 即使后续已有数据也必须独立保留。

## 十三、实施优先级

### P0：先确定模型再回放

- 锁定 claim dimensions、状态和敏感字段 denylist。
- 保持 aliases/name records 和 `reply_name` 不变。
- 为 claims 增加 evidence origin、extractor kind 和时间边界。
- 从 prompt 移除 stable ID、不透明分数和原始统计。

### P1：生成最小有用画像

- 第一条消息创建 observing profile。
- 确定性统计单独更新。
- 只从明确自述生成 group role、interaction preference、boundary 和 stable fact。
- 旧启发式 `interests/common_words/speak_style` 不再直接写入 active。

### P2：跨消息归纳

- expression style、interest、expertise、catchphrase 使用滚动样本和跨日证据。
- LLM 只输出 claim candidates；服务端按维度策略激活。
- 增加冲突失效、TTL 和 evidence reinforcement。

### P3：按需注入和 Web 治理

- 构建相关性选择后的 `[speaker_profile]`。
- Web 按 claim 管理证据、状态和有效期。
- 统计页与画像事实页分离。

### P4：reset 后回放

- 从 reset manifest baseline 创建 observing profiles。
- 重跑确定性统计和 claim extraction。
- 验证 aliases 完整、画像数大于 0、prompt 不含旧分数。

## 十四、测试矩阵

### 14.1 属性边界

- “我负责这次发布”可以生成 `group_role`。
- “我喜欢摄影”可以生成 `interest`，不能自动生成 `expertise`。
- “最近在看摄影”先进入中期或 candidate，不直接成为长期兴趣。
- “回答短一点”生成 `interaction_preference`。
- “不要在群里提我的住址”生成 boundary，但不保存住址正文。
- “他肯定是某公司高管”不能生成稳定身份。
- 玩笑、讽刺、自嘲和引用内容不能生成稳定事实。

### 14.2 时间与冲突

- 进行中项目过期后不再注入。
- 新偏好明确替代旧偏好时，旧 claim 变为 invalidated。
- 长期未确认事实降低召回权重，但保留审计。
- 临时 LLM 失败不推进需要重试的证据 cursor。

### 14.3 统计

- 重复 message ID 不增加统计。
- 统计按当前 stable room/member 隔离。
- `familiarity_level` 只由确定性互动数据计算。
- raw message count、activity 和旧 intimacy 不进入 prompt。

### 14.4 别名回归

- 仅有 alias、没有其他画像 claim 时，speaker prompt 仍包含 `reply_name` 和 aliases。
- 属性回放、claim 失效和 profile disable 不得误删 name records。
- A/B 群同名成员的 aliases 继续隔离。
- 人工 alias 的现有优先级和审核状态保持不变。

## 十五、验收标准

1. 群友画像能回答“这个人是谁、擅长什么、对什么感兴趣、希望怎么互动、有哪些边界、最近持续做什么”，且每项有证据。
2. 兴趣、专长、近期话题不再混为一个 `interests` 数组。
3. 表达风格与回复偏好分离。
4. 统计、熟悉度和人物事实分离，不再使用不可解释的亲密分。
5. 临时事项有有效期，冲突事实能失效而不是永久并集。
6. 敏感属性和人格标签不会被自动生成。
7. prompt 不包含 stable ID、原始计数和不透明分数。
8. 别名及 `reply_name` 在整个重构中保持可用，并继续服务拟人化称呼。
9. 所有 active claim 都能追溯 evidence、来源和最近确认时间。
10. 新模型落地后再执行 reset 后回放，避免二次迁移。
