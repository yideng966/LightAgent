# 微信群自由回复调度升级实施计划

> **面向执行 Agent 的要求：** 实施本计划时先使用 `superpowers:subagent-driven-development` 或 `superpowers:executing-plans`，按任务逐项推进。每个任务完成后更新本文件复盘段落。

**目标：** 将微信群自由回复从“单条消息本地判定”升级为“按房间聚合的被动接话调度”，减少频繁插话，同时在多人连续讨论时更自然地接话。

**架构：** 新增一个纯 Python 的 room 级调度器，负责 pending 消息窗口、聚合评分、近期机器人存在感惩罚和 no-action 退避。现有 `evaluate_wechat_group_free_reply()`、情绪修正、LLM judge、worker 和最终 `produce()` 链路继续复用，不改 `Bridge` / Agent 主链路。

**技术栈：** Python `unittest`、现有 `channel/wechat_group` 渠道层、现有 Web 控制台配置接口。

---

## 设计边界

- 只处理普通非 @ 群消息。`is_at = true` 或 `is_quote_self = true` 仍走必回链路，不进入 scheduler。
- 不新增“沉默后自动发言”的后台定时器。空窗补偿只在下一条普通群消息到达时生效，避免形成第二套主动发言调度器。
- 不修改 LLM 二次判定、Agent 主链路、sidecar JSON Lines 协议、消息发送协议。
- 不在本任务内完整实现“图片后追问”绑定。自由回复调度只决定“要不要接话”，多模态上下文注入负责在全局上下文装配阶段解析并注入可用图片/引用/转发/视频上下文。
- 不引入新依赖。
- 默认配置保持保守：新增 scheduler 开关默认关闭，避免影响已经启用自由回复的现有部署。用户开启后才使用聚合调度。
- `wechat_group_free_reply_enabled = false` 时 scheduler 不工作。

## 当前自由回复判断逻辑和链路

当前自由回复链路集中在 `channel/wechat_group/wechat_group_channel.py`、`wechat_group_free_reply.py`、`wechat_group_free_reply_worker.py` 和 `wechat_group_free_reply_judge.py`。

整体链路如下：

```text
sidecar 上报群消息
-> WechatGroupChannel._consume_message()
   - 去重
   - 跳过机器人自发消息
   - 校验是否属于已选择群
   - 写入群消息归档
-> WechatGroupChannel.handle_text()
   - 记录入站日志
   - observe_emotion() 更新群情绪
   - direct_reply = is_at or is_quote_self
-> 如果是 @ / 引用机器人
   - 直接进入 _compose_context() / produce()
   - 不经过自由回复本地评分和 worker
-> 如果是普通非 @ 文本
   - 调用 _should_enqueue_free_reply_message()
-> evaluate_wechat_group_free_reply()
   - 单条消息打分
   - 叠加群范围、低信息、敏感内容、冷却、小时上限、连续上限等抑制
-> emotion_service.adjust_free_reply_decision()
   - 根据 valence / energy / sociability 进一步抬高阈值或追加抑制
-> 如果 triggered = false
   - 记录 last_decision
   - 记录 skipped 日志
   - mark_observed() 重置连续触发计数
   - 当前消息结束，不进入 LLM judge
-> 如果 triggered = true
   - 提交 WechatGroupFreeReplyWorkerPool
   - mark_triggered() 记录 last_triggered_at / hourly / consecutive
-> WechatGroupFreeReplyJudge.judge()
   - 可选 LLM JSON 二次判定
-> 如果 LLM judge 通过
   - _submit_free_reply_after_judge()
   - _compose_context(wechat_group_force_reply=True)
   - context 标记 suppress_mention / no_need_at
   - produce()
-> Bridge / Agent 主链路生成回复
-> send()
   - 群内发送文本，默认不 @ 原发送者
```

当前本地评分逻辑如下：

- `bot_name_match`：文本提到机器人名，+45。
- `group_question`：开放式问题、求助、疑问词，+30。
- `bot_capability_match`：总结、文档、代码、识图、搜索等能力相关文本，+25。
- `memory_or_transcript`：提到群记忆、聊天记录、刚才、谁说等，+20。
- `ai_opinion`：明确问 AI 怎么看，+35。
- `banter_opportunity`：玩梗、吐槽、闲聊机会，+10。
- 如果命中 `group_question` 且最近消息数不少于 2，再加 `unanswered_question`，+25。

当前抑制逻辑如下：

- 总开关未启用：`disabled`。
- 当前群不在自由回复范围：`room_not_enabled`。
- 自发消息：`self_message`。
- 发送者被屏蔽：`blocked_sender`。
- 低信息短文本：`low_information`。
- 原始媒体 payload：`media_payload`。
- 敏感路径、密钥、cookie 等：`sensitive_or_dangerous`。
- 生图失败讨论：`image_generation_failure_discussion`。
- 最小间隔未满足：`min_interval`。
- 小时上限耗尽：`hourly_limit`。
- 连续发言上限耗尽：`consecutive_limit`。
- 分数低于当前档位阈值：`below_threshold`。

当前问题是：普通非 @ 文本是逐条独立判断。某一条短句可能分数不够就直接 skipped，系统不会保留“这个群过去两分钟已经连续出现多个相关问题”的压力状态；也不会根据近期机器人存在感主动降低接话频率。LLM judge 只在本地单条判断通过后才会执行。

## 修改后的自由回复判断逻辑和链路

改造后不替换现有评分器，而是在现有评分器和 worker 之间增加 room 级 scheduler。新的链路如下：

```text
sidecar 上报群消息
-> _consume_message()
   - 去重 / 自发消息过滤 / 群选择 / 归档
-> handle_text()
   - 记录日志
   - observe_emotion()
   - direct_reply = is_at or is_quote_self
-> 如果是 @ / 引用机器人
   - 仍然直接必回
   - 不进入 scheduler
-> 如果是普通非 @ 文本
   - _should_enqueue_free_reply_message()
-> evaluate_wechat_group_free_reply()
   - 保持现有单条评分和基础抑制
-> emotion_service.adjust_free_reply_decision()
   - 保持现有情绪修正
-> WechatGroupFreeReplyScheduler.evaluate()
   - 读取 base_decision
   - 记录当前 room 的 pending 消息窗口
   - 识别硬抑制，硬抑制不可覆盖
   - 对 below_threshold 做聚合压力判断
   - 计算 pending 数、空窗补偿、近期机器人存在感惩罚、退避状态
   - 输出追加了 decision["scheduler"] 的最终 local_decision
-> 如果 scheduler 后 triggered = false
   - 记录 last_decision
   - 记录 skipped 日志
   - pending 保留或按规则过期
   - 当前消息不进入 worker
-> 如果 scheduler 后 triggered = true
   - 提交 WechatGroupFreeReplyWorkerPool
   - 记录调度提交状态
-> WechatGroupFreeReplyJudge.judge()
   - 继续执行现有 LLM 二次判定
-> 如果 LLM judge 通过
   - _submit_free_reply_after_judge()
   - 预留多模态 resolver 接入点
   - _compose_context(wechat_group_force_reply=True)
   - suppress_mention / no_need_at
   - produce()
-> Bridge / Agent 主链路生成回复
-> send()
```

改造后的判断职责分层：

- `evaluate_wechat_group_free_reply()`：仍是基础单条评分器和安全/范围抑制器。
- `WechatGroupEmotionService.adjust_free_reply_decision()`：仍只调节情绪阈值和时段抑制。
- `WechatGroupFreeReplyScheduler`：只判断“当前是否到了适合接话的时机”，不调用 LLM，不调用 Vision，不生成回复。
- `WechatGroupFreeReplyWorkerPool` / `WechatGroupFreeReplyJudge`：继续做异步排队和 LLM 二次判定。
- `Bridge` / Agent：继续负责最终回复生成。

改造后的主要行为变化：

- 单条分数足够且没有硬抑制时，仍可按旧路径快速进入 worker。
- 单条分数不够但多条 pending 累计显示群里确实需要介入时，scheduler 可以把 `below_threshold` 转为触发。
- 如果机器人最近刚连续回复过，scheduler 会通过 presence penalty 降低再次插话概率。
- 如果连续多轮普通消息都不值得接话，会进入 no-action backoff；pending 数达到绕过阈值时可恢复评分。
- `min_interval` 不被覆盖，只等待下一条消息重新评估。
- 纯低信息批次不被聚合触发，避免“哈哈/嗯/ok”攒够条数后触发。

## 推荐方案

采用“本地单条判定 + scheduler 聚合修正”的方式：

1. 先用现有 `evaluate_wechat_group_free_reply()` 得到单条消息的 `base_decision`。
2. scheduler 记录当前房间最近普通消息的 pending 窗口。
3. scheduler 对软抑制做聚合修正，例如 `below_threshold`、低单条分数、低 pending 压力。
4. scheduler 不覆盖硬抑制，例如未启用、群未授权、自发消息、被屏蔽成员、敏感内容、媒体 payload、小时上限、连续上限、情绪低社交和低能量。
5. scheduler 输出 `schedule_decision`，追加到 `decision["scheduler"]`，再交给现有 worker。

这个方案的好处是改动集中、可回退、测试容易写；缺点是无法做到 MaiBot 那种“沉默一段时间后自己再检查 pending”的真实定时空窗补偿。该缺点是刻意取舍，因为 CowAgent 当前规则明确不新增独立主动发言调度器。

## 与全局多模态上下文注入的关系

用户另一个问题“图片消息后，普通文本通过自由回复后没有绑定刚才那张图”不被本 P0 计划覆盖。两者关系如下：

- 自由回复 scheduler 解决的是触发时机：普通非 @ 文本是否应该进入自由回复 worker。
- 全局多模态上下文注入解决的是上下文装配：只要本轮已经进入回复链路，就在 `_compose_context()` 的微信群上下文块装配阶段统一判断是否需要注入图片、引用、转发或视频上下文。
- 两者应该串联，不应该合并成一个评分器。scheduler 不调用 `Vision()`，也不决定图片内容；多模态上下文服务不决定是否接话，只在本轮已经要生成回复时作为 `<wechat-group-multimodal>` 的一部分注入上下文。

### 本地真实问题根因分析

本次用户提到的真实群聊问题已经在本机归档中复核：

- 归档库：`C:\Users\clancy\.cow\wechat_group\wechat_group_archive.db`。
- `2026-07-06 15:42:36`，群 `PT站看片狂魔小群` 中发送者 `@216d9...` 发出 `message_type = image`，且 `media_path` 非空。
- `2026-07-06 15:42:38`，同一发送者发出普通文本 `这是真的吗`。
- `2026-07-06 15:42:47`，机器人回复：`鱼哥你发了张啥图我没看到内容啊，再发一次或者描述下？[捂脸]`。

结论：图片已经成功入库，媒体文件路径也存在；这不是 sidecar 下载失败，也不是 `WechatGroupArchive.record_message()` 漏记。真正的问题在 Python 通道链路：

```text
15:42:36 图片入群
-> _record_inbound_message() 已归档 image + media_path
-> 非 @ 图片如果没有被自由回复图片链路选中，不进入当前回复上下文

15:42:38 文本“这是真的吗”
-> 普通非 @ 文本
-> _should_enqueue_free_reply_message()
-> evaluate_wechat_group_free_reply()
-> emotion adjust
-> worker / LLM judge
-> _submit_free_reply_after_judge()
   - 当前 msg.ctype == ContextType.TEXT
   - 不调用 _build_recent_image_understanding_content()
   - 不查最近图片
   - 不调用 Vision()
-> _compose_context() 只带纯文本和最近群聊
-> Agent 只能看到“这是真的吗”，看不到上一张图片的视觉摘要
```

现有 `_build_recent_image_understanding_content()` 只在“文本 direct reply”分支调用，也就是 `is_at = true` 或 `is_quote_self = true` 时才有机会查最近图片。自由回复文本即使通过了本地评分和 LLM judge，也不会进入最近图片识别链路。

还有一个次级问题：`_looks_like_image_understanding_request()` 当前不识别 `这是真的吗`、`真的假的`、`靠谱吗` 这类短追问。即使用户改成 `@机器人 这是真的吗`，也可能因为文本意图没命中而不查最近图片。后续 P0b 需要把这类短追问纳入“有可绑定近图时才生效”的视觉指代意图，而不是全局扩大自由回复评分。

推荐接入顺序：

```text
普通非 @ 文本
-> evaluate_wechat_group_free_reply()
-> WechatGroupFreeReplyScheduler.evaluate()
-> WechatGroupFreeReplyWorkerPool / LLM judge
-> _compose_context()
   -> _build_multimodal_context_block()
      -> WechatGroupMultimodalContextService.build_context()
-> Bridge / Agent
```

因此，本计划实施时只需要保证自由回复最终仍走 `_compose_context(wechat_group_force_reply=True)`，并把 `wechat_group_trigger_source = "free_reply"` 之类的来源信息传给 context；不要在 `_submit_free_reply_after_judge()` 里单独补图片识别逻辑。真正新增 `WechatGroupMultimodalContextService` 建议作为紧随 P0 后的 P0b 独立任务，避免一次改动同时触碰“接话频率”和“上下文注入”两个行为面。

如果后续实施 P0b，最小范围应为：

- 新增 `channel/wechat_group/wechat_group_multimodal_context_service.py`。
- 升级现有 `_build_multimodal_context_block()`，让图片理解摘要作为 `<wechat-group-multimodal>` 的全局上下文块注入，而不是只在自由回复某个点位补丁。
- direct reply、引用回复、自由回复文本、自由回复图片都通过同一个多模态上下文服务选择图片候选和生成摘要。
- 修改 `<wechat-group-image>` / `<wechat-group-multimodal>` 输出，避免把本机绝对路径暴露给 LLM，只保留 message_id、发送者、绑定原因和视觉摘要。
- 补测试：引用图片、同发送者短窗口追问、群内唯一近图、多图不明确不绑定、跨群不绑定、自由回复和 direct reply 均走全局注入。

P0b 的详细实施计划已单独放在 `plans/20260706_微信群多模态上下文全局注入.md`。如果后续一次性开发，建议顺序是先完成本文件 Task 1-4 的 P0 调度器，再执行 P0b；不要把 scheduler 评分和多模态上下文注入规则写进同一个类里。

## 关键规则

### 硬抑制

以下抑制出现时 scheduler 只能记录状态，不能改成触发：

- `disabled`
- `room_not_selected`
- `room_not_enabled`
- `self_message`
- `blocked_sender`
- `sensitive_or_dangerous`
- `media_payload`
- `image_generation_failure_discussion`
- `hourly_limit`
- `consecutive_limit`
- `emotion_low_sociability`
- `emotion_low_energy`
- `time_rule_blocked`

### 软抑制

以下抑制可以通过聚合评分参与最终结果：

- `below_threshold`
- `low_information`
- `min_interval`

其中只有 `below_threshold` 可以被聚合评分直接覆盖。`min_interval` 不被覆盖，只转成 `scheduler_wait_min_interval`；pending 会保留，等下一条消息到来后再评估。`low_information` 不能单独被覆盖，只有 pending 窗口中存在至少一条非低信息消息时，低信息消息才作为上下文压力参与聚合；如果整个 pending 窗口都是低信息短句，必须继续抑制。

### 聚合评分

每条 pending 消息保存：

- `message_id`
- `room_id`
- `room_name`
- `sender_id`
- `sender_name`
- `text`
- `message_type`
- `created_at`
- `base_score`
- `base_threshold`
- `base_reasons`
- `base_suppressions`

调度器计算：

- `content_score`：pending 内最高 `base_score`。
- `pressure_score`：pending 数量带来的压力分，默认最多 30 分。
- `idle_bonus`：距离上一条普通外部消息间隔较长时加分，默认最多 15 分。
- `presence_penalty`：最近 5 分钟机器人回复过多时扣分，默认最多 30 分。
- `aggregate_score = content_score + pressure_score + idle_bonus - presence_penalty`。

触发条件：

- 没有硬抑制。
- 不处于 no-action backoff，或 pending 数达到绕过阈值。
- 不处于 `min_interval`。
- pending 窗口不是纯低信息短句。
- `aggregate_score >= threshold`。

触发后：

- 以最新一条消息作为 `msg` 进入现有 worker。
- `decision["text_preview"]` 保持最新消息预览。
- `decision["scheduler"]` 写入 pending 数、聚合分、压力分、空窗补偿、存在感惩罚、命中原因。
- 当前房间 pending 清空。

未触发时：

- 记录 `scheduler_wait_pending`、`scheduler_low_pressure`、`scheduler_presence_penalty`、`scheduler_backoff` 等抑制原因。
- 若连续若干轮没有触发，增加 no-action 计数并进入短退避。

- `no_action_backoff_start_count`: 1 到 20。
- `no_action_backoff_bypass_pending_count`: 0 到 50。

## UI 控制要求

本次开发不应只改后台逻辑。为了让自由回复调度可控、可回退、可诊断，Web 控制台必须提供以下控制项和状态展示。除非用户后续明确要求桌面端，否则只修改 Web 控制台，不修改 Electron 桌面端。

### 必须提供的开关

- `启用自由回复`：沿用现有 `wechat_group_free_reply_enabled`，作为总开关。
- `启用聚合调度`：新增 `wechat_group_free_reply_scheduler_enabled`。关闭时完全恢复旧的单条评分行为。
- `启用大模型二次判定`：沿用现有 `wechat_group_free_reply_llm_judge_enabled`。
- `启用情绪调节`：沿用现有情绪模块开关，不在本次新增重复开关。

### 必须提供的调参项

- `pending 窗口秒数`：对应 `wechat_group_free_reply_pending_window_seconds`。
- `最多保留 pending 消息数`：对应 `wechat_group_free_reply_pending_max_messages`。
- `pending 触发条数`：对应 `wechat_group_free_reply_pending_trigger_count`。
- `存在感统计窗口秒数`：对应 `wechat_group_free_reply_presence_window_seconds`。
- `无动作退避基础秒数`：对应 `wechat_group_free_reply_no_action_backoff_base_seconds`。
- `无动作退避封顶秒数`：对应 `wechat_group_free_reply_no_action_backoff_cap_seconds`。
- `无动作退避启动次数`：对应 `wechat_group_free_reply_no_action_backoff_start_count`。
- `pending 绕过退避条数`：对应 `wechat_group_free_reply_no_action_backoff_bypass_pending_count`。

### 必须提供的状态展示

在自由回复面板的“最近判定”或新增“调度状态”区域展示：

- 当前 scheduler 是否启用。
- 当前 room pending 数。
- 最近一次聚合分：`aggregate_score`。
- 最近一次基础分：`content_score`。
