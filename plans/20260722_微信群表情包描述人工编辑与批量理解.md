# 微信群表情包描述人工编辑与批量理解开发计划

## 状态

- 当前状态：已完成代码、自动化回归、明暗主题与响应式 UI 验收。
- 默认实施端：Web 控制台的个人微信群表情包管理页，不修改 Electron 桌面端。
- 默认作用域：当前 UI 选中的 `stable_room_id`，不跨群统计或更新。

## 需求目标

1. 在表情包管理卡片中人工修改本地表情包描述，并立即持久化到现有 SQLite 表。
2. 在批量操作前展示当前群还有多少条描述未正确理解，以及其中多少条可以交给图片理解处理。
3. 提供“图片理解补全描述”按钮，复用 CowAgent 现有 `Vision` 能力批量更新待理解描述。
4. 保证批处理失败可重试、人工描述不被并发任务覆盖、不同微信群数据不串用。

## 现状结论

- 当前 Web UI 只读展示 `description`，仅支持搜索、状态筛选和停用，不支持修改描述。
- 新表情包自动收藏时不会调用 LM/Vision。通道先传入媒体文件名，服务会过滤微信 XML、纯数字和长哈希；无法得到有效文件名时保存安全占位描述“群聊表情包”。
- 仓库已有 `scripts/label_wechat_group_stickers.py`：它会复用 `agent.tools.vision.vision.Vision`，GIF 会先转成最多四帧的 PNG 联系图；正式更新前备份 SQLite，只对旧描述仍未变化的行执行条件更新，失败项保留原值以便续跑。
- 上述图片理解能力当前仅由命令行脚本触发，没有接入 Web API/UI，也不会在表情包入库后自动更新描述。
- 现有脚本的候选范围主要是传输 XML、纯数字和长哈希，尚未覆盖当前新数据使用的通用占位描述，也没有按 UI 当前群返回统计和任务进度。

## “待理解”判定口径

本次默认把当前群中状态为 `active` 且描述符合以下任一条件的本地表情包判定为“待理解”：

- 空描述；
- 安全占位描述“群聊表情包”或等价的无语义通用占位；
- 微信 `<msg><emoji ...>` 传输 XML；
- 纯数字消息 ID；
- 长十六进制哈希文件名。

正常中文/英文语义描述默认视为“已理解”。系统无法仅凭文本可靠判断一条看似正常的描述是否与图片事实不符，这类误判通过人工编辑修正，本次不引入主观打分模型或自动覆盖正常描述。

统计应同时返回：

- `pending`：待理解总数；
- `processable`：媒体文件存在且非空、可调用 Vision 的数量；
- `missing_files`：媒体文件不存在的数量；
- `empty_files`：媒体文件为空的数量；
- 当前批处理任务状态及进度。

## 方案设计

### 1. 统一描述质量与图片理解逻辑

- 新增微信群表情包描述服务模块，把现有脚本中的候选判定、语义标签清洗、GIF 联系图、数据库备份和 Vision 调用下沉为运行时与 CLI 共用逻辑。
- 保留 `scripts/label_wechat_group_stickers.py` 作为命令行入口，改为调用共用服务，避免 UI 和脚本形成两套标注规则。
- 不新增数据库字段或迁移表结构；使用明确、可测试的描述质量判定计算待理解数量。
- 批量任务开始前必须成功备份整个表情包 SQLite；备份失败则不启动 Vision 调用。

### 2. 存储层原子更新

- 在 `WechatGroupStickerStore` 增加按 `room_id + sticker_id` 更新描述的方法。
- 人工保存时校验记录确实属于当前稳定群，描述去除首尾空白，限制为 1–200 个字符，并拒绝 XML、纯数字和长哈希等不安全描述。
- 批量更新使用 `WHERE room_id = ? AND sticker_id = ? AND description = ?` 条件写入；如果用户在 Vision 处理期间人工改过描述，本次结果自动跳过，绝不覆盖人工值。
- 更新成功后同步刷新 `updated_at`，现有按描述搜索能力立即使用新值。

### 3. Web API

在现有 `/api/wechat-group/stickers/(.*)` 路由中增加动作，全部继续经过登录鉴权和稳定群身份解析：

- `GET description-status`：返回当前群待理解统计及批处理状态。
- `POST update-description`：人工更新单个本地表情包描述，返回更新后的序列化记录和最新统计。
- `POST describe-pending`：确认统计后启动当前群批量图片理解；没有可处理项或已有任务运行时拒绝重复启动。
- `GET describe-status`：返回 `pending/running/completed/partial_failed/failed`、已处理数、成功更新数、失败数、跳过数等进度。

批处理在后台线程运行，Web 请求只负责启动任务；Vision 使用现有脚本已支持的受限并发，默认采用保守的 2 路并发，不新增用户配置。进程内同一时间只允许一个表情包描述批处理任务，避免模型限流和数据库写竞争。服务重启会终止内存任务状态，但已完成的逐条提交仍保留，未成功项仍满足待理解条件，可重新执行。

### 4. Web UI 交互

- 在当前群的表情包列表工具区展示“待理解 N 条，其中 M 条可处理”，统计不受当前搜索词和列表 30 条上限影响。
- 增加带图片理解图标的“补全描述”按钮；`processable = 0` 或任务运行时禁用。
- 点击后先显示确认信息，明确当前群、处理数量、会调用已配置的 Vision 并创建数据库备份；确认后才启动。
- 运行期间展示稳定尺寸的进度条和 `已处理/总数`，轮询任务状态；完成后显示更新、失败、文件缺失/为空和并发跳过数量，并刷新卡片与统计。
- 每张本地表情包卡片增加“编辑描述”操作，展开内联输入框、保存和取消；保存中禁用重复提交，失败信息贴近输入框展示，成功后收起并刷新当前卡片。
- 在线搜索结果不提供人工编辑；已停用的本地表情包仍可人工修改描述，但不进入默认批量处理统计。
- 沿用现有 Tailwind、Font Awesome、明暗主题和响应式布局；补齐可见焦点、`aria-label`、按钮禁用态和键盘保存/取消，不增加新的装饰性样式体系。

## 风险与回退

- Vision 可能不可用、超时或限流：逐条记录失败并保留原描述，任务可续跑。
- 批量识别可能产生错误语义：只处理明确异常候选，正常描述不覆盖；用户可在 UI 人工修正。
- 服务重启导致任务中断：使用逐条条件提交，已完成项保留，剩余项重新统计后继续。
- 数据库更新风险：批处理前强制 SQLite 在线备份；人工编辑为单行事务。
- 回退时可停止后台任务入口并使用本次备份恢复数据库；代码改动按独立模块、API 和 UI 原子回退。

## 已确认口径

1. 批量处理默认只作用于当前选中的稳定群，不提供“一次处理所有群”。
2. “待理解”只自动识别空值、通用占位、XML、纯数字和长哈希；语义看似正常但事实错误的描述由人工编辑修正，不让 Vision 自动覆盖全部正常描述。
3. 新表情包入库仍不自动调用 Vision，避免消息接收延迟和不可控成本；仅由用户在 UI 点击按钮后批量处理。
