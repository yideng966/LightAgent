# 深度思考开关与强度统一适配开发计划

## 一、计划状态

- 当前阶段：开发、文档与本地验证已完成，等待提交。
- 实际实现遵循“统一启停 + 四档强度 + Provider 协议转换”，未扩大到非文本模型路由。
- 目标范围：Agent 发起的文本 LLM 请求；视觉、生图、Embedding、ASR、TTS 保持独立路由，不纳入本次改造。

## 二、最终需求定义

Web 控制台「配置 -> Agent 配置」提供两个相关设置：

1. 深度思考开关：可以明确关闭或开启。
2. 思考强度：提供 `low`、`medium`、`high`、`max` 四档，默认 `low`。

LightAgent 使用这一套统一配置表达用户意图：

```json
{
  "enable_thinking": true,
  "reasoning_effort": "low"
}
```

发起请求时，Provider 适配层负责把统一开关和档位转换为当前厂商、当前模型实际支持的协议。不得把 `reasoning_effort=none` 作为通用关闭参数发送给所有上游。

消息渠道不分别配置：Web、微信群、企业微信、CLI 等入口均使用同一套 Agent 深度思考配置；差异只发生在模型 Provider 请求层。

## 三、当前实现与缺口

### 3.1 配置和 UI

- `config.py` 与 `config-template.json` 当前把 `reasoning_effort` 默认设为 `high`，需要改为 `low`。
- Web 控制台当前只有 `enable_thinking` 开关，没有强度控件。
- `/config` 的 GET 未返回 `reasoning_effort`，POST 白名单也不允许保存该字段。
- Agent 请求层缺少配置值的统一枚举校验，当前只接受 DeepSeek 使用的 `high/max`。

### 3.2 路由层

- `bridge/agent_bridge.py` 已根据 `enable_thinking` 生成 `thinking.type=enabled/disabled`。
- 当前只有 `high/max` 会进入请求；`low/medium` 会被丢弃。
- Scorer 使用 `request_options.reasoning_effort=none` 表示仅当前请求关闭思考。
- 通用 OpenAI-compatible 适配器会把这个内部 `none` 原样发送给上游，存在 400 风险。

### 3.3 Provider 现状矩阵

下表描述当前代码，不代表所有协议已完成最新官方核验：

| Provider | 当前行为 | 缺口 |
|---|---|---|
| DeepSeek | V4 使用 `thinking.type` 和 `reasoning_effort=high/max`；R1 固定思考 | 需把四档映射到其合法档位 |
| MiMo | 使用 `thinking.type` | 缺少统一强度映射 |
| 豆包 | 直接发送 `thinking.type` | 未按模型能力过滤，缺少强度映射 |
| 智谱 GLM | 发送 `thinking.type` | 模型能力判断和强度映射不完整 |
| Qwen / DashScope | Qwen3/QwQ 转换为 `enable_thinking` | `thinking_budget` 未与四档统一 |
| Kimi | 部分模型使用 `thinking.type`；部分代码模型固定思考 | 固定思考模型不能发送非法 disabled |
| LinkAI | 直接发送 `thinking.type` | 代理模型的强度协议不确定 |
| OpenAI | 走通用 OpenAI-compatible 适配器 | 未正确应用全局开关和四档能力 |
| Claude | 当前忽略开关 | 扩展思考启停和预算未接入 |
| Gemini | 当前忽略开关 | `thinkingConfig` 和模型档位未接入 |
| MiniMax | 固定发送 `reasoning_split=true` | 该字段是输出分离，不等同于启停或强度 |
| ModelScope | 根据模型名强制 `enable_thinking=true` | UI 关闭无效，且依赖模糊名称判断 |
| 百度千帆 | 走通用 OpenAI-compatible 适配器 | 普通模型与固定推理模型未区分 |
| Custom | 只有 Key、Base URL 和模型 | 不知道应使用哪一种思考协议 |

## 四、统一语义设计

### 4.1 配置模型

继续使用现有两个顶层字段，不增加第二套全局配置：

| 字段 | 类型 | 默认值 | 合法值 | 含义 |
|---|---|---|---|---|
| `enable_thinking` | bool | `false` | `true/false` | 是否请求模型启用思考 |
| `reasoning_effort` | string | `low` | `low/medium/high/max` | 开启思考时的统一强度档位 |

行为规则：

- 关闭时保留已选强度，但请求层不应用强度。
- 重新开启时恢复用户上次保存的强度。
- 新配置、缺少该字段的旧配置以及运行时无效值，默认回落到 `low`。
- 旧配置中显式设置的合法 `high/max` 保持原值，不强制降级。
- Web POST 遇到非法值时返回校验错误，不写入配置。

### 4.2 请求级覆盖

Scorer 等特殊无状态任务需要关闭当前一次思考时，改用内部选项：

```python
request_options={"disable_thinking": True}
```

兼容读取旧的 `reasoning_effort=none`，但在路由层立即转换并消费，不再发送给 Provider。`reasoning_effort` 从此只表示强度。

### 4.3 Provider 能力分类

每个 Provider/模型归入以下一种能力：

| 能力 | 开关行为 | 强度行为 |
|---|---|---|
| `switchable_with_effort` | 可显式启停 | 四档转换为厂商档位或预算 |
| `switchable` | 可显式启停 | 不支持强度，忽略档位 |
| `always_on_with_effort` | 无法关闭 | 可转换强度 |
| `always_on` | 无法关闭 | 不支持强度 |
| `unsupported` | 不发送思考参数 | 不发送强度 |
| `unknown` | 不猜测、不发送 | 不猜测、不发送 |

固定推理模型收到“关闭”意图时，不发送非法禁用参数，也不伪装为已关闭；通过诊断日志标记 `always_on`。

### 4.4 四档映射规则

各 Provider 使用显式映射表，不在运行时按字段名猜测：

1. 厂商支持四档时一一映射。
2. 厂商少于四档时保持单调映射：`low` 必须对应最低强度，`max` 必须对应最高强度，`medium/high` 可按官方档位数量合并。
3. 厂商使用 token budget 时，由官方建议和合法上下限形成四档预算表；不得随意发明数值。
4. 厂商只有启停能力时，四档均只映射为“开启”，不发送伪强度字段。
5. 厂商模型固定思考时，按其支持情况仅映射强度或完全忽略设置。
6. 每个映射必须写单元测试，验证最终请求体，而不是只测试内部对象。

示意：如果某 Provider 只支持 `high/max` 两档，可采用：

```text
low -> high
medium -> high
high -> high
max -> max
```

该示意只有在官方协议确认最低合法值确为 `high` 后才能落地。

## 五、Web 控制台交互计划

### 5.1 控件结构

在现有“深度思考”配置项中保留开关，并在其下方增加四档分段选择：

```text
深度思考                         [开关]
思考强度             [低] [中] [高] [极高]
```

保存值始终为 `low/medium/high/max`，中英文显示文案分别为：

- 中文：低 / 中 / 高 / 极高
- 英文：Low / Medium / High / Max

### 5.2 状态联动

- 开启：强度分段控件可操作。
- 关闭：强度控件使用原生 `disabled`，视觉降低强调但仍显示当前档位。
- 切换开关只改变交互状态，不重置强度。
- 保存按钮一次提交 `enable_thinking` 和 `reasoning_effort`，避免出现半保存状态。

### 5.3 可访问性与响应式

依据 `ui-ux-pro-max` 的控件与表单规则：

- 使用语义化 radio group 或项目现有等价组件，不使用无语义的文本按钮拼装状态。
- 提供可见 label、`role="radiogroup"`、选中状态和键盘方向键操作。
- 禁用时同步 native `disabled` 与 `aria-disabled`，不能只降低透明度。
- 焦点样式在浅色、深色主题均清晰。
- 单个档位触控区不小于 44px，高度和宽度稳定，切换不引发布局位移。
- 375px 视口允许四档保持同一行；空间不足时整体按稳定的 2x2 网格换行，不产生横向滚动或文字重叠。
- 不新增装饰动画；状态切换沿用现有 150-300ms 控件过渡。

涉及文件：

- `channel/web/chat.html`
- `channel/web/static/js/console.js`
- `channel/web/static/css/console.css`（仅在现有 utility class 无法满足稳定布局时修改）
- `channel/web/web_channel.py`

## 六、Provider 适配方案

### 6.1 官方协议核验

编码前逐项核对 OpenAI、Anthropic、Gemini、DeepSeek、Qwen、豆包、智谱、Kimi、MiniMax、ModelScope、百度千帆、MiMo 的官方文档，记录：

- 支持启停的模型范围。
- 开启和关闭的实际字段。
- 合法强度枚举或预算范围。
- 固定推理模型及不可关闭限制。
- 流式、工具调用和 reasoning 历史回传要求。
- 与 temperature、top_p、tool_choice 等参数的冲突。

无法确认的模型标记 `unknown/unsupported`，不凭 OpenAI-compatible 名称或模型字符串猜测。

### 6.2 集中能力判定

建议新增 `models/thinking_policy.py`，只负责：

- 校验和规范化 `enable_thinking/reasoning_effort`。
- 根据明确的 Provider、模型和 Custom 协议返回能力分类。
- 返回 Provider 适配所需的统一意图。
- 生成不含消息内容、密钥或 Prompt 的诊断摘要。

各 Provider 仍在自己的请求构造函数内生成厂商字段，避免形成一个掌握所有请求体的巨型模块。

### 6.3 协议映射方向

以下是待官方核验后落地的协议类别：

| 协议 | 关闭转换 | 开启转换 | 强度转换 |
|---|---|---|---|
| `thinking_object` | `thinking.type=disabled` | `thinking.type=enabled` | 仅在协议另有强度字段时发送 |
| `enable_thinking` | `enable_thinking=false` | `enable_thinking=true` | 映射为官方 budget/level |
| `openai_reasoning` | 仅模型明确支持时发送关闭值 | 发送对应 reasoning 配置 | 四档映射到模型合法 effort |
| `anthropic_thinking` | 按官方要求省略或禁用 | 发送扩展思考结构 | 四档映射到合法预算 |
| `gemini_thinking` | 按模型规则关闭或设最低允许值 | 发送 `thinkingConfig` | 四档映射到 level/budget |
| `none` | 不发送 | 不发送 | 不发送 |

### 6.4 主备模型隔离

`TextModelRouter` 在每次候选调用时，必须使用当前候选 Provider 和模型重新解析能力与映射。故障转移到备用模型时不得复用主模型的字段、协议或强度值。

## 七、Custom Provider 方案

为 `custom_providers[]` 增加受控字段：

```json
{
  "thinking_protocol": "none"
}
```

首批枚举：

- `none`
- `thinking_object`
- `enable_thinking`
- `openai_reasoning`

要求：

1. 旧 Custom 配置缺少字段时默认 `none`，升级后不突然发送未知参数。
2. Web Custom Provider 弹窗增加“思考协议”选项集，不允许用户输入任意字段名或 JSON。
3. 后端严格验证枚举，未知值拒绝保存。
4. legacy `custom` 增加 `custom_thinking_protocol`，默认 `none`。
5. 每个 Custom Provider 独立保存协议，备用 Provider 使用自己的协议。
6. 当前 `deepseek-v4-flash-free` 自定义渠道只有配置为 `thinking_object` 后，才按全局开关转换 `thinking.type`；其强度只有在上游协议明确支持时才发送。

## 十一、风险与回退

- 厂商协议和模型能力变化可能导致 400，必须先查官方文档并测试最终请求体。
- 档位名称相同不代表计算量相同，文档只承诺相对等级，不承诺跨厂商等价 token 数。
- 固定推理模型无法满足关闭意图，必须如实记录为 `always_on`。
- Custom 协议选错可能导致请求失败，默认 `none` 降低升级风险。
- 回退时可删除新增 Custom 协议字段，并恢复为不发送未知思考参数；现有布尔开关和配置文件仍可兼容读取。
