# 修复发布打包失败计划

## 背景

`v2.1.7` 标签触发的两条 GitHub Actions 均失败：

- Windows 桌面构建在执行 `scripts/stamp_release_version.py` 后打印中文成功信息时，因 Runner 标准输出使用 `cp1252` 而触发 `UnicodeEncodeError`。
- Docker 基础镜像构建成功，`skills-full` 的 ARM64 构建在 APT 下载 `libsrt1.4-gnutls` 时被远端重置连接；当前 Dockerfile 未配置下载重试，单次瞬时网络错误会终止整个多架构构建。
- `v2.1.8` 首次桌面构建已确认 Windows x64 与 macOS arm64 成功，但 macOS x64 在 `npm ci` 下载依赖时耗尽默认重试并收到 `ECONNRESET`；当前正在仅重跑失败 Job，并为后续发布补充 npm 有限重试。
- `v2.1.8` 重跑后两种 Docker 变体和两个 macOS 架构均成功，但 Windows Job 在同一 Bash step 执行 `npm run build` 后未继续运行 electron-builder；上传步骤忽略空文件，使工作流和 Release 假成功且 Assets 仅有两个 `.dmg`。

`v2.1.7` 与 `v2.1.8` 均已有远端产物，因此不得移动任一标签。完整产物修复使用新补丁标签 `v2.1.9` 发布，避免同一版本对应不同源码、镜像或桌面资产。

## 目标

- 让版本同步脚本在非 UTF-8 标准输出编码下也能正常结束。
- 为 Docker 多阶段构建中的 APT 下载配置有限重试，降低瞬时连接重置导致的发布失败。
- 为桌面发布中的 npm 依赖下载配置有限重试，降低 Registry 瞬时断连导致的单平台缺失。
- 拆分桌面源码编译和安装包打包步骤，并让任一平台缺少安装包时强制失败。
- 补充能稳定复现上述边界的回归测试。
- 发布并验证 `v2.1.9` 的基础镜像、完整技能镜像、Windows/macOS 桌面资产和 GitHub Release。

## 实际改动

- `scripts/stamp_release_version.py` 的成功状态改用 ASCII 输出，兼容 `cp1252` 等非 UTF-8 标准输出编码。
- `docker/Dockerfile.latest` 在 Node 侧车和 Python 运行阶段分别配置 3 次 APT 获取重试，所有直接及间接 APT 调用均继承该配置。
- `.github/workflows/release.yml` 将桌面 npm 获取重试提高到 5 次，并限制退避时间。
- 桌面源码编译和 electron-builder 打包拆成独立步骤；Actions artifact 缺失策略收紧为 `error`。
- 新增版本脚本真实子进程编码回归和逐 Docker stage 的重试合同测试。
- 同步更新发布规则、变更记录及 `v2.1.8`、`v2.1.9` 用户发行说明。
