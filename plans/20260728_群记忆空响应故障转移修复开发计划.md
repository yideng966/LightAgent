# 群记忆空响应故障转移修复开发计划

> **状态：** 本地实施与验证已完成，待发布后验收
> **创建日期：** 2026-07-28
> **本地完成日期：** 2026-07-28
> **任务类型：** 共享文本模型路由修复 / 群记忆 Dream 稳定性 / 运行诊断
> **优先级：** P1
> **实施原则：** 最小修改、复用统一文本模型主备链、失败不推进游标、不记录或暴露模型推理正文

## 1. 任务目标

修复同步无状态文本补全在主模型返回“HTTP 成功但正文为空”时不进入备用模型的问题，使群记忆 Dream 在主模型输出 token 被推理过程耗尽后，可以在当前请求内按既有 `model_fallbacks` 顺序尝试下一候选模型。

本计划同时补齐必要的失败诊断字段，确保以后可以直接从日志和学习运行记录判断失败阶段、空正文原因及退避状态，不再依赖 `status=failed http=0` 进行猜测。

## 2. 已确认事实基线

### 2.1 远端运行现象

2026-07-28 对远端 Docker 实例进行了只读调查，未修改容器、配置或数据库。确认结果如下：

| 项目 | 结果 |
|------|------|
| 容器版本 | LightAgent `2.1.14` |
| 容器状态 | 正常运行，无重启、崩溃或健康检查异常 |
| 故障范围 | 本次容器启动后共出现 24 次相同群记忆失败，涉及 4 个稳定群 |
| 主要失败阶段 | 23 次摘要阶段失败，1 次摘要成功后深度蒸馏阶段失败 |
| 统一失败原因 | `text model completion returned empty content` |
| HTTP 状态 | 上游请求成功，无错误状态码，因此现有日志显示 `http=0` |
| 数据状态 | 失败批次未推进游标，未写入群记忆 |
| 重试行为 | 按默认空闲时间约每 10 分钟重新处理同一批次 |

20:03 告警对应运行的持久化状态为：

```text
trigger_source=idle
summary_status=failed
dream_status=not_run
batch_message_count=39
batch_start_row_id=3509
batch_end_row_id=3509
group_memory_upsert_count=0
failed_reason=text model completion returned empty content
```

### 2.2 同配置最小探针

使用相同主模型、相同摘要提示结构和 `max_tokens=800`，以不包含真实群消息的合成材料执行诊断探针，稳定复现：

```text
model=deepseek-v4-flash-free
finish_reason=length
completion_tokens=800
reasoning_tokens=800
message.content=""
router_success=true
```

结论：800 个输出 token 全部被模型推理过程消耗，模型没有生成最终正文；响应仍是正常 OpenAI-compatible 成功结构。

额外探针结果：

1. 显式传入 `reasoning_effort=none` 时，上游供应商返回 HTTP 400，不能作为兼容解决方案。
2. 使用当前已配置备用模型 `agnes-2.0-flash`，相同材料和 `max_tokens=800` 正常返回正文，`finish_reason=stop`。
3. 因主模型响应不包含 `error`，当前候选路由没有调用备用模型，也没有产生 fallback 日志。

### 2.3 当前代码链路

```text
WechatGroupMemoryDreamService
  -> MemoryDreamEngine.complete(max_tokens=800/1600)
  -> TextModelRouter.complete()
  -> TextModelRouter.call()
  -> 主模型返回 content="" + reasoning_content + finish_reason=length
  -> call() 判定为非临时错误并记录主模型健康
  -> _extract_text_response() 以 content is not None 判定 success=true
  -> MemoryDreamEngine 最终发现正文为空并抛出 MemoryDreamError
  -> 学习运行记录 failed，游标不推进
  -> trigger 退避后重复处理同一批次
```

## 3. 根因分析

### 3.1 模型侧原因

当前主模型会产生独立 `reasoning_content`。群记忆摘要使用固定 `max_tokens=800`，本次请求的全部生成预算被推理 token 占用，最终 `message.content` 为空且 `finish_reason=length`。

这不是网络故障、HTTP 错误、JSON 解析失败或单条群消息污染。多个群、不同批次数量均出现相同行为，合成材料也能复现。

### 3.2 路由侧缺陷

`TextModelRouter.call()` 目前只在响应属于 408、429、5xx、timeout、rate limit 等临时错误时尝试下一候选模型。OpenAI-compatible 的成功响应即使没有可消费正文，也会被当作健康结果直接返回。

随后 `_extract_text_response()` 使用 `content is not None` 判断成功。空字符串不是 `None`，因此形成 `success=true, content=""` 的矛盾结果。

### 3.3 诊断信息不足

群记忆学习表保存了 `failed_reason`，但 trigger warning 只输出 `status` 和 `llm_status_code`。无 HTTP 错误时用 `0` 补位，遗漏以下关键字段：

- `run_id`
- `summary_status`
- `dream_status`
- `transient`
- `failed_reason`
- 模型的 `finish_reason`

因此单看日志无法区分 HTTP 故障、空响应、JSON 非法或 evidence 校验失败。

## 5. 设计方案

### 5.1 定义“同步文本候选不可用”

在共享文本路由内部增加一个小范围响应检查，只用于同步、无工具文本请求。满足以下条件时，当前候选结果不可用：

1. 响应不是已有的显式错误 envelope；
2. 当前请求未声明工具；
3. 响应中不存在非空、非纯空白的最终正文；
4. 响应也不存在需要保留的合法工具调用。

当 `finish_reason` 为 `content_filter`、`safety`、`blocked`、`moderation` 或等价安全拒绝时，不进入备用模型，避免跨 Provider 绕过安全策略。

需要兼容检查以下常见响应位置：

- `choices[0].message.content`
- `choices[0].text`
- 顶层 `content`
- 顶层 `message`

`reasoning_content` 只用于判断和安全诊断长度，绝不能拼接到正文。

首版只以“最终正文为空”为 fallback 条件。`finish_reason=length` 作为原因元数据记录；对已有非空正文但 `finish_reason=length` 的行为暂不改变，避免扩大本次修改范围。

### 5.2 候选切换规则

在 `TextModelRouter.call()` 的现有同步候选循环中加入不可用结果分支：

1. 主候选正文为空且仍有下一候选时，记录不含正文和推理内容的 warning，并继续下一候选。
2. 任一备用候选正文为空且仍有下一候选时，继续按原配置顺序尝试。
3. 最后一个候选仍为空时，保留原始响应返回，由 `complete()` 标记 `success=false`，上层继续执行现有失败保护。
4. 显式 `provider/model` override 继续只调用指定候选，不隐式进入全局备用链。
5. 现有 408、429、5xx 和 timeout fallback 行为保持不变。
6. HTTP 400、鉴权错误和其他非临时错误保持不 fallback，避免掩盖错误配置。

### 5.3 熔断状态语义

空正文属于“当前请求下候选结果不可消费”，不直接等同于供应商临时不可用。为避免群记忆任务打开全局熔断并影响普通聊天：

1. 空正文不增加 `_ModelFailoverState` 的临时故障计数。
2. 空正文不调用 `_record_primary_healthy()`，避免错误清零已有连续故障状态。
3. 当前请求允许立即 fallback，但不改变后续普通文本请求的起始候选。
4. 真正的 HTTP/网络临时故障继续使用现有连续失败、熔断、半开探测和恢复机制。

### 5.4 `complete()` 成功判定

调整 `_extract_text_response()`：

- 最终文本必须包含非空白字符，才返回 `success=true`。
- `content=""`、`content=[]`、缺少 choices/content 等无正文响应返回 `success=false`。
- 非空字符串、文本 block 列表和现有错误 envelope 保持兼容。
- 不改变工具调用响应的 Agent 流式解析路径。

### 5.5 Dream 失败诊断

当全部候选均没有可消费正文时，`MemoryDreamEngine` 从原始响应中提取有限、安全的诊断元数据：

- `model`
- `finish_reason`
- `completion_tokens`
- `reasoning_tokens`

失败原因建议格式：

```text
text model completion returned empty content (model=<model>, finish_reason=length, completion_tokens=800, reasoning_tokens=800)
```

限制：

1. 不记录 prompt、群消息、最终正文、`reasoning_content`、API Key、Header 或完整原始响应。
2. 继续使用现有 `failed_reason` 字段，最大长度保持现有 500 字符边界。
3. 不新增数据库迁移。

### 5.6 Trigger 告警

将群记忆失败 warning 调整为包含：

```text
room=<stable_room_id>
run=<run_id>
status=<status>
summary=<summary_status>
dream=<dream_status>
transient=<bool>
http=<status code or ->
reason=<bounded failure reason>
```

日志只输出已经过服务层收敛的失败原因，并做长度限制及换行清理。成功路径不新增高频日志。

### 5.7 游标、写入与重试保持不变

1. 主模型空正文、备用模型成功时，仅对备用模型结果执行既有 JSON、evidence、token 和群作用域校验。
2. 校验及写入成功后才推进当前群游标。
3. 所有候选失败时仍不推进游标、不写候选记忆。
4. trigger 继续使用现有退避时间，不增加后台线程或额外重试层。

5. 显式 Provider/model override、HTTP 400、鉴权错误及合法工具调用保持原行为。
6. 所有候选失败时，群记忆不推进游标、不写入任何记忆，并保留可读失败原因。
7. 群记忆 warning 可以直接识别 run、失败阶段、HTTP 是否存在和受限原因。
8. 日志、数据库和返回结果均不包含 `reasoning_content`、prompt、群消息正文或密钥。
9. Agent 流式推理、普通文本、会话标题和既有临时错误 fallback 回归通过。
10. 不新增配置项、数据库迁移、群记忆专属模型链或跨群访问面。

## 11. 风险与控制

### 11.1 空正文误判

风险：部分工具调用响应允许正文为空。

控制：首版检查只应用于同步且未声明工具的文本请求；包含合法工具调用的响应不进入该分支。

### 11.2 影响全局模型熔断

风险：将空正文计为临时故障会导致群记忆任务打开全局熔断，影响普通聊天。

控制：空正文只触发当前请求 fallback，不增加或清零共享临时故障计数。

### 11.3 额外模型请求

风险：主模型空正文后会立即调用下一候选，单次任务请求数增加。

控制：最多按用户已配置候选数量各调用一次，不增加外层重试；成功后游标推进，避免当前每 10 分钟无限重复消耗。

### 11.4 日志泄露

风险：直接记录 raw response 可能包含推理、群消息或供应商内部信息。

控制：只提取白名单元数据和现有安全失败原因，限制长度、去除换行，禁止输出 raw、prompt 和 reasoning 正文。

### 11.5 提高 token 上限的诱惑

风险：单纯提高 800/1600 上限会增加成本，且无法保证模型在新上限内生成最终正文。

控制：本计划不调整 token 配置；优先使用已经验证可工作的备用模型链。
