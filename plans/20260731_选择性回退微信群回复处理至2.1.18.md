# 选择性回退微信群回复处理至 2.1.18 计划

## 1. 用户目标

撤销自 `44ed6819` 起围绕微信群思考泄漏、协议标签泄漏和中间结果误判所做的多轮处理，恢复到 `v2.1.18` 时期的回复处理逻辑，同时避免整体回退仓库和撤销同期无关功能。

## 2. 已验证事实

- `v2.1.18` 使用逐段正则处理 `<think>...</think>`，无法可靠处理标签跨 SSE 分片。
- `v2.1.18` 不识别 `<thinking>`、`<send>`、`<message>`、文本化 `<tool_calls>`、`</s>` 等 Provider 标签或残片。
- `v2.1.18` 与当前通用 Agent loop 都采用“正文非空且无原生工具调用即结束”的规则，因此仍会把“让我继续看看”等中间过程文本当成最终答复。
- `v2.1.18` 到 `44ed6819` 之间的 `172d6f69` 只更新发布计划，没有修改运行时代码，可以把 `ea131ea0` 作为准确行为基线。
- 后续提交同时加入了候选请求快照、坏工具调用拒绝、候选完整缓冲、发送确认和上下文隔离。整提交回退会撤销这些与文本泄漏并非同一层面的安全能力。

结论：精确恢复 `v2.1.18` 行为可以撤销近期实现，但不能从代码层解决当前三类反馈；当前反馈样本在该旧逻辑下仍会通过。

## 3. 可选回退口径

### 方案 A：精确行为回退

在当前架构中恢复 `v2.1.18` 的输出接受规则：

- 恢复旧的 `<think>` 正则过滤语义；
- 删除微信群严格 `<final_response>` / `<send>` 候选协议；
- 删除已知 Provider 协议残片拒绝；
- 恢复候选一旦产生普通正文即直接进入 AgentStream 的行为；
- 保留当前 V2 会话、归档、发送确认和其他无关功能，避免全仓库回退。

预期：最接近用户要求的旧行为，但三类现有问题均可能继续出现，不建议直接发布到生产环境。

### 方案 B：选择性行为回退

恢复 `v2.1.18` 的简单回复流程，但保留确定性、非语义猜测型安全边界：

- 保留标准 `reasoning_content` 隔离和跨分片结构化思考解析；
- 保留不可变请求快照、候选完整缓冲、坏工具调用拒绝和发送确认；
- 移除近期复杂的最终答复 XML 协议依赖；
- 在统一 Provider 响应边界精确清洗已知控制块和标签残片，包括 `</s>`、`</analysis>`；只要清洗后仍有可发送正文，就接受当前候选并保持主模型健康，不因标签本身切换备用模型；
- 为工具成功后的轮次增加明确完成状态验证，避免把中间过程文本直接作为最终结果；
- 不恢复“用户要求”“我应该”“让我看看”等自然语言正则。

预期：不是逐字节恢复 `v2.1.18`，但可以减少近期协议复杂度，同时继续处理当前三类问题。

## 8. 剩余风险

- 未连接真实微信群做 Provider canary；发布后仍需观察实际主备模型是否持续把标准 reasoning 与最终 `content` 分离。

- 不支持 `lightagent_finish` 的模型会额外产生一次最终答复请求；首段纯文本保持隐藏，但第二次结果的语义质量仍依赖模型遵循最终答复提示，服务端不使用自然语言正则猜测正文含义。

## 9. v2.1.26 线上回归与修正方案

只读远端日志确认，多种正常工作的自定义模型在贴纸搜索和发送工具完成后返回了纯文本，但没有调用内部 `lightagent_finish`。路由层把每个候选都判为 `missing required finish tool call`，最终生成 422 技术错误并发送到群里。

修正边界：

- 缺少 `lightagent_finish` 不再表示模型或候选故障，不得因此切换备用模型或产生 422；
- 支持该内部工具的模型继续一次完成最终答复；
- 不支持的模型返回纯文本时，第一次文本不进入消息事件、Agent 历史或渠道发送；
- 在当前候选仍健康的前提下追加一次临时最终答复提示，并以不强制 `lightagent_finish` 的请求重试；临时提示在调用后从历史删除；
- 重试仍可继续调用真实工具；只有重试得到的纯文本或原生完成工具正文才能作为最终结果。
