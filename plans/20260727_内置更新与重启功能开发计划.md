## 复审修订摘要

本轮在原计划基础上补充了以下必须先解决的合同，避免出现“本次更新成功、下次开机却回到旧 Python”或“代码恢复后数据库已无法回退”等问题：

1. 将完整更新范围从所有 `git_source` 收紧为 `managed_git_source`，新增稳定 Launcher、运行时档案和一次性迁移门槛。
2. 把 `run.sh`、`scripts/run.ps1`、`scripts/start.sh`、`scripts/shutdown.sh` 以及外部 Supervisor 纳入启动合同，不再只改 CLI。
3. 正式 GitHub Release 是发布就绪信号；原始标签只用于辅助发现和 SHA 核对，不能单独证明该版本已通过发布门禁。
4. 状态文件仍放数据根，候选源码和持久 venv 分离到主工作树外的安装级目录；venv 必须直接创建在最终稳定路径，不能创建后移动。
5. 候选项目使用非 editable 安装，避免清理候选 worktree 后留下失效的 `.pth` 或入口脚本。
6. 增加操作租约、Relay 一次性交接令牌、切换日志和启动恢复规则，填补文件锁释放瞬间的竞态。
7. 增加只允许本机、一次性令牌保护的 readiness 协议，Relay 必须核对目标版本、提交 SHA 和新 `boot_id`，不能只探测 `/auth/check`。
8. 增加 `quiescing`/`drain_blocked` 状态，重启前停止接收新任务并等待 Agent、SSE、工具调用、消息发送和 scheduler 到安全点。
9. 首期不提供“立即取消依赖安装”；准备任务接受后在后台运行到安全终态，避免伪装成可随时中断的操作。
10. 自动恢复仅承诺代码与运行时层面的受控恢复；目标 Release 必须声明数据迁移向后兼容，否则 Web 自动更新直接阻止。
11. 补充浅克隆、detached HEAD、submodule、Git LFS、自定义 filter/hook、网络文件系统和多 worktree 的支持边界。
12. 补充磁盘估算、失败清理、保留上限、Windows 长路径和 venv/Node 目录锁测试。

## 一、结论先行

本功能不能直接把现有 `lightagent update` 绑定到 Web 按钮，也不能原样照搬 `sub2api` 的单二进制替换逻辑，原因如下：

1. LightAgent 是 Python 源码、Python 依赖、Web 静态资源和微信群 Node.js sidecar 的组合，不是单个可原子替换的二进制。
2. 当前 `lightagent update` 会先停止服务再执行 `git pull`；拉取或依赖安装失败时可能无法自动恢复，而且 Linux 路径没有严格检查每个依赖安装命令的返回码。
3. 当前版本源不一致：`cli/VERSION` 为 `2.1.2`，`desktop/package.json` 为 `2.1.3`，`pyproject.toml` 为 `1.0.0`；当前 Git 最近标签与最新稳定 Release 已为 `v2.1.6`，但该标签内上述三个版本值仍分别为 `2.1.2`、`2.1.3` 和 `1.0.0`。若直接比较文件版本，会持续误报。
4. GitHub `releases/latest` 已可返回 `v2.1.6`，但 Release 没有更新 manifest 或独立源码 Assets，标签为 annotated 但 `unsigned`。首期可把正式 Release 作为“已发布”门禁，并校验标签最终提交；不能把这描述为发布者签名或完整供应链验证。
5. Docker 设计明确要求 `/app` 随镜像升级且不持久化。容器内覆盖源码会在容器重建后丢失，并破坏镜像不可变约束；默认挂载 `/var/run/docker.sock` 又等价于向应用开放宿主机高权限，不可接受。
6. 现有 `self-restart` 仅支持 Unix，且依赖 `.lightagent.pid`。直接用 `python app.py`、旧脚本、Windows、外部 Supervisor 和 Docker 启动都需要不同的、可被能力检测的重启策略。
7. 即使候选 venv 成功拉起新版本，如果后续开机仍由旧 Python 或旧 systemd `ExecStart=python app.py` 启动，新依赖也会丢失，因此“持久启动合同”必须先于 Web 更新动作落地。

因此，推荐采用“两阶段更新”而不是“边运行边覆盖源码”：

```text
登录后检查正式稳定 Release
  -> 下载并在隔离目录准备候选版本
  -> 校验 Release、目标提交、候选运行时和 sidecar
  -> 状态变为 ready_to_restart，当前服务仍运行旧版本
  -> 用户点击“重启并完成更新”
  -> 应用停止接收新任务并排空进行中工作
  -> 独立 Relay 接管租约、切换 Git 版本与 active runtime
  -> 通过受管 Launcher 启动候选运行时
  -> readiness 核对版本、SHA 与 boot_id：提交新版本
  -> 启动失败且数据兼容：恢复旧提交和旧运行时
```

这仍满足“一键更新，然后再次操作重启”，同时把停机窗口和失败范围压缩到最后的版本切换阶段。

## 二、目标与非目标

### 2.1 目标

1. Web 控制台侧栏版本入口可检查最新稳定版，并明确显示当前版本、目标版本、部署方式和可执行能力。
2. 对满足条件的受管官方 Git 源码部署，用户点击一次即可在后台完成下载、候选运行时构建和预检。
3. 更新准备成功后，用户通过第二个明确动作“重启并完成更新”使新版本生效。
4. 更新、重启、失败和恢复状态可持久化；刷新页面或关闭后重新打开，不丢失当前进度。
5. 更新过程中不覆盖 `config.json`、`LIGHTAGENT_DATA_DIR`、`agent_workspace`、用户技能、用户插件、记忆、知识库、数据库、微信登录态和媒体数据。
6. 准备失败时旧服务保持在线；版本切换后失败时，仅在发布 manifest 声明数据向后兼容且切换日志仍满足恢复条件时，自动恢复旧提交和旧运行时。
7. Web、CLI 共用同一更新核心、锁和状态，不再维护两套更新逻辑。
8. Windows 与 Linux 的受管源码部署均有可验证的重启实现，并通过“模拟机器重启”验证 active runtime 持久生效；不支持的环境必须返回真实的 `can_restart=false`。
9. Docker、桌面端、源码包等部署模式返回准确能力和可执行的人工指引。
10. 所有破坏性接口必须经过 Web 登录、CSRF/同源校验、操作确认和全局互斥锁。
11. Web 宽屏侧栏和移动端顶栏持续提示新版本；每个目标版本首次发现时额外给出一次非阻塞通知。

### 2.2 非目标

1. 首期不做无人值守自动安装，只自动检查，不自动下载、不自动重启。
2. 首期只跟踪稳定 `vX.Y.Z` 标签，不支持 nightly、master、beta、rc 或自定义更新通道。
3. 首期不提供任意版本选择或手动降级 UI；只保留更新失败时的内部自动恢复能力。
4. 不允许用户在 UI 中输入仓库地址、下载 URL、Shell 命令或目标 Git ref。
5. 不在应用容器中执行 `docker pull`、`docker compose`、`sudo`、`apt` 或宿主机命令。
6. 不默认挂载 Docker Socket，不引入 Watchtower 或其他拥有宿主机容器控制权的第三方服务。
7. 不修改微信群、模型、Agent、记忆、技能或消息主链路。
8. 不重复实现桌面端更新 UI；现有 Electron 更新器继续负责安装包更新和应用重启。
9. 不在首期引入多节点滚动升级、集群协调或远程运维编排。
10. 首期不提供准备任务的即时取消 API；关闭页面只停止前端轮询，不中断后台准备。
11. 首期不把普通“随时重启服务”扩展为独立运维功能；重启动作只用于激活 `ready_to_restart` 的已准备更新。
12. 首期不自动修改 systemd、launchd、Windows Service 或第三方 Supervisor 配置；不满足受管启动合同时只给迁移指引。

### 3.2 现有缺陷需要先修正

1. 文档声称 `lightagent update` 在 `git pull` 失败时“服务不受影响”，但实际代码先执行 `stop()`，行为与文档不一致。
2. `subprocess.call()` 的依赖安装结果未全部转成失败状态，可能在依赖安装失败后仍继续启动。
3. Windows 更新通过项目根目录临时 `.bat` 和可见窗口执行，Web 场景无法可靠获取状态，也不适合无交互服务器。
4. Unix `self-restart` 在没有 PID 文件时使用 `old_pid=0`，会启动第二个实例并与原端口冲突。
5. `/api/version` 仅返回字符串，无法区分源码、Docker、桌面或打包部署。
6. 没有更新互斥锁、幂等操作 ID、可恢复状态文件和更新专用日志。
7. 当前没有更新前 Git 工作区清洁度、官方仓库身份、快进关系、写权限、磁盘空间或依赖变更检查。
8. `run.sh` 和 `scripts/run.ps1` 各自维护更新逻辑；`scripts/start.sh` 仍直接执行系统 `python3 app.py`，会绕过候选 venv 与 active runtime。
9. 当前官方安装脚本使用 `git clone --depth 10`，不能把所有 shallow clone 一概宣称支持，也不能在未证明祖先关系时快进。
10. 当前安装未记录运行时依赖档案；Playwright、语音和其他按需安装包可能在切换到全新 venv 后消失。
11. 当前多个 SQLite 存储会在启动时增量建表或加列，旧代码能否读取新版本写过的数据没有统一发布门禁，自动代码回退并不等于数据可回退。
12. 当前 Release 标签未签名，Python 依赖也未完全锁定；固定 GitHub 仓库和提交 SHA 只能提供来源约束与传输一致性，不能声称端到端供应链验证。

## 四、参考项目调研结论

参考快照：`Wei-Shaw/sub2api@dc893dd0b8eab41df5be595ae9fcd1aa74a062b8`，调研日期为 2026-07-27。

重点参考文件：

- `backend/internal/service/update_service.go`
- `backend/internal/handler/admin/system_handler.go`
- `backend/internal/pkg/sysutil/restart.go`
- `frontend/src/api/admin/system.ts`
- `frontend/src/components/common/VersionBadge.vue`

### 4.1 应吸收的设计

1. 检查、执行更新、重启是三个独立动作，更新完成后明确返回 `need_restart`。
2. UI 以版本徽标为入口，显示检查中、可更新、更新中、待重启、重启中和失败重试等状态。
3. 只对具备明确启动/恢复合同的构建开放按钮，其他源码构建显示迁移说明而不是假装支持。
4. 更新下载固定官方仓库，限制受信域、HTTPS 和最大响应体，并把 Release 标签最终指向的 commit SHA 与 Git fetch 结果做一致性核对。
5. 新产物在同文件系统临时目录准备，替换失败时恢复备份。
6. 使用全局系统操作锁和幂等键，避免重复点击导致并发更新、回滚或重启。
7. 长时间更新不依赖浏览器连接是否持续存在。
8. 重启响应先返回给浏览器，再异步停止进程；浏览器倒计时并轮询健康状态后刷新。
9. 网络检查失败可回退到上次缓存，但必须带 `warning`，不能把缓存结果伪装成实时结果。

### 4.2 不应照搬的部分

1. `sub2api` 原子替换的是单个 Go 二进制；LightAgent 必须同时处理源码、Python 依赖、Web 静态资源和可选 Node.js 依赖。
2. 参考项目通过 Linux 进程退出依赖 systemd 自动拉起；LightAgent 还要覆盖 Windows、CLI daemon、直接运行和 Docker。
3. 参考前端对更新请求最长等待 15 分钟；LightAgent Web 使用 web.py 线程池，首期应改为后台 Job + 状态轮询，避免长期占用请求线程。
4. 参考重启工具在非 Linux 下只记日志并返回成功。LightAgent 必须提前返回 `can_restart=false`，不能让 UI 进入虚假倒计时。
5. 参考项目可在 Docker 容器可写层替换二进制；这与 LightAgent 已确认的 `/app` 镜像不可变约束冲突，不采用。
6. 参考项目提供人工选择历史版本回滚；用户本次未要求该能力，首期不增加此 UI，只做失败自动恢复。

## 五、部署能力矩阵

服务启动时生成一次部署能力快照，API 和 CLI 共用，不由前端猜测。部署模式与启动模式分开判断：有 `.git` 只说明源码形态，不代表具备受管更新能力。

| 部署模式 | 识别依据 | 检查更新 | 一键准备更新 | Web 重启 | UI 行为 |
| --- | --- | --- | --- | --- | --- |
| `managed_git_source` | 官方 Git 工作树 + Launcher 标记 + active runtime/profile 完整 + 本地受支持文件系统 | 支持 | 满足 Release/Git/依赖预检后支持 | 仅激活已准备更新 | 完整两阶段流程 |
| `unmanaged_git_source` | 有官方 `.git`，但由 `python app.py`、旧脚本或未知 Supervisor 启动 | 支持 | 不支持 | 不支持 | 显示版本、阻塞原因和一次性迁移命令 |
| `external_supervisor` | 显式声明外部管理，但未验证其 `ExecStart` 使用 Launcher | 支持 | 首期不支持 | 首期不支持 | 显示 Supervisor 合同要求 |
| `docker` | `LIGHTAGENT_DEPLOYMENT=docker`，启发式仅作兼容 | 支持 | 不支持 | 不属于本计划 | 显示版本、两步升级命令和原因 |

| `packaged` | PyInstaller/frozen，非 Desktop | 支持 | 无官方通用产物时不支持 | 不支持 | 显示下载页 |

## 六、核心架构设计

### 6.1 统一版本与构建元数据

新增 `common/version.py` 作为运行时唯一入口，提供：

```python
get_version_info() -> {
    "version": "2.1.6",
    "display_version": "2.1.6",
    "revision": "aab8760e...",
    "dirty": False,
    "source": "git_tag|version_file|build_env",
    "deployment": "managed_git_source|unmanaged_git_source|external_supervisor|docker|desktop|packaged|source_archive|unknown",
}
```

解析优先级：

1. CI/镜像显式注入的 `LIGHTAGENT_VERSION` 与 `LIGHTAGENT_REVISION`。
2. Git 源码部署读取最近稳定标签和当前提交；精确位于标签时显示标签版本，标签之后的提交显示 `版本+短 SHA`，本地修改另加 `dirty=true`。
3. 非 Git 构建读取 `cli/VERSION`。
4. 无法识别时返回 `0.0.0` 和明确的 `source=unknown`，不参与自动更新。

同步修改：

1. `cli/__init__.py` 只转发统一版本入口，不再自行读文件。
2. `pyproject.toml` 改为从 `cli/VERSION` 动态读取版本，消除硬编码 `1.0.0`。
3. 标签构建以 Git Tag 为发布版本；CI 必须在构建 Python 后端、Docker 和 Desktop 之前先写入统一版本，不能在 PyInstaller 完成后才改 `package.json`。
4. 向 Docker 和 Desktop 后端注入版本、提交 SHA 和部署模式；发布流水线增加一致性断言，任一产物不一致时不得发布正式 Release。
5. 历史标签中的错误 `cli/VERSION` 不重写；源码部署通过 Git Tag 识别真实当前版本。

### 6.2 更新服务

新增 `common/update_manager.py`，并先建立以下两个前置合同。

#### A. 受管启动合同

1. 新增只依赖 Python 标准库的 `cli/runtime_launcher.py`，所有官方源码启动入口最终都由它读取 `active-runtime.json` 并启动指定 Python 与项目根 `app.py`。
2. Launcher 设置 `LIGHTAGENT_MANAGED_RUNTIME=1`、`LIGHTAGENT_INSTALLATION_ID` 和本次 `boot_id`；应用同时核对当前 `sys.executable`、项目根和 active runtime，不能只信一个可伪造环境变量。
3. `run.sh`、`scripts/run.ps1`、`scripts/start.sh`、`scripts/shutdown.sh` 改为 Launcher/CLI 的薄封装；删除各自的 `git pull + pip install` 更新分支和直接后台启动 fallback。
4. `python app.py`、`python app.py --cmd`、`lightagent start --foreground` 和 terminal-only 交互运行保留为开发/前台入口，但能力固定为 unmanaged/interactive unsupported，不能从 Web 执行完整更新或重启激活，因为 Relay 无法恢复原 TTY。
5. systemd、launchd、Windows Service 和第三方 Supervisor 只有在其启动命令明确调用 Launcher 且通过启动自检后，后续版本才可单独开放；首期不自动编辑这些系统配置。
6. 现有安装通过一次性 `lightagent runtime adopt` 建立受管 venv、安装 ID 和运行时档案；迁移验证失败时保持原启动方式并只开放版本提示。
7. 每次成功更新后必须完全停止服务，再分别通过官方 Linux/Windows 启动入口重新启动，证明机器重启后仍使用目标 venv，而不只是 Relay 本次启动成功。

#### B. 运行时依赖档案

1. `runtime-profile.json` 记录 Python 实现/版本、基础依赖清单哈希、受支持的可选依赖组、Playwright 安装状态和 sidecar 状态；不记录 pip 凭据、代理口令或完整环境变量。
2. `runtime adopt` 只迁移可识别的官方依赖与已知按需能力；本地路径包、私有 VCS 依赖或无法重建的未知包使完整更新保持禁用，并给出人工迁移指引。
3. 候选 venv 按档案重建并执行 `pip check`；不能只安装 `requirements.txt` 后假定语音、文档解析或浏览器能力仍存在。
4. `lightagent install-browser` 及后续官方按需安装入口必须同步更新运行时档案，否则下一次候选运行时会丢失该能力。
5. 当前 `requirements.txt`/`requirements-optional.txt` 未完全锁定且存在版本约束冲突风险；在依赖合同整理完成前，不得把候选成功描述为可复现供应链构建。

`UpdateManager` 集中承担以下职责：

1. 固定查询 `yideng966/LightAgent` 的正式、非 draft、非 prerelease GitHub Release，拒绝任意仓库、URL 和 ref。
2. 使用严格正则接受 `v<major>.<minor>.<patch>`；按语义版本比较，不依赖 API 返回顺序。若最新 Release commit 是当前 HEAD 的祖先，则返回 `ahead_of_release`，绝不把开发分支回退到标签。
3. 解析 Release 标签对象并取得最终 commit SHA；从固定官方 HTTPS 仓库 fetch 到临时 refs 后再次 peel 和核对，不覆盖本地同名标签。
4. 请求设置连接/读取超时、User-Agent、ETag、最大响应体和缓存；成功结果缓存 20 分钟，404/限流/网络失败等负结果最多缓存 60 秒，手动检查绕过本地 TTL 但仍可使用 ETag。重定向关闭或逐跳限制在 GitHub 官方 HTTPS 域。
5. GitHub API 失败时保留最近一次成功缓存并标记 `stale=true`；没有缓存时返回检查失败，不返回“已是最新版”。原始标签可作诊断 fallback，但不能单独令 `can_update=true`。刚发布的 Release 必须能在负缓存过期或手动检查后被发现。
6. 只接受唯一同名 Release Asset `lightagent-update-manifest.json`（限制 64 KiB）；核对版本、revision、最低 updater/Python 版本、支持的来源版本和数据回退兼容性。发布链应先在 draft 中上传 manifest 再公开 Release，已公开 manifest 不允许 `--clobber` 静默替换。manifest 缺失/重复时仍可提示新版本，但 Web 一键更新保持禁用；生成脚本在未提供显式兼容声明时默认输出 `auto_update=false`，不能乐观放行。
7. 识别部署模式、启动合同和更新/重启能力。
8. 执行 Git 形态、仓库身份、快进关系、磁盘、写权限、Python venv、运行时档案、Node/npm 和依赖变化预检。
9. 管理后台 Job、全局文件锁、持久租约、原子状态、切换日志、候选目录和更新日志。
10. 生成 Relay 所需的不可变交接清单，不直接从 Web 请求线程停止进程。

Release 已存在并不等于标签经过密码学签名。首期默认信任边界是 GitHub 官方仓库、TLS、正式 Release 和精确 commit SHA 一致性；API 返回 `verification_level=github_release_and_commit`，不得使用 `signature_verified` 等误导字段。是否增加内置公钥签名 manifest 见第十三节。

所有 Git、Python、pip、npm 命令必须使用参数数组和 `shell=False`；Git 自动化操作禁用本地 hooks，拒绝 submodule、LFS 和自定义 filter/smudge 场景。仓库 URL、标签格式、目标 SHA、cwd 和环境变量均由服务端构造。pip/npm 安装仍会执行受信 Release 依赖的构建或生命周期代码，隔离目录只是故障隔离，不是安全沙箱。

### 6.3 持久化布局

状态与大体积产物分离：状态放在 `get_data_root()/updates/<installation-id>`；源码部署默认数据根可能是项目根，因此同步把 `/updates/` 加入 `.gitignore`。候选源码、持久 venv 和 sidecar staging 必须位于主工作树外的安装级 artifact root，默认优先使用项目父目录下的受控兄弟目录；不可写、跨卷不支持原子切换或路径过长时直接阻止，不静默回退到易被系统清理的临时目录。

```text
<data-root>/updates/<installation-id>/
  state.json                 # 原子写入的公开状态，不含密钥
  operation.lock             # 跨进程互斥锁
  operation-lease.json       # 所有者、心跳和过期时间，只存令牌摘要
  switch-journal.json        # HEAD/runtime/sidecar 切换阶段与恢复依据
  update.log                 # 轮转的更新专用日志，敏感信息脱敏
  active-runtime.json        # 当前/上一运行时、项目根与提交信息
  runtime-profile.json       # 可重建的依赖与能力档案
  operations/<operation-id>/
    handoff.json             # 不含密钥的 Relay 交接数据
    handoff.token            # 用户权限限定、一次性、成功后删除
    ready.token              # readiness 一次性令牌
    previous.json            # 旧提交、旧运行时、旧 sidecar 备份指针

<artifact-root>/<installation-id>/
  operations/<operation-id>/
    candidate/               # detached linked worktree
    sidecar-node_modules/    # 仅 lock 变化且需要 sidecar 时准备
  runtimes/<target-revision>/venv/  # 从创建起即为最终路径，不移动 venv
```

要求：

1. `state.json`、`active-runtime.json`、`operation-lease.json`、`switch-journal.json` 和 `handoff.json` 使用临时文件 + `os.replace()` 原子提交；关键切换记录在退出前 flush/fsync。
2. Unix 使用 `fcntl.flock`，Windows 使用经最小实验验证的 `msvcrt.locking`；网络文件系统或无法证明互斥语义的路径不开放 mutation。
3. 文件锁负责瞬时互斥，持久租约负责跨进程所有权。旧进程写入带摘要的一次性交接租约并保持心跳，Relay 回报 `accepted` 后等待旧锁释放再接管；其他 CLI/Web 进程看到有效租约必须拒绝操作。
4. 启动时不能把所有非终态 Job 一律标成 `interrupted`：有效 Relay 租约继续等待；租约过期后按 `switch-journal`、当前 HEAD、active runtime 和进程存活状态决定恢复、回滚或人工介入。
5. venv 不可可靠搬移，必须直接在 `runtimes/<revision>/venv` 创建；准备失败仅删除带本安装 ID marker 且不被 active/previous 指针引用的目录。
6. 只保留当前和上一个成功运行时、最多 2 个失败操作诊断，默认 7 天后清理；清理由成功启动后的后台任务执行，不在重启关键路径删除备份。
7. 清理前 canonicalize 路径并验证其位于 installation-scoped artifact root，禁止根据未经校验的 JSON 路径递归删除。
8. 预检可用空间至少覆盖候选源码、目标 venv、sidecar 依赖、上一运行时和安全余量；检查 Windows 路径长度、目录锁和杀毒软件导致的重命名重试。
9. 交接文件不持久化完整环境变量、API Key、Cookie、代理口令或 pip 凭据；目录权限不满足当前用户独占要求时禁止更新。
10. API 不返回候选目录、Python 路径、Git remote 或完整日志路径。

### 6.5 源码更新事务

#### A. 检查与预检

1. 确认 Web 密码已启用，当前会话通过鉴权。
2. 确认部署模式为 `managed_git_source`，当前进程确由 active runtime 对应的 Launcher 以非交互后台模式启动，且运行时档案完整；terminal-only/foreground 运行只提示版本。
3. 获取正式稳定 Release，严格解析版本，并取得 Release 标签最终指向的目标 commit SHA；Release/manifest 缺失或声明人工迁移时只提示、不准备。
4. 确认项目 remote 属于 `yideng966/LightAgent` 的标准 HTTPS/SSH 形式；实际 fetch 始终使用服务端固定官方 HTTPS URL和临时 refs，不使用本地 remote 中的任意 URL，也不修改 `origin`。
5. `git status --porcelain=v2 --untracked-files=all` 必须为空；被 `.gitignore` 忽略的配置和运行数据不阻塞，任何未忽略文件、暂存修改、未暂存修改、merge/rebase 状态或 index lock 都阻塞。
6. 首期只自动切换普通命名分支；detached HEAD 返回 `DETACHED_HEAD_UNSUPPORTED`。同仓库存在其他 linked worktree 不自动阻塞，但目标分支占用、锁冲突或异常 worktree 状态必须阻塞。
7. shallow clone 仅在从固定官方源有界 deepen/unshallow 后能严格证明 `HEAD` 是目标祖先时支持；证明失败返回 `SHALLOW_HISTORY_UNPROVEN`，不得按版本号猜测快进关系。
8. 当前 HEAD 必须是目标提交祖先才允许目标 Release commit 的快进；若目标是当前 HEAD 祖先则返回 `ahead_of_release`，分叉或同版本无祖先关系返回阻塞，均不自动回退。
9. 当前仓库或目标树含 submodule、Git LFS、`.gitattributes` 自定义 filter/smudge 时首期阻止；自动 Git 命令使用空 hooks 目录，避免执行本地 hook。
10. 检查项目根、状态根、artifact root 的写权限与文件系统语义，检查 `venv`、目标 Python 兼容性、磁盘估算和 Windows 路径长度。
11. 检查从当前提交到目标提交是否修改 `requirements.txt`、`requirements-optional.txt`、`pyproject.toml`、sidecar `package.json` 或 lock 文件；结合 runtime profile 计算实际需要重建的依赖组并展示给用户。
12. 预先创建受保护的旧提交 backup ref 和切换计划，但此阶段不移动当前分支、不覆盖工作树。

#### B. 隔离准备

1. 在 artifact root 的操作目录用目标 SHA 创建 detached linked worktree；不检出用户输入的分支或 ref。
2. 在 `runtimes/<target-revision>/venv` 直接创建候选 venv，不修改当前进程所用 Python，也不在完成后移动 venv。
3. 按 runtime profile 安装目标基础与已知可选依赖，执行 `pip check`，再从候选源码构建并做非 editable 安装；不得让入口脚本或 `.pth` 指向稍后会删除的 candidate worktree。
4. sidecar lock 文件变化且当前能力需要 sidecar 时，在隔离目录执行 `npm ci` 和现有 sidecar 测试。npm 生命周期代码属于受信 Release 执行边界，不得使用 Web 输入改变 registry、脚本或参数。
5. 执行候选源码 `compileall`、统一版本/manifest 断言和专用 `update probe`。probe 必须是无监听端口、无外部渠道登录、对真实用户数据只读的子进程；单纯 `import app` 不作为充分自检。
6. 每个子进程设置合理超时、独立进程组、返回码检查和脱敏日志；首期无用户即时取消，超时/失败后只终止候选子进程并清理未引用产物。
7. 记录旧提交 SHA、旧运行时 Python、目标 SHA、候选运行时、sidecar 备份位置、manifest 兼容结论和磁盘快照。
8. 准备成功后只写入 `ready_to_restart`，不修改当前工作树，不停止当前服务；关闭浏览器不影响后台 Job。

#### C. 重启时切换

1. `POST /api/system/restart` 只接受 `ready_to_restart`；立即返回 202 后由后台协调器进入 `quiescing`，停止接收新工作并等待活动任务排空。
2. 排空成功后生成一次性 handoff/ready token，写入 Relay 租约并启动独立 Relay；Relay 回报 `accepted` 后，旧进程才完成状态 flush 并请求主线程退出。
3. 排空超时进入 `drain_blocked` 并恢复接收工作，不杀进程。用户可等待后重试；只有超时后再次明确确认才能使用 `force=true`，并提示工具调用可能存在外部副作用。
4. Relay 接管操作锁和租约后，再次确认工作树干净、HEAD/分支未变化、目标 SHA 与准备记录一致，防止准备后用户修改代码。
5. Relay 先写 durable `switch-journal`，再使用只允许快进且禁用 hooks 的 Git 操作切换到精确目标 SHA；不执行普通 `git pull`，不跟踪移动中的 `master`。
6. 候选 Python 依赖已在准备阶段完成，停机窗口内不得再次运行 pip。原子更新 `active-runtime.json`，sidecar 依赖变化时再切换准备好的 `node_modules` 并保留上一份备份。
7. Relay 通过标准库 Launcher 使用候选 venv Python 启动当前项目根 `app.py`，继承原 `LIGHTAGENT_DATA_DIR` 和必要运行环境，但不把完整环境写入交接文件。
8. 新服务通过内部 readiness 协议返回目标版本、目标 SHA、目标 operation、预期新 `boot_id` 和核心启动状态；全部匹配才写 `succeeded`。
9. 成功后浏览器先探测 `/auth/check`，再用原登录态读取更新状态并刷新静态资源；清理候选源码和旧运行时由新进程后台执行。

#### D. 自动恢复

1. 新进程启动失败、readiness 超时或版本/SHA/`boot_id` 不匹配时，Relay 停止失败进程并读取 `switch-journal`。
2. 只有 manifest 声明向后兼容、预检时工作树干净、当前分支/HEAD/active runtime 仍由本操作控制时，才允许恢复旧提交；不可逆迁移版本在准备阶段已被阻止，不能到失败后才赌回滚。
3. 以预期值更新分支/工作树，恢复旧 active runtime 和 sidecar 指针，再通过 Launcher 启动旧版本；任何外部改动或状态不一致立即停止自动覆盖。
4. 旧版本 readiness 成功后写 `rolled_back`，UI 明确提示“更新失败，已恢复旧版本”；这表示运行时恢复，不夸大为所有外部副作用均已撤销。
5. 旧版本也无法启动时写 `recovery_failed`，保留候选、backup ref、切换日志和诊断 ID，显示只读人工恢复指引；不得继续循环重启。
6. 断电/Relay 崩溃恢复按 journal 阶段处理：切换前继续旧版本；HEAD 已切换且目标运行时完整时恢复目标启动；状态矛盾时禁止猜测并要求人工介入。

### 6.6 跨平台重启协调器

新增 `cli/update_relay.py` 与 `common/runtime_lifecycle.py`，并把 `cli/commands/process.py` 的启动、更新激活和状态命令改为复用统一 Launcher、租约和运行时状态。

#### 任务排空与应用退出

1. `RuntimeLifecycle` 维护 `accepting_work`、待处理/活动工作计数、排空 deadline 和 shutdown event；已入队消息、Agent/Chat 推理、工具执行、SSE 尾部、消息发送和 scheduler 派发接入同一计数合同。
2. `quiescing` 后新聊天/调度任务不再进入执行队列；排空开始前已经入队的消息继续执行并计入 pending，更新 status、readiness 和已在途响应仍可完成。scheduler 暂停取新任务，不把暂停误记为任务成功。
3. 默认等待 60 秒；到期不强杀，恢复 intake 并进入 `drain_blocked`。显式 force 只在该状态可用，并使用第二次确认。
4. 主循环不再由后台线程调用 `sys.exit()`；收到 shutdown event 后统一停止 scheduler、所有 Channel、SSE janitor/队列和 sidecar，保存用户状态并退出。Web Channel 最后停止，确保 202 和最后状态已发送。
5. Unix 信号也转入同一 lifecycle；Windows 优先使用应用内 shutdown request，Relay 仅在旧进程超时不退出时使用系统强制终止作为最后手段。

#### Linux/macOS 源码部署

1. Relay 使用 `start_new_session=True` 脱离父进程。
2. Relay 使用 handoff 中经 boot_id 核对的真实 PID，不再仅依赖 PID 文件。
3. 正常路径等待应用内 lifecycle 退出；超时后发送 `SIGTERM`，最后才使用 `SIGKILL`。
4. 按交接文件和 journal 切换、通过 Launcher 启动并执行 readiness。

#### Windows 源码部署

1. 使用隐藏窗口、独立进程组和 detached process flags 启动 Relay，不再弹出交互式 `.bat` 窗口。
2. Relay 先完成租约握手，再等待应用内 lifecycle 令旧 PID 退出。
3. Windows 终止、detached flags、venv 路径和目录锁行为在实现前依据 Python 官方文档与最小实验确认；强制 `taskkill` 仅为超时兜底。
4. 新进程沿用当前端口，浏览器通过轮询恢复。

#### 内部 readiness

1. 新增仅供 Relay 使用的 `/api/system/readiness`；只接受回环地址请求和 operation-bound 一次性令牌，不使用浏览器 Cookie，也不向远端公开无令牌健康信息。
2. 令牌保存在当前操作用户权限限定文件中，短时有效、常量时间比较、成功后立即失效；错误响应不泄露目标 SHA 或 token 状态。
3. readiness 至少证明配置已加载、Web listener 已接受请求、UpdateManager 可读取状态、版本/revision/operation/boot_id 全部匹配。外部 IM 是否在线作为降级诊断，不作为核心进程存活的必要条件。
4. `/auth/check` 仅供浏览器判断登录服务恢复，不能替代 Relay readiness。

#### Docker

1. 官方 Compose 显式设置 `LIGHTAGENT_DEPLOYMENT=docker`。
2. Docker 内更新能力始终为 false；页面分两行给出 `docker compose pull` 和 `docker compose up -d` 指引。
3. 首期不从 Web 提供普通容器重启按钮，也不依赖 `restart: unless-stopped` 冒充版本激活。
4. 非官方容器不能仅凭 `/.dockerenv` 假定可由宿主机自动拉起。

#### Desktop

1. `LIGHTAGENT_DESKTOP=1` 时后端返回 `MANAGED_BY_DESKTOP`。
2. Electron 已有 `checkForUpdate`、`downloadUpdate`、`installUpdate` 和 `quitAndInstall`，继续保持单一所有者。
3. 不从 Web 后端重启 Electron 管理的 Python 子进程，避免与 `PythonBackend.restart()` 竞争。
4. Desktop 内嵌 Web 控制台不重复显示本计划的版本通知，避免与 Electron 更新提示重复。

### 6.7 Web API

新增路由：

| 方法 | 路径 | 用途 | 主要返回 |
| --- | --- | --- | --- |
| `GET` | `/api/system/update/status` | 返回本地持久化状态和部署能力，不触发长任务 | 版本、能力、Job 状态、动作令牌 |
| `POST` | `/api/system/update/check` | 强制检查官方最新稳定版 | 当前/最新版本、缓存状态、发布信息 |
| `POST` | `/api/system/update/prepare` | 启动后台候选准备任务 | HTTP 202、`operation_id` |
| `POST` | `/api/system/restart` | 仅对 `ready_to_restart` 执行排空、重启与版本激活；`drain_blocked` 后可显式 force | HTTP 202、`operation_id`、排空状态 |
| `GET` | `/api/system/readiness` | Relay 本机一次性启动证明，浏览器不调用 | 目标版本、SHA、operation、`boot_id` |

保留 `/api/version` 作为兼容只读接口，但改由统一版本入口提供数据；不把高风险能力塞入该旧接口。

接口约束：

1. 除内部 readiness 外，全部新接口调用 `_require_auth()`；readiness 使用回环地址和一次性令牌的独立门禁。
2. `prepare`、`restart` 在未设置 Web 密码时返回 403 `WEB_PASSWORD_REQUIRED`，即使现有控制台允许无密码访问。
3. 破坏性 POST 校验同源 `Origin`/`Host`，并要求状态接口签发的短时 HMAC 动作令牌；令牌绑定当前认证 Cookie、`boot_id`、动作和过期时间。
4. 前端为每次 mutation 生成幂等键；后端对同键重试返回同一 `operation_id`。
5. 另一个操作持锁时返回 409 `UPDATE_ALREADY_RUNNING`，并附当前公开状态。
6. 后台 Job 与请求生命周期解耦；浏览器关闭、代理超时或网络闪断不会取消准备。首期不提供 cancel mutation，状态文案明确“可关闭窗口，任务将在后台继续”。
7. 状态轮询默认 1.5 至 2 秒，并在终态停止；页面隐藏时降低频率。
8. Release notes 在后端限制长度，前端以安全文本或既有受控 sanitizer 渲染；所有外链固定官方 HTTPS、使用 `noopener`，不信任 Release 正文 HTML。
9. 原始命令输出只写脱敏日志，API 仅返回稳定错误码、诊断 ID 和简短可行动信息；首期不新增原始日志下载接口。

### 6.8 Web UI 与交互

入口沿用现有侧栏底部版本区域，不新增独立导航页：

1. 把 `sidebar-version` 从外链改为语义化按钮，保留 `LightAgent vX.Y.Z` 文本。
2. 有新版本时增加非纯颜色的“更新可用”点和文字/tooltip；点击打开“系统更新”模态框。
3. 模态框复用现有 Web 控制台的色彩、边框、8px 以内圆角、Font Awesome 图标和深色模式，不引入新 UI 库。
4. 发布页作为模态框内的次要外链，不再让点击版本直接离开控制台。

新版本必须主动提示，不能要求用户先打开更新模态框才知道：

1. 用户登录成功且控制台初始化完成后，在后台自动执行一次带 20 分钟缓存的更新检查；该请求不阻塞聊天页和其他管理页面渲染。
2. 检测到新版本时，Web 宽屏布局的侧栏版本区域持续显示“可更新”文字和状态标记；不能只靠颜色或一个无文字圆点表达。
3. 移动端侧栏默认隐藏，因此在顶栏显示带 `aria-label` 的更新图标和状态标记，点击后打开同一个更新模态框。
4. 每个目标版本首次发现时显示一次非阻塞通知，例如“发现新版本 vX.Y.Z”，并提供“查看更新”动作；通知可自动收起，也允许用户立即关闭。Desktop 模式不重复显示该通知。
5. 非阻塞通知的已读状态按目标版本保存在浏览器本地。关闭通知后，侧栏或移动端顶栏的持久更新标记仍保留，直到更新完成、目标版本变化或后端确认已无更新。
6. 不自动打开模态框，不抢夺输入焦点，不中断正在进行的聊天、配置编辑或其他操作。
7. 检查失败时不显示“有新版本”或“已是最新版”的错误结论；仅在用户打开更新模态框时展示上次成功结果及检查失败提示。

模态框按状态展示：

| 状态 | 主信息 | 主动作 |
| --- | --- | --- |
| 初次打开 | 当前版本、部署方式 | `检查更新` |
| 检查中 | 明确 loading 和上次检查时间 | 禁用重复操作 |
| 已是最新 | 当前版本与成功状态 | `重新检查` |
| 领先 Release | 当前开发提交和最新正式 Release | `查看发布`，不显示更新按钮 |
| 有更新 | 当前/目标版本、Release 说明、依赖变化、预计影响 | `更新到 vX.Y.Z` |
| Release 未就绪 | 已发现标签/Release，但 manifest 或兼容声明不足 | `查看发布`，不显示更新按钮 |
| 环境阻塞 | 稳定原因和恢复建议 | 可修复后 `重新检查` |
| 准备中 | 步骤列表：Release、拉取、运行时、sidecar、验证；提示可关闭窗口 | 无取消按钮 |
| 待重启 | “更新已准备，重启后生效” | `重启并完成更新` |
| 排空中 | 活动任务数量和等待状态 | 无重复按钮 |
| 排空超时 | 尚有任务未结束，服务已恢复接收工作 | `稍后重试` / 二次确认后 `强制重启` |
| 重启中 | 倒计时、连接检测、当前阶段 | 无重复按钮 |
| 成功 | 新版本和启动结果 | 自动刷新页面 |
| 已自动恢复 | 失败原因摘要、当前仍运行旧版本、诊断 ID | `复制诊断信息` / `重试` |
| Docker | 当前/最新镜像版本和升级说明 | `复制升级命令` / `查看发布` |
| Desktop | 由桌面应用更新器管理 | 不显示后端更新按钮 |

交互要求：

1. 点击更新前使用专用确认内容，显示当前版本、目标版本、依赖是否变化和“不会自动重启”。
2. 点击重启前再次确认短时不可用；按钮使用重启图标并在执行后禁用。强制重启只在排空超时后出现，必须再次说明可能中断有外部副作用的工具调用。
3. 错误提示必须包含原因和恢复路径，不只显示“更新失败”。
4. 进度区域使用 `aria-live="polite"`；模态框具备 `role="dialog"`、`aria-modal`、标题关联、焦点锁定、Escape 关闭和关闭后焦点归还。
5. 按钮可触区域至少 44x44px，键盘可完整操作，焦点样式清晰。
6. 状态变化不改变模态框主要宽度，长版本号、错误和发布说明允许换行，不与按钮重叠。
7. 动画只使用 150 至 200ms 的 opacity/transform，并遵守 `prefers-reduced-motion`。
8. 同时验证 375px、768px、1024px、1440px，浅色和深色主题均需满足对比度。
9. 不修改 `chat.html` 中 `console.js` / `console.css` 的静态地址查询参数，继续由 `ChatHandler` 注入缓存时间戳。
10. 当前版本低于最新正式 Release 时，即使部署不支持一键更新，也必须保留“有新版本”提示和发布页入口；能力限制只影响动作按钮，不应隐藏版本事实。

- [ ] 实现只读、无监听、无外部登录的 `update probe`，替代仅 `import app` 的弱检查。
- [ ] 为所有子进程增加超时、进程组清理、返回码检查和日志脱敏。
- [ ] 浏览器断开后 Job 继续，刷新可恢复状态；不实现 cancel API。
- [ ] 实现空间估算、marker 路径校验、失败清理和 current/previous runtime 保留。

完成标准：当前服务和主工作树不变，候选不含临时 editable 路径，状态可稳定进入 `ready_to_restart`。

### Phase 4：实现任务排空、Relay、readiness 与恢复

- [ ] 为 lifecycle intake 门禁、活动计数、scheduler 暂停、全渠道关闭顺序和 drain timeout 写测试。
- [ ] 实现 `quiescing -> drain_blocked`；默认超时恢复服务，force 仅在二次确认后可用。
- [ ] 实现旧进程到 Relay 的一次性 token、租约握手和锁接管，覆盖交接窗口竞争者。
- [ ] Linux/macOS Relay 覆盖应用内退出、SIGTERM 和最终 SIGKILL；Windows 使用隐藏 detached 进程及应用内退出，`taskkill` 仅兜底。
- [ ] 切换前二次核对 HEAD/工作树，写 durable journal，停机窗口内不再运行 pip。
- [ ] 实现回环地址 + 一次性令牌 readiness，验证目标版本、SHA、operation 和新 `boot_id`。
- [ ] 注入 Relay 崩溃、断电阶段、启动失败、端口失败、版本不匹配、token 重放和旧版本恢复失败。
- [ ] 仅对 manifest 声明向后兼容的版本执行自动恢复；状态矛盾时停止覆盖并给人工指引。

完成标准：新版本 readiness 成功才提交；机器重启后仍使用目标 runtime；失败恢复不覆盖外部新修改，也不会无休止重启。

### Phase 5：接入受保护 Web API

- [ ] 新增 Handler 测试，覆盖未登录、未设密码、CSRF 错误、重复请求、并发锁和有效租约。
- [ ] 注册 status/check/prepare/restart 与内部 readiness 路由；首期无 cancel 路由。
- [ ] 所有长任务返回 202 + `operation_id`，不占用 Web 请求线程。
- [ ] readiness 严格限制回环、一次性 token、有效期和 operation/boot 绑定。
- [ ] `/api/version` 改用统一版本入口并保持旧响应字段。
- [ ] Release notes 限长并安全渲染，错误映射为明确 HTTP 状态、稳定原因码和诊断 ID。

完成标准：仅合法同源登录用户能准备/激活更新；重复点击不会启动第二个操作；Relay 内部证明不能被远端或旧 token 调用。

### Phase 6：实现 Web 更新提示与模态框

- [ ] 登录后后台自动检查正式稳定 Release，不阻塞控制台初始化或聊天操作。
- [ ] 改造版本入口，并增加 Web 宽屏侧栏、移动端顶栏的持久更新提示。
- [ ] 每个目标版本首次发现时显示一次可关闭、可操作、不抢焦点的非阻塞通知；Desktop 模式抑制重复通知。
- [ ] 增加 Release 未就绪、unmanaged 迁移、准备中、排空中、排空超时、恢复失败等完整状态。
- [ ] 增加更新确认、重启确认和 force 二次确认，绝不自动重启。
- [ ] 增加 Docker 两步命令复制、Desktop 管理提示和阻塞原因恢复建议。
- [ ] 增加中英文 i18n；日文沿用项目现有 Web 控制台语言策略处理。
- [ ] 完成键盘、焦点、aria-live、reduced-motion、长文本和移动端适配。

完成标准：有新版本时用户无需打开模态框即可获知；能力限制只禁用危险动作，不隐藏版本事实；页面重载和网络闪断不会产生重复 mutation。

### Phase 7：Docker、发布链与文档闭环

- [ ] Dockerfile/Compose 注入明确部署、版本和 revision 元数据。
- [ ] 测试并文档化 Docker `can_update=false`，命令分两步展示，不挂载 Docker Socket。
- [ ] 在现有已提交 Release 工作流上增加 manifest、版本前置写入和发布就绪门禁，避免重复或覆盖当前自动发布逻辑。
- [ ] 验证正式 Release、目标 tag commit、Docker version tag 和 manifest revision 一致。
- [ ] 修正文档中“先拉取再停止”和直接启动可完整更新等错误描述。
- [ ] 更新中、英、日升级文档和 CLI 文档。
- [ ] 实施代码时更新 `CHANGES.md`，并回写本计划的实际改动、验证和剩余人工验收。

完成标准：用户不会把 Docker 指引误解为容器内更新；发布链只在一致性与兼容门禁通过后暴露可自动更新版本。

## 十、风险与控制措施

| 风险 | 影响 | 控制措施 |
| --- | --- | --- |
| 版本或发布源继续漂移 | 误报、半发布版本被更新 | 统一版本入口；正式 Release + manifest + tag commit + 产物一致性门禁 |
| Release 存在但标签未签名 | 误把 SHA 一致性当发布者签名 | API 明示 `github_release_and_commit` 信任级别；是否增加签名 manifest 作为实施前决策 |
| Python/npm 依赖未完全锁定 | 构建结果随时间变化、供应链风险 | runtime profile、lock 文件、`pip check`、候选验证和残余风险明示；不宣称可复现构建 |
| pip/npm 安装执行受信代码 | 候选阶段仍可访问当前用户资源 | 仅正式官方 Release、固定参数和最小权限用户；明确隔离不是沙箱，后续签名/锁定单独加强 |
| 本次更新成功但下次启动回旧 Python | 新依赖缺失、开机失败 | 只对受管 Launcher 开放；active runtime 原子指针；更新后模拟机器重启验收 |
| 运行时档案漏掉按需能力 | 浏览器、语音或文档能力更新后消失 | adopt 已知能力；官方安装入口同步 profile；未知私有/本地包阻止自动迁移 |
| 本地改动被覆盖 | 用户代码丢失 | dirty/untracked 预检、只允许快进、切换前二次核对 |
| shallow/detached/submodule/LFS/filter 误处理 | 祖先误判或执行本地扩展代码 | 有界深化后证明祖先；首期阻止不支持形态；禁用 hooks；临时 ref 核对 SHA |
| 依赖安装破坏旧环境 | 旧服务无法恢复 | 候选独立最终路径 venv、非 editable 安装，旧运行时保留到 readiness 成功 |
| 文件锁到 Relay 之间出现空窗 | 并发操作接管同一工作树 | 文件锁 + operation lease + 一次性 handoff + 心跳 + journal，竞争者见有效租约即拒绝 |
| 浏览器/代理断开 | 用户误以为任务已取消或重复发起 | 后台 Job 与 HTTP 生命周期解耦，刷新恢复同一 operation；首期不提供伪即时 cancel |
| 活动 Agent/工具被重启打断 | 消息丢失或外部副作用不确定 | quiescing、统一活动计数、超时恢复 intake；force 仅二次确认并明确风险 |
| 新版本写入不可逆数据后回滚 | 旧代码无法读取数据库/配置 | Release manifest 与 CI 兼容门禁；不可逆迁移禁止 Web 自动更新；恢复承诺限定为受控运行时 |
| Windows 父子进程同死或目录被锁 | 无法拉起/切换 sidecar | 应用内退出、隐藏 detached Relay、目录锁重试、真机与杀毒软件场景测试 |
| Relay 崩溃或切换时断电 | 服务停机、状态不确定 | durable switch journal、Launcher 启动恢复、阶段故障注入；矛盾状态停止自动覆盖 |
| readiness 只证明端口存活 | 错版本被误判成功 | 回环一次性 token，同时核对 Release revision、operation 和新 boot_id |
| 候选/venv/Node 占满磁盘 | 准备或恢复失败 | 预估空间 + 安全余量、稳定 artifact root、current/previous 保留、失败数量/时限清理 |
| Docker 内自更新丢失 | 重建后回退、镜像漂移 | Docker 永久 `can_update=false`，只给宿主机升级命令 |
| Docker Socket 泄露 | 宿主机被完全控制 | 默认方案禁止挂载，不引入容器内 Compose 控制 |
| GitHub 暂时不可用/限流 | 无法检查 | ETag、20 分钟缓存、stale 明示、手动重试 |
| 更新/readiness API 被滥用 | 远程停机或伪造启动成功 | Web 密码、同源/CSRF/HMAC；readiness 回环 + 一次性 token；固定官方源、无 shell、日志脱敏 |
| 清理路径被状态文件污染 | 任意目录删除 | installation marker、canonical path containment、active 引用保护和越界删除测试 |

## 十一、里程碑与建议拆分

建议拆成四个可独立回滚的交付批次，Web mutation 必须最后开放：

### M1：版本事实 + 只读检查

- 统一版本入口。
- 正式 GitHub Release 检查、commit 解析与缓存。
- 基础部署能力检测。
- Web 只读状态、宽屏/移动端持久提示和每版本一次通知，不开放 prepare/restart mutation。

验收后即使停止，用户也能准确看到版本与部署限制，不引入进程风险。

### M2：受管运行时 + 候选准备

- Launcher、runtime adopt/profile、官方脚本统一入口。
- UpdateManager、manifest、状态、租约、artifact root 和候选 venv。
- 候选 probe 完成后停在 `ready_to_restart`，暂不由 Web 激活。

验收后已能安全准备版本，但尚不引入进程退出风险。

### M3：任务排空 + CLI 激活与恢复

- RuntimeLifecycle、Relay、readiness、journal 和自动恢复边界。
- 先从 CLI/测试夹具验证 Linux/Windows 激活、模拟重启、断电和失败恢复。

验收后再开放 Web mutation，避免同时调试 UI、租约和进程切换。

### M4：Web 操作 + Docker/发布/文档闭环

- 受保护 API、完整更新模态框、排空状态和重启轮询。
- Docker 能力与命令提示。
- Release manifest 门禁、全量测试、Playwright、真实 Windows/Linux 验收和文档。

## 十二、最终验收标准

以下条件全部满足才算完成：

1. Web、CLI、Python 包、Docker 和 Desktop 后端构建元数据报告同一版本与 revision。
2. 登录 Web 后会自动检查并主动提示新版本；用户无需先进入更新模态框，且提示不会打断当前操作。
3. 当前版本低于最新正式 Release 时，即使部署不支持一键更新，Web 宽屏侧栏/移动端顶栏仍持续显示提示和发布页入口；Desktop 不重复提示。
4. 只有 Release/manifest、受管 Launcher、运行时档案、Git 形态、空间和迁移兼容全部通过的官方源码仓库才显示准备按钮。

## 十三、实施前需要确认的产品边界

推荐按以下默认值实施：

1. **更新目标：** 仅最新正式、非 draft、非 prerelease GitHub Release；原始标签只作辅助发现，不支持任选版本。
2. **发布门禁：** 自动更新目标必须带兼容 manifest 并与 Release tag commit 一致；`v2.1.6` 这类没有 manifest 的历史 Release 可提示，但不倒推为已满足未来自动更新合同。
3. **受管范围：** 首期完整流程只支持官方 Launcher 管理的源码部署；现有直接启动用户先执行一次 `lightagent runtime adopt`，不自动改 systemd 或第三方 Supervisor。
4. **操作顺序：** 更新只做下载与准备，必须由用户再次点击“重启并完成更新”才生效。
5. **任务排空：** 默认等待 60 秒，超时恢复服务；强制重启仅在超时后通过第二次风险确认开放。
6. **取消语义：** 首期无 cancel API；关闭页面不取消后台准备，依赖安装只受内部超时与失败控制。
7. **Docker：** 首期只检查和给出两步命令，不做容器内更新或 Web 重启，不挂 Docker Socket。
8. **回滚：** 首期只有兼容 Release 的失败自动恢复，不提供用户主动降级入口；不可逆数据迁移只允许人工升级。
9. **自动检查：** 登录 Web 后按 20 分钟缓存检查；手动刷新可强制检查；永不自动下载、安装或重启。
10. **危险操作门禁：** 未设置 Web 密码时禁止准备和重启；内部 readiness 使用回环一次性 token，不复用浏览器认证。
11. **供应链基线：** 推荐首期采用“GitHub 正式 Release + 固定官方 HTTPS 仓库 + 精确 commit SHA”并在 UI/文档明示标签未签名的残余风险。若要求发布者密码学身份验证，则必须把“内置公钥签名 manifest、密钥轮换和 CI 签名保护”加入 Phase 0 后再开放 mutation。
12. **依赖基线：** 只迁移官方可识别依赖组和已知按需能力；包含私有 VCS、本地路径包或未知运行时扩展的安装首期只检查，不自动重建。

如果产品要求“Docker 也必须在 Web 内一键更新并重建容器”，必须先确认愿意部署一个宿主机级、最小权限、独立认证的 Supervisor。该方案需要新的安装/升级合同、IPC 协议、权限模型和宿主机服务测试，不应混入本首期实现。
